# Skill 定义格式参考

这是 RhineCode 的 Skill 完整字段手册。写、改、适配任何 Skill 之前先读这一份，
**不要凭记忆写 frontmatter**——本系统与其它实现有几处语义不同，
其中一处正好相反，凭印象写必然出错。

---

## 一、文件放在哪、叫什么

### 三层目录，项目 > 用户 > 内置

| 层 | 位置 | 说明 |
| --- | --- | --- |
| 项目级 | `<项目根>/.rhinecode/skills/` | 随代码仓库分发，团队共享。**新建的 Skill 一律放这里** |
| 用户级 | `~/.rhinecode/skills/` | 跨项目可用。⚠️ **本版本无法用工具写入**，见下 |
| 内置 | 随程序分发 | 只读，用户永不写入 |

同名整份覆盖，高优先层胜出。**覆盖是整份替换，不做字段合并**——
项目级的 `commit` 完全取代内置的 `commit`，不会出现「正文用你的、预授权用内置的」
这种缝合结果。

> ⚠️ **用户级与内置目录都在项目工作区之外**，而路径沙箱对**写入**一律拒绝
> 越界路径（为读取随附资源建的那份只读白名单**不覆盖写入**）。
> 所以本版本只能创建项目级 Skill。用户要求装到用户级时，**如实告诉他做不到**、
> 让他手工把文件放过去，**不要尝试写入**——试了只会拿到一个「路径越界」的拒绝，
> 徒增困惑。

### 两种形态

- **单文件型**：`<名字>.md`
- **目录型**：`<名字>/SKILL.md` + 任意随附资源

入口文件名固定是 **`SKILL.md`**（全大写）。目录里没有它，整个目录会被记一条
加载失败。

### 命令名来自文件系统路径，不来自 frontmatter

| 形态 | 命令名 |
| --- | --- |
| `deploy.md` | `deploy` |
| `my-pack/SKILL.md` | `my-pack` |

frontmatter 里的 `name` **只是显示标签**，改它不会改变命令名。

命令名的唯一限制：不得是 `reload` / `off` / `prompt` / `run`
（那会让 `/skills <子命令>` 产生二义）。字符集与长度不限。

## 二、frontmatter 字段

**全部字段可选。** 一份只有正文、没有 frontmatter 的 Markdown 也是合法 Skill。

连字符与下划线两种写法都认（`allowed-tools` 与 `allowed_tools` 等价），
但**下划线的 `allowed_tools` 会触发一条语义变更警告**，见下方「四」。
新写的一律用连字符。

| 字段 | 含义 | 不写时 |
| --- | --- | --- |
| `name` | 显示标签（列表里怎么显示） | 取命令名 |
| `description` | 一句话说明「这个 Skill 做什么」 | 取正文第一段 |
| `when_to_use` | 说明「什么时候该用它」 | 无 |
| `allowed-tools` | **预授权**：列出的操作本次执行内免确认 | 不预授权 |
| `context` | 取值 `fork` 时开子对话执行 | 留在主对话 |
| `disable-model-invocation` | 为真时模型不得自行发起 | 假（模型可发起） |
| `user-invocable` | 为假时不注册斜杠命令 | 真 |
| `model` | 子对话用哪个模型，**仅 `context: fork` 生效** | 沿用全局配置 |

未知字段一律忽略，不报错。

### `description` 与 `when_to_use` 要怎么写（**决定这个 Skill 会不会被想起来**）

模型在启动时只看得到**命令名 + 这两句**，靠它们判断「要不要加载这个 Skill」。
正文在它决定加载之后才会被读到。

所以 `description` 不是给人看的文档，而是**触发信号**。

**① 把用户会真的说出口的词前置。**
不是它们的书面转述——用户会说「提交」「跑测试」「做个前端页面」，
不会说「执行版本控制提交操作」。前置是因为预算不够时是**从尾部砍**的。

```yaml
# ✅ 触发词在前，做什么在后
description: 跑测试。用户说「跑测试」「test」「测试挂了」，或改完代码想确认没弄坏什么时用

# ❌ 只说做什么——模型看不出什么时候该用它
description: 跑项目测试并解读失败
```

**② 触发词要放在 `description`，不要只放 `when_to_use`。**
`when_to_use` 不是开放标准的字段，**别的 Agent 工具只读 `description`**。
放对位置，这份 Skill 才能原样拿去别处用。`when_to_use` 留给补充场景。

**③ 宁可写得略强势。**
模型有**欠触发**的倾向——这是可测量的已知偏差，不是偶然。一个只写「做什么」的
说明会被反复漏过：用户说「帮我做个前端页面」，而你的 Skill 说明写的是
「前端页面构建规范」，它就想不到要加载。

**④ 控制在 100 字符以内。**
状态列表与命令菜单只显示 `description`，过长会撑成多行。
反例（真实踩过的）：把「做什么」和「什么时候用」全挤进 `description`、
写成两百多字符，结果列表撑成三行、而模型仍然判断不准。

### `context: fork`

不写 → 正文注入当前对话，模型接着往下做。
写 `fork` → 开一条**子对话**跑完，只把最后的结论回流主对话。

选 `fork` 的场景：任务产出的是**一个结论**（审查报告、调研结果），
中间过程（读了二十个文件）没必要留在主对话里占上下文。

⚠️ 子对话**一次性跑完、中途无法与用户往复**。需要引导用户、
需要逐步确认的流程**不要用 fork**。

## 三、`allowed-tools` 是**预授权**，不是限制

**这是本系统最容易被误解的一条，也是与旧版本语义相反的一条。**

> 列出的操作在**本次执行内免于人工确认**。
> 它**不限制**模型能调用哪些工具——没列出的工具照样能用，只是照常弹确认面板。

想**限制**模型能做什么，唯一手段是 `permissions.yaml` 的 `deny` 规则。
`allowed-tools` 只放宽，从不收紧。

### 写法

```yaml
# YAML 列表
allowed-tools: [Read, Grep, Bash(git status *), Bash(git diff *)]

# 或空格/逗号分隔的字符串（括号内的空格不会被切开）
allowed-tools: Bash(git add *) Bash(git commit *) Read
```

### 可用的类别

| 写法 | 覆盖 |
| --- | --- |
| `Read` | 读文件、`Glob`、`Grep`（标准里这三个名字都映射到 `Read`） |
| `Write` | 写新文件 |
| `Edit` | 改已有文件 |
| `Bash` | 执行命令 |
| `WebFetch` | 网络访问 |
| `mcp__<服务器>__<工具>` | 远端 MCP 工具 |

括号里是**参数模式**（glob 通配），只对该模式匹配的调用免确认。

### 四条容易写错的地方

1. **域名规则必须带 `domain:` 前缀**：
   `WebFetch(domain:github.com)` ✅ ／ `WebFetch(github.com)` ❌ **会被静默丢弃**。
2. **远端工具不要加参数模式**：`mcp__github__search` ✅ ／
   `mcp__github__search(...)` ❌ **加了就永远匹配不上**，预授权失效。
   要收窄就写具体的工具名，别写 `mcp__github__*`。
3. **纯通配等于没写**：`Bash(*)` 与裸写 `Bash` 效果**完全相同**，都是
   「所有命令免确认」。想收窄就写具体前缀。
4. **有副作用的操作要慎给**：裸写 `Bash` / `Write` / `Edit` / `WebFetch`
   等于该类别全部操作免确认。只预授权这个 Skill **必然要做**的那几件，
   真正落盘/发数据的那一步留给用户点确认。

### 预授权翻不过前两道防线

声明「放行全部命令」的 Skill，照样在**危险命令黑名单**被拦；
声明「放行全部写入」，照样在**路径沙箱**被拦。配置里的 `deny` 也压得过它。

预授权的有效期是**触发它的那一次执行**，用户发出下一条消息即失效。

## 四、本系统不支持的标准字段

写了这些字段不会报错，但**行为与你的预期不同**，加载时各会给一条提示：

| 字段 | 本版本的实际行为 |
| --- | --- |
| `background: true` | 不支持后台执行，会**同步等待**跑完 |
| `agent` | 没有子代理类型的概念，忽略 |
| `effort` | 思考强度由 `/think` 全局控制，忽略 |
| `hooks` | 不支持 Skill 级钩子，忽略 |
| `paths` | 不支持按路径自动激活，忽略 |
| `shell` | 命令走系统默认 shell，忽略 |

另有两处**语义差异**，从别处搬 Skill 过来时要特别检查：

- **`allowed_tools`（下划线）在旧版本里是「收窄可见工具集」**，现在是「免确认」，
  两者作用**相反**。加载时会给一条明确警告。
- **`disallowed-tools` 不支持**。要限制请用 `permissions.yaml` 的 `deny`。

## 五、正文

正文就是发给模型的操作手册，用 Markdown 写。**格式即语义**——缩进与空行会原样保留。

### `$ARGUMENTS`

用户传的参数会替换到 `$ARGUMENTS` 出现的**每一处**。

不写占位符也**不会丢参数**——它会被追加到正文末尾的「用户补充参数」段。
但那个位置固定在最后，模型可能读到得太晚。**希望参数出现在流程中间的某一步，
就在那一步写上占位符。**

参数是**字面替换**，不做 shell 分词、不做模板求值。

### 长度

正文有注入上限，超了会被**静默截断后半段**——而模型不知道自己只拿到一半，
会当成完整流程执行，产出一个「做了前三步就宣告完成」的结果。

`/skills` 会在逼近上限时提前提醒。太长的话：拆成几个更聚焦的 Skill，
或者改成**目录型**，把参考资料与模板挪进随附资源。

### 随附资源（目录型）

目录里除 `SKILL.md` 之外的文件都是随附资源。它们**不占注入预算**——
激活时只注入一份文件清单（含绝对路径），模型需要时自己去读。

大段的参考资料、模板、示例都该放这里，正文里只留一句「先去读 xxx」。

## 六、最小范例

### 单文件型

```markdown
---
name: changelog
description: 按最近的提交生成 CHANGELOG 条目
when_to_use: 用户说「写 changelog」「整理更新日志」时
# 只预授权只读调研；真正写文件那一步留给用户确认
allowed-tools: [Bash(git log *), Read]
---

按以下步骤整理更新日志。

## 1. 看最近的提交

`git log --oneline -30`，找出上一个版本标签之后的全部提交。

## 2. 分类

按 新增 / 修复 / 变更 / 移除 归类，跳过纯格式与纯测试的提交。

## 3. 写条目

每条一行，写「用户能感知到的变化」，不要写「改了哪个函数」。

## 本次的补充说明

$ARGUMENTS
```

### 目录型

```
review-pack/
├── SKILL.md          ← 入口，正文里写「先读 checklist.md」
├── checklist.md      ← 随附资源，不占注入预算
└── templates/
    └── report.md
```

## 七、改完之后

Skill 定义**不会自动重新加载**。改完文件要执行 **`/skills reload`**，
新的定义才生效、新增的斜杠命令才注册得上。

用 **`/skills`** 查看加载结果、错误与改进建议。
用 **`/skills prompt`** 查看当前**实际注入**了什么（排查「模型为什么没照我写的做」）。
