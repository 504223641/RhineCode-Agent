帮用户创建、适配或修复 Skill 定义文件。

## 第 0 步：先读格式手册（**不可跳过**）

用 `read_file` 读随附资源里的 `reference.md`（上面的资源清单给了绝对路径）。

**不要凭记忆写 frontmatter。** 本系统与其它 Agent 实现有几处语义不同，
其中 `allowed-tools` 正好相反——凭印象写必然出错，而错了是**静默的**：
文件能加载、命令能跑，只是行为和作者想的不一样。

## 第 1 步：判断用户要做哪一件

| 用户说的 | 走哪条分支 |
| --- | --- |
| 「把这套流程做成 Skill」「帮我写个 Skill」 | **A 创作** |
| 「我下了个 Skill，帮我适配」「这个 Skill 在这能用吗」 | **B 适配** |
| 「按 /skills 的建议修一下」「修复 xxx 的问题」 | **C 修复** |

拿不准就问一句，不要猜。

## 分支 A：创作

### A1. 问清楚要封装什么

用户说的往往是一句话（「每次改完代码跑测试再提交」）。把它问成一套**可执行的步骤**：

- 这个流程分几步？每步具体做什么？
- 有没有「必须先做 X 才能做 Y」的顺序？
- 有没有**不该做**的事？（这条经常被忽略，但它决定了 Skill 会不会帮倒忙）
- 每次执行有没有变化的部分？（那部分对应 `$ARGUMENTS`）

**问不清楚就别动手写。** 一份步骤含混的 Skill 比没有更糟——
用户会以为它在按流程做，实际上模型在自由发挥。

### A2. 与用户确认命令名

**必须问，不要自己定。** 命令名会变成斜杠命令（`/<名字>`），用户每天要敲它。

同时告诉用户：命令名取自**文件路径**，与 frontmatter 无关。
若与内置命令重名（`/help`、`/clear` 这类），短命令注册会被跳过，
只能用 `/skills run <名字>` 触发——发现重名时提前说明，让用户换一个。

### A3. 写文件

路径固定为 **`<项目根>/.rhinecode/skills/<命令名>.md`**（单文件型）。
需要随附资源时用目录型：`<命令名>/SKILL.md`。

**存放层级不用问，一律建项目级。** 新建的 Skill 多半服务当前这个仓库，
且项目级随代码分发、团队里其他人拉下来就能用。

用户明确要求「装到用户级 / 所有项目都能用」时：**如实告诉他本版本做不到**
（用户级目录在工作区外，写入会被路径沙箱拒绝），请他手工把文件放进
`~/.rhinecode/skills/`。**不要尝试写入**——试了只会拿到一个「路径越界」的
拒绝，白白让用户困惑。

写之前把完整内容念给用户看一遍。`write_file` 会弹确认面板，
那是**故意不预授权**的一步。

### A4. 收尾

告诉用户执行 `/skills reload`，然后 `/skills` 看加载结果——
若有改进建议会一并列出来。

## 分支 B：适配外部 Skill

### B1. 读进来

先 `read_file` 读那份文件。若是目录型，先看清楚目录里有什么。

### B2. 逐项对照手册检查

对照 `reference.md`，**逐条**列出差异，不要笼统说「有些字段不支持」：

- **`allowed_tools`（下划线）** → 语义在本系统是「预授权免确认」，
  与旧版「收窄工具集」**相反**。作者的本意是哪个？这条必须问清楚。
- **不支持的字段**（`background` / `agent` / `effort` / `hooks` / `paths` / `shell`）
  → 逐个说明本版本的实际行为是什么。
- **认不出的工具名**（`Task`、`TodoWrite` 之类）→ 会被丢弃，说明影响。
- **`disallowed-tools`** → 不支持。要限制得改用 `permissions.yaml` 的 deny。
- **命令名**：取自目录名/文件名，不是 frontmatter 的 `name`。

### B3. 报告并征得同意

把差异摊开给用户看，**提出改法，等他同意再改**。

⚠️ **不要自作主张直接改。** 格式差异是**语义**层面的——同一个字段名在不同
实现里含义可能相反，代码和模型都只能猜，而猜错是**静默的**：
用户会拿到一份看起来正常、行为却不对的 Skill，比直接报错危险得多。

## 分支 C：按体检建议修复

### C1. 拿到建议

用户通常已经看过 `/skills` 了。若他没说清是哪条，请他把建议贴过来，
或让他执行 `/skills` 再告诉你。

然后 `read_file` 读目标 Skill 文件。

### C2. 逐条问采纳与否

**一条一条问，不要一次性全改。** 每条建议说清楚：

- 现在是什么样
- 建议改成什么样
- 改了之后有什么不同

有些建议是**可以不采纳的**——比如「覆盖了内置样板」，如果用户就是有意定制，
那条建议本来就该忽略。替用户决定等于把建议变成了强制。

⚠️ **但「跳过」必须说出来。** 有些建议正文里自带「不需要就忽略本条」这类出口
（比如缺 `$ARGUMENTS` 那条）。你判断某条不适用而跳过时，**要明确讲一句
「这条我判断不适用，跳过了，理由是……」**，不能默默不改。

尤其当用户说了「**全部采纳**」时：那句话优先于建议里的出口。你若仍认为某条
不该改，就**回去问他一句**，而不是替他决定——他会以为都改了，
下次 `/skills` 里那条还在，他只会困惑。
（实测踩过：连着三轮都静默跳过了占位符那条，用户完全不知道。）

### C3. 改

用 `edit_file` 改，用户会在确认面板上看到改前改后。

### C4. 自查：**逐条**核对，一条都不能漏

**改完先自己对照一遍，再交给用户。**

第一步是**把建议列表再读一遍，逐条确认这一条真的改了**。多条建议一起改时最容易
发生的不是改错，而是**漏改**——尤其那些「只需加一行」的（比如补 `$ARGUMENTS`），
在处理完几条复杂的之后很容易被忘掉。**逐条打勾，不要凭印象。**

（实测踩过：四条建议里改了三条，漏掉的正好是最简单的那条占位符。）

然后检查这两处容易翻车的地方：

- **收窄预授权时，只能加括号里的参数模式。**
  把 `Write` 换成 `Edit`、把 `Bash` 换成别的类别，**都不算收窄**——
  裸写任何一个有副作用的类别，都是「该类别全部操作免确认」。
  （这是实测踩过的：改完之后同一条建议换个工具名又冒出来了。）
- **压缩 `description` 时别把信息挪没了**，该进 `when_to_use` 的要真的挪进去。

然后告诉用户执行 `/skills reload`，再 `/skills` 确认对应的建议消失了。
**建议没消失说明改的地方不对**，回去重看那条建议——
不要在汇总里给自己打勾，以 `/skills` 的实际输出为准。

## 通用硬规则

1. **落盘前把内容给用户看。** 写入与编辑都不预授权，确认面板必弹——
   这是设计如此，不要试图绕开。
2. **一律建项目级**，内置层永不写入（它随程序分发，写进去下次升级就没了）。
3. **`allowed-tools` 给最小集。** 只预授权这个 Skill **必然要做**的只读调研；
   真正落盘、执行命令、发网络请求的那一步留给用户点确认。
   拿不准就**不给**——少一条预授权只是多点几次确认，多一条可能让用户
   在毫不知情的情况下被执行了不该执行的操作。
4. **`description` 是触发信号，不是文档。** 它决定这个 Skill 会不会被想起来。
   - **把用户会真的说出口的那几个词前置**：「提交」「跑测试」「做个前端页面」，
     而不是它们的书面转述。
   - 写成「做什么 + 什么时候用」，控制在 100 字符以内；补充场景才放 `when_to_use`。
   - ⚠️ **触发词要放在 `description` 而不是只放 `when_to_use`**——
     `when_to_use` 不是开放标准的字段，别的 Agent 工具只读 `description`。
     放对位置，这份 Skill 才能拿去别处用。
   - ⚠️ 宁可写得**略强势**：模型有**欠触发**的倾向（这是可测量的已知偏差），
     一个只写「做什么」的说明会被反复漏过。
5. **正文里写上 `$ARGUMENTS`**，放在参数真正该出现的那一步。
