按以下步骤完成一次提交。

## 0. 边界：只提交，不改代码

本流程**只负责把工作区现有的改动提交上去**，不生产任何代码改动：

- 看到测试失败、改动不完整、代码有缺陷、注释写错——**照实提交现状**，
  把问题写进最后的回复告诉用户，由用户决定要不要修。不要顺手替他修；
- 同样不要用 `run_command` 变相编辑文件（`sed` / `Set-Content` /
  重定向写文件 / 跑脚本改内容都算），绕过工具限制去做本流程不该做的事；
- 更不要执行任何会丢弃工作区改动的命令（`git checkout -- <文件>`、
  `git restore`、`git reset --hard`、`git clean`）——那删掉的正是你要提交的东西；
- 用户想让你连修带提交，他会明说。他没说，就只提交。

## 1. 看清楚改了什么

- `git status` 看有哪些文件变动、是否有未跟踪文件；
- `git diff` 看已跟踪文件的具体改动；若已暂存，还要看 `git diff --cached`。

不要凭猜测写提交信息，必须先读到实际 diff。

## 2. 学习本仓库的提交风格

`git log --oneline -15` 看最近的提交，判断本仓库用的是哪种约定：

- 是否用 `feat:` / `fix:` / `docs:` 这类 conventional commits 前缀；
- 标题用中文还是英文；
- 是否习惯写多行正文说明「为什么」。

**照抄仓库既有风格**，不要套用你自己偏好的格式。

## 3. 写提交信息

标题一行说清「这次改动做了什么」，动词开头，不超过 50 字。
若改动不止一处，正文分点说明每处**为什么**要改——「是什么」看 diff 就知道，
「为什么」只有你现在知道。

## 4. 提交

- 只提交与本次改动相关的文件，不要 `git add -A` 把无关文件一起带上；
- 提交前再确认一次暂存区内容；
- **不要**推送到远端，除非用户明确要求。

## 5. 报告

提交完成后一句话说明提交了什么。若第 1 步里注意到了缺陷、失败的测试或
可疑之处，在这里如实列出——**指出问题，但不要动手改**。
