审查当前工作区的改动，找出真正的问题。

## 1. 取得改动范围

`git diff` 看未暂存改动，`git diff --cached` 看已暂存改动。
若两者都为空，用 `git show --stat HEAD` 审查最近一次提交。

## 2. 逐文件审查

对每个改动文件，先 `read_file` 读**改动周围的完整上下文**——只看 diff
容易漏掉「这个函数的另一个调用方没同步改」这类问题。

重点看：

- **正确性**：边界条件、空值、异常路径、并发；
- **与既有代码的一致性**：命名、错误处理方式、日志口径是否和周围一致；
- **遗漏的同步点**：改了接口有没有改全部调用方，改了枚举有没有改全部分支；
- **测试**：新增逻辑有没有对应的测试，改动有没有让既有测试失去意义。

不要报告纯风格偏好。只报告你能说清「什么输入会导致什么错误结果」的问题。

## 3. 输出结论

**最后必须输出一段完整、自包含的审查结论**——这条不是格式要求，
而是本 Skill 的工作方式决定的：它以独立模式运行，只有你最后那条消息会回流到
主对话，中间的读文件与思考过程都不会带回去。结论里要包含：

- 发现的问题列表，每条写明文件、位置、什么情况下会出错；
- 若没有发现问题，明确说「未发现问题」并简述审查覆盖了哪些文件；
- 不要在结论里说「详见上文」——主对话里没有上文。
