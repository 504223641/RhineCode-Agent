# 主对话的待办清单（Todo）

> 状态：待开工 · **建议走完整 `/spec`** · 预计 1–2 天
>
> 建议分支：`todo-list`（从 `main` 起）
>
> ⚠️ **一半的地基已经在了，但那一半是给别人用的。** C15 有一份共享任务清单
> （`team/board.py` + `/tasks`），它服务的是**子 Agent 之间的协作**，
> 不是主对话的进度追踪。第一件事就是决定：复用它，还是另起一份。

## 背景

用户在 tui-activity-fold 验收期提出的：

> 还有类似你这种任务列表如何实现
> ```
> ✔ 第一段 · 地基纯函数（T1-T4）
> ✔ 第二段 · A 组批次归并（T5-T16）
> ◼ 第五段 · 收尾与验收（T34-T38）
> ```

那是 Claude Code 的 `TaskCreate` / `TaskUpdate` 工具 + 一块常驻显示区。
它解决的是**多步骤任务里「现在做到哪了」看不见**的问题——模型自己维护一份
待办，用户随时能看到进度，也能看出它有没有漏掉什么。

RhineCode 现在没有这个：一个十几步的任务跑起来，用户只能从工具行推测进度，
而 tui-activity-fold 把工具行折叠之后，这件事反而更看不出来了
（**归并压掉的是「做了什么」，而待办清单回答的是「还剩什么」——两者互补**）。

## ⚠ 第一件要决的事：复用 C15 的清单，还是新起一份

这是本项目的**唯一实质设计分歧**，先想清楚再动手。

| | 复用 `team/board.py` | 新起一份 |
| --- | --- | --- |
| 数据结构 | 现成（任务、状态、认领人、依赖） | 要重写，但可以砍掉认领人与依赖 |
| 语义 | 「**谁**来做这条」——为多 Agent 抢活设计 | 「**做到哪了**」——单一执行者的线性进度 |
| 风险 | 主对话与子 Agent 的待办混在一张表里，`/tasks` 报告会变得难读 | 两套相似的东西并存，将来改一处忘另一处 |

⚠ **倾向新起一份，但要先验证这个判断**：C15 那份的核心是「认领」与「阻塞依赖」，
而主对话的待办里这两个字段恒为空——一份数据结构里一半字段永远不用，
通常说明它不是同一个东西。

⚠ 另一条：C15 的清单**刻意不提供命令层写路径**（CLAUDE.md 记着「两条并行的
写路径里，命令层那条绕开了『谁改的』这个记录」）。主对话的待办有没有同样的
约束，要单独想。

## 要做的事

### 1. 工具

一个让模型维护待办的工具。Claude Code 那边是**整表覆写**（每次传完整列表），
不是增量改——那样模型不必记住 id，也不会出现「改了一条但漏了另一条」的中间态。

⚠ **值得照抄整表覆写这个设计**：增量接口看起来更省 token，但它要求模型
维护 id 与状态机，而模型在这件事上不可靠（C15 的共享清单是增量的，
那里有多个写入方、不得不如此；主对话只有一个写入方，没这个必要）。

三个状态就够：待办 / 进行中 / 已完成。⚠ 不要加「已取消」「已阻塞」——
那是 C15 那种多方协作才需要的，单一执行者用不上。

### 2. 显示区

⚠ **位置要慎选，本项目底部已经很挤了**：活动区（子 Agent）、状态行（本回合）、
输入框、状态栏，四层。再加一层会让历史区显著变矮。

几个方向，各有代价：

- **并进历史区**：作为一条特殊的消息行，随对话滚动。不占常驻空间，
  但翻上去就看不见了（而「还剩什么」恰恰是随时要看的）。
- **独立常驻区**：最直观，但吃掉几行高度。可考虑只在「有未完成待办」时出现
  ——那又会引入 tui-activity-fold 刚修掉的**抖动**问题
  （见该扩展验收期修订：按需出现的区块会挤压历史区）。
- **折进状态行**：状态行现在是「◈ 处理中… (12s · ↑2.1k · esc 中断)」，
  可以加一段「3/7 项」。信息量小但零成本，且与 `Ctrl+O` 展开天然配合。

⚠ **不管选哪个，都要先读 tui-activity-fold 的验收期修订**：那一轮用两条不同的
路子解决了「新区块导致历史区抖动」（状态行固定占位、面板改浮层），
本项目会正面撞上同一个问题。

### 3. 与既有能力的接线

- **`/clear` / `/resume`**：待办属于「上一段对话的状态」，切换会话必须清空。
  ⚠ 走 `_reset_display_state`（tui-activity-fold 建的收口点），别另写一处。
- **trace**：新增事件类型要同步 `trace/reader.py` 的摘要表
  （CLAUDE.md 的成对维护点，漏了会显示成「未登记类型」）。
- **子 Agent**：待办工具该不该给子 Agent？⚠ 倾向**不给**——子 Agent 的进度
  已有活动区，再来一份会让两处数字对不上。若要给，先看
  `subagents/toolset.py` 的 `GLOBAL_DENIED_TOOLS`。

## 不做的事（建议写进 spec）

- 待办的跨会话持久化（与 C15 那份同理，spec 明确不做）
- 用户手动增删待办（那会引入第二条写路径，与 C15 「命令层不写」同理）
- 子任务树 / 优先级 / 时限（C15 spec 已把这些列为不做）
- 待办与 C15 共享清单的双向同步
