## 现在要做的：复测

**只改了文本，触发率是升是降没有实测过。** 三种可能的结果都要能分辨：

1. **恰当**——该派的派、不该派的不派。收工，删掉本文档。
2. **矫枉过正**——回到 2026-08-09 的欠触发。那就说明这个模型在两个方向上都
   「过度听话」，需要的是**中间地带的描述**而不是换一侧推。
3. **仍然过触发**——文本不是全部原因，要去 trace 里找模型的实际理由。

⚠ **不要只跑「该委派」的场景。** 旧版验收就是这么做的，于是只看得见欠触发。
必须两栏对照：**该派时派了几次 / 不该派时误派了几次**。

### 场景设计（两栏各至少三条）

**A 栏 · 不该委派**（本次用户反馈的症状，优先级最高）：

- 「`permission/rules.py` 里 deny 和 allow 分别用的哪个匹配函数？」（一次 grep）
- 「把 `tools/base.py` 的 `ToolResult` 加一个字段」（读一个文件 + 改一处）
- 「这个报错是什么意思」+ 一段 traceback（零到一次工具调用）

**B 栏 · 该委派**：

- 「整个代码库里 `system_serial` 这个标志影响了哪些行为？」（要扫很多处 + 只要结论）
- 「我想加一个新的权限层，先告诉我该怎么改」（牵动面广的方案）
- 用户**直接点名**：「用 explorer 去查 X」（主路径，必须 100% 命中）

⚠ **取样方法比实现更重要**——第 5 条 todo（P1b 无人值守回归）记着同一条教训：
别用自己写的 fixture 验自己的 spec。A 栏的三条来自真实使用记录，
后续补充也应当从真实对话里取。

### 怎么测

用 e2e 驱动设施跑，从 trace 数 `subagent_start` / `team_task` 事件：

```bash
python -m tests.e2e.host --mode live --seed tests.e2e.scripts:seed_team_project
python -m tests.e2e.client send "……"
python -m tests.e2e.client wait --until quiescent   # ⚠ 多 Agent 场景必须用它
python -m tests.e2e.client observe --types subagent_start
```

⚠ `wait` 缺省的 `terminal` 只看界面，后台委派在跑时界面照样 `idle`。

## 如果还要继续调，三个方向

按代价从小到大：

1. **只动 A 栏或只动 B 栏对应的那一句**，不要再整体反转一次。本文档记录的
   全部教训就是「整体推一侧」的代价。
2. **给判据加更多可数的锚点**。已经有「一两次工具调用」这一条，实测有效的话
   可以照这个形态补（模型对可数判据遵循得好，对抽象判断偷懒——这是 2026-08-09
   留下的唯一一条仍然成立的线索：同一次运行里它**加载了 `test` Skill**，
   说明「清单里有可匹配的具体项」它会读会遵循）。
3. **接受现状，改文档。** 在 README 里说明「需要时请直接说『用子 Agent』」。
   这不丢人——Claude Code 自己也把用户点名当作主路径。

⚠ **别为了让它触发而把场景编得越来越夸张。** 2026-08-09 那轮里模型说
「三个模块结构类似，修改很简单，我逐一进行编辑」很可能**是对的**——
「听起来适合并行」不等于「真的值得并行」。
