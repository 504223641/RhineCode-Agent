# `mcp_add_server` 没有 `classifier_scope`，不进 C16 分类器审查

> 状态：待开工 · 预计半天 · **优先级第四，因为它是纵深防御的第二道，不是唯一一道**
>
> 建议分支：`mcp-classifier-scope`（从 `main` 起）
>
> ⚠️ **别把它当成 B4 没修完。** B4 已经修完了 —— 现在那个动作会弹面板。
> 本条加的是**第二道**：让分类器在面板之前先看一眼。

## 背景

2026-08-31 修 B4 时，那个 Agent 报告：

> `mcp_add_server` 仍没有 `classifier_scope`，不进 C16 分类器。
> 加它是四处成对维护点，属独立改动，本次没做。

C16 给四类动作接了一个独立的分类器模型做执行前审查：跑命令、访问网络、
给队友发消息、上网搜索。**添加并启动一个外部 MCP Server 不属于这四类中的任何一类**，
所以它现在只有面板这一道。

## 为什么值得加

面板这道防线的真实强度 = **用户面对第 N 次确认面板时的判断力**。
这句话是本项目自己写在 web_fetch 那节里的，对本条同样成立 ——
而 `mcp_add_server` 的面板上要读的东西比一般的多：服务器名、
将要执行的完整命令、写进哪份配置。**一个看起来人畜无害的
`npx -y some-mcp-server` 到底会跑什么，面板上是看不出来的。**

分类器的价值恰恰在这里：它看得到**完整的对话上下文**，
因此能判断「用户根本没提过要装任何 MCP Server，而模型自己要装一个」
—— 那是面板给不出的判断。

## 为什么它排在第四而不是更前

三条理由，都要记住，免得下一个人以为这里有个洞：

1. **面板已经在了。** B4 修完之后这个动作在缺省预设下必弹面板，
   分类器是叠在它上面的第二道，不是唯一一道。
2. **分类器只在第④层生效。** 用户写的 `deny` 压得过它，写的 `allow` 直接短路它
   —— 而 `mcp_add_server` 的判定现在正是从第④层出来的，位置是对的，
   但这也意味着**它拦不住任何一条用户自己写下的放行规则**。
3. **它可能误伤。** 官方公布的拦截率是 89%，本项目已实测过分类器**对措辞敏感**。
   给一个低频动作接分类器，收益是「多一道」，代价是「偶尔莫名其妙被拒」。

## 要做什么

⚠ **这是一处四点成对维护点**，`paired-maintenance` Skill 里有条目，**开工前先加载它**。
按 B4 那个 Agent 报告的清单，要同步动的地方是：

1. `classifier` 包里的 `SCOPE_*` 常量 —— 新增一类
2. 工具那侧声明 `classifier_scope`
3. `agent/loop.py` 的 `_review_action` **两条分支**（⚠ 是两条，不是一条）
4. 分类器的提示词（`classifier/prompt.py`）—— 新增那一类的审查口径
5. `classifier/render.py` 的 `_SCOPE_LABELS` —— 界面文案

**漏掉任何一处都不报错**：少了提示词那条，分类器会拿一个它没被教过的类别去判；
少了 `_SCOPE_LABELS`，界面上会显示一个内部标识符。

⚠ **审查口径要单独想。** 另外四类的口径都是现成的（这条命令危不危险 /
这个地址该不该访问 / 这条消息该不该发 / 这个查询词发出去要不要紧），
而「该不该让这个 MCP Server 进来」的判据是**新的**：
它要看的是「用户有没有要求过装 Server」「这个 `command` 是不是模型自己编出来的」。
别直接套命令类的口径 —— 那会把 `npx` 判成一条普通命令。

## 判据

- `mcp_add_server` 声明了 `classifier_scope`，且五处全部同步
- 分类器拦下时给模型的是**固定文案**、具体理由只走界面与 trace（C16 既有纪律）
- 护栏钉住「五处同步」而不只是「能跑通」，并做变异实测
- 熔断计数**不按 scope 分桶**（C16 的既有不变量，新增一类时最容易踩）
- `python -m tests.run_parallel` 全绿
