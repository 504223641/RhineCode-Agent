# `test_subagent_e2e` 的时间断言在全量并发下偶发失败

> 建议分支：`subagent-e2e-timing-flaky` · 复杂度：小（半天）
> **这是测试设施的缺陷，不是产品缺陷** —— 产品行为一直是对的
> 来源：`trace-completeness` 分支的多次全量回归（2026-08-09）

## 问题

`tests/test_subagent_e2e.py` 里有两条**用挂钟时间做判据**的用例，
在全量 `unittest discover`（2267 项）的并发负载下偶发失败；
单跑那个文件必过，连跑三次都过。

```
FAIL: test_background_does_not_block_main
AssertionError: 0.2029999999795109 not less than 0.12 : 委派不得阻塞主对话

FAIL: test_conclusion_delivered_exactly_once
AssertionError: 0 != 1 : 结论只该被交付一次
```

第一条的判据是 `assertLess(elapsed, 0.12)`——它想验的是
「`background=true` 时主对话不等它」，而 0.12 秒这个数字是在一台空闲机器上
量出来的。全量跑的时候机器上同时有几十个线程、真实子进程与文件 IO，
一次线程调度延迟就能顶穿它。

第二条是同一个根因的另一面：交付发生在闸门的迭代级注入里，
判据在固定的等待窗口后取样，窗口太紧就取到了「还没注入」的那一刻。

## 为什么它要紧

**不是因为它红，而是因为它偶尔红。**

一个偶尔失败的测试会训练所有人忽略失败——包括忽略它某天开始报告的真问题。
本轮改造期间我至少三次要停下来确认「这条是我改坏的吗」，
每次都要单跑一遍 + 在 `main` 上跑一遍对照才能排除。
那个来回的成本比修它本身高得多。

CLAUDE.md 的测试章已经记过同型教训：
**「死锁护栏必须用完成计数而不是布尔标志」**——同一类问题，
用一个会随环境漂移的量做判据，判据就不可信。

## 修的方向（都不难，但要选一个）

⚠️ **不要简单把 0.12 调大。** 那只是把偶发概率降低，没有消除根因；
而且阈值一旦放宽到 1 秒，这条用例就**再也验不出「委派阻塞了主对话」**
——一次真的阻塞往往就是几百毫秒。

三个可选方向，建议第一个：

1. **换成事件同步，不看时间。** 让假的子 Agent 在一个
   `threading.Event` 上阻塞，主对话返回之后测试再放行它。
   判据从「主对话在 0.12 秒内返回」变成「**子 Agent 还没跑完，
   主对话就已经返回了**」——这才是那条用例真正想说的话，
   而且与机器快慢完全无关。
2. **判据改成相对量。** 先量一次「不委派时主对话花了多久」作基线，
   再断言「委派之后不显著变慢」。比绝对阈值稳，但仍然在看时间。
3. **交付那条改成轮询等待终态**（有上限），而不是固定窗口后取样。

第 1 条最彻底：它把一条**性能判据**改回它本来该是的**顺序判据**。

## 排除掉的可能

- **不是本轮改动引入的。** 在 `main`（改动前）上单跑同样通过，
  在全量下同样偶发——两边行为一致。
- **不是真实的阻塞。** 失败时 0.20 秒，而真正的阻塞形态是
  「主对话一直等到子 Agent 结束」，那会是几秒量级。
