# 模型不会主动组队（协作的触发率）

> 建议分支：`team-adoption` · 复杂度：中（**先做测量，再决定改不改**）
> 来源：C15 真实模型验收（2026-08-09）
> 对应 `CLAUDE.md`「已知后续工程项」第 17 条
> ⚠ 与 [`4-skill-recall-eval.md`](4-skill-recall-eval.md) **同源**（都是「模型欠触发」的评测问题），
> 那份的评测闭环建好之后，这份可以直接复用

## 问题

C15 的协作机制是好用的——用户明说「组一个队」时，模型一次就做对：
拆任务、起有语义的名字、并行派人、零冲突认领、成果正确、还会主动回报。

**但它不会主动去用。** 两轮自然场景（不提示协作）主 Agent 都全程自己做：

| 轮次 | 任务 | 结果 | 模型的原话 |
| --- | --- | --- | --- |
| 1 | 三个模块各把硬编码超时改成读 config | 0 次组队，自己改完 | 「三个模块结构类似，**修改很简单**。我逐一进行编辑。」 |
| 2 | 三个模块各补一份单元测试并跑通 | 0 次组队，11 轮自己做完 | —— |

**第 1 轮的判断可能是对的**——三个文件各改一行，委派开销（起线程、发请求、
回流结论）大于并行收益。⚠ 这条要记住：**「听起来适合并行」不等于「真的值得并行」**，
设计评测场景时别再犯同一个错。

**第 2 轮是实打实的欠触发**：三份测试各自要读模块、写文件、跑验证，
本身就是几轮的活，且完全独立。

## 已经做了什么

首轮查 trace 发现根因：**协作能力一个字都没进系统提示**。缺口一眼可见：

| 能力 | 系统提示里有没有 |
| --- | --- |
| C11 Skill | 有（140 槽位，清单 + 相当 pushy 的表头） |
| C13 委派 | 有（135 槽位，角色清单 + 「拿不准就委派」） |
| C15 协作 | **没有** |

已补 134「组队协作」槽位（`team/render.py::render_team_brief`），措辞相当 pushy，
判断依据定成「任务之间相不相干」而非「活多不多」。

**但补完之后第 2 轮仍然没组队**——所以它**必要不充分**。

## 最有价值的一条线索

同一次运行里，主 Agent **加载了 `test` Skill**（写测试的任务命中了 Skill 清单）。

也就是说：**系统提示里的「清单」它会读、会遵循；「说明」它没照做。**

差别很可能在于**有没有可匹配的具体项**——看到 `test` skill 它会想
「我这个任务是写测试，命中」；看到「任务之间相不相干」它得自己做一次抽象判断，
而模型在那种判断上系统性地偏向「还好，我自己来更快」。

**这条假设值得先验证再动手改。**

## ⚠ 开工前必须先做的一件事：换强模型复测

C15 验收全程用的是 `deepseek-v4-flash`——**快速小模型，指令遵循能力弱于同系列
大模型**。这一项**没有被排除**。

**先花很小的成本跑一轮对照**：同样的两个自然场景，换 `deepseek-v4` 或别的
更强模型。如果强模型会主动组队，那这就不是产品问题，本 todo 直接关掉、
只在文档里注明「小模型上触发率低」即可。

**不要在没做这个对照之前改产品代码。**

## 如果确实要改，三个方向

按代价从小到大：

1. **把「组队」变成一个可匹配的具体项。** 比如在角色清单里给每个角色加一句
   「可以同时派多个」，或者做一个「组队模式」的具名条目让模型能「命中」它。
   这是对上面那条线索最直接的检验。
2. **由代码给出一次提示。** 用户目标里出现「三个 / 每个 / 分别 / 各自」这类
   可拆信号时，在 `<system-reminder>` 里注入一句「这个目标看起来可以拆开并行」。
   ⚠ 这是**启发式**，本项目通篇忌讳它（C14 的环境初始化就明确拒绝了启发式），
   要做得先想清楚误报的代价。
3. **接受现状，改文档。** 在 README 里明说「需要时请直接说『组个队』」。
   这不丢人——Claude Code 自己的 subagent 也常要用户点名。

## 评测该怎么做（复用 `4-skill-recall-eval.md` 的闸门）

「触发率」这种东西**不能靠感觉判断**，那正是第 4 条 todo 要建的闭环：

- 一批**真实**的任务描述（不是为了触发而编的），标注「该不该组队」；
- 用 e2e 驱动设施批量跑，从 trace 里数 `team_task` / `team_member` 事件；
- 出一个「该组队时组了几次 / 不该组队时误组了几次」的两栏统计。

⚠ **取样方法比实现更重要**——第 6 条 todo（P1b）记着同一条教训：
别用自己写的 fixture 验自己的 spec。任务描述应当来自真实使用记录。
