# TODO —— 待选方向

**这个文件夹里的文档是「做完就删」的临时提醒**，不是长期设计资料。
每份都自带一段可一键复制的 Prompt，在新 session 里粘贴即可开工。

**每段 Prompt 都以分支检查开头**：先 `git branch --show-current`，
在 `main` 上就先起新分支再动手。建议分支名见下表，也写在各文档抬头与 Prompt 里。

## 命名规则

**文件名的数字前缀就是优先级，越小越优先。** 新增 TODO 时**重排全部序号**
（新事项可能插在中间），不是简单追加到末尾。重排用 `git mv` 保住历史，
并同步本文件的清单。

⚠ **重排时要改的不止本文件那张表。** 各文档正文与「一键开工 Prompt」里都写着
自己和别人的文件名，而那些 Prompt 是要被**原样粘到新 session** 的文本，
粘过去照着读文件会**直接读不到**。

**但重排之后什么都不用记** —— `tests/test_docs_links.py::TodoNumberingTest`
会把全仓所有过期序号逐处列出来（「引用了什么 / 当前应为什么」），它跟着
`run_parallel` 与 CI 一起跑。它查的是「**slug 还在、序号对不上**」，
所以本文件里那些提到**已删除**待办的历史记录不受影响。

⚠ **这里原先写着一条 `grep -rn "docs/todo/[0-9]\|第 [0-9] 条 todo" docs/todo/`
自检命令，已删除，理由值得记一笔。** 题面一直以为问题是「没人记得跑」，
R7 实测给出的是第三个答案：**跑了也查不出来**——在一棵有 2 处真悬空引用的树上，
那条命令输出 6 行、逐行核对全部正确、**退出码 0**。它的正则只认 `docs/todo/N`
这种带前缀的形态，而真实的悬空写成相对链接 `(<旧序号>-<slug>.md)` 与反引号裸文件名。
（⚠ 这里刻意用占位符而不是当时那个真实的过期文件名——写真的会被上面那条
护栏当场逮住，**而它逮得对**：那正是「文档里逐字引用一个过期引用」的形态。）**留着它比删掉更糟**：它会给出虚假的安心感，而人一旦跑过一次
拿到干净输出就不会再想这件事——下面那句「此处四次成为悬空引用」正是在这种
安心感下写出来的。

⚠ **护栏有一处盲区，别过度信任它：它只认 `N-slug.md` 这个字符串，看不见
「第 N 条」这种正文写法。** 2026-08-31 那次重排实测——护栏一次报出 **16 处**
过期引用（6 个文件，其中 4 个在 `docs/todo/` 之外），全部机械修掉；而**另外两处
正文里的「第 N 条」是人工翻出来的**，护栏一声没吭。

**这个盲区是刻意接受的，不是没做完。** 「第 N 条」在本仓库里到处都是（spec 条款、
安全边界第 N 条、已知项第 N 条……），去匹配它必然大量误报，而**一个会误报的门禁的
结局是被整体关掉**——那样连现在能查出来的 16 处也一起没了。

所以重排之后仍有一个动作要做，但它很小、也很具体：

```bash
grep -rn "第 [0-9] 条" docs/todo/
```

⚠ 逐条看，**别机械替换**：那个文件里大半的「第 N 条」出现在**历史重排记录**与
「⚠ 上一版这里写的是……」里，它们引用的是**当时**的编号，是对的，改了反而错。

⚠ 同样被实测推翻的还有本段原先那句「要改的都在 `docs/todo/` 里」——
所以那条命令的搜索路径才写死成了这个目录。**实际上一半以上的过期引用在这个
目录之外**（`docs/guide/`、`docs/extensions/` 各有分布），而那些恰恰最要紧。

## 权限模式三条 —— 2026-08-14 **已全部落地**（存档，不再是待办）

> ✅ 原本是三条，**前两条都已于 2026-08-14 实现**：保护路径层
> （[`docs/extensions/protected-paths/`](../extensions/protected-paths/spec.md)）
> 与 auto/plan 两 preset（[`docs/extensions/auto-plan/`](../extensions/auto-plan/spec.md)）。
> 下面这段来龙去脉保留全部三条的结构——去掉已完成的那些会让剩下这条
> 看起来像凭空冒出来的。

**这三条是一次讨论的产物，必须串行，顺序不可颠倒。** 三条**都已完成**——
这段来龙去脉留下来是因为它解释了「为什么当初非得按这个顺序做」，
而那个理由对将来动这几层的人仍然有用。

### 起因

用户问「Claude Code 的三种模式怎么工作的」，顺着查了官方文档，又对照了
Codex 的做法，最后落到一句需求：**RhineCode 只想要两个模式，`auto` 与 `plan`，
而且 `auto` 的体验要跟 Claude Code 的 auto 一样**（连 `run_command` 也自动批准）。

三条 todo 是这个需求拆出来的三步，**三步都已做完**。

### 两家的做法，以及我们抄哪一家

| | auto 靠什么保证安全 | 我们能不能用 |
| --- | --- | --- |
| **Claude Code** | 一个 **classifier 模型**逐动作审查 | ✅ 已实现（C16，`docs/c16/`）|
| **Codex** | **OS 级沙箱**（macOS Seatbelt / Linux Landlock+seccomp），越界物理上做不到 | ❌ **两家都不支持原生 Windows**（Claude Code 官方原话 *Native Windows is not supported*，Codex 文档只写 macOS 与 Linux） |

结构上抄的是 **Codex**：它对用户只暴露三个 preset，底下其实是
`sandbox`（能做什么）× `approval`（什么时候问）两条正交轴。
我们的「权限档 × 规划阶段」正好同构，所以 `auto` / `plan` 做成 **preset 而不是
新枚举值**——**已完成**（`docs/extensions/auto-plan/`）。

判定上抄的是 **Claude Code**：没有 OS 沙箱就没法让命令「在工作区内自由跑」，
于是用分类器补那个洞——**已完成**（`docs/c16/`）。
⚠ 落地时范围比官方**窄**（只审命令 / 网络 / 队友消息，不审文件写入），
且失败口径与初版设想**相反**（初版写「降级为 ASK、别照抄 fail-closed」，
查证官方文档后改成了 fail-closed）——详见 `docs/c16/spec.md` 末尾的对照表。

⚠ **OS 沙箱曾被考虑放在最前面，评估后否掉了**：它在主力平台 Windows 上没有
便宜落点（要么只做 macOS/Linux、要么要求 WSL2、要么自己啃 AppContainer 而
无现成参考），**而且它并不是这三条的前提**——它只解锁「命令一概放行」那一格，
而 preset 那条已经通过用户拍板直接放行了那一格。它仍长期登记在
`CLAUDE.md` 已知项 #4。

### 顺序为什么不能动

```
✅ 保护路径（已实现）→ ✅ 两个 preset（已实现）→ ✅ 分类器（C16，已实现）
```

- **preset 先于保护路径 = 安全性净下降。** preset 那条把「写文件弹面板」去掉了，
  而那次面板正是保护路径那个缺口（模型改写自己的 `permissions.yaml` /
  `hooks.yaml` / `agents/`）的唯一实际拦截。**已按正确顺序做完。**
- **两者改同一个文件**（`permission/engine.py`）。实际落地时 preset 那条
  **一行判定逻辑都没动**（只改了两处 docstring），`_apply_protected` 原样在位。
- **分类器盖在 preset 之上。** 分开做是刻意的：preset 做完就有一个能用的 auto，
  分类器万一体验太慢或做砸了，`classifier.enabled: false` 一关就退回一个完好的产品。
  合起来做的话中间没有可用状态。**这条退路已按设计实现并有护栏钉着。**
