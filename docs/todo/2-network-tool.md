# 2 · 网络访问工具

> 状态：待开工 · **必须走完整 `/spec`** · 预计多天
>
> 建议分支：`web-fetch`（从 `main` 起）
>
> ⚠️ **不要作为别的任务的附属品顺手加。** 它是第一个能主动向外发数据的工具，
> 权限模型要重新想一遍。

## 背景

用户提出的原始需求是「从网络上安装 Skill」，但发现目前**没有任何访问网络的工具**。

这个能力的价值远超 Skill 场景 —— 查文档、读 issue、抓 API 参考都要它，
是 Claude Code / Codex 都有的基础能力（`WebFetch` / `WebSearch`）。

## ⚠️ 为什么必须单独立项

RhineCode 现有的全部工具都是**本地的**：读文件、跑命令、编辑。五层权限管线的
前两层是围绕这个前提设计的：

- 第①层**危险命令黑名单** —— 只对 `kind == "command"` 生效
- 第②层**路径沙箱** —— 只对 `read_path` / `write_path` / `glob` 生效

一个网络工具会落进 `kind == "other"` 分支，**前两层对它完全无效**，只剩
第③层规则与第④层模式兜底。也就是说：现有的安全边界对它是空的。

这不是「加个工具」，是**给系统开一个新的外部面**。要想清楚的问题至少有：

- 域名白名单/黑名单放在哪一层？是新增第⑥层还是扩展第③层规则语法？
- 抓回来的内容是不是要当成不可信输入（prompt 注入面）？
- 有没有大小上限、超时、重定向次数上限？
- 会不会把工作区里的内容**发出去**（POST？请求头？URL 参数）？
- 与已知项 #5「权限系统后续项：网络请求限制」的关系

## 判据

- 模型能读一个 URL 的正文内容
- **权限规则能限制它能访问哪些域名**，且该限制不可被权限模式放开
- 抓回的内容在上下文里被明确标注为「来自外部、不可信」
- 关掉它之后，系统行为与现在逐字一致

## 要读的文件

- `rhinecode/permission/engine.py` —— 五层管线，看清 `other` 分支绕过了什么
- `rhinecode/permission/adapter.py` 的 `_TOOL_MAP` —— 工具 → 规则名的映射
- `rhinecode/mcp/transport.py` 的 `HttpTransport` —— 已有的 HTTP + SSE 实现，可参考
- `CLAUDE.md` 的「安全边界」一节
- `docs/c6/spec.md` —— 权限系统当初明确不做网络限制的理由

## 已知的坑

- `kind="other"` 的工具名走 `fnmatch` 匹配，`allow: web_*` 会一次放行一整批 —— 设计规则语法时注意
- MCP 工具也在 `other` 分支，别把两者的规则语义搞混
- 如果做 `WebSearch`，那是**另一个**工具（要调搜索 API、有配额与密钥），
  建议先只做 `WebFetch`
