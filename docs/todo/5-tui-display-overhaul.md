# TUI 显示体系改造（对齐 Claude Code）

> 建议分支：`tui-display-overhaul` · 复杂度：大（**范围是「所有显示的地方」，必须走 /spec**）
> 来源：用户 2026-08-10 提出——「不止子 Agent 状态这一个显示的地方要改，
> 其他所有有显示的我都想改」
> ⚠ 本文档里**只有「子 Agent 活动区」那一节做过实地调研**，其余都是待盘点的清单

## 问题

用户的起点是一个具体症状：**子 Agent 在工作时界面上没有任何状态**，
派出去之后是几分钟的静默，直到结论回流。

但他要的范围更大——**整个显示体系对齐 Claude Code 的观感**，
所以这不是「补个进度条」，值得单独走一遍 `/spec`。

⚠️ **别把它做成只改子 Agent 那一处**。用户明确说了范围，
而显示这类东西**局部改会更难看**：一处用了新观感、其余保持旧样式，
不一致比统一的旧样式更刺眼。

## 已经定下来的（用户 2026-08-10 拍板）

**方案 A：独立的常驻活动区域**，而不是复用工具行、也不只加状态栏计数。

当时给了三个方案，选 A 的理由是它语义最干净：

| 方案 | 做法 | 为什么没选 |
| --- | --- | --- |
| A ✅ | 界面上开一块「后台任务」区 | —— |
| B | 让委派的工具行活到子 Agent 结束 | 要在一条**踩过坑的护栏**上开例外（`TOOL_RESULT` 必须 `pop`，写成 `get` 踩过「绿色完成行被覆写成失败·未执行」那次） |
| C | 只在状态栏加一个计数 | 只有「有没有」，没有细节 |

**并且要与 Claude Code 的三层显示一致**（见下节）。

## Claude Code 是怎么显示的（四层）

⚠ 确定性分级：**第 4 层是 Claude Code 系统提示里明文写的**（确定）；
前三层是产品 TUI 的行为观察，**版本间会有出入**。

**第 1 层 · 工具行是活的**

```
● Explore(Find permission layer usages)
  ⎿  Running… (23s · ↑ 3.1k tokens · 8 tool uses)
```

三个数字：**经过时间 / 累计 token / 工具调用次数**。
关键在于三个都是**不用理解内容就能判断「它在动、动得快不快」**的指标——
不要试图把子 Agent 正在做什么翻译成人话展示，那既贵又容易误导。

**第 2 层 · 默认折叠，可展开**

按 `Ctrl+O` 掀开看内部逐条的工具调用。**默认折叠是刻意的**：
子 Agent 的全部价值就是「中间过程不占你的上下文」，
把它全喷到界面上等于在视觉上抵消掉这个价值。但必须留掀开的口子，
否则出问题时无从排查。

**第 3 层 · 终态留痕**

```
● Explore(Find permission layer usages)
  ⎿  Done (14 tool uses · 28.5k tokens · 1m 12s)
```

完成后**保留成本信息**。这一条与刚做完的委派触发口径改造
（[`3-delegation-trigger-eval.md`](3-delegation-trigger-eval.md)）是**一件事的两面**：
模型靠提示词知道委派贵，用户靠这行数字建立同样的直觉。

**第 4 层 · 通知由系统产生**（Claude Code 系统提示原文）

> `Subagents run in the background by default; you'll be notified when one completes.`
> `Never fabricate or predict a pending agent's results — the notification is
> never something you write yourself`

完成通知**是系统写的，不是模型自述的**。与 C14 已定下的「交付信息由系统追加
而非模型自述」同一条原则——模型会漏报、会编造进度。

另有一条与本项目现状一致、无需改动：
`The agent's final report is not shown to the user — relay what matters.`
（子 Agent 结论只进模型上下文，用户看到的是主 Agent 的转述。）

## 四条设计原则（从上面提炼，做其它显示面时同样适用）

1. **进度指标要「无需理解内容」**——时间 / token / 次数。
2. **默认折叠，但要能掀开**——不掀开时保护主界面，掀开时能排查。
3. **终态留成本痕迹**——用户建立成本直觉的唯一途径。
4. **通知走系统通道，不经模型**。

## 子 Agent 活动区：已查实的地基（**这一节是实地调研过的**）

**好消息：三个数字全是现成的。** `subagents/tasks.py` 的 `TaskRecord`
已有 `turns`、`usage_tokens`、`started_at`（可算耗时），且它是**可变的**、
运行器在跑的过程中持续更新。

⚠ **更要紧的是它 docstring 里的一句话**：

> 「运行器会在跑的过程中更新轮次与用量，**TUI 轮询**与 `/agents` 会读它」

**设计时就预期 TUI 用轮询读它，而不是子 Agent 线程往主线程推。**
这一条直接绕开了本项目**已经死锁过四次**的那条路（加锁临界区里做跨线程调度）：
主线程 `set_interval` 每秒读一次即可，`ToolCallWidget` 已有先例
（`tui/widgets.py` 的注释：「计时不依赖 Worker 线程：`on_mount` 中用
`set_interval` 在主线程每秒触发重绘」）。

⚠ 论证要写进 spec：读 `TaskManager` 要拿锁，但**临界区只做纯内存读写**，
主线程不会被长时间阻塞。这与那条不变量是自洽的，**但必须显式论证**，
否则下一个人会以为主线程拿锁是个疏忽。

**缺的数据只有一个**：`TaskRecord` 有 `turns` 没有「工具调用次数」。
Claude Code 显示的是 tool uses，要在 runner 里新增一个计数（小改动）。

### ⚠ 一个架构障碍，实现前必须先决策

**`background=true` 的委派，工具调用本身已经返回了。**
`tools/run_agent.py` 的 `_summary()` 在那一刻就定了终态
（`委派 explorer · 后台 [task-id]`），`TOOL_RESULT` 一到，
那行按成对维护点必须被 `pop` 掉、定成绿色「完成」。

**于是工具行的生命周期与子 Agent 的生命周期就此分叉。**

Claude Code **没有这个问题**——它的 Agent 工具调用本身就代表整个 agent 的
生命周期，工具行活着 = agent 活着。本项目的委派是「发起即返回」，
这是 C13「委派永不阻塞」契约的直接结果，**不打算改**。

所以活动区必须是**独立的**（方案 A 正是因此而选），
不能指望复用工具行那套结算逻辑。

### 四个待定的决策点（当时问到一半用户喊停，未拍板）

1. **活动区位置与出现时机**——历史区下方按需出现（当时的推荐）/ 常驻占位 / 顶部。
2. **展开怎么触发**——快捷键切换全区（对齐 `Ctrl+O`，推荐）/ 上下键选中单条
   （要引入焦点切换，与输入框、命令面板的键位体系会打架）/ 不做展开。
3. **第三个数字**——工具调用次数（对齐 Claude Code，需新增采集）/
   轮次 `8/15`（零成本，且能带上角色的 `max_turns` 上限，
   **这是 Claude Code 没有的信息量**）/ 两个都显示（一行四个数字偏挤）。
4. **终态怎么处理**——区内留片刻 + 历史区留永久痕（当时的推荐）/
   一直留到 `/clear` / 跑完即消失（**这个等于放弃第 3 层**）。

⚠ 还有一个当时没来得及问的：**活动区与 `/agents` 命令的关系**。
后者现在就能查进度，两者的信息高度重叠——要想清楚是「活动区取代它」
还是「活动区给概览、`/agents` 给全量」。

## 其余显示面：**待盘点，本文档没有调研过**

用户说的是「所有有显示的地方」。已知的显示面至少有这些，
**开工第一步应当先盘一遍、逐个判断要不要动**：

- **工具行**（`ToolCallWidget`）——四种视觉状态、参数摘要、耗时
- **状态栏**（`compose_status_text`）——模型 / 模式 / 用量等
- **确认面板 / 澄清面板 / 会话面板**——权限确认的呈现
- **历史区**——用户消息、AI 正文、工具行、系统提示行
- **命令报告**——`/agents` `/tasks` `/skills` `/hooks` `/memory` `/context` 等
  纯文本报告（它们现在是一大段 markdown 文本）
- **通知与系统提示行**——笔记完成、上下文压缩、启动提示等

⚠ **别一次全改**。建议 spec 阶段就把范围切成几批，
每批独立可验收——显示改造最容易失控的地方是「顺手把这个也调一下」。
