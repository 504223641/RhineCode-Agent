# 3 · trace 与调度器的专项审查（查 bug + 补功能）

> 建议分支：`trace-driver-audit`
> 复杂度：中大（多天）。两套设施一起审，因为它们是**配对使用**的。

## 范围

> ⚠ **「调度器」= `tests/e2e/` 那套端到端驱动设施**（`host.py` / `client.py` /
> `control.py` / `protocol.py` / `scripted.py`），也就是「让 Claude 看 trace、
> 再模仿真人操作界面来驱动 RhineCode 跑完整闭环」的那个东西。
> 项目里没有任何组件叫这个名字，`CLAUDE.md` 的测试设施那一段有术语提醒。

两套一起审：**trace 记下「发生了什么」，调度器让「那件事发生」。**
单独审任一套都会漏掉接缝上的问题。

- `rhinecode/trace/`（`models.py` / `recorder.py` / `reader.py`）
- `tests/e2e/`（宿主 / 客户端 / 驱动核心 / 协议 / 剧本 / 夹具）

## 起因与已经攒下的线索

2026-09-17 用一份真实 trace 查那个存盘死循环（已知项 #21）时，**暴露出阅读器
的能力缺口**——那次排查我**一条 `reader` 命令都没用上**，全程手写了 5 个
一次性 python 脚本才把结论拿出来。这不是个例，值得作为本轮的起点。

### trace 阅读器：功能缺口（都是那次实测出来的）

`reader` 目前只有三个开关：`--type` / `--scope` / `--seq`。它能回答
「第 42 条是什么」，回答不了下面这些——而**这些恰恰是排查时真正要问的**：

| 那次实际要问的 | 现在怎么拿到 | 缺的能力 |
| --- | --- | --- |
| 哪些工具调用在**重复**？有没有原地打转？ | 手写脚本按 `(tool, arguments)` 分组 | **循环/重复检测**。这是发现 #21 的关键一步 |
| token 花在哪了？某一段占多少？ | 手写脚本累加 `api_response.usage` | **用量汇总**（按轮次 / 按 scope / 按用户消息分段） |
| 一条用户消息跑了几轮、停在什么原因上？ | 手写脚本按 `user_input` 切窗口 | **按用户消息分段的时间线** |
| 某条 `tool_execute` 的结果后来被存盘了吗？ | 手写脚本对 `tool_call_id` 做交集 | **跨事件的因果串联**（调用 ↔ 结果 ↔ 存盘 ↔ 再读） |

⚠ **还有一个当场踩到的坑**：`reader` 自己有一段处理 GBK 的注释，但**拿 python
直接读 jsonl 打印时会 `UnicodeEncodeError`**（Windows 默认 GBK 编码不了 `⚠`）。
排查的人第一反应是自己写脚本，然后立刻撞这个。值得在文档或 reader 里给一句。

### 调度器：已知的缺口与坑

- **P1b 无人值守回归还没开工**（范围清单在
  `docs/c11/testing/p1-driver/spec.md` 末节）。⚠ 记忆里那条
  `project_rhinecode_p1b_pending` 记着一条**必须先修正的取样方法**——
  别再用自己写的 fixture 验自己的 spec。做这条前先读它。
- ⚠ **Git Bash 驱动必须 `MSYS_NO_PATHCONV=1`**，否则 `send "/mode"` 会被
  改写成 `send "C:/Program Files/Git/mode"`，斜杠命令**根本没送到应用**。
  live 模式下那是真花钱调一次模型，而且模型会一本正经地解释「我无法访问那个
  路径」，**看起来像产品坏了**。这条已经在 `CLAUDE.md` 里，但值得想想能不能
  在 `client.py` 里直接检测并报错（现在只能靠人记得）。
- `client.py` 的子命令目前 10 个（`status` / `send` / `wait` / `answer` /
  `keys` / `screen` / `observe` / `cancel` / `quit` / `hosts`）。
  审一遍够不够——比如有没有「把这段 trace 读出来给我」的直通命令
  （现在要先 `--keep-workspace` 保留产物再自己去找路径）。
- `control.py` 的四条不变量（加锁四段式 / `wait` 不持锁 / 应答前复核面板就绪 /
  跨线程只走 `run_on_main`）要逐条复核还成不成立——C15/C16 之后新增了
  待命唤醒与分类器两条异步路径。

### 接缝上的问题

- `scripted.py` 的 `is_classifier_request` ↔ `classifier/prompt.py` 的
  `CLASSIFIER_MARKER` 是一处成对维护点（分类器与主对话**共用**
  `provider_factory` 是刻意的，绕过它会让一次端到端测试**静默连上真实网络**）。
- `host.py` 是 `bootstrap.build_app` 的**第二个真实调用方**，`build_app` 加参数
  时漏改它会让驱动设施与真实启动行为分叉——**而分叉处恰恰是验收依据**。
- `exclude_tools` 摘掉的两个工具是隔离边界的一部分，见 `CLAUDE.md` 安全边界
  那一节的第③条。

## ⚠ 三条纪律

1. **trace 不许有阈值、不许截断。** 观测设施丢内容就不是证据了
   （2026-08-09 已整体删除截断，理由记在已知项 #10）。
   裁剪只能发生在「给模型看的那份」上，且必须另存完整原文。
2. **记录失败一律静默**——观测设施绝不能反过来阻断被观测的系统。
   审查时如果想加校验/报错，先想清楚这条。
3. **两套设施的产物都是高敏感**（trace 含完整请求响应与工具输出原文，
   可能有明文 API Key）。加任何「导出 / 汇总 / 分享」类功能时，
   先读 `CLAUDE.md` 安全边界里 trace 那三条纪律。
