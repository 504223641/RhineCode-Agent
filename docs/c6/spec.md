# C6 五层防御权限系统 Spec

## 背景

RhineCode 当前（C5）的工具系统只有两道很薄的防线：

- **沙箱雏形**：`path_guard.py` 对文件类工具做项目根边界校验（解析符号链接后判前缀）。
- **人工确认**：副作用工具（写文件 / 改文件 / 跑命令）执行前弹确认面板，支持本会话免确认。

但 `run_command` **没有任何危险命令拦截**——其注释里明确写着「本章不做沙箱/黑名单，危险操作由用户确认弹窗兜底」。这意味着一旦用户手滑点了确认、或选了「本会话免确认」，`rm -rf` 之类的命令就会直接执行。同时也**没有可配置的细粒度规则**，用户无法声明「git 命令一律放行、push 一律拦截」这类策略。

更根本的问题是：现有防线**依赖模型的自觉和用户的逐次判断**，而安全边界不应该由模型的善意来保证。

## 目标

给 RhineCode 装上一套**五层防御权限系统**，在每个工具执行前由**代码**（而非模型/prompt）计算出「放行 / 拒绝 / 问用户」的决定。五层按固定顺序构成一条决策管线，第一个能下定论的关卡说了算：

| 层 | 职责 | 关键特性 |
|----|------|----------|
| ①危险黑名单 | 正则拦截已知高危 shell 命令 | **不可被任何配置或模式放开** |
| ②路径沙箱 | 文件读写限制在项目根内 | 复用并强化 `path_guard.py` |
| ③可配置规则 | `Tool(模式)` 声明 allow/deny | **deny 永远优先**，跨三层 YAML 合并 |
| ④权限模式 | 严格/默认/放行三档 | 只兜底「③未命中」的灰色地带 |
| ⑤人在回路 | 弹确认面板 | 三档放行：本次/本会话/永久 |

并满足一条贯穿全局的行为：**权限被拒不终止 Agent Loop**，把结构化拒绝原因回灌给模型，让它调整策略后继续。

### 决策管线（从上到下，第一个下定论的层说了算）

```
①黑名单   命中→拒绝（不可配置放开）
②沙箱     越界→拒绝
③规则     三层合并后：任意层 deny 命中→拒绝 / allow 命中→放行 / 未命中→下沉
④模式（仅当③未命中）：
     严格   → 拒绝
     默认   → 问用户（HITL）
     放行   → 允许
⑤HITL 面板（本次 / 本会话 / 永久 / 拒绝）
```

只读工具（read_file / glob / grep）走简化分支：只受 ②沙箱 与 ③的 deny 约束，不因 ④模式 被问/拒。

## 功能需求

> 每条 F 聚焦「系统做什么」，不绑定具体函数名/文件名（留给 plan.md）。括号标注对应的防御层。

- **F1 — 统一权限判断入口（决策管线）**：提供唯一的权限判断入口。输入是「一次工具调用（工具名 + 参数）」加「当前上下文（权限模式、已加载的三层规则、会话级临时规则）」，输出三选一——**放行 / 拒绝（附结构化原因）/ 交人工确认**。判断按 ①→②→③→④ 固定顺序短路，第一个能定论的层即返回。*（贯穿五层）*

- **F2 — 危险命令黑名单**：对 `run_command` 在执行前，用一组**固定的正则**匹配已知高危 shell 命令；命中即判**拒绝**。这层**不可被规则、权限模式或人工确认放开**（circuit breaker）。匹配前需按 shell 分隔符（`&&`、`||`、`;`、`|`、换行等）**逐段拆分**复合命令，任一子命令命中即整条拒绝。覆盖类别至少包括：递归强删（`rm -rf` 等）、磁盘/分区破坏、`git` 破坏性操作（`reset --hard`、`push --force`、`clean -fd`）、fork 炸弹、向关键系统路径写入。*（①黑名单）*

- **F3 — 路径沙箱**：文件类工具（读 / 写 / 改 / glob / grep）的目标路径必须落在项目根内。校验时**先解析符号链接再做项目根前缀判断**，拒绝：含 `..` 的路径、解析后越界的绝对路径、指向项目外的符号链接。在现有 `path_guard.py` 基础上强化并纳入统一管线。*（②沙箱）*

- **F4 — 可配置规则**：规则写成 `工具名(模式)`，结果只有 `allow` 或 `deny`，分用户级 / 项目级 / 本地级三层配置文件声明。求值采用**哲学 A（deny 永远优先）**：三层规则合并后，**任意层有 deny 命中即拒绝**；否则有 allow 命中即放行；否则本层不定论，交给 ④。模式匹配：shell 命令支持前缀 + glob 通配（` *` 带词边界，`npm:*` 不误伤 `npmx`）；文件路径支持精确与 gitignore 风格 glob。*（③规则）*

- **F5 — 多档权限模式**：提供严格 / 默认 / 放行三档，**只决定「③规则未命中」时的兜底行为**：严格→拒绝，默认→交人工确认，放行→放行。放行档**翻不了** ①黑名单、②沙箱越界、③的 deny。启动时默认处于「默认」档，并提供运行时切换三档的方式（斜杠命令）。*（④模式）*

- **F6 — 人在回路**：当管线决定为「交人工确认」时，弹出确认面板，提供四个选择：**本次放行 / 本会话放行 / 永久放行 / 拒绝**。「本会话放行」登记为一条**内存中的会话级 allow 规则**（关程序即失效）；「永久放行」**写入本地级配置文件**的一条 allow 规则（不提交 git）。复用现有确认面板与三档免确认机制。*（⑤人在回路）*

- **F7 — 只读工具特殊处理**：只读工具（`read_file` / `glob` / `grep`）只受 ②沙箱 与 ③规则中的 **deny** 约束：沙箱越界拒、命中 deny 规则拒（如 `Read(config.yaml)` 护住密钥），否则一律放行；**不因权限模式（含严格）而被拒或被问**。*（②③，只读分支）*

- **F8 — 拒绝不终止 Agent Loop**：任意层（黑名单 / 沙箱 / deny 规则 / 严格模式 / 用户拒绝）产生的「拒绝」，都不终止循环，而是返回一条**结构化的工具失败结果**（标明被哪一层、因什么原因拒绝）回灌给模型，Agent Loop 继续下一轮。*（贯穿）*

- **F9 — 配置加载与容错**：启动时加载三层配置文件；文件缺失视为空规则集；文件格式错误时给出**可读的错误提示并降级为「该层无规则」**，绝不因配置坏掉而崩溃或意外放开权限（fail-safe）。*（③规则的支撑）*

## 非功能需求

- **N1 — Fail-safe（安全优先）**：任何不确定或出错的情形都必须**偏向更严**：配置加载失败 → 当作无规则而非全放开；判断有歧义 → 倾向拒绝或交确认。①黑名单与②沙箱在任何模式/配置下都不可被绕过。

- **N2 — 权限由代码强制，不依赖模型**：判断结果完全由工具层代码决定，模型输出、系统提示、CLAUDE.md 都无法改变某条命令的放行/拒绝结论。

- **N3 — 轻量与低延迟**：权限判断在每次工具调用前同步执行，必须轻量（正则、字符串/glob 比对、路径解析），不引入可感知延迟。三层配置在**启动时加载一次并缓存**，判断时不重复读盘。

- **N4 — 与现有架构解耦**：权限系统作为独立模块，通过清晰接口接入 Agent Loop；不侵入 Provider 层；与 TUI 的交互沿用现有 `AgentEvent` 单向事件流和确认回调。

- **N5 — 可测试性**：决策管线的核心是**纯逻辑**：给定「工具调用 + 模式 + 三层规则」即可断言预期决定，单元测试不依赖 TUI、不真正执行命令、不真正读写文件。

- **N6 — 兼容性与非破坏**：仅在 `protocol: deepseek` 工具模式下生效；不破坏现有 Plan Mode、确认面板、会话级免确认、`path_guard` 的既有行为；Anthropic / OpenAI 的纯对话能力不受影响。

- **N7 — 配置可读可维护**：三层 YAML 人类可读、可手工编辑；规则语法（`Tool(模式)`）直观；加载错误给出指明文件与问题的可读提示。

- **N8 — 跨平台正确性**：项目主要运行在 Windows（`win32` + PowerShell），兼顾类 Unix。黑名单正则、命令分隔符拆分、路径解析与项目根前缀判断都必须在 **Windows 路径语义**下正确工作（盘符、反斜杠、大小写不敏感等），不假设 POSIX。

- **N9 — 中文注释规范**：所有新增 / 修改代码遵循项目 `CLAUDE.md` 的中文注释规范：核心函数说明用途、参数、返回、主要步骤、副作用与边界条件。

## 不做的事

- **网络请求限制**——不做域名 allowlist / denylist、不拦截 `curl`/`wget` 目标地址。（留给后续章节）
- **资源配额**——不做 CPU / 内存 / 磁盘 / 进程数配额；`run_command` 仍只有现有超时上限。
- **审计日志**——不把每次权限决定持久化成审计轨迹。（留给后续章节）
- **OS 级沙箱**——不接入 Seatbelt / bubblewrap 等内核级隔离。沙箱层仍是应用层路径前缀校验，并坦承其局限：管得住本项目的文件工具，但管不住 `run_command` 跑起来的脚本自己用代码 open 的文件。这是已知边界。
- **规则管理交互界面**——不做类似 `/permissions` 的可视化规则增删改 UI；规则靠手工编辑 YAML（外加 F6「永久放行」自动追加 allow）。
- **扩展到其他 Provider**——权限系统只在 `deepseek` 工具模式生效；不给 Anthropic / OpenAI 的工具调用接线。
- **黑名单可配置化**——①黑名单是固定内置集，不开放为用户可增删的配置项。
- **命令参数级深度语义分析**——承认 shell 命令模式匹配本质脆弱（如 `curl` 经重定向绕过、变量拼接绕过）。本章只做前缀 + glob 级匹配，真正致命的操作交由①黑名单兜底。
- **企业级 / managed 配置层**——不做不可被覆盖的管理员策略层；只做用户 / 项目 / 本地三层。

## 验收标准

- **AC1**（F1）— 给定「工具调用 + 模式 + 三层规则」，统一入口稳定返回 `放行 / 拒绝 / 确认` 之一，且遵守 ①→②→③→④ 短路顺序（多场景单测断言）。
- **AC2**（F2）— `run_command` 收到 `rm -rf /` 类命令被黑名单拒绝并返回结构化原因；复合命令 `git status && git push --force` 因第二段命中而整条被拒；且即便处于放行档或已选「本会话免确认」，黑名单命中仍被拒。
- **AC3**（F3）— 文件工具访问 `../outside.txt`、解析后越界的绝对路径、指向项目外的符号链接均被沙箱拒；项目内正常路径放行。
- **AC4**（F4）— 配置 `allow Bash(git *)` 后 `git status` 直接放行无需确认；无任何规则命中的命令落入模式兜底。
- **AC5**（F4·deny 优先）— 用户级 `deny Bash(git push *)` 叠加项目级 `allow Bash(git *)`，执行 `git push origin main` 被拒绝（deny 赢，不看层级远近）。
- **AC6**（F5）— 同一条「规则未命中」的命令：严格档→拒绝、默认档→弹确认、放行档→放行；且放行档下 `rm -rf /` 仍被①拒、命中的 deny 规则仍拦。
- **AC7**（F6）— 决定为确认时面板出现四选项；选「永久放行」后对应 allow 规则出现在本地级 YAML 中，重启后同命令直接放行；选「本会话放行」重启后恢复弹确认。
- **AC8**（F7）— 严格档下 `read_file` 读项目内文件不弹确认直接放行；但配置 `deny Read(config.yaml)` 后读 `config.yaml` 被拒。
- **AC9**（F8）— 被拒的工具调用返回 `ok=False` 的结构化结果，Agent Loop 不终止，模型收到拒绝原因后进入下一轮（可观测：事件流未进入停止状态）。
- **AC10**（F9）— 提供一个语法损坏的项目级 YAML，启动不崩溃、给出可读错误、该层降级为「无规则」且不意外放开任何权限。
- **AC11**（N8）— 在 Windows 路径语义下，盘符绝对路径的越界判断、命令分隔符拆分均正确（用 Windows 风格输入的单测断言）。
- **AC12**（N2）— 权限判断不读取模型输出；模型在文本里声称「已获授权」不改变任何拒绝结论（构造单测验证）。
