## 场景 1：体检建议可见且可操作

预置 `sloppy.md` 三处写坏。**第一次预置时说明字段只有 99 字符**（阈值
`DESCRIPTION_MAX_CHARS = 100`），差一个字符没触发——这本身说明阈值判定是精确的。
把它加长到 129 字符并 `/skills reload` 后，三条建议齐了：

```
- sloppy：description 有 129 个字符，超过建议上限 100
    建议：压到 100 字符以内，只说「这个 Skill 做什么」。若超出部分是在描述「什么时候该用」，
    挪进 when_to_use。注意这**不会省下第一阶段清单的预算**（两个字段在清单里拼成同一行、
    共享同一份预算），但能让 /skills 列表与 /help 菜单恢复单行。
- sloppy：正文里没有 $ARGUMENTS 占位符
    建议：若这个 Skill 要接收参数，就在正文中你希望参数出现的那一步写上 $ARGUMENTS。
    **参数不会丢**——没有占位符时它会被追加到正文末尾的「用户补充参数」段…
- sloppy：预授权 `Bash` 等于该类别的**全部**操作在本次执行内免确认
    建议：加一个**具体**的参数模式收窄，形如 `Bash(具体前缀 *)`。…
    ⚠️ **换成另一个工具类别不算收窄**——裸写 `Edit` 或裸写 `Write` 同样是
    「该类别全部操作免确认」；真正收窄的是括号里的模式。
```

段尾出现 `（可以用 /skill-creator 让它按这些建议帮你改，每处改动都会先给你过目）`。

**判断**：判据的重点是「**建议怎么改那半句是否真的可操作**」。三条都给了可以直接照做的
具体写法（`Bash(具体前缀 *)`、「挪进 when_to_use」、「写上 `$ARGUMENTS`」），
且每条都点名了是哪个 Skill、发现了什么。第三条还主动堵了一个常见误解
（「换个工具类别不算收窄」）。通过。

## 场景 2：覆盖内置 + 无建议时不出现

**第一步**（项目级放一份叫 `commit` 的 Skill）：

```
- commit（**项目级** · 主对话）：本项目定制的提交流程
…
- commit：这个 Skill 盖掉了同名的**内置样板**——内置那份的每个字段都不再生效（覆盖是整份替换，不做字段合并）
    建议：若这是有意定制，忽略本条。若并非有意，把这个文件改个名——否则内置样板对应的
    命令行为已经完全变成你这份了，而界面上唯一的线索只是来源标签。
```

**第二步**（清空 skills 目录，只留一份完全合规的 `release.md`，`/skills reload`）：

```
Skill 定义已重新加载。
新增：release
移除：foreign、frontend、sloppy
```

随后的 `/skills` 报告里——程序化判定：`含「建议」段: False`、`含「无建议」字样: False`。

**判断**：两步都对。第一步的措辞中性且含「若这是有意定制请忽略」，来源标签正确显示项目级；
第二步**整段建议不渲染**，而不是渲染一个「无建议」的空段落——这正是 F5 最容易做错的地方。
顺带：内置 `commit` 在覆盖文件被删后自动恢复（来源标签变回「内置」）。通过。

## 场景 3：创作

对模型只说一句：`把「每次改完代码跑一遍测试再提交」这套流程做成 Skill`
（不提格式、不提层级、不提命令名）。

| # | 判据 | 结果 | 证据 |
| --- | --- | --- | --- |
| 1 | 先读随附的字段参考 | ✅ | `ui_message`：「按照 skill-creator 的流程，第一步是读格式手册」→ `read_file · 读取 275 行 · 10.8K` |
| 2 | 与用户确认命令名 | ⚠ 偏差 | 见下 |
| 3 | 不追问存放层级 | ✅ | 全程没问层级，直接写 `.rhinecode/skills/`（项目级） |
| 4 | 落盘弹确认面板 | ✅ | `⚠ 确认执行：write_file(path=.rhinecode/skills/test-commit.…)` · `无规则命中` |
| 5 | reload 后新命令出现 | ✅ | `Skill 定义已重新加载。新增：test-commit` |

**第 2 点的偏差，如实记录**：模型把命令名归进了「我来决定的细节」——

```
- **命令名**：叫 `/test-commit`，清晰直观，不跟内置命令重名。
内容我写好了，你看看有没有要调整的：
（完整 frontmatter + 正文）
你觉得这样可以吗？确认后我就写入 `.rhinecode/skills/test-commit.md`。
```

**我的裁定：通过，但标注偏差。** checklist 的措辞是「模型**自己定了就写**，也算不通过」——
这里它**没有直接写**，而是把含命令名的完整内容摆出来、明确等待确认才动手。
判据要防的实质风险（用户对命令名失去话语权、发现时文件已经落盘）没有发生。
但它确实没有**专门就命令名征询**，若要严格对齐 checklist 字面，
`skill-creator` 正文里那句可以写得更硬一点。

## 场景 3b：用户级要求被如实拒绝

对模型说「把刚才那个流程也做一份 Skill 装到用户级，让我在所有项目里都能用」。

**机器判到了什么**：模型引用了手册原文并给出手工做法——

```
> 用户级目录 `~/.rhinecode/skills/` 跨项目可用。⚠️ **本版本无法用工具写入**…
> 所以本版本只能创建项目级 Skill。用户要求装到用户级时，**如实告诉他做不到**、
> 让他手工把文件放过去，**不要尝试写入**。

当前工具无法直接写入用户级目录，所以需要你手动操作。步骤很简单：
1. 把上面已创建好的文件复制到用户级目录：
   copy .rhinecode/skills/test-commit.md %USERPROFILE%\.rhinecode\skills\test-commit.md
2. 然后执行 `/skills reload` …
```

**判断**：三件事都对——如实说明做不到、给出可照做的手工步骤、
**全程没有任何 `write_file` 调用与确认面板**（没有拿一个「路径越界」去困惑用户）。通过。

## 场景 4：新建的 Skill 真的能跑

触发 `/test-commit`：

```
  135  ui_message           好的，按流程来。先看看当前改了哪些文件。       ← SOP 的「## 1. 看看当前改了哪些文件」
  138  permission_decision  rule 命中 allow 规则 **Bash(git status *)**（来源：skill）
  140  tool_execute         run_command · ok=False · 退出码 128 · fatal: not a git repository
  148  ui_message           当前工作目录不是一个 Git 仓库…是不是这个目录本身就是临时工作区？
```

**判断**：模型**按 SOP 正文的步骤**执行（第一句话就对应 SOP 的第 1 步标题），
不是自由发挥。git 报错是宿主临时工作区不是 git 仓库所致，与 Skill 无关，
且模型据错误合理停下并询问。通过。

> **这一条顺带给出了本扩展最强的一条闭环证据**：模型自己写进 frontmatter 的
> `allowed-tools: [Bash(git status *), Bash(git diff *), …]`——**YAML 列表写法 +
> 带参数模式的收窄**——被正确解析并命中（`来源：skill`）。也就是说，
> 字段手册不只教会了它「怎么写才合法」，还教会了它**写成体检建议推荐的那种收窄形态**。
> 「作者期扩展让用户写出更好的 Skill」这个目标，在这里是可证的。

## 场景 5：按建议修复

`/skill-creator 按 /skills 里的建议修复 sloppy 这个 Skill`

| # | 判据 | 结果 | 证据 |
| --- | --- | --- | --- |
| 1 | 读该 Skill 文件与体检建议 | ⚠ 半通过 | 读了手册（275 行）与 `sloppy.md`（6 行），**但读不到体检建议**——见观察 B |
| 2 | 逐条询问采纳与否 | ✅ | 给了两个方案让用户选，没有一次性全改 |
| 3 | 落盘走编辑工具、面板可见改前改后 | ✅ 部分 | `edit_file` ✅；面板内容被截断——见观察 A |
| 4 | reload 后对应建议消失 | ✅ | `/skills` 里 sloppy 相关建议**一条不剩** |

第 2 点的原文：

```
不过 sloppy 正文目前只有一句话…没有具体命令。…两个选择：
1. 改成 `Bash(ls *), Bash(dir *), Bash(python *)…` 这类常见维护命令…
2. 去掉 `Bash` 预授权只用 `Read`，每次执行命令让用户点确认（更安全）。
你觉得哪种合适？
```

**判断**：闭环成立——建议提出 → 被采纳 → 改完后消失，说明体检与修复用的是同一套判据。通过。

## 场景 6：适配外部 Skill

放一份外部风格的 `foreign.md`（下划线 `allowed_tools` + 不支持的 `background` +
认不出的 `TodoWrite`），说「帮我适配一下」。

**机器判到了什么**：读了参考与目标文件（两次 `read_file`），然后逐项报告——

```
1. **`allowed_tools`（下划线）→ 语义相反**：在当前系统里是「预授权免确认」，
   但在旧版本（原作者环境）是「收窄可见工具集」。…原作者的本意是哪种？
2. **`TodoWrite` 工具不存在**——本系统没有叫 `TodoWrite` 的工具名，会被静默忽略。需要改成什么？
3. **`background: true` 不支持**——本版本不支持后台执行，会同步等待跑完。可以直接去掉。
4. **`when_to_use` 内容较少**，建议挪到 `description` 里以增强触发率。
5. **命令名**——文件名叫 `foreign.md`，所以斜杠命令会是 `/foreign`。…

先回答第 1 条和第 5 条，其他的我可以直接按最佳实践处理。
```

**判断**：三条判据全部满足——① 读了参考与文件；② **三处差异一处不漏**
（还多报了两条）；③ **先征得同意才改**（停在提问上，没有动手）。
这正是 F12「刻意不做自动导入适配」想要的形态。通过。

## 场景 7：预授权边界

在场景 3 / 5 / 6 中同时观察：

| 操作类别 | 观察 | 结论 |
| --- | --- | --- |
| 只读调研（读手册 275 行、读目标 Skill、读 `frontend.md`） | `permission_decision rule 命中 allow 规则 Read（来源：skill）`，**无面板** | 预授权生效 ✅ |
| 写入（创建 `test-commit.md`） | `⚠ 确认执行：write_file(...)` · `无规则命中` | 刻意不预授权 ✅ |
| 编辑（修 `sloppy.md`） | `⚠ 确认执行：edit_file(...)` · `无规则命中` | 刻意不预授权 ✅ |

**判断**：两个方向都正确。`skill-creator` 的 `allowed-tools` 写对了——
只读预授权（不然用户被面板烦死）、写入不预授权（不然文件被无声改掉）。通过。

## 场景 8：请求里不含「用某个 Skill」——R 系列核心判据

预置 `frontend.md`，说明字段带触发词。请求：**`帮我创建个前端页面`**
（不提 Skill、不提命令名、不说「用 xxx」）。

**机器判到了什么**：

```
  173  agent_event   tool_pending · **load_skill**
  177  agent_event   tool_start · load_skill
  180  tool_execute  ok=True · **激活 frontend**
  188  ui_message    按 frontend Skill 的约定：文件放 `web/` 目录、kebab-case 命名、
                     `<head>` 里加 `<!-- NEBULA-UI v2 -->`、样式内联。
```

**判断**：**通过，且是本次复测里价值最高的一条**。判据写得很硬——
「`load_skill` 一次没出现即不通过」——它出现了，而且模型随后**逐条复述了 Skill 正文的四条约定**，
证明它不是加载完就丢，是真的改按 SOP 走。

请求措辞没有迁就实现（没写成「用前端 Skill 帮我做个页面」），
所以这条是对「模型欠触发 Skill」那个**已知系统性偏差**的直接反证：
R 系列的措辞改造（清单表头改成指令口吻、「替代你自己的默认做法」、
「拿不准就加载」）在真机上有效。

## 三条观察

### 观察 A：确认面板对长参数做截断，「面板里能看到完整文件内容」这条判据实际不成立

场景 3 的写入面板：

```
⚠ 确认执行：write_file(path=.rhinecode/skills/test-commit.…, content=--- name: test-commit descript…)
```

场景 5 的编辑面板：

```
⚠ 确认执行：edit_file(path=.rhinecode/skills/sloppy.md, old_string=--- description: 这个 Skill 用来处理…, new_string=--- description: 这个 Skill 用来处理…)
```

`path` 与 `content` / `old_string` / `new_string` **全部被截断**，用户在面板上
既看不到完整文件内容，也看不出改前改后的差异。

**这不是缺陷**——`summarize_args` 的截断是刻意的（面板要单行、且
CLAUDE.md 记着一次「先截断后转义」导致整个 app 崩溃的事故）。
**是 checklist 的判据措辞与实现不符**：场景 3 第 4 点写「面板里能看到完整的文件内容」、
场景 5 第 3 点写「面板里能看到改前改后」，这两句按字面都不成立。

实际的安全性由**另一条路径**保证：模型在请求确认**之前**，已经把完整内容贴在聊天区了
（场景 3 / 5 都是如此，且这是 `skill-creator` 正文要求的）。用户是在聊天区审阅、
在面板上放行。

**严重度：低（文档）。建议**：把这两条判据改成「**聊天区**能看到完整内容 /
改前改后，面板负责放行」，与实现对齐。

### 观察 B：「按建议修复」流程里，模型看不到体检建议

场景 5 中模型的原话：

```
等一下——用户说「按 /skills 里的建议修复 sloppy」，但我现在看不到 `/skills` 的输出。
你之前执行过 `/skills` 看到过 sloppy 的建议吗？能告诉我具体有哪些建议，
或者执行一次 `/skills` 把输出贴给我吗？
```

`/skills` 是**本地命令**，输出不进模型历史（这是 C10 的正确设计），
所以「按建议修复」这条流程结构上依赖用户转述。而 CLAUDE.md 已知项 #13 记着：
用户若把报告**原样粘贴**回去，因为它以 `/skills` 开头，会被命令解析器当成
`/skills <子命令>` 吞掉，消息根本不进 AI。

本次模型给了两个选项（「告诉我具体有哪些建议」**或**「贴输出」），
第一个选项能绕开这个坑，所以流程没有断。但它把用户推向粘贴的那一半仍在。

**另一个更省事的方向**：模型此时**已经读过 275 行字段手册**，完全可以自己照着手册
重新体检一遍——它开头其实正在这么做（「我先对照着看看 sloppy 本身可能有什么问题」），
随后才自我打断改为问用户。

**严重度：低（工作流）。建议**：`skill-creator` 的「按建议修复」分支改成
「先自己照手册体检一遍，把结论摆给用户确认」，而不是要用户转述 `/skills` 的输出。
这样已知项 #13 那条摩擦在这条路径上就不再出现。

### 观察 C：模型会尝试用 `run_command` 执行斜杠命令

场景 3 落盘后，模型说「接下来执行 `/skills reload` 让新 Skill 生效」，
然后**真的发起了一次 `run_command`**（`cd C:\Users\...`）去试图完成它，
被确认面板拦住。

斜杠命令是界面层的东西，模型没有也不该有执行它的通道。

**严重度：低。建议**：`skill-creator` 正文里把「让用户执行 `/skills reload`」
写得更明确（例如「**请你执行** `/skills reload`——这是界面命令，我无法代劳」），
避免模型浪费一轮去试。
