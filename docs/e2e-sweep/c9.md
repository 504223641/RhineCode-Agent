## 一条方法说明：P1a 下「重启」怎么验

宿主每次启动都建**全新**的临时工作区与临时用户目录，所以凡是判据形如
「**重启之后 X 仍然生效**」的场景（本章的 2 / 3 / 5，以及 C6 的永久放行）
在 P1a 下**本来一条都验不了**——新宿主看到的是空目录。

本次新增 `sweep_scenarios.seed_restore` 解决它：把上一台宿主的工作区与用户目录
复制到暂存区，新宿主在**装配之前**还原回去。对产品而言这与「同一个项目目录被第二次
打开」完全等价——它读到的就是上次留下的会话存档、记忆、本地规则。
标为「等价形态」的场景都是这么验的。

## 场景 1：冷启动记忆注入

预置项目根 `RHINE.md`（含一条**可观测且模型不会自发遵守**的硬性要求：每条回复第一行
必须是 `【NEBULA-ACK】`）与被引用的 `docs/style.md`（snake_case / 中文 docstring /
中文提交格式）。

**机器判到了什么**：

- `/memory` 报告：`[项目根] …\RHINE.md — 已加载（167 字符）`，**无 include 警告**
  （167 = RHINE.md 本体 + `docs/style.md` 展开后的内容）；
- 模型每一条回复的第一行都是 `【NEBULA-ACK】`；
- **关键**：模型在**第一轮、尚未调用任何工具**时就说出了
  「代码风格约定（snake_case 命名、中文 docstring、中文提交信息）」——
  这些文字**只存在于 `docs/style.md` 里**，RHINE.md 本体没有。

**判断**：第三条是 include 展开真正生效的硬证据（如果没展开，模型必须先读文件才可能知道）。
三层加载与 `@` 展开都成立。通过。

## 场景 2：中断恢复

把带 11 条历史（含一个刻意植入的事实「部署代号 ORION-7」）的工作区还原进新宿主。

**机器判到了什么**：

```
📂 选择要恢复的会话（↑↓ 选择，回车载入，Esc 取消）
  2. 20260731-031443-0zyc · 2026-07-31 03:18 · 11 条 · 用一句话说说这个项目，另外我想加个新函数，你会怎么命名？
→ 已恢复会话 20260731-031443-0zyc（11 条消息）。
→ 追问「这个项目的部署代号是什么？」→ 【NEBULA-ACK】这个项目的部署代号是 **ORION-7**。
```

**判断**：面板字段齐全（编号 / ID / 时间 / 消息数 / 标题），载入后**模型真的记得**
恢复前的内容——历史确实回灌进了模型上下文，不只是界面回放。通过。

## 场景 3：越用越懂你

告诉 Agent 一条长期偏好（「所有项目日志用英文」）→ 自然停止后记忆沉淀 →
「重启」（还原目录）→ 新会话（历史为空）里追问。

**机器判到了什么**：

记忆落盘 `<user_dir>/memory/log-language-english.md`：

```markdown
---
name: 日志语言偏好
summary: 所有项目日志用英文，不用中文
category: preference
---
用户要求所有项目的日志文本必须使用英文编写…此偏好仅约束日志的文本语言，不影响 docstring…
```

索引 `MEMORY.md`：`- 日志语言偏好（log-language-english.md）[用户偏好] — 所有项目日志用英文，不用中文`

新会话里的模型回复：

```
1. **日志语言偏好**：所有项目日志用英文，不用中文（**来自用户级记忆索引 log-language-english.md**）。
```

**判断**：四件事都对——① 记忆内容准确且带 frontmatter；② `scope` 判为 `user`
（跨项目偏好，正确）；③ 索引同步多一行；④ **新会话首条消息就体现了该偏好，
且模型自己点明了来源是记忆索引**——索引注入生效。通过。

顺带核实一条安全设计：记忆 LLM 请求 `tools=None`，产出是纯 JSON 动作数组
（`{"op":"add","scope":"user","filename":"log-language-english.md",…}`），
写入路径由代码按白名单校验，模型碰不到文件系统。

## 场景 4：双实例并发

还原目录时把上一台留下的 `.lock` 一并带过来了（那份锁未过期），
这在产品眼里与「另一个实例正占着这个会话」完全一致。

**机器判到了什么**：`/resume` → `没有可恢复的其它会话（仅有当前会话或均被其它实例占用）。`

删掉那份锁后再 `/resume`，会话正常出现在面板里。

**判断**：锁定会话被正确排除并给出可读原因，锁释放后恢复可选。
这就是 AC22「B `/resume` A 的会话被拒并提示占用」的行为。通过。

> 真正的「两个终端同时开」本次没做——P1a 的两台宿主各有独立工作区，
> 天然不共享 `.rhinecode/`。上面这种「带着别人的锁去开」是它的等价形态，
> 且验的是同一段判定逻辑（`NOTE_LOCK_STALE` / 会话锁新鲜度）。

## 场景 5：隔天回来

把会话存档全部消息的 `ts` 改成 30 小时前，然后恢复它。

> ⚠️ 这条**顺序很讲究**，我第一次做错了：如果在会话仍是「当前会话」时改 ts，
> 之后任何一条新消息都会以**当前时间**追加进去，`last_time` 立刻被刷新，
> 提醒就不会触发。正确顺序是**先 `/clear` 脱离该会话，再改 ts，最后恢复**。

**机器判到了什么**（`api_request` seq 173 的尾部 system 提醒）：

```
<system-reminder>
当前运行环境：
- 工作目录（项目根）：…
- 当前日期：2026-07-31
- 模型：deepseek-v4-flash（protocol: deepseek）

距上次对话已过去 30 小时，工作区状态（文件、分支、依赖）可能已变化，涉及时效的结论请先重新核实。
</system-reminder>
```

**判断**：阈值（`TIME_GAP_HOURS = 24`）判定正确、措辞正确、位置正确
（在 `<system-reminder>` 内、紧跟环境信息之后）、**不进持久历史**
（下一条 `notes` 作用域的请求里没有它）。通过。

## 场景 6：`/init` 引导

项目根已有 RHINE.md 的情况下执行 `/init`。

**机器判到了什么**：

```
  43  command_dispatch  /init
  47  ui_message        【NEBULA-ACK】让我先读取现有的 RHINE.md，然后探索项目整体现状。
  55  tool_execute      read_file · ok=True · 读取 9 行
  57  tool_execute      glob_files · ok=True · 找到 10 个文件
```

**判断**：走完整 Agent Loop 探索项目、已存在时不覆盖只出建议——两条都符合。通过。

> 内容是完整的内置提示词（「请分析当前项目并生成（或改进）项目指令文件 RHINE.md…」）。
> 双内容分流成立。

## 发现一：AC19「记忆变更时界面出现低打扰提示」不可观测 · ✅ **已于 2026-08-05 修复**

> 埋点已补，但**位置与下方建议不同**：排在 `call_from_thread` **之后**而不是
> 照 `show_message` 先记后显示——这里的提示尚未显示，先记会在退出竞态下留一条
> 界面上从未出现过的记录。护栏见 `tests/test_e2e_control.py::MemoryNotifyRecordedTest`
> （含一条专门钉顺序的用例）。以下保留复测当时的原始记录。

**这是观测缺口，不是已确认的产品缺陷。**

判据「记忆实际变更时界面出现低打扰提示」本次**无法判定**，原因：

- 记忆确实写成功了——`/memory` 报告 `最近一次自动更新：已更新 1 条笔记。`（逐字引用当时的产品输出；该行现已改口为「记忆」，见 tui-display 扩展 G 组），
  说明 `manager.py:300` 的 `if applied:` 分支确实进去了，而 `self.notify(...)`
  就在同一个分支里（`:303`）；
- 但**整个 trace 里没有任何「🧠 已更新记忆」的 `ui_message` 事件**。

原因在埋点：`ui_message` 的 trace 事件是由 `tui/app.py` 的**调用方**发出的
（`show_message()` 里 `_trace_ui_message("system", …)` 与 `append_system(text)` 成对），
而 `_notify_memory()`（`app.py:247`）**直接调 `append_system`，绕过了 `_trace_ui_message`**。

于是两种情况在 trace 上完全无法区分：

1. 提示显示了，只是没被记录（埋点漏了）；
2. 提示压根没显示（`notify` 为 None，或 `_notify_memory` 里那个
   `except Exception: pass` 吞掉了异常）。

P1a 的控制通道只能读面板与 trace，读不到聊天区正文，所以**用驱动设施判不了这一条**。

**严重度：中（观测性）。** 它的实际影响是：这条判据在任何基于 trace 的验收里都是盲区，
而 CLAUDE.md 恰好有一条成对维护点在讲 `ui_message` 的产出点必须齐全
（那条讲的是 `_do_stream` 的四个调用点，说的是同一类问题：漏一处，界面正常但记录里没有）。

**建议（不在本分支修，已登记进 `summary.md`）**：给 `_notify_memory` 补一行
`self._trace_ui_message("system", text)`，与 `show_message` 同口径。
这样 AC19 立刻变成可自动判定的判据。

## 发现二：`@include` 的真实语法是 `@<路径>`，不是 `@include <路径>`

复测时我按 CLAUDE.md 的写法「三层 RHINE.md 项目指令（含 `@include` 展开）」，
在 RHINE.md 里写了 `@include docs/style.md`。结果：

```
[项目根] …\RHINE.md — 已加载（101 字符）
    ⚠ @include 目标不存在，未展开：include
```

正则是 `@([^\s@`]+)`（`memory/instructions.py:32`），也就是 **`@` 直接跟路径**。
`@include docs/style.md` 被解析成「引用一个叫 `include` 的文件」，
自然找不到，于是按 fail-safe 跳过。

**产品行为完全正确**（跳过 + 可读提示 + 不崩溃）。问题在**措辞**：

- CLAUDE.md 写「含 `@include` 展开」；
- 错误文案也叫「**@include** 目标不存在」。

两处都在暗示语法是 `@include <路径>`。我按文档写、然后踩坑，
这本身就是这条建议的证据。

**严重度：低（文档/文案）。** **建议**：CLAUDE.md 与 `docs/c9/` 里把它称为
「`@路径` 引用」并给一个正例；错误文案改成「`@` 引用的目标不存在，未展开：{raw_ref}」。
