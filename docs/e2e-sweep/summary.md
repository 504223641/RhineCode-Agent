## 二、问题清单（按严重度）

### 🔴 缺陷（1 条，全在测试设施，不影响产品）

**D1 —— P1a 客户端在宿主被强杀时抛裸异常，而不是可读提示** · ✅ **已于 2026-08-05 修复**（见第六节）

> 下面保留复测当时的原始记录（现象、成因、复现），它是这条修复的依据。

- **位置**：`tests/e2e/client.py:76-98` 的 `send_command`
- **现象**：`wait` 挂起期间强杀宿主 → `ConnectionResetError: [WinError 10054]` 裸 traceback
- **成因**：循环只处理「`recv` 返回空 bytes（EOF）」。优雅退出发 FIN → 走可读提示；
  **强杀发 RST → `recv` 直接抛异常**，未捕获
- **为什么算缺陷**：`docs/c11/testing/p1-driver/checklist.md` 场景 4② **点名**要求
  「可读提示而非异常堆栈」；且 `client.py` 自己的 docstring 就把
  「三种失败必须翻译成人话」列为设计目标——那张表漏了 RST 形态
- **复现**：稳定（本次跑两次形态一致）
- **修法**：`except (ConnectionResetError, ConnectionAbortedError)` 转成同一条 RuntimeError 文案，
  并把 docstring 那张表补成四行。详见 [testing-p1a-driver.md](testing-p1a-driver.md)

### 🟢 低severity 观察（7 条）

- **O3**（C6）**会话存档让被 deny 的内容可被 grep 重新捞出**。`deny` 只挡新读取，

## 三、专条：`tools=None` 时的标记泄漏（O13）

这是本次唯一一条**用户可见的产品行为异常**，虽然不影响正确性，但值得单独说清楚。

**触发路径**：用户在确认面板选「拒绝」→ C6 的硬约束生效，下一轮 `tools=None`
（`_RoundContext.user_denied`）→ 模型**仍然想调工具**，但物理上发不出 tool_call，
于是把工具调用写进了**文本流**：

```
好的，项目当前是干净的工作树。我直接创建文件。

<｜｜DSML｜｜tool_calls>
<｜｜DSML｜｜invoke name="write_file">
<｜｜DSML｜｜parameter name="file_path" string="true">halt.txt</｜｜DSML｜｜parameter>
<｜｜DSML｜｜parameter name="content" string="true">hello</｜｜DSML｜｜parameter>
</｜｜DSML｜｜invoke>
</｜｜DSML｜｜tool_calls>
```

**安全性没有问题**：硬约束确实生效了——没有 `tool_execute` 事件，`halt.txt` 没被创建。
**问题只在呈现**：用户看到一段乱码般的内部标记，而不是「我本想创建文件，但这一轮没有工具可用」。

**为什么这条特别值得记**：CLAUDE.md 把「软硬两道缺一不可」写成了 C6 的核心设计
（软=拒绝文案、硬=`tools=None`），并记载了「只留文案时模型会把 25 轮全烧在重试上」。
硬约束是对的，但它的**副作用**此前没有被观察到——因为要同时满足
「用户拒绝 + 模型下一轮仍想调工具」才会暴露。

**建议**：低成本做法是在流式渲染层过滤掉 `<｜｜DSML｜｜...>` 这类 provider 内部标记；
更彻底的是在 `tools=None` 那一轮给模型一句明确提示（「本轮没有可用工具，请用文字回复」）。

## 五、这次复测本身的三条方法论收获

**① 真实模型会悄悄把待验的那一步跳过。**
web_fetch 场景 3 里，我问「再试一次抓 b.test」，模型**凭上一轮的拒绝结论直接回答**，
根本没调工具——trace 里一条 `permission_decision` 都没有，判据看似通过实则没验。
必须明确要求「请你**实际调用**一次……不要凭之前的结论替我判断」才逼出真实调用。
**教训**：判据涉及引擎行为时，要从 trace 确认那次调用真的发生了，而不是看模型怎么说。

**② 模型太守规矩会让「错误路径」验不到。**
C3 场景 3 想验 `edit_file` 匹配失败，连试三种提示词都被模型合规避开
（两次拒绝「不读就改」、一次自行加 `replace_all`）。最后用 TOCTOU
（面板挂起期间从进程外改文件）才确定性触发。
**这三次"失败"本身是有价值的证据**——它们证明 C5 的「编辑前必先读」与工具描述的
`replace_all` 指引在真机上是硬生效的。

**③ 「重启后仍生效」这类判据在 P1a 下本来一条都验不了。**
宿主每次都建全新临时目录。本次新增 `seed_restore`（把上一台的目录树还原进新宿主）
才把 C9 的场景 2/3/5 与 C6 的永久放行验出来。这个还原对产品而言与
「同一个项目目录被第二次打开」完全等价。
