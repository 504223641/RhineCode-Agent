## 场景 1：真实 stdio Server 接入

预置项目级 `.rhinecode/mcp.yaml`：

```yaml
mcpServers:
  everything:
    command: npx
    args: ["-y", "@modelcontextprotocol/server-everything"]
  brokenserver:
    command: this-command-does-not-exist-9d41f7
    args: []
```

> `command` 刻意写 `npx` 而不是 `npx.cmd`：产品侧 `mcp/transport.py:resolve_stdio_command`
> 负责在 Windows 上兜底找 `.cmd/.exe/.bat`，写死了就等于把这条真实的
> Windows 兼容性判据从测试里摘掉。**这条逻辑本次实测生效**。

### ① 工具注册

启动后 `status` 的 `tool_names` 从 8 个变成 **21 个**，新增 13 个：

```
mcp__everything__echo, mcp__everything__get_annotated_message, mcp__everything__get_env,
mcp__everything__get_resource_links, mcp__everything__get_resource_reference,
mcp__everything__get_structured_content, mcp__everything__get_sum,
mcp__everything__get_tiny_image, mcp__everything__gzip_file_as_resource,
mcp__everything__simulate_research_query, mcp__everything__toggle_simulated_logging,
mcp__everything__toggle_subscriber_updates, mcp__everything__trigger_long_running_operation
```

**判断**：命名规则 `mcp__<server>__<tool>` 正确。注意**名字被规范化**了——
远端的 `get-annotated-message`（连字符）注册成 `get_annotated_message`（下划线）。
这正是 CLAUDE.md 安全边界一节提醒的那条：「若工具名被规范化，规则要写注册名而不是远端原名」。
`/mcp` 报告把两个名字都列出来（`注册名 <- 远端原名`），用户不用去猜。通过。

### ② 调用与权限

输入：`用 MCP 的 get_sum 工具算一下 1234 加 5678`

```
   16  permission_decision  mode 默认模式：无规则命中，交由用户确认
       ⚠ 确认执行：mcp__everything__get_sum(a=1234, b=5678)
   19  tool_execute         executed · ok=True · MCP everything/get-sum · 1 块
   27  ui_message           计算结果：**1234 + 5678 = 6912** ✅
```

**判断**：三件事都对——① MCP 工具走的是**同一套** `loop._execute` + `engine.decide`
路径，没有 MCP 特例分支；② 因为 `read_only=False`，默认档下每次调用都到第⑤层人在回路；
③ 远端结果被正确转换成工具结果并回灌，模型据此作答。通过。

## 发现：`mcp.yaml` 顶层键拼错会**静默**当成「未配置」

复测过程中我第一版预置把顶层键写成了 `servers:`（正确的是 `mcpServers:`）。
结果是：

- 启动**完全正常**，没有任何警告；
- `status` 的 `tool_names` 仍是 8 个（一个 MCP 工具都没有）；
- `/mcp` 回的是 **「未配置任何 MCP Server（可在 ~/.rhinecode/mcp.yaml 或项目级
  .rhinecode/mcp.yaml 声明）」**——而那个文件明明就在那儿，内容也是合法 YAML。

**严重度：低（可用性，非安全非正确性）。** 行为本身符合 fail-safe 原则
（解析不出 Server 就当没有，绝不瞎连），也符合 spec 的容错设计。
但 C7 checklist 的 AC4 写的是「某条目**结构非法**→跳过该条并收集可读错误」——
**顶层键拼错不属于「条目非法」**，它让整个文件被当成空，而收集错误的那条路径根本没被走到。

用户视角下这是最难排查的一类失败：文件在、YAML 合法、程序不报错，只是「MCP 就是不生效」。

**建议（不在本分支修，已登记进 `summary.md`）**：`_load_layer` 在文件存在、
解析成 dict、但**顶层没有 `mcpServers` 键**时收集一条提示，例如
「`mcp.yaml` 存在但未找到顶层键 `mcpServers`（发现的顶层键：servers）」。
这不改变 fail-safe 行为，只是把静默变成可见。
