## 场景 3：并发与串行

输入：`同时做三件事：读 README.md、读 config.ini、用 grep 搜所有含 timeout 的行。一次性并行发起，不要分轮。`

**机器判到了什么**：

```
  204  02:40:51.215  tool_execute  read_file     · executed · 并发 · 读取 26 行
  206  02:40:51.217  tool_execute  read_file     · executed · 并发 · 读取 9 行
  208  02:40:51.228  tool_execute  grep_content  · executed · 并发 · 52 处匹配
```

写操作侧（另一轮）：`edit_file · executed · **串行**`。

**判断**：三条只读调用的时间戳落在 **13 毫秒**之内且都标「并发」，走的是只读并发通道；
有副作用的 `edit_file` 标「串行」。通过。

## 场景 4：确认三态

三态分三次触发，都取自 `permission_decision` 与面板原文：

| 选择 | 面板 | 后续行为 |
| --- | --- | --- |
| `once` | `⚠ 确认执行：edit_file(...)` | 本次执行，下次同类操作**仍然弹面板** |
| `session` | 同上 | 下次同类操作 `permission_decision rule 命中 allow 规则 Edit(config.ini)（**来源：session**）`，**不弹面板** |
| `deny` | `⚠ 确认执行：write_file(path=notes.txt, ...)` | 见 [c3.md](c3.md) 场景 2，软硬两道约束都生效 |

第四态 `permanent` 在 [c6.md](c6.md) 场景 3 单独验（它要检查落盘）。

**判断**：四个选项语义各不相同且都正确落到第③层规则表。通过。

## 场景 5：用户取消

在一个「逐个读 6 个文件」的多轮任务跑到一半时经控制通道发 `cancel`（等价真人按 Esc）。

**机器判到了什么**：

```
   60  agent_event  finished · stop_reason=user_cancelled
   61  ui_message   [system] ⏹ 已取消
```

随后发「刚才取消了，你还在吗？」，界面正常回复。

**判断**：循环在安全点停止、系统行提示、TUI 仍可继续输入。通过。

## 场景 6：迭代上限

`MAX_ITERATIONS = 25`（`agent/loop.py:101`）。造 30 个文件并强制模型「每轮只读一个」，
让它必然撞上限。

**机器判到了什么**：

```
  340  ui_message    [system] 🔄 第 25 轮
  350  agent_event   finished · stop_reason=max_iterations · 已达到迭代上限（25 轮），自动停止。
  351  ui_message    [system] ⚠ 已达到迭代上限（25 轮），自动停止。
```

**判断**：恰好在第 25 轮停止、有明确提示、进程不挂死（随后状态 `idle`、可继续输入）。通过。

## 场景 7：连续未知工具 —— 结构不可达

真实模型只能调用 schema 里给出的工具名，**没有办法让它稳定产出一个不存在的工具名**。
这条判据在 live 模式下结构上无法触发。

它由单元测试覆盖（`agent/loop.py:581-589` 的连续未知计数 + `StopReason.UNKNOWN_TOOL`），
也可以用 `--mode scripted` 的假模型剧本构造。**本次不做**：那样验的是剧本，
而本次复测的定位是「真实模型行为」。记为未覆盖及原因。

## 场景 9：Plan 开关与状态栏

\[deepseek] deepseek-v4-flash | 思考模式：高效 | [bold #00D7D7]\[PLAN][/bold #00D7D7] | 权限模式：默认 | …

## 场景 10：Plan 只读 + 引导

输入一个宽泛需求「给这个项目加一个日志功能」。

**机器判到了什么**：

- 规划阶段的 `api_request` 一律 `tools=6 个`（正常态是 8 个）——写类工具被摘掉、
  换上 `ask_user` / `present_plan`；
- 整个规划阶段实际调用的工具只有 `glob_files`（5 次），`permission_decision` 全部是
  `allow（③规则）· 只读工具默认放行`；
- 没有任何 `write_file` / `edit_file` / `run_command` 调用。

**判断**：规划阶段的只读约束在真机上成立。通过。

## 场景 11：Plan 澄清面板

**机器判到了什么**（`ask_user` 的实际参数）：

```json
{"question": "你说的「加日志功能」具体是指什么？…",
 "options": [
   {"summary": "在 config.ini 中添加 [logging] 配置节",
    "detail": "新增一个 [logging] 节，包含 level、file、format、max_bytes / backup_count…"},
   {"summary": "创建 nebula 包的基础目录和一个 logging 模块",
    "detail": "创建 src/nebula/ 包结构…改动会涉及新建文件和修改 config.ini。"},
   {"summary": "在 config.ini 中添加日志相关配置并更新 README",
    "detail": "…不改代码，只改配置和文档。"}]}
```

**判断**：每个选项都有 summary + detail 两级，问题一次只问一个。通过。

> ⚠️ **checklist 措辞过时**：原文写「推荐项排首位**带标记**」。实现是**刻意不加标记**的——
> `tui/widgets.py:1142` 的注释写明理由：「推荐顺序由模型保证（第一位即最推荐），
> 概述文本本身已带推荐信息，故不再额外加『⭐ 推荐』前缀，避免重复提示」。
> 按当前状态判为通过，建议更新 checklist 措辞。

> ⚠️ **「上下导航只在概述间移动」P1a 驱动不了**。尝试 `answer 0 --via keys` 时驱动器明确拒绝：
> 「候选项之间夹着 disabled 详情行，按键次数无法从选项下标稳定推出」。
> 这条错误信息本身反过来证明了详情行确实是 disabled 的（即导航会跳过它们），
> 但**没有直接验到光标移动**。记为设施限制。

## 场景 12：Plan 两段式执行

**拒绝分支**：

```
  286  agent_event  tool_start · tool_name=present_plan
  289  agent_event  finished · stop_reason=plan_rejected
  290  ui_message   [system] ⏹ 计划未执行
  291  ui_message   [assistant] ## 目标 / 在 config.ini 末尾新增 [logging] 配置节 / ## 改动文件 …
```

计划全文进入聊天记录 ✅；`stop_reason=plan_rejected` ✅；Plan Mode **仍开启**——
下一条新消息（「就按刚才那个计划做」）重新进入规划阶段并再次弹出审批面板 ✅。

**批准分支**：应答 `yes` 后立刻弹出 `⚠ 确认执行：edit_file(path=config.ini, old_string=retry=3,
new_string=retry=3  \[logging] level=INFO …)`——**获批后放开了工具，但副作用工具仍逐个确认** ✅。
应答后计划正确落盘（`config.ini` 末尾出现完整 `[logging]` 节，6 个配置项）。

**判断**：两条分支的全部判据都成立。通过。

> 顺带一条**致命不变量的真机验证**：那次确认面板的参数里含字面 `[logging]`，
> 面板原文渲染为 `\[logging]`——`tui/widgets.py` 的 `escape` 正确转义了方括号，
> 界面没有崩。这正是 CLAUDE.md 里「落单的 `[` 会让整个 app 退出」那条护栏保护的场景。
