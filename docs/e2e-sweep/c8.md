## 场景 1：第一层存盘

这条是在 C4 复测途中**自动**触发的（不是刻意构造），证据更自然：
一次 `grep_content` 命中 52 处、跨 3 个文件，结果超过存盘阈值。

**机器判到了什么**：

```
  208  tool_execute  grep_content · executed · ok=True · 52 处匹配 · 3 个文件
  214  ui_message    [system] 📦 已把 1 个大型工具结果存盘，历史仅保留预览与路径。
```

落盘核对：

```
.rhinecode/context/call_02_8jQpZTxvkn0qQ0bYBzFc7165.txt    355137 字节
```

`/context` 同步显示 `已存盘工具结果：1 个`。后续对话正常继续。

**判断**：系统行提示、存盘文件落地、`/context` 计数、历史转预览四项一致。通过。

## 场景 2：`/context` 只读

**机器判到了什么**（小窗口宿主上的三次采样）：

```
估算 token：0      窗口上限：32768  距上限余量：32768  已存盘工具结果：0 个   ← 冷启动
估算 token：19556  窗口上限：32768  距上限余量：13212  已存盘工具结果：0 个
估算 token：30690  窗口上限：32768  距上限余量：2078   已存盘工具结果：0 个
```

**判断**：四项字段齐全、数值自洽（余量 = 上限 − 估算）、窗口上限正确反映配置值 32768。
连续调用不改变任何状态（估算值只随真实对话推进而变）。通过。

> 顺带验到 `context_window` 配置项真的贯通到了估算器——默认 1M 的宿主上显示 `976.6K`，
> 本宿主显示 `32768`。

## 场景 3：`/compact` 手动摘要

在估算 30690（已被场景 4 自动压到 18412 之后）再手动 `/compact`：

```
  260  ui_message  [system] 🗜 已摘要早前 2 条消息，保留近 17 条原文。
```

**判断**：**无余量阈值**——刚自动压缩过、余量还很充裕（14356）的情况下仍然执行了压缩，
符合「主动触发即尝试」的设计。走后台不卡界面（`wait` 期间界面保持响应、随后落 `idle`）。通过。

## 场景 4：自动兜底不溢出

窗口 32768 时的触发线：`window − _derive_margin(32768)` = `32768 − min(32768×0.21, 13000)`
= `32768 − 6881` = **25887**。保留区预算：`min(32768×0.16, 10000)` = **5242**。

把历史推到 30690（越线 4803）后发一条普通消息：

**机器判到了什么**：

```
  238  summary  api_request   turn=1 msgs=1 **tools=None** system_len=444
  239  summary  api_response  【分析草稿】 用户要求读取 notes/ 目录下 rec_01.md 到 rec_24.md 共 24 个文件…
  240  main     context_compaction
  241  main     agent_event   notice
  242  main     ui_message    [system] 🗜 已摘要早前 28 条消息，保留近 16 条原文。
```

**判断**：五件事都对——

1. **自动触发**，用户没有敲 `/compact`；
2. 摘要走**独立的 `summary` 作用域**，与主对话的 `main` 分开记账；
3. 摘要请求 **`tools=None`**（seq 238）——「摘要阶段模型无法调用任何工具」这条安全约束成立；
4. 产出是**先草稿后正式摘要**的两段式（`【分析草稿】` 开头，正式摘要在 `<<<正式摘要>>>` 之后）；
5. 压缩后估算从 30690 降到 18412，对话不因溢出中断，Agent 循环继续推进。

通过。

> 这一条同时验到了**已知工程项 #8 的修复**：`RETAIN_TOKENS` 与 `auto_margin` 按窗口比例
> 缩放之后，32K 这种小窗口上触发线是正数（25887）、保留区（5242）小于窗口，
> 第二层摘要**真正压缩了**而不是每轮空转。修复前这里会是「触发判据恒真 + 每次都无可摘要」。

## 场景 5：熔断不死循环 —— 结构不可达

checklist 原文建议的构造方式是「临时把窗口配得极小 + 断网/坏 key 使摘要请求失败」。
本次实测这条**在 live 模式下用配置层做不到**，原因是：

摘要请求与主对话请求**用同一个 provider、同一个 model、同一份凭据**。
坏 key 或断网会让**两者一起失败**——主对话都发不出去，历史根本撑不起来，
也就永远走不到「摘要连续失败 3 次」那一步。要让摘要单独失败，只能改产品代码
注入一个会抛异常的 summarizer，而本次复测的前提是**不改代码**。

**已有覆盖**：`tests/test_context_manager.py` 有三条针对性用例——

- `:89-91` 连续 `MAX_SUMMARY_FAILURES` 次失败后 `kind == "circuit_break"` 且 `_circuit_broken`；
- `:96-100` 熔断后 `before_request` **不再触发摘要**（provider 调用次数不再增加）——
  这正是「不死循环」的判据；
- `:207-213` 熔断在状态栏上高亮并带 ⚠ 标记。

记为**未覆盖及原因**，不计入失败。若将来要在真机上验它，需要给宿主加一个
「注入失败 summarizer」的开关（属于 P1b 范围的设施增强，不是产品改动）。
