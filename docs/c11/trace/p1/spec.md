# TUI 驱动器（P1）Spec

> **定位：跨阶段的测试设施，不是新章节的产品能力。**
> 与 Trace 记录器（P0）同属一套设施，不占章节号，文档放在 `docs/c11/trace/p1/` 下。
>
> 本轮范围是需求交底（`brief.md`）§9 划分的 **P1（TUI 驱动器）**。
> P0（Trace 记录器）已交付，见上一级目录的 `spec.md` / `plan.md` / `task.md` / `checklist.md`。

---

## 背景

### 现状：证据能留下了，但触发的一侧仍然是人

P0 解决了「证据留不下来」——运行过程中实际发生了什么，现在被写成十五类结构化事件，
配一个只读阅读器可以事后过滤、摘要、按号展开。

但**触发这些行为的一侧仍然是人**。`docs/c11/checklist.md` 的十一个端到端场景全部标注
【手测】，实际执行方式是：人在真实终端里启动、敲一段真实请求、等模型跑完、替它点确认
面板、再肉眼比对界面与记录。于是三个老问题只解决了一半：

1. **不可重复**——证据有了，但每次跑的输入与时序仍由人临场决定，回归仍无从谈起；
2. **成本高**——一轮完整验收要占用人几十分钟，因此实际上没人会为一次小改动重跑它；
3. **覆盖不稳**——手测清单越长，人越倾向于只跑「这次改动相关的那几条」，
   而回归恰恰是要跑「与本次改动看起来无关的那些」。

### 已具备的地基（P0 交付，已核实）

| 地基 | 它解决了什么 |
| --- | --- |
| 可复用的装配入口 | 能在**测试进程内**装配一套完整应用并拿到中间组件逐个断言，不必起子进程 |
| 用户级目录参数化 | 项目指令与笔记、Skill、权限规则、MCP 配置四类用户级内容的**读取**可指向临时目录，同一场景在两台机器上结果一致 |
| 清理动作复位进程级状态 | 只读路径白名单、会话锁、外部连接在每次清理后归零，同进程连跑多场景互不污染 |
| 十五类结构化事件 | 断言的事实来源——每轮实际发出的工具集、权限决策命中哪层、界面显示了什么、状态栏长什么样，全部可查 |
| 只读阅读器 | 记录的加载与过滤能力已存在，断言层可复用而不必另写一份对格式的理解 |

### 尚缺的四件事（本轮要补）

1. **没有驱动手段**。项目里已有用真实按键驱动界面的先例，但只覆盖不涉及 Agent 循环的
   纯界面交互（补全菜单、按键关闭），既没有「等一轮跑完」的判据，也没有「替人应答确认
   面板」的能力，更不碰模型调用——其中出现过的「确认面板」用例是直接改写内部待决态，
   并非真的应答一块已挂载的面板。
2. **假模型装不进真实装配**。装配入口内部自行创建模型 Provider，调用方无法替换它。
   于是「跑完整流程但不联网、不烧 token」这件事目前做不到——要么全真（慢、贵、不可
   复现），要么只测局部（当前全部单元测试的做法）。
3. **断言要手写解析**。阅读器只有命令行形态，没有可供程序断言的查询接口。
4. **应答来源在记录里恒为「人工」**。三处交互结算点都把来源写成固定值。驱动器一旦替人
   应答，记录会把自动应答伪装成人工，于是「自动应答有没有越界」——这件最需要被审计的
   事——反而查不出来。

---

## 目标

1. **一条命令跑完一个端到端场景**：无人值守地驱动真实界面完成一次完整会话，
   产出记录并给出通过/失败判定，不需要人坐在终端前。
2. **确定性场景进回归**：不联网、不依赖模型、可重复，随全量测试一起跑，
   使 C2–C11 的既有能力第一次拥有可重复的端到端护栏。
3. **真实场景可单独跑**：同一套骨架换上真实模型即可验收「模型是否真按指令行事」——
   这是确定性模式在原理上验不了的部分。
4. **断言基于结构化事实而非截屏**：判定依据是 P0 的结构化事件、会话存档与假模型留存的
   原始请求参数，不依赖终端渲染结果，也不依赖屏幕尺寸与终端类型。
5. **自动应答不扩大权限面**：驱动器替人应答时受显式策略约束，
   且「它替人放行了什么」本身在记录里可审计。

## 功能需求

### 一、驱动器核心

- **F1 场景运行骨架**：驱动器提供可复用的运行骨架——准备隔离环境 → 装配应用 →
  驱动界面 → 基于结构化事实断言 → 清理。一个场景由「一次装配配置 + 一串驱动步骤 +
  一串断言」构成，**以宿主语言的代码单元表达**，不引入独立的场景描述语言。
  （本条不单独验收，由 AC26 与 AC29 覆盖——骨架不可用则一条场景也跑不起来。）
- **F2 输入步骤**：能把一段文本送进输入框并提交，走的必须是**真人敲键盘的同一条提交
  入口**（经输入解析与命令分发），不得绕到内部方法上直接调用。
  理由：绕过去就验不到命令分发、回显与提交守卫这些正是要验收的东西。
- **F3 空闲判据**：「本轮结束」须同时满足三个条件——不处于运行忙碌态、无待决交互、
  无会话选择面板展示中；且**必须带超时上限**，超时以失败结束而非挂死。
  理由：运行忙碌态在确认面板挂着时**仍然成立**，只等它必然死等到超时。
  此外，Agent 循环自然结束后仍有**异步后台工作**（自动笔记会另起线程再调一次模型并
  写盘），本判据不覆盖它——见 F16 的收敛要求。
- **F4 面板应答**：能应答四类面板——工具确认（四态）、需求澄清、计划审批、会话选择。
  应答**必须发生在对应面板已展示且已获得焦点之后**。
  理由：前三类面板的待决交互态在面板挂载**之前**就已置位，一看到置位就应答会落在空处、
  然后死等到超时；会话选择面板走的是另一条路径（不经待决交互态），故判据统一写成
  「面板已展示且已获得焦点」，对四类都成立。
  另需预期到：确认与审批面板期间输入框**不被禁用**，此时提交会得到一条可见提示而非无
  反应——这是既有的有意行为，不是异常。
- **F5 应答来源如实记录**：记录中的交互事件须反映真实的应答来源（人工 / 驱动器自动
  策略），不得把自动应答记成人工。为使二者可区分，**自动应答须经一条与人工按键不同的
  专用应答通道**：人工＝面板按键路径，自动＝驱动器专用入口；该通道同样受 F4 的时机约束
  （早于面板挂载去结算会让面板永远关不掉）。
  这是产品侧的一处必要改动——当前三处交互结算点的来源字段都是固定值。
- **F6 自动应答策略**：默认策略**只自动放行只读工具与只读版本控制子命令**，
  其余一律**自动拒绝并如实记入记录**（被拒不终止循环，正好顺带覆盖拒绝路径）。
  场景可显式放宽为全放行，但**必须在场景里写出来，不能是缺省值**。
  两条硬约束：
  - **自动放行一律取「仅本次」这一档**，不得使用「本会话放行」或「永久放行」——
    后两者会登记会话规则或写盘到本地权限配置，从而改变后续运行的权限求值结果；
  - 第①层危险命令黑名单不受本策略影响，且这一点须有护栏。
- **F7 沙箱前置校验**：驱动器启动前校验工作区是本次运行新建的临时目录；
  不满足则**拒绝启动**。理由：自动应答等于拿掉第⑤层人在回路，工作区必须是可丢弃的。
  另须约束**会写向真实用户级目录的工具**（自动添加 MCP Server 时可显式指定写入用户级
  配置，该写入路径不受用户级目录参数约束）：场景脚本不得驱动模型调用它。
  默认策略下它因非只读会被自动拒绝，但显式放宽为全放行时这层保护即失效，故须显式约束。
- **F8 取消与可诊断超时**：能主动请求取消当前循环；任何等待都有上限。
  超时失败时须输出**当时卡在哪一步、三个空闲条件各自的取值**，而不是一句「超时」。

### 二、可替换的模型

- **F9 装配入口支持注入模型 Provider**：使装配出的应用走假模型，而其余部分——
  工具、权限、Skill、上下文、记忆、命令、界面——**全部为真**。
  注入参数**可选、缺省等于现状**（沿用 P0 用户级目录参数的同一条硬纪律）。
- **F10 覆盖换模型旁路**：独立模式 Skill 声明自定义模型时协调层会另建一个 Provider，
  该旁路须走同一注入点。否则该场景下子对话会**静默连上真实网络**——
  这与 P0 的记录旁路是同一处，是最容易漏的一条。
- **F11 脚本化假模型**：能按脚本产出「正文 / 思考 / 工具调用 / 流错误」四类数据块的
  序列，**支持按轮次给出不同响应**（如第 1 轮调工具、第 2 轮出结论），
  并**留存每轮实际收到的稳定系统提示、动态提醒消息、完整消息列表与工具 schema**
  供断言。脚本耗尽后若仍收到请求（自动笔记的异步调用、上下文摘要调用都会造成这种情况），
  须以**确定性的兜底响应**应对而非抛错或挂起，且该兜底可被识别。
- **F12 真实模式**：同一场景骨架改用真实模型运行。**无凭据或未显式开启时该场景跳过
  而非失败**。真实模式的断言只针对**模式与存在性**（调用了哪类工具、某类事件是否出现、
  作用域是否正确），不断言模型措辞。

### 三、断言层

- **F13 事实来源与查询**：断言层提供对记录产物的程序化查询——按类型取、按作用域取、
  按序号取、取某类的第 N 条、取某字段。**须复用产品包内已有的记录加载与过滤能力，
  不得自行解析记录文本**，避免两边对格式的理解各自漂移。
  三类事实的**权威来源在此裁决**，避免实现时各挑一个：
  - **系统提示与工具 schema** —— 以假模型留存的原始请求参数为权威（F11）。
    理由：记录中的对应字段受长度截断约束，且稳定系统提示与动态提醒分处两个位置；
    记录只作真实模式下的退化来源，且接受截断。
  - **主对话历史的消息条数** —— 以会话存档为权威。
    理由：十五类事件中没有任何一类承载「当前主历史有多少条」，而记录中的请求消息列表
    受条数与长度双重截断，不能当作历史全貌。
  - **其余全部事实**（工具执行结局、权限决策、界面消息、状态栏、作用域、事件次序等）
    —— 以记录为权威。
- **F14 断言词汇**：至少覆盖十一项——
  ① 某轮实际发出的工具名集合；② 某工具是否被执行过及其结局；③ 界面消息是否包含某文本；
  ④ 状态栏快照是否包含或不包含某段；⑤ 权限决策命中的防御层与结果；⑥ 事件的作用域归属；
  ⑦ 两个事件的先后次序；⑧ 某类事件的条数；⑨ 主对话历史的消息条数；
  ⑩ 某轮的**稳定系统提示**是否包含某段文本；⑪ 某轮附加的**动态提醒**是否包含某段文本。
  第 ⑩⑪ 两项必须分开：稳定段与动态段分处请求的两个位置，已激活的 Skill 正文在动态段，
  混作一谈会写出永远失败的断言。
- **F15 失败可诊断**：断言失败时输出足以定位的上下文——相关事件的序号与摘要行，
  而不只是「期望 X 实际 Y」。理由：端到端失败的根因通常在失败点之前若干个事件。

### 四、环境隔离

- **F16 每场景独立工作区**：每个场景在新建的临时目录中运行，结束后清理。
  清理**必须在异步后台工作收敛之后**进行——自动笔记线程在循环结束后仍会写盘，
  此时删目录会失败或留下残迹，表现为随机失败。故驱动器须要么等待其收敛、
  要么在确定性场景中关闭自动笔记，二选一但必须明确。
- **F17 每场景独立用户级目录**：经装配入口的用户级目录参数指向临时目录，
  四类用户级内容一律不读开发者真实目录。
- **F18 连跑不污染**：场景之间进程级全局状态不残留——只读路径白名单、
  当前工作目录、会话锁三者均须复位。
- **F19 确定性模式无外部副作用**：不建立任何外部连接——模型为假、MCP 声明为空。
  额外约束：场景脚本**不得驱动模型调用会发起网络请求的只读工具**（解析 MCP Server
  名称的工具会访问外部包索引）。这条不能靠自动应答策略兜底——只读且被规则放行的工具
  根本不会弹面板，驱动器压根不会被问到。

### 五、场景交付

- **F20 C11 场景覆盖**：交付覆盖 `docs/c11/checklist.md` 场景 **1–5、8–11 共九条**的
  场景实现。场景 6（启动失败须以退出码终止、不留孤儿子进程）与场景 7（第三方仓库首启
  提示）**不在同进程内驱动**，本轮不重复实现——但须在场景清单中**逐条点名其覆盖来源
  （具体到测试方法）并注明口径差异**，使「谁覆盖了它、覆盖到什么程度」有据可查。
  已知的口径差异：场景 7 的提示渠道在 C11 已从启动时打印改为经 `/skills` 报告呈现，
  既有测试断言的是后者。
- **F21 记录器自身场景覆盖**：交付覆盖 P0 checklist 第九节中**可自动化的四条**——
  作用域交错可读、人在回路拒绝路径与黑名单直拒、压缩动作可解释、与会话恢复共存。
  其余五条留手测，理由各不相同：基本可用与敏感产物确认依赖真人阅读产物；
  白名单外调用依赖模型的偶发越界行为，不可控；关闭时肉眼无差别是观感项；
  落盘失败不阻断的机制部分已有子进程自动化覆盖，仅「界面无错误提示」一半需人眼。
- **F22 场景清单可见**：能列出全部已实现场景及其**运行模式**（确定性 / 真实 / 两者）
  与所对应的手测条目，并标明该手测条目是**已被替代**还是**仅部分覆盖、不得撤销**。
  理由：C11 场景 1、3、4 的核心判据本身就是模型行为（是否按 SOP 查提交记录、是否自己
  发起加载、是否因看不到写工具而改用其它方式），确定性模式只能验机制不能验行为；
  清单若不区分，会把这三条误标为已自动化，手测反而被悄悄放弃。

## 非功能需求

- **N1 产品行为零变化**：除 F5（应答来源如实记录）与 F9/F10（可选的模型注入参数）
  两处必要改动外，产品代码对外行为不变；两处改动的缺省值均等于现状。
- **N2 驱动器不进产品包**：驱动器是测试设施，放在测试目录下，不随产品分发、
  不新增控制台入口、不进产品命令行的选项集合。依赖方向单向：
  测试依赖产品（F13 复用记录加载能力），产品不得反向依赖驱动器。
- **N3 确定性场景零外部依赖**：不联网、不读开发者用户目录、不依赖终端类型与屏幕尺寸、
  不依赖当日日期或版本控制分支名。
- **N4 可随全量测试运行**：确定性场景能被既有的测试发现方式收录，
  单条场景耗时在数秒量级。**本项目当前无持续集成，「进 CI」不作为本轮验收项**
  （持续集成本身是已登记的后续工程项）。
- **N5 真实场景不进全量**：默认跳过，须显式开启，避免全量测试意外产生费用与网络调用。
- **N6 不引入新的跨线程锁，不死锁**：驱动器要在界面主线程与 Agent 工作线程之间等待并
  应答，与既有的死锁教训（持锁跨线程回调 + 阻塞式跨线程调度）拓扑同类。
  不得新增与既有锁交叉的锁，且须有超时护栏——护栏须**用完成计数而非布尔标志**判定，
  同线程版本在可重入锁下会静默通过、不可简化。
  （已核实**不适用**的一条：只读并发通道内的异常回灌风险对本轮不构成威胁——
  人在回路回调只在串行路径被调用，驱动器的应答不会跑在并发通道里。记此以免重复纠结。）
- **N7 失败即失败**：驱动器不得为了让场景通过而重试、放宽断言或吞掉超时。
  一个会自我安慰的护栏比没有护栏更危险。
- **N8 中文注释**：新增与修改的代码按项目《代码注释规范》撰写中文注释，
  说明设计意图、执行流程与边界条件。
- **N9 编码与平台**：在 Windows 下运行；落盘与子进程一律显式使用 UTF-8，
  不依赖系统默认编码。界面文本中的字面方括号在记录与断言时须区分「转义前原文」与
  「渲染文本」，沿用 P0 已确立的口径。

## 不做的事

明确不在本轮范围，避免范围扩散：

1. **不做声明式场景语言**（YAML 或自定义 DSL）——场景以宿主语言代码表达。
   自造一门小语言意味着每加一种断言都要扩语法、写解析、写错误提示，且断点调试困难。
2. **不做录制回放**——不实现录制真实模型响应并离线重放的机制。
3. **不替代人眼**——观感是否流畅、工具行是否逐个出现、面板是否美观，仍需人看。
   驱动器解决「行为是否正确」，不解决「体验是否顺畅」。
4. **不做项目根参数化与沙箱层重构**（P0 明确推给本轮的第一条，此处处置为「不做」）
   ——沿用既有测试惯例：切换进程工作目录。项目内已有十余个测试文件如此，
   零新机制、零产品代码改动。代价是场景不能并行，见第 5 条。
5. **不做场景并行执行**——工作区与只读路径白名单均为进程级状态，并行不安全。
6. **不做用户级配置写入侧的参数化**（P0 明确推给本轮的第二条，此处处置为「不做，
   改以约束规避」）——写入侧仍写向真实用户目录，由 F7 的场景约束防止被无人值守地触发。
   理由：写入侧只有一个触发点（自动添加 MCP Server），且它是非只读工具，
   默认策略下必被自动拒绝；为它做一次参数化的收益不抵改动面。
7. **不做持续集成接入**——见 N4。
8. **不做性能基准与多实例并发测试**。
9. **不做截屏比对与视觉回归**。
10. **不覆盖 C2–C10 各章的历史端到端场景**——驱动器建成后加一条场景即写一个代码单元，
    按需增补。
11. **不做失败场景的自动重跑与不稳定用例隔离**——见 N7。
12. **不做记录产物的清理与轮转**——沿用 P0 结论，磁盘占用由使用者自行处理。

## 验收标准

### 驱动器核心（F2–F8）

- **AC1**：驱动器提交的文本走的是真人提交的同一入口——该输入产出的事件种类与手工输入
  一致（验证：驱动一次普通消息与一次命令，断言各自产出输入事件与命令分发事件）。
- **AC2**：确认面板挂着时不被误判为空闲（验证：构造一个必然弹确认面板的确定性场景，
  断言驱动器在面板期间判定为「未空闲」，且整场未超时）。
- **AC3**：四类面板各能被应答一次（验证：工具确认、需求澄清、计划审批、会话选择各构造
  一次，断言各产出一条交互事件；前三类须断言被阻塞的循环得以继续，会话选择须断言历史
  被载入——它不隶属任何循环，不能用「循环继续」判定）。
- **AC4**：自动应答在记录中标为自动策略，人工应答仍标为人工——**同一次运行内两条交互
  事件的来源字段不同**（验证：一条走驱动器专用应答通道、一条走面板按键路径，
  分别断言来源字段）。
- **AC5**：默认策略下非只读工具被自动拒绝，且循环未终止、拒绝原因回灌模型
  （验证：脚本化模型请求写文件，断言该工具执行事件的结局为「用户拒绝」，
  且其后仍有模型请求事件）。
- **AC6**：场景显式放宽为全放行时，危险命令仍被拦截（验证：脚本化模型请求一条黑名单
  命令，断言权限决策事件命中黑名单层、且无对应的工具执行成功事件）。
- **AC7**：自动放行只取「仅本次」——一次自动放行之后，本地权限配置文件未被写入，
  且同一工具的下一次调用**仍然**触发一次交互（验证：连续两次同一工具调用，
  断言产出两条交互事件，且本地权限配置无新增条目）。
- **AC8**：工作区不是新建临时目录时驱动器拒绝启动
  （验证：以项目根为工作区启动并断言被拒绝，且未产生任何装配副作用）。
- **AC9**：能主动取消运行中的循环（验证：脚本化一个多轮响应，在第一轮后请求取消，
  断言循环以「用户取消」结束且场景正常收尾）。
- **AC10**：超时失败的输出含可诊断信息（验证：构造一个**耗时超过场景超时上限**的假模型
  ——不可用「永不结束」，非守护线程会在解释器退出时被汇合、导致测试进程挂死——
  断言失败信息中同时出现三个空闲条件的取值与最后执行的步骤）。
- **AC11**：驱动器不死锁——每条交付的确定性场景均在超时上限内结束
  （验证：全量运行时无一条命中超时；护栏判定用完成计数而非布尔标志）。

### 可替换的模型（F9–F12）

- **AC12**：注入假模型后应用其余部分为真（验证：断言权限引擎、Skill 管理器、
  命令注册表、记录器均为真实实例，且工具注册中心包含真实工具）。
- **AC13**：模型注入参数可选，不传时行为与现状一致
  （验证：保留一组不传该参数的装配调用并断言正常装配）。
- **AC14**：独立模式 Skill 声明自定义模型时，子对话也走注入的假模型
  （验证：构造带自定义模型的独立模式 Skill 场景，断言全程无外部连接，
  且子对话的模型请求事件出现在记录中、作用域为该 Skill 的子对话）。
- **AC15**：假模型能按轮次给出不同响应，且每轮的动态提醒与工具 schema 可被断言
  （验证：两轮脚本——第 1 轮加载 Skill、第 2 轮出结论——断言**第 1 轮的动态提醒不含
  该 Skill 正文而第 2 轮含**，这正是「第 N 轮激活、第 N+1 轮生效」的判据。
  注意断言对象是动态提醒而非稳定系统提示：已激活的 Skill 正文在前者里）。
- **AC16**：四类数据块均可脚本化且被消费方正确处理（验证：正文与思考各断言一次渲染
  结果；工具调用断言产出工具执行事件；**流错误断言循环以流错误停止**）。
- **AC17**：脚本耗尽后仍收到的请求得到确定性兜底而非抛错或挂起
  （验证：脚本只给一轮，触发一次会额外调用模型的路径——自动笔记或上下文摘要——
  断言场景正常结束且兜底响应可被识别）。
- **AC18**：真实模式在无凭据或未显式开启时跳过而非失败
  （验证：不设开关运行一次真实场景，断言结果为「跳过」）。
