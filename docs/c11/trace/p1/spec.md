## 背景

### 现状：证据能留下了，但触发的一侧仍然是人

P0 解决了「证据留不下来」——运行过程中实际发生了什么，现在被写成十五类结构化事件，
配一个只读阅读器可以事后过滤、摘要、按号展开。

但**触发这些行为的一侧仍然是人**。`docs/c11/checklist.md` 的十一个端到端场景全部标注
【手测】，实际执行方式是：人在真实终端里启动、敲一段真实请求、等模型跑完、替它点确认
面板、再肉眼比对界面与记录。于是三个老问题只解决了一半：

1. **不可重复**——证据有了，但每次跑的输入与时序仍由人临场决定，回归无从谈起；
2. **成本高**——一轮完整验收要占用人几十分钟，因此没人会为一次小改动重跑它；
3. **闭环断裂**——发现问题的人（真人）与改代码的人（AI 协作方）不是同一个，
   现象要靠人复述、证据要靠人复制粘贴，一来一回失真。

### 定位修正：驱动位上坐的是 AI 协作方，不是一份脚本

交底文档设想的驱动器是「写死一批场景脚本、无人值守跑完给个红绿灯」。
需求澄清阶段确认，真正要的是另一件事：

> 让 AI 协作方（Claude Code）自己坐在驱动位上——往输入框打一句真实请求 → 读记录看它
> 实际做了什么 → **弹出确认面板时由它自己判断该不该放行** → 应答 → 继续观察 →
> 发现问题就改代码 → 重启再跑。把「测试 → 发现 → 优化」变成一个它能独立走完的闭环。

**这里有一层关系必须先点破，否则整份文档会被读歪**：被驱动的那个 Rhine 会话跑在一个
**可丢弃的临时工作区**里（它在那里读文件、跑命令、写文件）；而 AI 协作方修改的是
**RhineCode 自身的源码仓库**。两者是两个不同的目录，不要混为一谈。
「工作区必须是临时目录」这条约束约束的是前者，与后者无关。

这个修正带来两处根本变化：

1. **人在回路那一层没有被拿掉，只是换了执行者**。原设想里驱动器按固定策略替人点面板，
   属于「绕过第⑤层」；修正后，面板弹出时正确的行为是**停下来、把面板内容报出去、
   等外部决策**——决策者从坐在终端前的人变成了 AI 协作方，但决策这个动作还在。
2. **必须有一个常驻的会话宿主**。界面测试框架提供的驱动上下文是**一次进程内的异步
   上下文**（进去、跑完、出来，生命周期在一次调用里结束）；而外部驱动者的每一次操作
   都是**互相独立的进程调用**，上一次结束后什么都不剩。若不引入常驻宿主，
   「打一句 → 看一眼 → 再打一句」这个闭环根本搭不起来——每次操作都会从零启动一个新
   实例，上一轮的对话历史、已激活的 Skill、挂起的面板全部丢失。

### 已具备的地基（P0 交付，已核实）

| 地基 | 它解决了什么 |
| --- | --- |
| 可复用的装配入口 | 能在**任意进程内**装配一套完整应用并拿到中间组件，不必起真实终端 |
| 用户级目录参数化 | 项目指令与笔记、Skill、权限规则、MCP 配置四类用户级内容的**读取**可指向临时目录 |
| 清理动作复位进程级状态 | 只读路径白名单、会话锁、外部连接在每次清理后归零，且幂等 |
| 十五类结构化事件 | 观察与断言的事实来源——每轮实际发出的工具集、权限决策命中哪层、界面显示了什么 |
| 记录逐条落盘并刷新 | 序号只在成功落盘后推进，故**记录文件随时可被外部读取**，这是「边跑边观察」的前提 |
| 只读阅读器 | 记录的加载与过滤能力已存在，观察层与断言层可复用而不必另写一份对格式的理解 |

### 架构可行性已实测确认（非推断）

本轮的核心不确定性——「能不能从另一个线程驱动一个跑在异步上下文里的界面应用」——
已在真实应用上实测排除：常驻宿主可长期存活；跨线程调用可驱动按键（含中文逐字符输入）、
可调用协程并取回返回值；面板的展示态与聚焦态运行期可读；跨线程结算待决交互耗时毫秒级；
会话忙碌期间的状态查询延迟在**零点几毫秒**量级（界面主线程只做渲染，循环跑在工作线程）。

同一轮实测还证实了两件事，直接决定本文两条需求的写法：

- **面板应答的抢跑窗口是真实存在的**：紧密轮询下，待决交互态已置位但面板尚未展示、
  尚未聚焦的采样占比为 8869/8870。故 F4 必须写死「等到展示且聚焦之后」。
- **待决交互未结算时宿主无法退出**：工作线程阻塞在等待应答上，异步运行时收尾时会去
  汇合该线程，进程**永不退出**（实测为超时终止）。故 F14 必须写死「退出前先强制结算」。

### 尚缺的五件事（本轮要补）

1. **没有常驻会话宿主与控制通道**——闭环的地基，完全空白。
2. **没有驱动手段**。已有的界面驱动先例只覆盖不涉及循环的纯界面交互（补全菜单、
   按键关闭），没有等待判据、不碰模型调用——连那条看着像「确认面板」的用例，
   实际是直接改写内部待决态，并没有真的应答一块已挂载的面板。
3. **假模型装不进真实装配**。装配入口内部自行创建模型 Provider，调用方无法替换它。
4. **断言要手写解析**。阅读器只有命令行形态，没有可供程序断言的查询接口。
5. **应答来源在记录里恒为「人工」**。三处交互结算点都把来源写成固定值，
   于是「这次放行是谁决定的」——真人、外部驱动者、还是固定策略——无从区分。

## 目标

1. **闭环可走完**：外部驱动者能以「打字 → 观察 → 决策 → 继续」的方式完整驱动一次会话，
   全程不需要真实终端、不需要人参与、**不需要中途重启会话**。
2. **面板决策交还给驱动者**：任何需要人拍板的交互（工具确认、需求澄清、计划审批、
   会话选择）都能被暂停、上报、由外部决策后继续。
3. **真实模型可驱动**：闭环的主用法是接真实模型跑真实请求，观察真实模型行为；
   确定性假模型用于验证机制本身与不花钱的重复验证。
4. **断言基于结构化事实而非截屏**：判定依据是 P0 的结构化事件、会话存档与假模型留存的
   原始请求参数，不依赖终端渲染结果、屏幕尺寸与终端类型。
5. **不扩大权限面**：工作区必须是可丢弃的隔离环境，
   且「这次是谁决定放行的」在记录里可审计。
6. **为 P1b 铺路**：内核、应答者接缝、断言层与环境隔离一次做对，
   使后续补无人值守场景时只需增加场景、不需重构内核。

## 功能需求

### 一、驱动内核

- **F1 运行内核**：提供可复用的运行内核——准备隔离环境 → 装配应用 → 驱动界面 →
  观察与断言 → 清理。内核须与「谁来应答面板」「谁来发起下一步」解耦，
  使 P1b 追加无人值守形态时无需改动内核。
  （本条不单独验收，由 AC1 覆盖——内核不可用则闭环走不通。）
- **F2 输入步骤**：能把一段文本送进输入框并提交，走的必须是**真人敲键盘的同一条提交
  入口**（经输入解析与命令分发），不得绕到内部方法上直接调用。
  理由：绕过去就验不到命令分发、回显与提交守卫这些正是要验收的东西。
- **F3 状态判据**：能判定会话当前处于三种状态之一——**空闲**（可接受下一次输入）、
  **忙碌**（循环运行中且无待决交互）、**待决**（有面板等待应答）。
  判据须同时考察运行忙碌态、待决交互态与会话选择面板展示态三者。
  理由：运行忙碌态在确认面板挂着时**仍然成立**，只看它会把「待决」误判成「忙碌」，
  于是驱动者死等到超时。
  此外，循环自然结束后仍有**异步后台工作**（自动笔记会另起线程再调一次模型并写盘），
  本判据不覆盖它——见 F16 的收敛裁决。
- **F4 面板应答时机**：应答**必须发生在对应面板已展示且已获得焦点之后**。
  理由：工具确认、需求澄清、计划审批三类面板的待决交互态在面板挂载**之前**就已置位，
  实测抢跑窗口占比 8869/8870，一看到置位就应答几乎必然落在空处、然后死等到超时；
  会话选择面板走的是另一条路径（不经待决交互态），故判据统一写成「面板已展示且已获得
  焦点」，对四类都成立。
  另需预期到：确认与审批面板期间输入框**不被禁用**，此时提交会得到一条可见提示而非无
  反应——这是既有的有意行为，不是异常。
- **F5 应答来源三态记录**：记录中的交互事件须区分三种应答来源——
  **面板按键路径**、**外部驱动者**（经控制通道决策）、**固定策略**（无人值守自动应答，
  P1b 才会用到，但字段本轮一次定义到位）。这是产品侧的一处必要改动：
  当前三处交互结算点的来源字段都是固定值。
  两点说明：① 来源标注的是**结算走的哪条路径**，不是对操作者身份的断言——
  模拟按键归入「面板按键路径」；② P1b 的「脚本预设应答」归入「固定策略」，
  不新增第四个取值。
  理由：「这次放行是谁决定的」是本设施的核心审计项——外部驱动者可能误判，
  固定策略可能被写宽，二者都需要能从记录里查出来。
- **F6 应答者接缝**：内核不直接决定如何应答面板，而是把应答委托给一个可替换的应答者。
  **本轮只交付「外部决策应答者」**（阻塞等待控制通道的指令）；
  固定策略应答者与脚本预设应答者推后到 P1b，但接缝本轮就要留出来。
- **F7 取消与可诊断超时**：能主动请求取消当前循环；任何等待都有上限。
  超时失败时须输出**当时处于哪种状态、三个判据分量各自的取值、最后执行的动作**，
  而不是一句「超时」。
- **F8 沙箱前置校验与危险工具排除**：两条：
  - **工作区校验**：会话启动前校验工作区**位于系统临时目录根之下、且由本次运行创建**；
    不满足则拒绝启动。该判据与「目录是否为空」**解耦**——工作区可以有预置内容（F15）。
    理由：决策者无论是真人、AI 还是策略都可能误判，工作区必须是可丢弃的。
  - **危险工具排除**：自动添加 MCP Server 的工具会**写向真实用户级目录**
    （其写入路径不受用户级目录参数约束），须**在装配时把它排除出宿主的工具集**，
    使模型在代码层面根本调不到它。
    理由：靠「不驱动模型调用它」约束不住——真实模式下调什么工具由模型决定，
    唯一闸门是面板，而面板决策者可能误判。这条不做，一次误放行就写进开发者真实主目录。

### 二、常驻会话宿主与控制通道

- **F9 常驻会话宿主**：提供一个可在后台长期存活的宿主进程，它启动时按给定的工作区、
  用户级目录、运行模式（确定性 / 真实）装配一套完整应用并保持运行，
  直至收到退出指令、空闲超时或发生致命错误。三条约束：
  - **一个宿主进程只承载一个会话**，不做多会话复用；
  - **宿主一律开启记录**，不提供关闭选项（观察面与断言面都取自记录，关掉即失明）；
  - **宿主不做热重载**。它在启动时把产品代码载入内存，之后修改产品源码不会生效。
    为避免「改了没生效」被误判成「改错了」，宿主须在启动时计算一个**代码版本标识**
    并在状态查询响应中返回，使外部驱动者能一眼看出「当前宿主跑的是不是我刚改的代码」。
- **F10 控制通道**：宿主进程在**本机回环地址**上提供一条请求—响应式控制通道，
  外部驱动者经一个瘦客户端逐条发送指令并取得结构化响应。四条约束：
  - 端口由系统分配，宿主进程把**端口、工作区路径与自身进程标识**一并写入一个
    **与工作区无关的固定可发现位置**。
    理由：工作区是宿主自己新建的随机临时目录，客户端启动时并不知道它在哪；
    若把发布文件放进工作区，客户端要先找到工作区才能找到它——是个死循环。
  - 发布文件须携带宿主进程标识，使客户端在**连不上时能判定是陈旧残留**
    并给出明确提示，而不是超时；
  - 只监听回环地址，不对外暴露；
  - **不做鉴权**——通道生命周期短、只在本机、承载的是测试会话。
    这是**明确记录在案的边界**，不是疏漏（见「不做的事」）。
- **F11 指令集**：控制通道至少支持七类指令——
  - **发送输入**：把一段文本送进输入框并提交（走 F2 的入口）；
  - **查询状态**：返回当前状态（空闲 / 忙碌 / 待决）、待决面板的类型与**展示原文**、
    **可选项列表**、记录的最新序号、**代码版本标识**；
  - **等待**：阻塞直到会话进入终态并返回是哪一种终态（见 F12）；
  - **应答面板**：按面板类型给出决策（确认四态之一 / 澄清选项之一 / 审批是否 /
    会话选择项之一）；
  - **取消**：请求取消当前循环；
  - **取观察数据**：按记录序号增量取事件摘要，以及界面消息与状态栏快照；
  - **退出**：优雅关闭并执行完整清理（见 F14）。
- **F12 阻塞等待的两种终态**：等待指令须能在**空闲**与**待决**两种终态上返回，
  并明确告知是哪一种；两者都不满足时按超时返回并附 F7 的诊断信息。
  理由：若等待只认「空闲」，一旦弹出面板就会死等到超时；若只能轮询，
  外部驱动者要么高频空转、要么错过短暂的中间态。
- **F13 观察面基于记录**：界面消息与状态栏的观察数据**取自记录事件**，
  不遍历界面控件。理由：界面上只有部分消息以纯文本承载，AI 正文是富文本渲染对象、
  工具行是自定义控件，遍历控件取不出原文；而记录里这三类本就有完整原文。
  这样观察面与断言面共用同一份事实，不会出现「看到的」与「断言的」不一致。
  已知边界：界面消息在记录侧受长度截断约束，超长正文在观察数据里是截断的
  （截断事实与原长可见，沿用 P0 口径）。
- **F14 退出、强制结算与兜底清理**：宿主退出（无论因退出指令、空闲超时还是致命错误）
  须按固定顺序执行：
  1. **强制结算全部待决交互**，以安全默认值（拒绝 / 取消）结算，
     并以**可识别的来源**记入记录；
  2. 确认无阻塞中的工作线程后，执行装配入口提供的清理动作（释放会话锁、回收外部连接、
     复位进程级只读白名单、关闭记录文件）；
  3. 进程退出。
  **第 1 步不可省略**：实测证实，待决交互未结算时工作线程会一直阻塞在等待应答上，
  异步运行时收尾时会去汇合该线程，导致进程永不退出——而外部驱动者「长时间不发指令」
  最常发生的时刻，恰恰是它正卡在一个面板决策上。
  另须有**空闲超时自动退出**（长时间收不到指令即自行按上述流程退出），
  致命错误须经控制通道以可识别的错误响应告知，**不得静默挂起**——
  外部驱动者分不清「还在跑」和「已经死了」是最难排查的失败形态。

### 三、环境隔离与预置

- **F15 工作区与用户级目录预置**：会话启动时可声明需要预置的初始内容——
  项目文件、版本控制初始化与初始提交、项目级与用户级 Skill 定义、权限规则、
  项目指令。预置发生在 **F8 的工作区校验之后、会话装配之前**。
  理由：多数有意义的场景需要一个**非空**工作区（要查提交记录就得有提交历史，
  要验热更新就得有 Skill 目录，要验目录型 Skill 就得有随附资源）；
  没有这条需求，「工作区必须是新建临时目录」会被实现成「必须是空目录」，
  于是这些场景一条都启动不了。
- **F16 独立工作区与异步收敛裁决**：每个会话在新建的临时目录中运行，结束后清理。
  清理**必须在异步后台工作收敛之后**进行——自动笔记线程在循环结束后仍会写盘，
  此时删目录会失败或留下残迹，表现为随机失败。**裁决**（不留给实现选）：
  - **确定性形态关闭自动笔记**——它本身就是不确定性来源，与「可复现」直接冲突；
  - **真实形态保留自动笔记，退出前等待其收敛**——它是被验收对象之一。
- **F17 独立用户级目录**：经装配入口的用户级目录参数指向临时目录，
  四类用户级内容（项目指令与笔记、Skill、权限规则、MCP 声明）一律不读开发者真实目录。
- **F18 连跑不污染**：同一进程内先后装配两次时，进程级全局状态不残留——
  只读路径白名单、当前工作目录、会话锁三者均须复位。
- **F19 确定性形态无外部副作用**：不建立任何**外部**连接——模型为假、MCP 声明为空。
  控制通道的回环连接是本机通信，不属本条约束的「外部连接」。
  额外约束：不得驱动模型调用会发起网络请求的只读工具（解析 MCP Server 名称的工具会
  访问外部包索引）。这条不能靠应答策略兜底——只读且被规则放行的工具根本不会弹面板，
  应答者压根不会被问到。

### 四、可替换的模型

- **F20 装配入口支持注入模型 Provider**：使装配出的应用走假模型，而其余部分——
  工具、权限、Skill、上下文、记忆、命令、界面——**全部为真**。
  注入参数**可选、缺省等于现状**（沿用 P0 用户级目录参数的同一条硬纪律）。
- **F21 覆盖换模型旁路**：独立模式 Skill 声明自定义模型时协调层会另建一个 Provider，
  该旁路须走同一注入点。否则该场景下子对话会**静默连上真实网络**——
  这与 P0 的记录旁路是同一处，是最容易漏的一条。
- **F22 脚本化假模型**：能按脚本产出「正文 / 思考 / 工具调用 / 流错误」四类数据块的
  序列，**支持按轮次给出不同响应**（如第 1 轮调工具、第 2 轮出结论），
  并**留存每轮实际收到的稳定系统提示、动态提醒消息、完整消息列表与工具 schema**
  供断言。脚本耗尽后若仍收到请求（上下文摘要调用会造成这种情况），
  须以**确定性的兜底响应**应对而非抛错或挂起，且该兜底可被识别。
- **F23 真实模式**：宿主可改用真实模型运行，**这是闭环的主用法**——
  外部驱动者提真实请求、观察真实模型行为。真实模式须显式开启，无凭据时明确报错而非
  静默降级。断言只针对**模式与存在性**（调用了哪类工具、某类事件是否出现、
  作用域是否正确），不断言模型措辞。

### 五、断言层

- **F24 事实来源与查询**：断言层提供对记录产物的程序化查询——按类型取、按作用域取、
  按序号取、取某类的第 N 条、取某字段。**须复用产品包内已有的记录加载与过滤能力，
  不得自行解析记录文本**，避免两边对格式的理解各自漂移。
  三类事实的**权威来源在此裁决**，避免实现时各挑一个：
  - **系统提示与工具 schema** —— 以假模型留存的原始请求参数为权威（F22）。
    理由：记录中的对应字段受长度截断约束，且稳定系统提示与动态提醒分处请求的两个位置；
    记录只作真实模式下的退化来源，且接受截断。
  - **主对话历史的消息条数** —— 以会话存档为权威。
    理由：十五类事件中没有任何一类承载「当前主历史有多少条」，而记录中的请求消息列表
    受条数与长度双重截断，不能当作历史全貌。
  - **其余全部事实**（工具执行结局、权限决策、界面消息、状态栏、作用域、事件次序等）
    —— 以记录为权威。
- **F25 断言词汇**：本轮须实现十一项——
  ① 某轮实际发出的工具名集合；② 某工具是否被执行过及其结局；③ 界面消息是否包含某文本；
  ④ 状态栏快照是否包含或不包含某段；⑤ 权限决策命中的防御层与结果；⑥ 事件的作用域归属；
  ⑦ 两个事件的先后次序；⑧ 某类事件的条数；⑨ 主对话历史的消息条数；
  ⑩ 某轮的**稳定系统提示**是否包含某段文本；⑪ 某轮附加的**动态提醒**是否包含某段文本。
  第 ⑩⑪ 两项必须分开：稳定段与动态段分处请求的两个位置，已激活的 Skill 正文在动态段，
  混作一谈会写出永远失败的断言。
  （本轮只验「均已实现且各自可用」；「每项都在交付场景中被使用」的完备性要求
  依赖 P1b 的场景交付，推后。）
- **F26 失败可诊断**：断言失败时输出足以定位的上下文——相关事件的序号与摘要行，
  而不只是「期望 X 实际 Y」。理由：端到端失败的根因通常在失败点之前若干个事件。

## 非功能需求

- **N1 产品行为零变化**：除三处必要改动外，产品代码对外行为不变，且三处的缺省值均等于
  现状——① F5 应答来源三态记录；② F20/F21 可选的模型注入参数；③ F8 的工具集排除
  （仅作用于宿主装配，真实启动不受影响）。
- **N2 驱动设施不进产品包**：驱动内核、宿主进程与控制通道客户端都是测试设施，
  放在测试目录下，不随产品分发、不新增控制台入口、不进产品命令行的选项集合。
  依赖方向单向：测试依赖产品（F24 复用记录加载能力），产品不得反向依赖驱动设施。
- **N3 确定性形态零外部依赖**：不联网、不读开发者用户目录、不依赖终端类型与屏幕尺寸、
  不依赖当日日期或版本控制分支名。
- **N4 控制通道的响应上限**：状态查询与观察指令须在**一秒内**返回，
  不得因会话正忙而阻塞——**只有等待指令是阻塞式的**，其余指令随时可应答。
  理由：外部驱动者需要在会话运行期间查看进度，若查询也被阻塞就退化成了黑盒。
  （实测余量充裕：忙碌期跨线程调用延迟在零点几毫秒量级。）
- **N5 真实模式的成本与缓存**：交互形态下宿主须可配置**单次会话的模型调用轮次上限**，
  触顶时以可识别的响应告知，避免一次失控的驱动烧掉大量额度。
  另记一条已知现象：Skill 清单进的是可缓存的稳定通道，
  **反复重启宿主会让前缀缓存命中率波动，这不是异常**。
- **N6 不引入新的跨线程锁，不死锁**：控制通道在独立线程接受指令，而界面运行在主线程、
  循环运行在工作线程，与既有的死锁教训（持锁跨线程回调 + 阻塞式跨线程调度）拓扑同类。
  不得新增与既有锁交叉的锁，且须有超时护栏——护栏须**用完成计数而非布尔标志**判定，
  同线程版本在可重入锁下会静默通过、不可简化。
  （已核实**不适用**的一条：只读并发通道内的异常回灌风险对本轮不构成威胁——
  人在回路回调只在串行路径被调用，应答不会跑在并发通道里。记此以免重复纠结。）
- **N7 失败即失败**：驱动设施不得为了让判定通过而重试、放宽断言或吞掉超时。
  一个会自我安慰的护栏比没有护栏更危险。
- **N8 中文注释**：新增与修改的代码按项目《代码注释规范》撰写中文注释，
  说明设计意图、执行流程与边界条件。
- **N9 编码与平台**：在 Windows 下运行；落盘、子进程与控制通道一律显式使用 UTF-8，
  不依赖系统默认编码。界面文本中的字面方括号在记录与观察时须区分「转义前原文」与
  「渲染文本」，沿用 P0 已确立的口径。

## 不做的事

明确不在本轮范围，避免范围扩散：

1. **控制通道不做鉴权、不做加密、不对外暴露**——只监听本机回环地址、生命周期与一次
   测试会话等长。这是**记录在案的边界**：同一台机器上的其它进程理论上可以连上它并驱动
   会话；真实模式下宿主进程内持有真实凭据，故驱动会话期间的本机环境应视为可信环境。
   因通道只在测试期间存在、工作区是可丢弃的临时目录，本轮接受这个风险。
2. **不做多会话与多路复用**——一个宿主进程一个会话。要并行就起多个宿主进程，
   但受第 4 条限制，**同一进程内**不行。
3. **不做远程驱动**——控制通道不跨机器。
4. **不做项目根参数化与沙箱层重构**（P0 明确推给本轮的第一条，此处处置为「不做」）
   ——沿用既有测试惯例：切换进程工作目录。项目内已有十余个测试文件如此，
   零新机制、零产品代码改动。代价是同一进程内不能并行。
5. **不做用户级配置写入侧的参数化**（P0 明确推给本轮的第二条，此处处置为
   **「不做参数化，改以工具集排除彻底断掉该路径」**，见 F8）。
   P0 当初不做它的理由是「本轮无自动驱动器，该路径不会被无人值守地触发」——
   本轮交付的正是那个驱动器，该理由已失效，故必须给出新的处置而不能沿用。
6. **不做宿主热重载**——改完产品源码必须重启宿主；由 F9 的代码版本标识把这件事显式化。
7. **不做录制回放**——不实现录制真实模型响应并离线重放的机制。
8. **不替代人眼**——观感是否流畅、工具行是否逐个出现、面板是否美观，仍需人看。
   驱动设施解决「行为是否正确」，不解决「体验是否顺畅」。
9. **不做截屏比对与视觉回归**。
10. **不做持续集成接入**（本项目当前无持续集成，它本身是已登记的后续工程项）。
11. **不做性能基准与多实例并发测试**。
12. **不做失败判定的自动重跑与不稳定用例隔离**——见 N7。
13. **不做记录产物与残留临时目录的清理**——宿主被强制终止时留下的临时工作区与发布文件
    由使用者自行清理，与 P0 「不做记录轮转」同口径。
14. **无人值守回归与场景交付整体推后到 P1b**——清单见下一节。

## 推后到 P1b 的内容（**不得遗失**）

P1b 是本轮的直接续作，在 P1a 交付并经真实驱动磨稳之后另开一份 spec。范围如下：

**一、无人值守形态**

**二、场景交付**
- C11 场景 **1–5、8–11 共九条**的无人值守场景实现。
- 场景 6（启动失败以退出码终止、不留孤儿子进程）与场景 7（第三方仓库首启提示）
  不在同进程内驱动，不重复实现，但须在场景清单中**逐条点名覆盖来源（具体到测试方法）
  并注明口径差异**——已知差异：场景 7 的提示渠道在 C11 已从启动时打印改为经

- P0 checklist 第九节中**可自动化的四条**：作用域交错可读、人在回路拒绝路径与黑名单
  直拒、压缩动作可解释、与会话恢复共存。其余五条留手测（理由：基本可用与敏感产物确认
  依赖真人阅读产物；白名单外调用依赖模型的偶发越界行为，不可控；关闭时肉眼无差别是
  观感项；落盘失败不阻断的机制部分已有子进程自动化覆盖，仅「界面无错误提示」需人眼）。

**三、场景清单**
- 列出全部已实现场景及其运行模式（确定性 / 真实 / 两者）与对应手测条目，
  并标明该手测条目是**已被替代**还是**仅部分覆盖、不得撤销**。
  C11 场景 1、3、4 的核心判据本身就是模型行为，确定性形态只能验机制不能验行为，
  必须标成后者，否则手测会被悄悄放弃。
- F25 十一项断言词汇的**使用完备性**验收（每项至少被一个场景使用）挪到此处。

**四、其它**
- 无人值守场景随全量测试运行（单条耗时数秒量级）；真实场景默认跳过、须显式开启。

## 验收标准

### 闭环（F9–F14，本轮的核心交付）

- **AC1**：外部驱动者能在**一个宿主进程内**完整走完一次会话——启动 → 发送输入 →
  等待并得知进入待决态 → 读取面板展示原文与可选项列表 → 应答 → 继续等待至空闲 →
  再发送第二次输入 → 退出，**全程不重启宿主进程**；且第二次输入时上一轮历史仍在
  （验证：按此序列驱动一次，断言每步响应符合预期，且**会话存档**中含两轮用户输入）。
- **AC2**：以**真实模型**启动宿主，走完 AC1 的完整序列（含一次面板决策），
  断言记录中出现真实模型的请求与响应事件、且至少一条工具执行成功
  （验证：显式开启真实模式运行一次；本条须显式开启、不进全量）。
- **AC3**：等待指令能在空闲与待决两种终态上返回并告知是哪一种；两者都不满足时超时返回
  并附诊断信息（验证：分别构造「会跑到空闲」与「会弹面板」两种脚本各等待一次，
  断言返回的终态标识不同；再构造一次超时并断言诊断字段齐备）。
- **AC4**：会话正忙时状态查询与观察指令**单次返回耗时小于一秒**
  （验证：在一次长循环运行期间连续发若干次状态查询，逐次断言耗时上限且反映忙碌态）。
- **AC5**：宿主发生致命错误时经控制通道以可识别的错误响应告知，不静默挂起
  （验证：注入一次装配期致命错误，断言客户端收到明确的错误响应而非超时）。
- **AC6**：**有待决面板时退出仍能在上限时间内完成**，且该次强制结算在记录中可识别
  （验证：驱动到弹出确认面板后直接发退出指令，断言进程在上限内退出、
  记录中存在一条来源可识别的强制结算交互事件。**这条是实测挂死路径的护栏，不可省**）。
- **AC7**：空闲超时后宿主自行退出，**跨进程可观测项**齐备——进程退出、会话锁文件消失、
  记录文件可完整解析且末条为会话结束事件、临时工作区可被删除
  （验证：设一个短空闲超时，不发任何指令，逐项检查）。
- **AC8**：清理动作的**进程内项**正确——同一进程内执行「装配 → 清理」后，
  只读路径白名单已复位、外部连接已回收（验证：在同进程内直接调用清理动作后断言；
  与宿主进程退出解耦，因为进程都没了就无从检查内存状态）。
- **AC9**：控制通道只监听回环地址；发布文件含端口、工作区路径与宿主进程标识，
  客户端据此一步连上（验证：断言监听地址、解析发布文件、客户端连接成功）。
- **AC10**：发布文件陈旧（宿主已不在）时客户端给出**明确提示而非超时**
  （验证：伪造一份指向不存在进程的发布文件，断言客户端立即报出可识别的错误）。
- **AC11**：状态查询返回代码版本标识，且修改产品源码后重启宿主该标识发生变化
  （验证：取一次标识 → 改动产品源码 → 重启宿主再取一次 → 断言两者不同）。

### 驱动内核（F2–F8）

## P1a 实际交付相对 plan 的偏离（**P1b 不要照着过期设计做**）

1. **`ConversationManager` 的工厂改为延迟绑定**。plan 写的是构造时
   `provider_factory or create_provider`；实际实现存 `None`、到 `_provider_for` 里再解析。
   原因：构造时固化会让既有 `test_skill_isolated.py` 的模块属性猴补**静默失效**——
   那才是真回归。P1b 若要再加注入点，沿用「存 None、用时现取」这个口径。

2. **`AC10「耗时 < 1 秒」按字面执行做不到**。Windows 上操作系统自己就要约 2.03 秒
   才把 `ConnectionRefusedError` 返回给用户态（实测裸 `socket.connect` 连测三次
   2.032 / 2.031 / 2.016 秒，与本设施代码无关）。实际判据改为
   「**不等满调用方给的超时**」：给 30 秒超时、断言远早于它返回且异常类型是连接被拒。

3. **`test_zzz_no_global_leftovers` 只保证类内次序**。unittest 按字典序排类，
   `CleanupTest` 排在最前，所以这条「全局无残留」的检查**实际上跑在大多数用例之前**。
   它仍有价值（能抓住上一轮的残留），但真正的兜底是每条用例自己的 `addCleanup`。
   P1b 若要一条可靠的「最后检查」，需要另做（如 `tearDownModule`）。

4. **发现一处 P0 遗留的观测缺口，本轮未改产品代码**：
   `ui_message` 的 AI 正文由 `tui/app.py` 的 `reset_text_widgets()` 在
   「下一轮开始 / 工具开始 / 历史回放」三个时机收尾产出，因此
   **一轮运行里最后一段 AI 正文不会产生 `ui_message` 事件**
   （实测：跑完两轮对话，`ui_message` 里只有两条 `user_echo`，两段 AI 正文一条都没有）。
   影响面是断言词汇③「界面消息含某文本」在「最后一句话」上不可用。
   本轮的规避办法是改用 `api_response`（模型实际回了什么）。
   **修法很小**（在事件流消费的 `finally` 里补一次 `reset_text_widgets()`），
   但它属于 P0 的埋点范围、超出 P1a 约定的三处产品改动，故留给 P1b 或单独处理。
