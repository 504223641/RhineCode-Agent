# Trace 记录器 Spec

> **定位：跨阶段的测试设施，不是新章节的产品能力。**
> C2–C11 每章交付的是给用户的产品能力（工具系统、权限、MCP、上下文、记忆、命令、Skill），
> 本模块交付的是给开发者的**可观测性设施**——它服务已完成的 C2–C11 与未来所有阶段的
> 验收与排查，因此不占章节号，作为 C11 的子开发放在 `docs/c11/trace/`。
>
> 本轮范围为需求交底（`brief.md`）§9 划分的 **P0（Trace 记录器）**。
> P1（TUI 驱动器）明确不在本轮，见「不做的事」。

---

## 背景

### 现状：端到端验收全靠人肉

`docs/c11/checklist.md` 的十一个端到端场景要求「在真实终端里跑真实对话，逐条记录实际
观察结果」——即全部为手工验收。实际执行方式是人在终端敲命令、肉眼看输出、把屏幕内容
复制给协作方判断。三个问题：

1. **不可重复**——同一场景跑两次观察到的细节不同，回归无从谈起；
2. **证据链断裂**——协作方只看到人复制过来的片段，看不到系统内部状态；
3. **判断滞后**——出了问题才回头找证据，而证据当时往往没留下。

### 会话存档不能替代（关键事实，已核实）

一个自然的想法是「读会话存档就行」。**不行**。`<项目根>/.rhinecode/sessions/*.jsonl`
每行**至多**六个字段（`ts`/`role`/`content`/`tool_calls`/`tool_call_id`/`display_content`，
其中后三个有值才写）。它记的是**模型历史**，不是「这次会话发生了什么」。

| 存档里有 | 存档里没有 | 为什么缺失致命 |
| --- | --- | --- |
| 用户消息、助手正文、工具调用与结果 | 绕过 Agent 的命令及其输出 | 存档里**连敲过 `/skills` 都看不出来**，更别说它回了什么 |
| 提示词命令的双内容 | **系统提示全文**（七个稳定模块 + 项目指令 + 记忆索引 + Skill 清单 + 动态提醒 + 已激活 SOP 正文） | 「SOP 到底注入没注入」「第 N 轮激活第 N+1 轮生效」这类 C11 核心验收项无从查证 |
| — | **每轮实际发出的工具 schema** | 「白名单是否真的收窄了」的唯一判据 |
| — | **权限决策**（命中哪层、放行/拒绝/问、用户选了什么） | 五层防御的验收全靠它 |
| — | **系统提示事件**（上下文压缩通知、Skill 降级警告） | 「用户可见反馈是否给到」是明确的验收项 |
| — | **上下文压缩的具体动作** | 事后无法解释「这轮消息为什么突然短了」 |
| — | **状态栏与界面内容** | 界面态验收项 |
| — | **用量、思考内容、每轮耗时** | 现状只有缓存命中数一行调试日志 |

### 实证：缺记录的真实代价

C11 手测场景 1 暴露了两个真 bug，两次都是「现写脚本捞证据」：

- **命令中文输出被静默吞掉**：子进程按系统默认编码解码 UTF-8 输出，解码异常死在读取
  线程里被吞，标准输出变空串而**退出码仍是 0**。存档里只看到「命令成功、无输出」，
  靠人工比对「哪些命令有输出」才发现规律是「含中文的全空」。
- **模型调用了本轮没发给它的工具**：白名单只发 4 个工具，模型却成功调用了写文件工具。
  要证明「schema 里确实没有它」，**只能另写探针脚本**模拟完整启动装配、用假 Provider
  记录工具参数——因为运行时没有任何地方留下这个信息。

如果当时有记录，第一个 bug 只需看一眼「原始字节长度 1024、解码后长度 0」，第二个 bug
只需看一眼那一轮实际发出的工具名列表。**本模块就是把这件事一次性做掉。**

## 目标

1. **单一事实来源**：跑完一次运行后，**一个文件**里能回答——模型每轮看到了什么系统提示
   与工具集、说了什么、调了什么工具、每次调用过了哪层权限、结果是什么、界面显示了什么、
   状态栏长什么样、用户敲了什么命令、命令回了什么、上下文被压缩过什么。
2. **零侵入**：记录关闭时，系统对外行为与引入本模块之前一致，且这一点是**可自动验证**的
   （而非靠承诺）。
3. **证据可提取**：记录产物能被过滤、摘要、按需展开，使关键片段可以被读取和分享——
   记了但拿不出来等于没记。
4. **为后续驱动器铺路**：产出的记录格式足以支撑后续 TUI 驱动器（P1）的全部断言；
   启动装配被抽成可复用入口，使得在测试进程内构造一套完整、与开发者本机环境无关的
   运行环境成为可能。

## 功能需求

> 说明：下文出现的事件类型标识（`session_start` 等）与公共字段名是**产物的对外契约**
> ——阅读器按类型过滤、后续驱动器按字段断言都依赖它们，故在 spec 层写死。
> 除此之外不涉及任何实现标识。

### 一、记录器核心

- **F1 结构化事件流**：以「一行一个事件」的结构化文本格式追加落盘。每个事件恒含四个
  公共字段——单调自增序号 `seq`、时间戳 `ts`、事件类型 `type`、作用域 `scope`，
  以及一份类型专属的负载。
  **序号仅在成功落盘时分配并递增，被丢弃的记录不占号**，从而序号序列始终连续无空洞，
  可作为稳定标识供阅读器按号展开与后续断言引用。
- **F2 作用域标识**：每个事件标注它属于**主对话**还是**某个独立模式 Skill 的子对话**，
  子对话须携带该 Skill 名。**不隶属任何对话的事件（会话启停、命令分发、状态栏等）
  一律标注为主对话作用域。**
  理由：独立模式 Skill 会开子对话，子对话与主对话的请求会**交错**出现在同一份记录里；
  「主历史恰好新增两条配对消息」「子对话的几十次读文件没撑大主上下文」这类断言，
  没有作用域标识就无法表达。
- **F3 并发写入串行化**：事件会在主线程、Agent 循环工作线程、只读工具并发线程池、
  笔记后台线程中被记录。写入须串行化到「一行永远完整、多行永不交错」的程度，
  且串行化手段**不得与系统中任何既有锁产生交叉**。
- **F4 失败静默**：落盘失败、序列化失败、负载构造异常，一律吞掉并放弃该条记录，
  **绝不阻断对话、绝不向上抛出**（对齐会话存档与上下文存盘的既有做法）。
- **F5 配置快照脱敏**：会话启动事件携带配置快照时，其中的 API 密钥字段须替换为固定掩码。
  本条只约束**结构化配置字段**；工具输出中可能出现的密钥明文（模型读过配置文件时）
  不在本条承诺范围内，由 N6 的产物隔离兜底。
- **F6 长内容截断与原长保留**：超过阈值的文本负载可截断，但**必须同时记录截断前的原始
  长度**，且截断事实本身可被识别。理由见「实证」第一条——中文输出被吞的 bug，唯一
  判据就是「原始长度 1024、解码后长度 0」这个对比。
- **F7 开关默认关闭**：不显式开启时，本模块不产生任何文件、不创建任何目录、
  不在模型调用链路上插入任何中间层、不执行任何额外计算。
- **F8 双重开启途径**：既可通过**命令行参数**开启，也可通过**编程方式**开启
  （在测试或工具进程内构造运行环境时直接注入记录器），两条途径产出的记录格式一致。
  理由：后续驱动器在同一进程内启动应用，**根本不走命令行解析**；开关只挂命令行会在
  开发中途才暴露缺口。
- **F9 缺省落盘位置**：命令行开启但未指定路径时，落盘到项目根下专用的记录目录，
  文件名含启动时间戳，使多次运行互不覆盖。该目录须被版本控制忽略，**忽略写法与既有
  运行时数据目录（上下文存盘、会话存档、笔记）同口径**，以便在嵌套项目场景下同样生效。
- **F10 一次运行一份记录**：记录文件的生命周期对应**一次进程运行**，而非一次会话。
  运行期间的清空历史、恢复会话属于「本次运行中发生的事」，记录为事件而**不换文件**。

### 二、事件类型（十五类）

- **F11 会话级事件**（2 类）
  - `session_start`：项目根、脱敏后的配置、Provider 与模型、权限模式、Plan Mode 状态、
    已注册工具名清单、MCP 连接状态、Skill 清单快照。**记录器的构造与本事件的产出必须
    分为两个时机**——构造可以最早（只需一个路径），但本事件的负载必须在 MCP 连接完成、
    Skill 工具集绑定完成**之后**才产出，否则会记出一份半空的快照。
  - `session_end`：结束原因、总轮数、总耗时。
- **F12 输入与命令事件**（2 类）
  - `user_input`：提交进输入框的原始文本。
  - `command_dispatch`：命令名、别名、参数、命中的命令规格、**命令类型**（本地执行 /
    界面状态 / 提示词三类之一）、是否为未知命令。须能区分三类，不得笼统记作「本地命令」。
- **F13 模型交互事件**（2 类）
  - `api_request`：第几轮、系统提示**全文**、工具的**名字列表与完整 schema**、
    完整消息列表、思考模式强度。按 F6 截断并记原长。
  - `api_response`：拼接后的正文、思考内容、工具调用列表、用量、耗时、是否为流错误。
- **F14 决策与执行事件**（3 类）
  - `permission_decision`：工具名、规范化后的权限请求、命中的防御层、决策结果、理由。
  - `interaction`：面板类型（工具确认 / 需求澄清 / 计划审批 / 会话选择）、展示内容、
    应答来源、最终结果。**四类面板的记录须口径一致**（三项俱全）——注意会话选择面板
    与其余三类的触发路径不同，须各自覆盖。
  - `tool_execute`：工具名、参数、成败、摘要、输出（按 F6 截断记原长）、耗时、
    是否走只读并发通道。
- **F15 界面事件**（2 类）
  - `ui_message`：界面新增的一条消息（用户回显 / AI 正文 / 系统提示 / 错误），
    带来源与原始文本。**须记录界面 markup 转义前的原始文本**，与渲染后文本区分。
  - `status_bar`：状态栏文本快照（含 Skill 段、上下文用量、模式标记）。
- **F16 内部机制事件**（4 类）
  - `agent_event`：Agent 循环产出的每个事件的类型与流控信息，尤其是系统提示事件的内容
    与结束事件的停止原因。
  - `context_compaction`：第一层存盘的调用标识列表与落盘路径；第二层摘要的保留边界索引、
    重构前后消息条数。
  - `skill_state`：激活列表变化、降级情况（正文截断 / 整段丢弃）、白名单计算结果。
  - `history_restored`：载入的历史须标明「这是恢复来的历史，不是本次新产生的」，
    并记录载入条数与来源会话标识。**须覆盖两条来源**：启动时恢复（命令行恢复参数）
    与运行中恢复（恢复命令）。二者机制不同——启动恢复发生在装配阶段、**不产生任何
    事件流**，须单独产出本事件；运行中恢复走事件流。
- **F17 事件间去重裁决**：多类事件可能覆盖同一件事实（如工具执行既出现在 `tool_execute`
  也出现在 `agent_event`）。裁决为：**每份事实以其专属事件为权威来源，`agent_event`
  只记类型与停止原因等流控信息，不重复携带正文、工具参数与工具输出等重负载。**

### 三、覆盖完整性

- **F18 模型请求全覆盖**：所有发往模型的请求都须被记录，**包括独立模式 Skill 声明了
  自定义模型时新建的那个 Provider**。这是最容易漏的一条旁路——协调层在该场景下会绕过
  启动时装配好的实例、另行创建并缓存 Provider。
- **F19 事件流单点收口**：Agent 事件流的记录须挂在**所有事件流的共同必经之处**，
  而不是只覆盖部分调用路径。手动压缩与运行中恢复（含携带历史快照的恢复事件）走的路径
  与常规对话不同，不得遗漏。
- **F20 装配期行为覆盖**：发生在事件流之外、装配阶段内的行为（启动时会话恢复、
  Skill 扫盘与白名单校验结果、MCP 连接结果）须在装配阶段直接产出对应事件，
  不得因「不经过事件流」而留下空洞。

### 四、启动装配重构

- **F21 可复用的启动装配入口**：把现有主入口中「按严格顺序拼装全部运行期组件」的那段
  逻辑抽成一个**可被任意调用方复用**的装配入口。它接收已加载的配置、用户级配置目录、
  是否恢复会话、可选的记录器，返回**装配好的应用与配套的清理动作**。
  **项目根仍取调用时的当前工作目录，不作为参数**——项目根在现有实现中是多处独立实时
  读取进程工作目录得出的，改成可传参属于沙箱层重构，不在本轮范围（见「不做的事」）。
  理由：装配顺序有多处不可挪动的硬约束（工具注册与白名单计算的先后、Skill 校验夹在
  两个特定步骤之间、清理动作里必须释放会话锁与回收 MCP 子进程）；这段逻辑只存在一份，
  改一次全都对，复刻则会静默错位。
- **F22 装配失败以异常表达**：装配过程中的**全部**致命错误（命令注册冲突、Provider
  初始化失败、Skill 白名单笔误等）须以**异常**表达，由命令行入口负责转成退出码与人可读
  提示。理由：装配入口要能被测试调用，直接终止进程会让测试无法捕获。命令行入口的对外
  行为（退出码、提示文案、「白名单笔误时不留孤儿子进程」）必须保持不变。
- **F23 用户级目录参数化**：**凡影响系统提示内容与权限求值结果的用户级配置目录取值，
  一律提升为参数**，缺省值保持不变。按能力划分共四类：项目指令与笔记索引、Skill 定义、
  权限规则、MCP Server 配置。
  理由：不参数化则任何自动化验证都会读取开发者真实的用户目录，把用户级项目指令、
  笔记索引、Skill、权限规则带进系统提示与权限求值，甚至按开发者本机的 MCP 配置拉起
  外部子进程，导致同一场景在两台机器上结果不同。
  说明：配置文件自身的路径解析（首次运行模板生成、配置加载）不属本条范围——它由命令行
  入口处理、不进装配入口。
- **F24 清理动作复位进程级状态**：装配入口返回的清理动作除释放会话锁与回收 MCP 连接外，
  还须复位本次装配写入的进程级全局状态（如只读路径白名单的累积），使**同一进程内连续
  装配两次互不污染**。理由：这是后续驱动器连跑多场景的前提，此处不做则 P1 必然返工。
- **F25 命令行参数**：新增开启记录的命令行参数，可选携带路径；不携带时按 F9 落盘。
  不新增配置文件字段。

### 五、阅读器

- **F26 交付形态**：阅读器是**测试设施**，与记录格式强耦合，故与记录层同处一处以避免
  格式变更时两边漂移；但**不新增控制台入口、不进产品命令行**，通过解释器的模块执行
  方式调用。产品的用户文档不为它增加章节。
- **F27 时间线摘要**：默认输出「一行一个事件」的时间线——序号、时间、作用域、类型，
  以及该类型的一句话关键信息，使一次长会话可在一屏内看出脉络。
- **F28 过滤**：支持按事件类型与作用域过滤，两者可组合。
- **F29 单条展开**：支持按序号展开单个事件的完整负载（含被截断字段的原长标注），
  输出为人可读的排版而非原始单行文本。
- **F30 纯读取**：阅读器只读取与格式化，不修改记录文件，不依赖运行中的应用。

## 非功能需求

- **N1 零开销**：记录关闭时热路径无实质开销。免去「调用点判空」的兜底手段**不等于**
  免去「构造负载」的开销——模型请求事件的负载是系统提示全文加完整工具 schema 加全部
  消息，每轮序列化一遍再丢进一个什么都不做的接收方绝非零开销。故规则是：**调用点可用
  统一接口避免散落判空分支，但凡负载昂贵的埋点必须先经开关守卫再构造负载**。
  两者是分工，不是二选一。
- **N2 不改变时序，不引入死锁**：埋点不得引入与既有锁交叉的锁、不得在任何既有锁的临界区
  内做落盘、不得跨线程调度。既有教训是 Skill 管理器——临界区内做回调、回调走 TUI 的
  阻塞式跨线程调度、主线程又要同一把锁，构成确定性死锁并冻结整个界面。
- **N3 埋点异常不外泄**：只读工具并发通道里抛出的异常会被当成「工具执行异常」回灌模型。
  所有埋点必须自行兜住异常。
- **N4 分层单向**：新增层是叶子层，只被上层依赖，不反向依赖上层。允许的唯一例外是
  Provider 侧埋点需要引用 Provider 抽象——该抽象是零副作用的纯接口定义。该例外须在技术
  设计阶段明确写下并给出理由，不得留待实现时临时决定。
- **N5 不破坏既有分层约束**：工具包的包初始化文件不得导出任何子模块——工具与 Skill、
  工具与 MCP 都是包级互相依赖，不成环唯一依靠该文件为空。
- **N6 敏感产物隔离**：记录含被读过的文件内容与命令输出，**若模型读过配置文件则可能含
  API 密钥明文**，与会话存档同属敏感产物，须加入版本控制忽略清单，且不应外传。
- **N7 仅覆盖 DeepSeek 工具模式**：工具、权限、Skill、上下文管理均只在该模式下生效，
  相应事件类型也只在该模式下有内容。不为其它协议做兼容设计。
- **N8 编码与平台**：落盘一律显式使用 UTF-8。Windows 下不得依赖系统默认编码。
- **N9 中文注释**：新增与修改的代码按项目《代码注释规范》撰写中文注释，说明设计意图、
  执行流程与边界条件。

## 不做的事

明确不在本轮范围，避免范围扩散：

1. **TUI 驱动器（P1）**——程序化驱动界面、场景脚本、自动应答策略、等待判据、断言器。
   本轮只交付其地基（记录格式、装配入口、用户级目录参数化、进程级状态复位）。
   后续另开一轮 spec。
2. **项目根的参数化与沙箱层重构**——项目根仍由进程工作目录实时决定。使装配入口接收
   项目根参数需改动路径边界层的多个独立取值点，属沙箱重构，留待 P1。
3. **不替代人眼**——「界面卡不卡、工具行是否逐个出现、面板长什么样、观感如何」仍要人看。
4. **不做录制回放**——不实现录制真实 API 响应并在离线重放的机制。
5. **不做性能基准与多实例并发测试**。
6. **不加配置文件开关**——命令行加编程式两条途径已足够，本模块是测试设施而非产品功能。
7. **不做 HTML 报告或图形化时间线**——阅读器只做命令行文本输出。
8. **不做增量记录与内容去重**——每个事件自包含，不引入跨行引用。
9. **不做记录文件的轮转、清理与生命周期管理**——磁盘占用由使用者自行处理。
10. **不做工具输出中意外泄露密钥的全局清洗**——见 F5 与 N6 的分工。
11. **不改变任何现有功能行为**——除装配重构带来的内部结构调整外，对外行为零变化。

## 验收标准

### 零侵入（F7、F3、N1–N3）

- **AC1**：同一输入下，开启与关闭记录各跑一次，**关闭侧**产出的系统提示稳定段与动态段、
  发往模型的工具 schema、会话存档内容三者，与固化的黄金基线**逐字节相等**；
  开启侧的同三项与关闭侧亦逐字节相等（验证：自动化对比测试）。
- **AC2**：关闭记录时，模型调用链路上不存在为记录而插入的中间层——协调层持有的就是
  装配时创建的原始 Provider 实例（验证：自动化断言实例身份，把「零侵入」变成可测的）。
- **AC3**：关闭记录时跑一次完整装配，不产生任何记录文件、不创建记录目录
  （验证：装配后检查文件系统）。
- **AC4**：跨线程读取记录器状态不会死锁（验证：另起线程读状态并带超时汇合，
  用完成计数而非布尔标志——同线程版本在可重入锁下会静默通过，不可简化）。
- **AC5**：埋点在只读并发通道内抛出异常时不会被当成工具执行异常回灌模型
  （验证：注入必然抛异常的记录器，断言工具结果正常返回）。
- **AC6**：多线程并发产出 N 条记录后，文件行数为 N、每行均可独立解析、无交错半行
  （验证：多线程并发写入压力测试）。

### 记录正确性（F1、F2、F5、F6、F11–F20）

- **AC7**：开启记录后跑一轮带工具调用的对话，产出文件每行均为合法结构化数据，
  序号严格自增、无重复、无跳号；**在注入落盘失败（对应 AC19）之后，序号序列仍连续**
  （验证：解析全文件并检查序号序列）。
- **AC8**：十五类事件均能在对应操作发生时被产出，且各自的关键负载字段非空
  （验证：构造覆盖各事件类型的场景，逐类断言）。
- **AC9**：模型请求事件里的工具名列表，与该轮实际发往模型的工具 schema 完全一致
  （验证：与假 Provider 收到的参数对比——这正是「白名单是否真收窄」的判据）。
- **AC10**：独立模式 Skill 声明自定义模型时，其子对话的请求出现在记录中；且**子对话
  期间产生的全部事件**（模型请求响应、权限决策、工具执行、循环事件）作用域均标注为
  该 Skill 的子对话（验证：构造带自定义模型的独立模式 Skill 并逐类断言）。
- **AC11**：手动压缩与运行中恢复两条路径产生的事件流均被记录（验证：分别触发并断言）。
- **AC12**：启动时恢复会话（命令行恢复参数）产出恢复事件，标明来源为启动恢复、
  携带载入条数与来源会话标识（验证：预置存档后带参数装配并断言事件存在）。
- **AC13**：命令分发事件能区分本地执行、界面状态、提示词三类命令类型
  （验证：各触发一条并断言类型字段）。
- **AC14**：超长文本被截断时，记录中同时含截断标记与截断前原始长度
  （验证：构造超阈值输出并断言两个字段）。
- **AC15**：会话启动事件的配置快照中 API 密钥字段为掩码，不含明文
  （验证：断言该事件负载）。
- **AC16**：界面消息事件记录的是 markup 转义前的原始文本（验证：构造含字面方括号的
  文本并断言记录内容未被转义污染）。
- **AC17**：循环事件不重复携带正文、工具参数与工具输出等重负载（验证：同一次工具调用
  产生的循环事件与工具执行事件对比，前者不含后者的重负载字段）。
- **AC18**：不隶属任何对话的事件（会话启停、命令分发、状态栏）作用域为主对话
  （验证：断言这些事件的作用域字段）。

### 不阻断（F4）

- **AC19**：记录落盘失败时（目标目录不可写、写入抛异常、负载序列化异常三种情形）
  对话正常继续、不抛异常、不产生用户可见错误（验证：分别注入三种失败并断言对话结果不变）。

### 开关与落盘（F8、F9、F10、F25、N6）

- **AC20**：命令行带记录参数（含带路径与不带路径两种形态）启动时，记录生效并落到预期
  位置（验证：分别启动并检查产物）。
- **AC21**：编程方式注入记录器时记录生效，且产出格式与命令行途径一致
  （验证：装配入口注入记录器后断言产物）。
- **AC22**：不指定路径时缺省文件名含启动时间戳，同一项目下两次运行产出两个文件、
  互不覆盖（验证：连续两次装配并检查文件数）。
- **AC23**：记录目录已加入版本控制忽略清单，且写法与既有运行时数据目录同口径，
  在嵌套项目路径下同样生效（验证：在子目录中创建记录后 `git status` 不显示它）。
- **AC24**：一次进程运行内执行清空历史与恢复会话，记录文件不切换、两个动作各自留下
  事件（验证：单次运行内依次触发并检查文件数与事件）。

### 启动装配（F21–F25）

- **AC25**：装配入口可在测试进程内被调用，返回可用的应用实例与清理动作；执行清理动作
  后会话锁被释放、MCP 连接被回收（验证：调用装配入口并检查锁文件与连接状态）。
- **AC26**：装配失败以异常表达，命令行入口捕获后以退出码 1 终止并输出可读提示；
  白名单笔误场景下 MCP 连接尚未建立，不留孤儿子进程（验证：构造笔误 Skill 后跑子进程
  断言退出码与错误信息，并断言连接步骤未被执行）。
- **AC27**：装配入口传入临时用户级目录时，四类用户级内容均不读取开发者真实用户目录——
  系统提示中不含用户级项目指令与笔记索引、用户级 Skill 不出现在清单、用户级权限规则
  不参与权限求值、用户级 MCP 配置不被连接（验证：传入空临时目录后逐项断言）。
- **AC28**：同一进程内连续执行两次「装配 → 清理」，第二次的只读路径白名单不含第一次
  注册的路径（验证：两次装配使用不同用户目录并断言白名单内容）。
- **AC29**：命令行不带记录参数时的行为与重构前完全一致（验证：既有全部测试保持通过，
  见 AC36）。

### 阅读器（F26–F30）

- **AC30**：阅读器不新增控制台入口，产品命令行的子命令与选项集合无变化
  （验证：检查打包配置与命令行帮助输出）。
- **AC31**：对一份真实记录执行摘要，输出为每事件一行、含序号与类型的时间线
  （验证：运行并观察输出格式）。
- **AC32**：按类型与作用域过滤能正确缩小结果集，两者可组合（验证：对同一文件分别过滤
  并对比条数）。
- **AC33**：按序号展开单个事件，输出含完整负载与被截断字段的原长标注
  （验证：展开一条已知被截断的事件并观察）。
- **AC34**：阅读器运行后记录文件内容未被修改（验证：运行前后比对文件哈希）。
