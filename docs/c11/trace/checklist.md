# Trace 记录器 Checklist

> 每一项通过**运行代码或观察行为**来验证，聚焦系统行为而非代码结构。
> 覆盖 `spec.md` 的 AC1–AC39 与 N8/N9，外加 `plan.md` 的架构与集成验证点。
> 标注【手测】的条目需在真实终端里跑，其余为自动化。
>
> **验收顺序建议**：按三段推进，每段完成后先跑该段的自动化项，全绿再进下一段；
> 端到端场景留到三段全部完成后一次性走完。

## 一、零侵入（AC1–AC7）

- [ ] **稳定段与工具 schema 逐字节稳定**（AC1）
  验证：黄金基线用例通过。该用例必须在**临时工作区 + 临时空用户目录**下取基线——
  否则会把本仓库的 `RHINE.md` 与项目级 Skill 内容固化进基线，之后任何文档改动都让它变红。
- [ ] **动态段与会话存档在开关两侧逐字节相等**（AC2）
  验证：同一输入、同一环境下开启与关闭记录各跑一次，两侧的动态段与存档内容比对相等。
  **不与固化基线比**——动态段带当日日期、工作目录绝对路径、git 分支，存档每行首字段是
  写入时刻时间戳，固化必然跨天或换目录即红。
- [ ] **关闭记录时模型调用链路上没有中间层**（AC3）
  验证：装配后断言协调层持有的 Provider 实例不是包装类型；独立模式取自定义模型的那条
  旁路返回的也不是。这是把「零侵入」变成可测的关键一条。
- [ ] **开启记录时转发的数据块与内层逐个相等**（AC3 的开启态对应项）
  验证：包装一个产出已知块序列的假 Provider，断言消费方收到的块与内层**逐个相等**。
  AC3 只覆盖关闭态的实例身份，开启态的「不改变行为」要单独验。
- [ ] **消费方提前中断后仍产出响应事件且顺序正确**
  验证：假 Provider 产出若干块后给一个错误块，消费方在此 `break`，
  断言仍有一条响应事件，且其序号**小于**对应的循环错误事件。
- [ ] **关闭记录时不产生任何文件与目录**（AC4）
  验证：临时工作区里跑一次完整装配，`.rhinecode/traces/` 不存在。
- [ ] **跨线程读记录器状态不死锁**（AC5）
  验证：护栏用例在超时内完成。该用例必须**另起线程**读状态并带超时汇合、
  **用完成计数而非布尔标志**判定——同线程版本会静默通过，不可简化。
- [ ] **埋点抛异常不会被当成工具执行异常回灌模型**（AC6）
  验证：注入一个记录调用必抛的记录器，跑一轮含只读并发工具的循环，
  断言工具结果 `ok` 为真且输出**不含**「工具执行异常」。
- [ ] **并发写入不交错、不重号**（AC7）
  验证：多线程各写 M 条，文件行数为线程数×M、每行可独立解析、序号集合恰为 1..N 无重复。

## 二、记录正确性（AC8–AC21）

- [ ] **每行合法、四个公共字段齐备、序号连续**（AC8）
  验证：跑一轮带工具调用的对话，解析产物——每行可解析，序号/时间戳/类型/作用域均非空，
  序号严格自增无重复无跳号。
- [ ] **注入落盘失败后序号仍连续**（AC8）
  验证：分别注入「写入抛异常」与「负载序列化异常」，之后的序号序列仍连续。
  （「目录不可写」发生在构造期、不产出文件，见 §三。）
- [ ] **十五类事件均能产出且关键字段非空**（AC9）
  验证：构造覆盖各类型的场景后做一次总清点，断言十五个类型全部出现。
- [ ] **模型请求里的工具名列表与实际发出的 schema 完全一致**（AC10）
  验证：与假 Provider 收到的工具参数比对。**这是「白名单是否真收窄」的唯一判据。**
- [ ] **子对话期间产生的全部事件作用域正确**（AC11）
  验证：跑一次声明了自定义模型的独立模式 Skill，断言其间的模型请求响应、权限决策、
  工具执行、循环事件作用域**均**为该 Skill 的子对话；结束后新事件回到主作用域。
- [ ] **摘要与笔记的模型调用有各自的作用域**（AC11 的延伸）
  验证：触发一次手动压缩、触发一次笔记钩子，两次请求的作用域分别为摘要与笔记，
  且**主对话后续事件仍为主作用域**。
- [ ] **手动压缩与运行中恢复两条路径的事件流被记录**（AC12）
  验证：分别触发 `/compact` 与 `/resume`，两条路径的事件均出现；
  且一次 `/resume` 只产出**恰好一条**恢复事件（来源为「恢复命令」）——
  产出该事件的地方只有一处，界面侧的历史回放分支不得重复产。
- [ ] **启动恢复产出恢复事件并标明来源**（AC13）
  验证：预置存档后带恢复参数装配，断言恢复事件存在、来源标为「启动恢复」、
  携带载入条数与会话标识。这条容易漏——启动恢复**不经任何事件流**。
- [ ] **装配期的 Skill 扫盘与白名单结果被记录**（AC14）
  验证：预置一个带白名单的 Skill 后装配，断言 Skill 状态事件含白名单计算结果。
- [ ] **命令分发能区分三类命令**（AC15）
  验证：各触发一条本地执行 / 界面状态 / 提示词命令，断言类型字段可区分。
- [ ] **命令分发事件排在该命令的输出之前**（AC15 的时序要求）
  验证：触发一条会产生输出的本地命令（如 `/skills`），断言分发事件的序号**小于**
  它产生的界面消息事件。时间线倒置会让阅读体验彻底错乱。
- [ ] **四条命令出口各产出恰好一条分发事件**（AC15）
  验证：未知命令 / 必需参数缺失 / 处理函数抛异常 / 正常命中各触发一次，
  断言分发事件**恰好四条**。
- [ ] **空输入零副作用**
  验证：直接回车提交空输入，trace 里**不新增任何事件**（沿用 C10 的空输入零副作用语义）。
- [ ] **四类交互面板各产出恰好一条交互事件**（AC16）
  验证：工具确认、需求澄清、计划审批、会话选择各触发一次，断言交互事件**恰好四条**，
  且展示内容、应答来源、最终结果三项俱全。会话选择的触发路径与其余三类不同，须单独覆盖。
- [ ] **超长内容截断时同时记录原始长度**（AC17）
  验证：构造超阈值的工具输出，断言记录中含截断标记与截断前原长两个字段。
- [ ] **配置快照中的密钥为掩码**（AC18）
  验证：断言会话启动事件的配置快照里 `api_key` 是掩码、不含明文。
- [ ] **界面消息记的是转义前的原始文本**（AC19）
  验证：显示一条含字面 `[` 的系统消息，断言记录内容未被 markup 转义污染。
- [ ] **循环事件不重复携带重负载**（AC20）
  验证：同一次工具调用产生的循环事件与工具执行事件比对，前者**不含**工具参数、
  工具输出、正文本身。
- [ ] **六种工具结局各产出一条工具执行事件**（F14 的完整性）
  验证：执行成功 / 白名单外 / 未知工具 / 参数非法 / 权限拒绝 / 用户拒绝各构造一次，
  断言各有一条对应事件且结局字段可区分。
- [ ] **白名单外调用的回灌原文被保留**（本模块的立项理由之一）
  验证：断言「白名单外」那条事件的输出含「工具不可用」字样。
  它既不在权限决策事件里（没进引擎），也不在循环事件里（被去重裁决剥掉），
  **这是唯一物证**。
- [ ] **逐文件权限过滤不淹没时间线**
  验证：跑一次命中很多文件的内容搜索，断言权限决策事件只有该次**工具调用**对应的一条，
  而不是数百条。逐文件过滤器刻意不埋点，这条是它的反向护栏。
- [ ] **不隶属任何对话的事件归主作用域**（AC21）
  验证：断言会话启停、命令分发、状态栏三类事件的作用域为主作用域。
- [ ] **中文内容不乱码**（N8）
  验证：让工具输出与界面消息都含中文，断言记录文件以 UTF-8 完整解析、中文原样可读，
  阅读器输出同样不乱码。**本模块的立项理由之一就是一个中文编码 bug**，
  落盘编码错了会直接毁掉这类证据。

## 三、不阻断（AC22）

- [ ] **写入抛异常时对话正常继续**（AC22）
  验证：注入写入必抛的记录器，断言对话结果与不注入时一致、不抛异常、界面无错误提示。
- [ ] **负载序列化异常时对话正常继续**（AC22）
  验证：注入一个不可序列化的负载，同上。
- [ ] **目标路径不可写时降级为关闭态、程序照常启动**（AC22）
  验证：把记录路径指向一个**父路径是普通文件**的位置（如 `<tmp>/somefile/x.jsonl`），
  断言——记录器构造返回关闭态、**不抛异常**、不产生文件、程序照常启动、退出码正常、
  界面无错误提示。
  注：该情形在 Windows 上抛 `FileExistsError`、在 POSIX 上抛 `NotADirectoryError`，
  故实现的捕获范围必须是 `OSError` 而非某个具体子类。

## 四、开关与落盘（AC23–AC27）

- [ ] **命令行两种形态都创建记录文件**（AC23）
  验证：子进程分别用 `--trace` 与 `--trace <路径>` 启动，配一个**发生在记录器构造之后**的
  确定性退出条件（如合法配置 + 一个白名单笔误的 Skill，装配中途抛错退出码 1）+ `timeout`。
  断言两种形态下目标文件均被创建。
  ⚠️ 退出条件若发生在记录器构造**之前**（如配置占位符拦截），根本不会有文件；
  若发生在**首个事件产出之前**，文件会是空的。故「首行可解析」只在文件非空时断言。
- [ ] **编程注入生效且与命令行途径格式一致**（AC24）
  验证：装配入口注入记录器后产出的事件，字段集合与命令行途径产出的同类事件一致。
- [ ] **缺省文件名含时间戳且两次运行不覆盖**（AC25）
  验证：同一项目下连续两次装配，产出**两个**文件。
  秒级时间戳在同秒内会返回同一路径、追加模式下写成一个文件，故实现必须带更细精度。
- [ ] **记录目录被版本控制忽略且嵌套路径下同样生效**（AC26）
  验证：在**子目录**里造一个 `.rhinecode/traces/x.jsonl`，`git status --porcelain` 不显示它。
  写法须与既有运行时数据目录同口径（带 `**/` 前缀）。
- [ ] **一次进程运行只写一份记录**（AC27）
  验证：单次运行内依次执行 `/clear` 与 `/resume`，断言记录文件**不切换**、
  两个动作各自留下事件。清空历史与切换会话本身就是「本次运行发生的事」。

## 五、启动装配（AC28–AC32）

- [ ] **装配入口可在测试进程内调用并返回可用组件**（AC28）
  验证：返回结果的应用对象是应用类型的实例、协调层的工具能力为真、清理动作可调用。
- [ ] **清理动作释放会话锁、回收连接，且可重复调用**（AC28）
  验证：执行清理后会话锁文件消失、MCP 连接被回收；**连续调两次不抛异常**，
  且开启记录时结束事件**恰好一条**。
- [ ] **三类装配期致命错误各以异常表达，命令行侧退出码与文案不变**（AC29）
  验证：命令注册冲突 / Provider 初始化失败 / Skill 白名单笔误各构造一次，
  断言装配入口抛异常；子进程实跑断言退出码 1 与 stderr 文案。
  **三段文案必须与重构前逐字一致**（既有启动测试断言的正是它们）。
- [ ] **白名单笔误时不留孤儿子进程**（AC29）
  验证：断言 MCP 连接步骤未被执行（此刻一个子进程都还没起）。
- [ ] **传入临时用户目录时四类用户级内容均不生效**（AC30）
  验证：在一个临时用户目录下预置内容可识别的项目指令、笔记索引、Skill、权限规则、
  MCP 配置各一份，再用**另一个空目录**装配，断言——系统提示不含前两者、
  该 Skill 不在清单、该权限规则不参与求值、该 MCP 未被连接。
- [ ] **同进程连续两次装配互不污染**（AC31）
  验证：两次用不同用户目录「装配 → 清理」，断言第二次的只读路径白名单不含第一次注册的路径。
- [ ] **不带记录参数时的行为与重构前一致**（AC32）
  验证：**子进程实跑**（独立判据，不能只依赖既有测试——因为迁桩被明示允许），
  比对退出行为与可观察输出。
- [ ] **用户目录参数确实可选**
  验证：保留一组只传配置的无参调用，能正常装配。改成必选会把回归面从零推到五个测试文件。

## 六、阅读器（AC33–AC37）

- [ ] **不新增控制台入口，产品命令行选项集合无变化**（AC33）
  验证：`pyproject.toml` 的脚本入口只有 `rhine` 一项；`python -m rhinecode --help`
  输出不含阅读器相关选项。
- [ ] **时间线摘要每事件一行、含序号与类型**（AC34）
  验证：输出行数等于（过滤后）事件数，每行含序号与类型字段。
- [ ] **按类型与作用域过滤，两者可组合**（AC35）
  验证：对同一文件分别加 `--type`、`--scope` 与两者组合，比对条数逐步收窄。
- [ ] **按序号展开单条含全部负载字段与原长标注**（AC36）
  验证：`--seq n` 的输出含该事件的全部负载字段；被截断的字段显式打印原始长度
  （注意是**打印原长这个数字**，不是还原截断前的原文）。
- [ ] **阅读器不修改记录文件**（AC37）
  验证：运行前后比对文件哈希相等。
- [ ] **坏行被跳过并计入报告**
  验证：手工往记录里插一行非法 JSON，阅读器不崩溃、末尾报告跳过条数。
- [ ] **未登记的事件类型显式提示而非空白**
  验证：手工插一条类型为虚构值的记录，摘要行显示「未登记类型」。
  这是新增事件类型时的自检信号——显示成空白且不报错才是真隐患。

## 八、架构与集成（来自 plan）

> 本节验的是**架构不变量**（分层方向、依赖边、无环），它们变了就是需求被违反，
> 不属于「实现细节」。

- [ ] **trace 层是叶子层，不反向依赖上层**
  验证：`trace/` 全部模块的 import 中，除**同包内互引**外只有标准库；
  唯一的向上依赖是装饰器模块引用 Provider 抽象（spec N4 明示的唯一例外）。
- [ ] **包导出刻意不含装饰器**
  验证：`python -c "import rhinecode.trace as t; print(hasattr(t,'TracingProvider'))"`
  输出 `False`。这让 N4 的唯一例外在调用方代码里保持显式可见。
- [ ] **工具包的包初始化文件仍无任何 import 与 re-export**
  验证：`rhinecode/tools/__init__.py` 未新增任何导入或导出（现状是纯 docstring）。
  工具与 Skill、工具与 MCP 都是包级互相依赖，不成环唯一依靠它没有导出。
- [ ] **记录器向下传递链完整、无静默失效**
  验证：开启记录跑一次完整对话，六类接收方（主 Agent、子对话 Agent、上下文管理器、
  记忆管理器、命令分发器、Skill 管理器）产出的事件全部出现。漏传的症状是拿到关闭态对象、
  什么都不报。
- [ ] **Skill 状态埋点全在锁外**
  验证：`tests/test_skill_manager.py` 的跨线程死锁护栏通过；激活、卸载、清空、热更新
  各触发一次，界面不冻结。
- [ ] **作用域泄漏有防护**

## 九、端到端场景【手测】

> 以下场景需在 tmux 或真实终端里跑**真实对话**，逐条记录实际观察结果。
> 场景 1–3 是本模块的价值验证（能不能真的替代「现写脚本捞证据」），
> 场景 4–5 是回归确认，场景 6–9 是边界。
>
> **场景 2 需要前置准备**，见该条说明。

- [ ] **场景 1（基本可用：一条命令跑完 + 读日志）**
  `rhine --trace` 启动 → 提一个会触发工具调用的真实请求（如「看看这个项目的测试怎么组织的」）
  → 正常完成 → 退出 → `python -m rhinecode.trace.reader <产出文件>` →
  观察时间线能看出脉络：会话启动 → 用户输入 → 每轮的模型请求与响应 → 权限决策 →
  工具执行 → 界面消息 → 会话结束。
  **然后回答一个原本答不出的问题**：`--type api_request --scope main` 后展开第一轮，
  确认能看到「模型这一轮实际收到了哪些工具」，以及系统提示内容
  （超过截断阈值时会带截断标记与原始长度——**这是已知行为，不是缺陷**）。
- [ ] **场景 2（复现立项理由：白名单外调用）**
  **前置准备**：三个内置样板都不是纯只读白名单（`review` 与 `commit` 含 `run_command`、
  `test` 还含 `edit_file`），必须先自己造一个——在 `<项目根>/.rhinecode/skills/` 放一个
  `allowed_tools: [read_file]`、`mode: shared` 的临时 Skill，`/skills reload` 生效。
  步骤：让模型「用这个 skill 处理某个任务」以促使它调用加载工具（**工具集收窄发生在
  模型自己加载 Skill 之后**，走短命令的 run 路径语义不同）→ 让它尝试改文件 →
  `--type tool_execute` 找结局为「白名单外」的那条 → 展开 → 确认输出含「工具不可用」
  与当轮可用工具列表。
  **对照项（必查）**：同一次运行里 `--type api_request` 展开那一轮，确认发出的工具名列表里
  确实没有写文件工具。
  **通过判据**：对照项必须通过。「白名单外」那条依赖模型是否真的越界调用
  （当初那个 bug 属偶发幻觉，不可控）——若本次未触发，以自动化用例的结果为准，
  本场景仍算通过，但要如实记录「未自然复现」。
- [ ] **场景 3（作用域交错可读）**
  `/review`（内置的独立模式 Skill）→ 跑完 → `--scope main` 与
  `--scope isolated:review` 分别过滤 → 确认两条时间线各自完整、互不混淆。
  **具体判据**（不要按「主作用域只有两条事件」判——界面消息、命令分发、状态栏一律归主
  作用域，必然远多于两条）：`--scope main` 里**没有**子对话的模型请求与工具执行事件；
  主历史新增**恰好两条**配对消息（用 `/resume` 回放或看会话存档确认）。
  再看 `/context` 报告，确认主上下文没被子对话的多次读文件撑大。
- [ ] **场景 4（关闭时肉眼无差别）**
  不带 `--trace` 启动，跑一次与场景 1 相同的请求，逐项观察（四个二元判据）：
  ① 流式输出逐块出字；② 工具行逐个出现并正常转色；③ 状态栏用量随轮次变化；
  ④ 确认面板可弹出、四个选项可选。
  再确认工作区里没有 `.rhinecode/traces/` 目录。
  整体观感差异（是否更卡）属主观项——如实记录，**不作为红绿门**。
- [ ] **场景 5（与会话恢复共存）**
  `rhine --trace --continue` 启动 → 观察历史被回放 → 从 trace 里确认有一条恢复事件
  且来源标为「启动恢复」→ 继续对话若干轮 → 运行中再 `/resume` 切另一个会话 →
  确认第二条恢复事件来源标为「恢复命令」，且**两次都写在同一个记录文件里**。
- [ ] **场景 6（人在回路与拒绝路径）**
  开 `--trace` → 触发一次写文件确认面板 → 选「拒绝」→ 从 trace 里确认三者能串起完整因果：
  一条权限决策事件（判定为「问用户」）、一条交互事件（结果为拒绝）、
  一条工具执行事件（结局为「用户拒绝」）。
  再直接要求模型执行一条危险命令（如 `rm -rf` 类）→ 确认权限决策事件的命中层是**黑名单**、
  **且确认面板根本没弹**（第①层直接拒绝，不进人在回路）。
- [ ] **场景 7（压缩动作可解释）**
  → 界面出现压缩提示 → `--type context_compaction` →
  确认第一层能看到哪几个工具结果被存盘及其落盘路径、第二层能看到保留边界与前后条数。
  **这就是原本「这轮消息为什么突然短了」答不出的那个问题。**

  **⚠️ 原先写的「用 `context_window: 8192` 触发两层」是错的，已实测推翻。**
  那个配方能让第二层**被走到**，但**永远压不动**：`summarize.RETAIN_TOKENS = 10000`
  是**固定常量、不随窗口缩放**，窗口 8192 时保留区比整个窗口还大，早段恒为空
  ——实测连续三次全是 `no_early_segment`。照旧配方做只会怀疑 C8 坏了。

  **可控做法（实测跑通，见 `tests/e2e/p0_scenarios.py`）**：
  - **第一层存盘**：`context_window: 8192` + 让模型读一个大文件（单个工具结果
    超 4K token 即触发）。这一半原配方是对的。
  - **第二层摘要**：必须**同时**满足三件事，缺一不可——
    ① 窗口正常（用默认 64K 或更大），且估算逼近 `窗口 − 13K 余量`
       （脚本化假模型可用 `usage` 块把锚点直接顶到 6 万）；
    ② 历史里有**多轮 user 消息**——保留边界要回退到「最近一个 user」，
       只有一条 user 消息时必然回退到 0，早段还是空的（**最容易漏的一条**）；
    ③ 体量要放在 **assistant 正文**里——第一层只动 `role="tool"` 的消息，
       放在工具结果里会先被存盘吃掉。
  - 判据补充：`reconstruct` 的结构是 `[摘要, 边界提示, *保留区]`，故
    `after_count = 2 + retained_count`。**摘要 2 条时条数持平（如 7→7）是正确的**
    （换成了两条合成消息，条数不变但 token 变少），不要按「条数必须变少」判。
  - `/compact` 作为对照。
- [ ] **场景 8（落盘失败不阻断）**
  用 `--trace` 指向一个**父路径是普通文件**的位置（如 `--trace CLAUDE.md/x.jsonl`）启动 →
  确认程序**正常启动**、对话完全正常、界面没有任何错误提示、退出码正常 →
  退出后确认没有产生文件。
  （不要用「系统保护目录」——Windows 管理员账户下通常仍可写，构造不出确定性失败。）
- [ ] **场景 9（敏感产物确认）**
  开 `--trace` 跑一次会读取 `config.yaml` 的对话 → 打开产出文件确认：
  会话启动事件的 `api_key` 是掩码；但**工具输出里可能出现明文密钥**
  （这是已登记的边界，不是缺陷）→ 确认该目录已被 git 忽略、`git status` 干净。
  **场景结束后删除该 trace 文件**（它含真实密钥，勿留存、勿外传）。
