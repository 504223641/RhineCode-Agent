# C11 Skill 系统 Spec

> 状态：待批准（2026-07-26，第 3 轮修订：已按两轮独立审查的全部阻塞级与重要问题修订并补齐审查末轮点名的三处精度问题）

## 背景

到 C10 为止，RhineCode 的「可复用操作」只有两种形态：

1. **内置斜杠命令**（C10）——行为写死在 `commands/builtins.py` 的处理函数里，改一条要动代码、重装、重启。用户无法自己新增。
2. **`/init` 那种内置提示词命令**（C9/C10）——提示词是代码里的一个 Python 字符串常量（`INIT_PROMPT`），只有一条，同样不可扩展。

结果是：用户每次想让 AI 做一件重复性的事（按团队规范写 commit message、按固定清单做代码审查、按项目约定跑测试并解读失败），都得手打一遍同样的长提示词。提示词质量随手感波动，团队内也无法共享。

同时还有两个已经暴露出来的实际问题：

- **工具选择准确率**：到 C7 为止，模型每轮能看到的工具已包含 6 个内置工具 + 2 个 MCP 配置工具 + 若干远端 MCP 工具。工具越多，模型在具体任务里选错工具的概率越高。但「哪些工具与当前任务相关」是任务级知识，全局裁剪会破坏通用能力。
- **上下文污染**：像代码审查这类任务会读几十个文件、产生大量工具结果，这些中间噪音全部堆进主历史，挤占 C8 的上下文预算，而用户真正需要的只是最后那份结论。

C5 在设计系统提示分层时已经为此预留了位置——`agent/prompt/modules.py` 的 `optional_slots()` 里那个至今为空的 **「已激活 Skill」槽位（priority 120）**，就是留给本章填的。C10 建立的单一 `CommandSpec` 注册表也已经具备承接「动态来源命令」的结构。本章把这两处预留兑现。

**Provider 范围**：本章及后续所有开发只针对 DeepSeek Provider（工具模式），不为 Anthropic / OpenAI 设计兼容路径。

## 本章对既有代码的已知改造点

本章有两处必须改动 C5/C10 既有结构，在此集中登记，避免 plan 阶段才发现：

1. **动态段需支持逐轮重算**（F9 要求）。当前 Agent 循环接收的动态内容是每条用户消息计算一次的固定字符串，循环内每轮只是把同一份重新包一次；照现状实现会导致「模型在循环里激活了 Skill，本次循环剩余轮次却完全看不到它的指令」。
2. **命令注册表需支持运行时移除与整批原子替换**（F26 热更新、F27 自动卸载要求）。当前注册表只支持启动期追加注册，没有移除能力；且重建必须原子——「先删后加」中途失败若已删掉旧条目，用户会丢掉原本可用的短命令，因此失败时须保持热更新前的注册状态不变。
3. **输入提交守卫需从静默忽略改为给出可见提示**（F31 要求）。当前 TUI 在流式运行期间对提交的输入是裸返回、无任何回显。该改动**影响运行期间的所有输入路径**，不只 Skill 命令，回归面超出 Skill 层，需一并考虑连按回车时的防刷屏。

三处的具体形式由 plan 决定。

## 目标

- 让用户把可复用的 AI 操作沉淀成独立的 Markdown 文件，不必反复输入同样的提示词，并可随项目提交、随团队共享。
- 用两阶段加载控制成本：启动时模型只知道有哪些 Skill 及各自一句话用途，需要时才把完整 SOP 指令载入上下文。
- 用任务级工具白名单收窄模型可见工具，提升选对工具的准确率，同时不损害未激活 Skill 时的通用能力。
- 提供两种执行模式，让「结果需要留在主对话里继续往下做」和「只要结论、不要中间噪音」两类任务各得其所。
- Skill 加载后即成为一等公民：有斜杠短命令入口、可热更新、可显式卸载、状态可查。

## 功能需求

### 一、Skill 定义格式

- **F1**：单个 Skill 由 YAML frontmatter 与 Markdown 正文两段组成。frontmatter 承载元信息，正文是实际发给模型的 SOP 指令。frontmatter 键名是 Skill 作者手写的用户契约，因此在此写死：

  | 键名 | 必填 | 含义 | 缺省 |
  |---|---|---|---|
  | `name` | 是 | Skill 唯一名字，用于加载、短命令与列表展示 | 无 |
  | `description` | 是 | 一句话用途说明，第一阶段注入模型、并在列表中展示 | 无 |
  | `allowed_tools` | 否 | 可见工具白名单，字符串列表 | 不声明即不收窄 |
  | `mode` | 否 | 执行模式，取值 `shared` / `isolated` | `shared` |
  | `history_messages` | 否 | 独立模式从主历史尾部带入子对话的消息条数，非负整数 | `0`（不带） |
  | `model` | 否 | 子对话使用的模型名，仅独立模式生效 | 沿用全局配置模型 |

  未知键忽略（向前兼容，与 C9 笔记 frontmatter 的宽松解析口径一致）；键值类型不符（如 `allowed_tools` 写成字符串而非列表）按 F5 记为加载失败。

- **F2**：支持两种物理形态。**单文件型**：一个 `<任意名>.md` 文件即一个 Skill。**目录型**：一个目录即一个能力包，目录内固定名为 `SKILL.md` 的入口文件承载 frontmatter 与正文，其余文件（模板、示例、辅助脚本、参考文档）作为该 Skill 的随附资源，整个目录可作为一个整体分发。Skill 的名字一律以 frontmatter 的 `name` 为准，**不要求**与文件名或目录名一致。

- **F3**：Skill 从三个固定位置加载，优先级由高到低为：

  1. **项目级** `<项目根>/.rhinecode/skills/`（随仓库提交、团队共享）
  2. **用户级** `~/.rhinecode/skills/`（跨项目个人常用）
  3. **内置** 随程序分发的样板目录

  同名 Skill 按优先级覆盖，且是**整份替换**而非字段级合并——高优先级那一份完全生效，低优先级那一份完全不生效，避免出现「正文来自 A、白名单来自 B」这种难以推理的混合体。列表展示时标注每个 Skill 实际来自哪一层。项目级 Skill 目录设计为随仓库提交，需在 `.gitignore` 的既有说明中登记（该说明目前已列出项目级 RHINE.md / permissions.yaml / mcp.yaml 属于可提交内容）。

- **F4**：`name` 必须匹配「小写字母开头，仅含小写字母、数字与连字符」且长度不超过 32 个字符；且不得为保留子命令词 `reload` / `off` / `prompt` / `run`（这四个词是 F26 管理命令的子命令）。之所以这里比 F25 的同名处理（照常加载、只是不注册短命令）更严厉，是为了让 `/skills <词>` 的解析**不需要任何歧义消解规则**——只要保证 Skill 名与子命令词不相交，`/skills off` 永远是「卸载全部」，不必区分它是否指某个叫 `off` 的 Skill。不满足者按 F5 记为加载失败。该限制的目的是让名字能安全地直接用作斜杠命令名与展示文本，不需要额外转义。

- **F5**：加载容错。单个 Skill 因下列任一原因无法加载时，**只跳过该 Skill 并记录可读原因**，不影响其它 Skill，也不阻断程序启动；原因可通过 Skill 状态查询（F26）看到：
  - frontmatter 解析失败或键值类型不符
  - 缺 `name` 或 `description`
  - `name` 不合法或使用了保留子命令词（F4）
  - 目录型 Skill 缺入口文件
  - 文件读取失败
  - **与同层内已加载的 Skill 重名**（见 F29）

- **F29**：**同层内重名**——同一层目录里两份 Skill 声明了相同 `name` 时，保留按文件名字典序在前的那一份，后一份按 F5 记为加载失败并给出「与同层 `<文件名>` 重名」的原因。之所以要定死这条规则，是因为跨层重名由 F3 的优先级解决，但层内重名若不处理，会在 F24 的短命令注册阶段撞上 C10 注册表的冲突校验。

### 二、两阶段加载

- **F6**：**第一阶段（启动即注入）**——把当前全部可用 Skill 的「名字 + 一句话说明 + 执行模式」组成一份清单，注入系统提示的**稳定可缓存通道**，作为一个**新增**的稳定模块（C5 预留的 120 槽位归 F9 的正文使用）。清单不含任何 SOP 正文。

  两条约束：

  - **位置**：清单排在稳定段所有既有内容之后。理由是稳定段是前缀缓存的作用对象，任何一段变化都会让其后的内容一并失效；把随热更新变化的清单放在最后，使热更新只失效清单自己那一小段，不波及项目指令与记忆索引。热更新导致一次前缀缓存失效是可接受代价，需如实登记。
  - **上限**：清单总量上限 **200 行 / 25KB**（沿用 C9 记忆索引的既有阈值），超限时只注入到超限前的部分并在末尾标注被省略的条数。

- **F7**：**第二阶段（按需加载）**——提供一个名为 `load_skill` 的内置工具，模型传入 Skill 名字与可选参数即可加载该 Skill。行为规定：

  - 加载**共享模式** Skill 成功 → 该 Skill 进入激活态（第三节），工具**只返回一句简短确认**（已激活哪个 Skill）。完整 SOP 正文不通过工具结果回灌历史，而是进入激活槽位，保证正文在上下文中只有一份。
  - 请求加载**独立模式** Skill → 返回结构化错误，说明该 Skill 为独立模式、需由用户触发，并给出**当前实际可用的入口**：该 Skill 的短命令；若其短命令因 F25 未注册，则给出 `/skills run <name>`。错误文案不得指向不存在的命令。**模型不能发起独立模式执行。**
  - 加载不存在的 Skill → 返回结构化错误并附上可用 Skill 名字列表。

  以上任何一种失败都不终止 Agent 循环。第一阶段清单（F6）标注执行模式，正是为了让模型据此判断该自己加载还是建议用户执行短命令。

  > **为什么模型不能发起独立模式执行**：工具执行接口返回的是一次性结果而非事件流，若让加载工具内部同步跑完整个子对话，用户在长达数分钟的执行期间将看不到任何进度（而短命令路径走 Worker 事件流，进度完整可见）。两条路径 UX 严重不对称，且工具内嵌套 Agent 循环显著增加复杂度。本章选择把独立模式收敛为纯用户发起的路径。

- **F8**：`load_skill` 是**系统级**工具：在主对话中，无论当前激活了哪些 Skill、白名单如何收窄，它对模型永远可见。否则一个声明了严格白名单的 Skill 会把「加载下一个 Skill」的能力自己锁死。但在独立模式子对话中**不暴露**该工具（见 F23）。

### 三、激活态

> **总纲：激活态只适用于共享模式。** 独立模式 Skill 不进入激活列表——它的 SOP 只注入子对话的系统提示，子对话结束即释放，不占用主对话的槽位、不并入主对话的白名单。下述 F9–F11、F14 中的「激活」一律指共享模式。

- **F9**：已激活 Skill 的完整 SOP 正文注入 C5 预留的「已激活 Skill」槽位（priority 120，动态通道），排在环境信息之后，利用近因效应处在动态段的显著位置。**生效时机必须精确到轮**：

  - 用户通过短命令激活的 Skill，自该次请求的第一轮起生效。
  - 模型在循环内通过加载工具（F7）激活的 Skill，自**同一次 Agent 循环的下一轮请求**起生效，此后每一轮都重新注入，直到卸载。

  这要求动态段逐轮重算（见「已知改造点」第 1 条）。

  **注入上限与截断可见性**：单个 Skill 正文上限 **300 行 / 12KB**，全部已激活正文合计上限 **600 行 / 24KB**，超限时按 F10 的激活顺序拼接、**在拼接尾部截断**（即后激活的 Skill 先受影响），理由是正文每轮重发、无界增长会持续侵蚀 C8 的上下文预算，且它不在对话历史里、C8 的第二层摘要压不到它。截断**必须对用户可见**，且须**指名是哪个 Skill 受影响、是被整段丢弃还是被切掉后半段**：激活时给出警告，并在 `/skills` 列表与 `/skills prompt` 中标记。

  **与 C8 预算的对账**：合计上限 24KB 按 C8 的换算口径（每 token 约 3 字符）约合 8K token 的**每轮常驻**开销，且这部分不可被第二层摘要压缩。C8 现有的 13K 自动压缩余量是在没有这块常驻开销的前提下定的，plan 阶段须确认二者相容——必要时下调本条的合计上限，或调整 C8 的余量设定。之所以比 C9 索引截断要求更高的可见性——索引截断只是少召回几条，而 SOP 截断会切断一段有序流程（五步只剩三步），模型会照半份 SOP 产出「做了一半」的结果，用户若不知情极难排查。

- **F10**：多个 Skill 可同时激活，正文按激活先后顺序拼接，各自带明确的边界标识，模型能分辨哪段指令属于哪个 Skill。

- **F30**：**重复激活幂等**。同一个 Skill 被重复激活（模型重复调用加载工具，或用户连按两次短命令）时不产生第二份正文；其在 F10 拼接顺序中的位置保持首次激活时的位置，参数以最后一次为准。

- **F11**：激活态**常驻**，直到用户执行清空对话或显式卸载。清空对话时连同已激活 Skill 一并清除。另提供显式卸载能力（F26），可摘掉单个或全部已激活 Skill，不必为取消一个误激活的 Skill 而清空整个对话历史。

- **F12**：**参数占位符**。SOP 正文中的 `$ARGUMENTS` 会被替换为调用时传入的参数串。若正文未包含 `$ARGUMENTS` 而调用时又传了非空参数，参数以一段明确标注的「用户补充参数」附在正文末尾——参数在任何情况下都不会被静默丢弃。参数不做 shell 分词，原样保留（与 C10 的参数处理口径一致）。只做这一个占位符的字面替换，不做任何模板求值。

- **F13**：**目录型 Skill 的资源可达**。激活目录型 Skill 时，注入的正文中附带：

  - 该 Skill 资源目录的**绝对路径**；
  - 该目录下随附文件的**相对路径清单**（可设条数上限）。

  之所以要给清单而不只给目录路径：搜索类与枚举类工具受工作区边界约束，对位于工作区外的用户级/内置 Skill 资源目录无法枚举也无法搜索，模型只能在已知确切文件名时读取。给出清单使读取不必靠猜。项目级 Skill 的资源目录在工作区内，枚举与搜索正常——这一不对称属于已知边界，如实记录。

  系统须保证模型对这三层 Skill 目录中**位于工作区外的部分**的只读访问不被路径沙箱拦截（具体机制由 plan 决定）。辅助脚本的执行仍走常规命令执行工具与完整五层权限管线，不获得任何豁免。

### 四、工具白名单

- **F14**：Skill 声明了 `allowed_tools` 时，激活期间模型可见的工具收窄到白名单内。多个 Skill 同时激活时，可见工具是**各白名单的并集**——每个 Skill 声明自己需要什么，叠加激活即能力叠加。未声明白名单的 Skill 不参与收窄（等价于「不限制」，只要有一个这样的 Skill 激活，本轮就不收窄）。未激活任何 Skill 时的工具集见 N3。

  **运行期自愈**：每轮计算可见工具集时，白名单按**当前**工具注册中心取交集，注册中心里已不存在的名字静默跳过。这样 C7 的运行时 MCP 重载（`mcp_add_server` 会注销旧工具、注册新工具）不会让白名单指向幽灵工具，也不需要用户手动干预。

- **F15**：白名单与 Plan Mode 的只读约束是**与**的关系——两者都允许才可见。加载工具（F8）以及 Plan Mode 的两个交互专用工具 `ask_user` / `present_plan` 不受白名单影响。

- **F16**：**白名单工具名校验，分两段进行**：

  - **第一段（MCP 连接之前）**：校验白名单中**不以 `mcp__` 开头**的名字。校验基准是「内置工具集 ∪ 加载工具 ∪ `ask_user` / `present_plan`」——后两类虽不在工具注册中心里（加载工具是系统级、两个交互工具由 Plan Mode 单独拼装），但声明它们是作者的合理写法，不能当笔误处理；对它们只给「该工具不受白名单影响，声明无效果，可删除」的提示，不终止启动。基准之外的名字判定为 Skill 作者笔误——打印出**是哪个 Skill 文件的哪个工具名**后以非成功状态终止启动。

    **执行窗口必须写死**：本段校验须在工具注册中心完成**全部**内置工具注册**之后**、MCP 连接**之前**执行。这个窗口很窄且有陷阱——`mcp_add_server` 是内置工具，但它依赖 MCP 管理器实例，因此比其它内置工具晚注册；而它的名字是**单**下划线 `mcp_`，不匹配 `mcp__` 判别式，会落进本段的严格校验。若把校验放在「核心工具注册完成」这个看似自然的位置，一个写了 `allowed_tools: [mcp_add_server]` 的**完全合法**的 Skill 会被判为笔误并硬终止启动。

    校验之所以能提前到 MCP 连接之前，是因为分级依据是「名字是否以 `mcp__` 开头」而非「是否在注册中心里」，上述基准在该窗口内已完全确定；提前的收益是此时尚未创建任何 MCP 子进程与网络连接，终止启动干净利落，不会留下孤儿进程。两处副作用如实记录：(a) 任何以 `mcp__` 开头的名字都会绕过第一段的严格校验、落到第二段的降级处理；(b) `mcp_resolve_server` 与 `mcp_add_server` 这两个单下划线的内置工具走第一段严格校验，不受第二段的降级保护。

    **错误信息须提示版本错配的可能**。本段的判定前提是「工具名不存在 = 作者笔误」，有一种情形该前提为假：Skill 引用的是另一个 RhineCode 版本里的工具名（新版新增、或后续章节重命名/移除了某内置工具）。此时正确的修复是对齐版本而非改文件，因此错误信息须附一句「若确认该工具名无误，可能是 RhineCode 版本与该 Skill 不匹配」。连带备忘：**今后重命名或移除内置工具，会让所有引用它的 Skill 变成硬启动失败**，属于 breaking change，需要迁移策略。

  - **第二段（MCP 连接之后）**：校验白名单中**以 `mcp__` 开头**的名字。不存在则判定为运行时外部依赖缺失（对应 Server 未配置或本次未连上），从该 Skill 白名单中剔除该项并在启动提示中警告，**不阻断启动**——保住 C7「单个 MCP Server 失败只跳过、不影响整体」的隔离设计。

  > **为什么这一处偏离项目一贯的 fail-safe**：坏 YAML、坏 include 这类失败可能是编辑中途的瞬时状态，跳过是合理的；而「工具名拼错」是确定性的作者错误，其后果（模型静默少一个工具、行为莫名其妙）极难从现象倒推原因。这一点对**团队共享的项目级 Skill 尤其成立**——一个笔误会静默影响所有拉取该仓库的人，正是最需要在第一时间被拦下的场景。错误信息给出 Skill 文件路径与具体工具名，而该文件就在用户已检出的工作副本里，改一行或删一个文件即可恢复启动，代价可控。

- **F17**：若某 Skill 的白名单在剔除（F16 第二段或 F14 的运行期自愈）后变为空集，该 Skill 降级为「未声明白名单」并警告，避免激活它之后模型一个工具都看不到、彻底无法工作。该降级在启动期与运行期同样适用。

### 五、执行模式

- **F18**：**共享模式**——Skill 指令注入当前对话上下文，后续推理与工具调用都发生在主对话里，全部过程文本、工具调用与结果都留在主历史中，用户可以直接接着往下提要求。

- **F19**：**独立模式**——开一条独立的对话历史跑完整 Agent 循环，跑完把结论回流主对话。

  **主历史新增恰好两条配对消息**：F24 定义的自包含用户消息，加上一条承载结论的助手消息。之所以不是只写结论一条——孤立的助手消息在历史中没有对应用户轮，既不符合角色交替、又会让 C8 第二层摘要的保留边界（回退到最近的用户消息）判断失准，`/resume` 回放时也会渲染出一条无来由的 AI 回复。

  结论取子对话自然结束时的**最后一条助手正文**。子对话的中间消息（含全部工具调用与结果）**不进入主历史**。若子对话未产生任何正文（被取消、达迭代上限、流出错、触达模型上下文上限），助手消息位写入一条如实说明未产出结果**及其原因**的文本，而不是静默不加——配对结构在任何情况下都成立。

- **F20**：**独立模式的子对话历史构造**为：

  1. 按 `history_messages` 从主历史尾部带入最近若干条消息（缺省 0，即不带）。截取边界会回退调整，保证不拆散「含工具调用的助手消息」与其对应的工具结果消息，避免子对话拿到不成对的历史而请求失败。
  2. 其后追加**一条用户消息**，内容与 F24 写入主历史的自包含语义文本同源。

  第 2 步不可省略：缺省不带历史时，子对话若没有这条用户消息就完全没有用户轮，模型会收到一个只有系统提示、没有任务陈述的请求。同源复用也保证主历史与子对话对「本次要做什么」的表述完全一致。

- **F21**：**独立模式的执行环境**：

  - **系统提示**复用主对话的固定模块、环境信息、项目指令与记忆索引，**并在槽位 120 注入本 Skill 的 SOP 正文**（含 F12 的参数替换与 F13 的资源清单）；主对话已激活的其它 Skill 正文**不带入**子对话。
  - **工具集**取该 Skill **自己的** `allowed_tools`（不是主对话激活集合的并集，因为独立模式 Skill 不进激活列表），并同样受 F14 运行期自愈、F15 只读约束、F17 空集降级的约束；加载工具不在其中（F23）。
  - **复用**主对话的权限引擎与人在回路确认回调、以及取消信号；子对话执行期间事件照常流式渲染到界面，用户能看到进度并可随时取消。
  - **参与 C8 第一层工具结果存盘**——该层零成本、不调模型，而独立模式恰恰是最可能产生海量工具结果的路径，把它排除在外没有任何收益。是否参与**第二层摘要**由 plan 决定；若决定不参与，须说明子对话触达上下文上限时的兜底与用户可见反馈（该兜底最终落到 F19 的「未产出结果及原因」）。
  - **子对话本身不写会话存档、不触发自动笔记**——它是一次内部执行，只有回流的结论才是对话事实。但整条短命令执行结束时，主对话照常产出自然完成事件，C9 挂在协调层单点上的笔记钩子照常针对**主历史**（此时已含 F19 的两条消息）触发一次，这是期望行为，不要一并关掉。

- **F22**：**指定模型仅在独立模式生效**。共享模式的 Skill 声明了 `model` 时，该字段被忽略，并在**扫描加载时**（而非等到激活时）即给出警告——这个组合在读到 frontmatter 的那一刻就能判定。理由是共享模式中途换模型会让同一段历史跨模型、使 C5 的稳定前缀缓存整段失效，收益不抵代价。

- **F23**：独立模式子对话中**不向模型暴露加载工具**（避免白费 schema token 与一次必然失败的往返）；若模型仍硬编发起调用，返回结构化错误并继续循环，作为防御性兜底。目的是防止 Skill 相互嵌套激活导致递归。

- **F31**：**与运行中循环的并发**：

  - Skill 的**激活**只可能由用户发起短命令（循环开始前）或模型在循环内调加载工具发起，生效时机见 F9。
  - Agent 循环运行期间，`/skills` 的**全部形态均不可用**（现有输入提交守卫拦的是全部输入，无法按命令区分粒度），但必须给出**可见的本地提示**——现有守卫是静默忽略，本章要求改为给出提示行。该提示对运行期间的所有输入生效，不只 Skill 命令。
  - 热更新不影响**正在运行**的循环或子对话，其结果自下一次循环起生效。不做排队。

### 六、命令与生命周期集成

- **F24**：每个成功加载且短命令名可用的 Skill 自动注册一条斜杠短命令 `/<name> [参数]`。执行该短命令等价于「激活该 Skill 并立即发起一次执行」：共享模式在主对话跑，独立模式开子对话跑完回流。短命令与内置命令共享同一套解析、大小写不敏感、Tab 补全、候选菜单与命令高亮（C10 能力自动继承）。

  **写入模型历史的内容**沿用 C10 的双内容模型：界面与会话回放显示用户原始输入（如 `/commit 修复登录超时`），模型历史与会话存档中的这条用户消息则写入一段**自包含的语义文本**，必含三项——Skill 名字、其一句话说明、原样参数——使这条消息脱离激活态仍可被理解。该文本同时被 F20 复用为独立模式子对话的首条用户消息。

  > **与 C10 F27 的关系（有意的取舍）**：C10 要求提示词命令把「展开后的完整提示词」写进历史，以保证 C8 摘要与 `/resume` 恢复后语义完整。C11 不照搬，因为 Skill 的 SOP 正文走的是每轮重注入的槽位，若再写进历史就会在长会话里出现两份、持续占用预算。代价是恢复历史会话后，那条消息只剩「执行过哪个 Skill、它是干什么的、带什么参数」而非完整 SOP。这个降级被明确接受并登记在「不做的事」中；Skill 文件仍在磁盘上，名字即指针。

- **F25**：**短命令冲突时内置优先**。Skill 短命令与任何内置命令的规范名或别名重名时，**不注册该短命令**并在启动提示中警告；该 Skill 本体仍完全可用——模型可经加载工具调用（共享模式），用户可用 `/skills run <name>` 执行（两种模式皆可），它也照常出现在列表与第一阶段清单里，只是少一个斜杠快捷入口。Skill 之间的同名已在 F3 跨层覆盖与 F29 层内去重阶段解决，注册时不会再有 Skill 互撞。

- **F26**：新增内置管理命令 `/skills`，提供五种形态：

  | 形态 | 行为 |
  |---|---|
  | `/skills` | 列出全部已发现 Skill：名字、来源层级、说明、执行模式、是否已激活、短命令是否可用、正文是否被截断；并列出加载失败的 Skill 及原因 |
  | `/skills reload` | 热更新：重扫三级目录、重建索引与短命令注册、重跑白名单校验 |
  | `/skills off [name]` | 卸载指定的已激活 Skill；省略名字则卸载全部 |
  | `/skills run <name> [参数]` | 显式执行指定 Skill，等价于其短命令；为短命令未注册（F25）的 Skill 提供唯一入口。`<name>` 之后的**全部内容原样**作为该 Skill 的参数，不做 shell 分词（沿用 C10 与 F12 的口径） |
  | `/skills prompt` | 只读输出当前实际注入的内容摘要：第一阶段清单、已激活 Skill 正文（可截断）、当前生效的可见工具集 |

  `/skills prompt` 的存在使 F6/F9/F14 这类「注入内容是否正确」的行为可以被手工验收，而不必只能靠单元测试白盒断言；它同时是 F5 加载失败原因与 F16/F17 各类降级警告的查看载体。热更新对注册表的原子性要求见「已知改造点」第 2 条。

- **F27**：热更新后，此前已激活但在新一轮扫描中已消失（文件被删或改到解析失败）的 Skill 自动卸载并提示；仍存在的 Skill 保持激活，其注入正文更新为新内容，并沿用最后一次激活时的参数重新做 F12 的占位符替换（新正文若不再含 `$ARGUMENTS`，参数按 F12 的补充段规则处理）。

- **F32**：**状态栏展示**。底部状态栏在有 Skill 处于激活态时展示一段标记（至少含已激活数量），无激活时不展示该段，语义与既有的 MCP 段、上下文段「无内容即隐藏」一致。理由是激活态会同时改变模型指令与可见工具集，属于用户需要随时知晓的会话状态。**两条激活路径都必须触发刷新**——用户短命令路径由命令处理函数显式刷新，模型经加载工具激活的路径发生在 Worker 线程，需跨线程调回主线程刷新。标记文本若含字面方括号需按既有约定转义。

- **F28**：内置三个样板 Skill 随程序分发：**commit**（共享模式，按项目约定生成提交信息并提交）、**review**（独立模式，审查当前改动并只回流结论）、**test**（共享模式，跑项目测试并解读失败）。它们同时充当「怎么写一个 Skill」的可读示例，其中 review 覆盖独立模式这条执行路径。

## 非功能需求

- **N1**：**独立分层**。Skill 能力作为独立包实现，纯逻辑加单点接入，对齐既有的权限层 / 上下文层 / 记忆层 / 命令层范式：不导入 TUI 框架与 Provider SDK，可在无终端、无网络的测试进程中用替身独立验证。

- **N2**：**fail-safe**。除 F16 第一段明确规定的「内置工具名笔误即终止启动」这一处例外，加载、校验、激活、卸载、热更新的任何单点失败都只降级受影响的那个 Skill，不阻断启动，也不中断正在进行的对话。

- **N3**：**受控回归**。未激活任何 Skill 时，除下列两处**必然且有意**的差异外，系统提示与每轮暴露给模型的工具集与 C10 一致：
  1. 稳定段新增第一阶段 Skill 清单（因 F28 内置样板存在，该段开箱即非空）；
  2. 工具集新增加载工具（F8 要求它永远可见）。

  「已激活 Skill」槽位在无激活时为空并整体跳过，动态段其余部分与 C10 逐字节一致。

- **N4**：**激活态是会话级内存状态**，不写入会话存档、不随会话恢复重建。恢复历史会话后激活列表为空、槽位为空。

- **N6**：独立模式子对话有自己的迭代上限，与主循环的迭代计数互不共享，避免子任务耗尽主循环预算。

- **N7**：所有新增与修改的代码遵循项目的中文注释规范，关键设计意图、边界条件与副作用需写明。

## 安全边界

Skill 正文是**被注入系统提示、以系统指令身份呈现给模型**的第三方内容，信任位置高于工具结果，因此必须明确其信任模型与约束。

- **N5**：**沙箱只读面按先例扩大，写与搜索面不变**。三层 Skill 目录中位于工作区外的两层（用户级、内置）经只读放行，使模型可读取其资源文件；该放行**只对读类判定生效**，写类与搜索类判定完全不动（与 C9 放行用户级记忆目录的处理方式一致）。Skill 机制本身不提供任何写入这些目录的路径。项目级 Skill 目录本就在工作区内，无需额外处理。

- **N8**：**信任模型与可见性**。Skill 正文视为**用户与团队提供的可信输入**，与 RHINE.md 项目指令同级。但项目级 Skill 随仓库分发，意味着 clone 一个仓库并在其中启动 RhineCode，就会让该仓库的 Skill 自动进入系统提示、自动占据斜杠命令入口。因此：**每次启动**时若发现项目级 Skill，就在启动提示中列出发现了哪些、来自哪个目录，让「仓库带来的指令」不是无声生效的。

  这里刻意采用「每次都提示」而非「只提示一次」：后者需要一份持久化的「已提示过」状态，一旦仓库更新新增了 Skill 而状态未失效，新增的指令就会被静默吞掉——这恰是本条要防的情形。每次提示是零状态方案，与 C9 启动提示同构，成本一行。

- **N9**：**Skill 无任何权限豁免**。Skill 正文诱导的一切工具调用照常经过完整的五层防御管线（危险命令黑名单 → 路径沙箱 → 可配置规则 → 权限模式 → 人在回路）。Skill 不能放宽黑名单、不能突破沙箱、不能改写权限规则、不能免除确认。这条适用于整个 Skill 机制，不限于 F13 的辅助脚本。

- **N10**：**工具白名单不是安全边界**。它只收窄模型**可见**的工具以提升选择准确率；它会在「有未声明白名单的 Skill 激活」（F14）或「剔除后为空」（F17）时塌缩为不限制。实际的权限约束始终由 C6 的五层管线判定，不得把白名单当作沙箱使用，后续章节也不应在其上构建安全假设。

## 不做的事

- Skill 的市场分发、远程安装、版本管理与更新检查。
- **子对话内的嵌套激活**——独立模式子对话中不能再加载任何 Skill（F23）。多个共享模式 Skill 在主对话中叠加激活是支持的（F10/F14），不属此列。
- **模型自主发起独立模式执行**——独立模式只能由用户经短命令或 `/skills run` 触发（F7 已说明理由）。
- frontmatter 参数的结构化 schema（声明参数名、类型、必填与校验规则）——本章参数只有一个原样传入的字符串。
- Skill 正文的模板引擎（条件、循环、include 等）——只有 `$ARGUMENTS` 单一占位符的字面替换。
- 多个 Skill 并行执行。
- 独立模式子对话的中途追问（用户不能在子对话进行中插话，只能取消）。
- Skill 激活态的跨会话持久化与随会话恢复重建。
- **Skill SOP 正文写入会话存档**——因此恢复历史会话后，短命令产生的那条用户消息语义弱于 C10 的提示词命令（只剩 Skill 名、说明与参数，见 F24 的取舍说明）。
- 文件系统监听式的自动热更新（只做显式命令触发）。
- 卸载与热更新的排队执行（循环运行中触发直接拒绝，F31）。
- 共享模式下的模型切换。
- 为 Anthropic / OpenAI Provider 适配本章能力。

## 验收标准

**定义与加载**

- **AC1**（F1）：一个写全六个 frontmatter 键的 Skill 可被正确加载，各字段值与文件声明一致；只写 `name` 与 `description` 时其余取到表中缺省值；含未知键时该键被忽略且加载成功；`allowed_tools` 写成字符串时按 F5 记为加载失败。
- **AC2**（F2）：单文件型与目录型 Skill 都能被发现并加载；目录型能正确定位 `SKILL.md`，并记录其资源目录路径；`name` 与文件名不一致时以 `name` 为准。
- **AC3**（F3）：同名 Skill 同时存在于三层时，实际生效的是项目级那一份，且其正文与白名单**整份**来自项目级；`/skills` 列表中标注的来源层级正确。
- **AC4**（F4）：名字含大写字母、空格、路径分隔符、超长、或取值为 `reload`/`off`/`prompt`/`run` 的 Skill 被拒绝加载，其它 Skill 不受影响。
- **AC5**（F5）：目录中放入 frontmatter 语法损坏、缺必填字段、名字非法、目录型缺入口文件四种坏样本，程序正常启动，其余 Skill 全部可用，`/skills` 中能看到这四份各自的失败原因。
- **AC31**（F29）：同层放两份 `name` 相同的 Skill，字典序在前的生效，另一份在 `/skills` 中显示「与同层 X 重名」的失败原因，且短命令只注册一条。

**两阶段加载**

- **AC6**（F6）：`/skills prompt` 显示的第一阶段清单含全部可用 Skill 的名字、说明与模式，且**不含**任何 SOP 正文；构造超过 200 行 / 25KB 的 Skill 集合时，清单被截断并标注省略条数。
- **AC7**（F7）：模型调用加载工具加载共享模式 Skill 后，工具结果是一句简短确认而非完整正文；请求加载独立模式 Skill 时返回结构化错误并给出**实际可用**的入口（短命令已注册时给短命令，未注册时给 `/skills run <name>`）；加载不存在的 Skill 时返回结构化错误并列出可用名字。三种情况循环均继续。
- **AC8**（F8）：激活一个白名单极窄（如只含读文件）的 Skill 后，加载工具仍出现在主对话的模型可见工具中。

**激活态**

- **AC9**（F9）：模型在循环第 N 轮调用加载工具激活某 Skill，第 N+1 轮请求的动态段中即含该 Skill 完整正文，且此后每轮都在；正文超过 300 行 / 12KB 时被截断，且截断同时对模型（正文末尾标注）与用户（激活警告 + `/skills` 标记）可见。
- **AC10**（F10）：先后激活两个 Skill，动态段中两份正文都在，且各自边界清晰可辨。
- **AC32**（F30）：同一 Skill 连续激活两次，动态段中只有一份正文，其位置为首次激活时的位置，参数为第二次传入的值。
- **AC11**（F11）：执行清空对话后已激活列表为空；执行 `/skills off <name>` 后该 Skill 从注入内容中消失、其余仍在；`/skills off` 无参清空全部。
- **AC12**（F12）：带参数调用含 `$ARGUMENTS` 的 Skill，注入正文中占位符被替换为原样参数（含空格与引号）；对不含 `$ARGUMENTS` 的 Skill 带参数调用，参数出现在正文末尾的补充段中。
- **AC13**（F13）：激活目录型 Skill 后，`/skills prompt` 中可见其资源目录绝对路径与随附文件相对路径清单；模型能按该清单直接读取用户级 Skill 目录内的参考文档。

**工具白名单**

- **AC14**（F14/N10）：激活声明白名单的 Skill 后，发给模型的工具集恰为白名单内容加加载工具；再激活另一个白名单不同的 Skill，工具集为两者并集；再激活一个未声明白名单的 Skill，工具集恢复全量（验证 N10 所述的塌缩）；卸载全部后恢复全量。运行时注销某个白名单内的 MCP 工具后，下一轮工具集自动跳过它且不报错。
- **AC15**（F15）：Plan Mode 与白名单 Skill 同时开启时，可见工具为「白名单 ∩ 只读工具」加上加载工具与 `ask_user` / `present_plan`。
- **AC16**（F16）：白名单写一个不存在的内置工具名启动 → 进程以非成功状态终止，错误信息含 Skill 文件路径与该工具名，且**终止发生在任何 MCP 子进程创建之前**（可通过无 MCP 子进程残留观察）；白名单写 `ask_user` 或 `load_skill` → 正常启动，仅给「声明无效果」提示；白名单写 `mcp_add_server`（单下划线的内置工具）→ 正常启动、视为合法声明，不被误判为笔误；改为写一个未连接的 `mcp__` 工具名 → 正常启动、有警告、该 Skill 可用且白名单中不含该项。
- **AC17**（F17/N10）：白名单只写一个未连接的 MCP 工具时，该 Skill 激活后不收窄工具集，并给出警告。

**执行模式**

- **AC18**（F18）：执行共享模式 Skill 后，其推理文本与全部工具调用记录都出现在主对话历史中。
- **AC19**（F19）：执行独立模式 Skill 后，主历史新增的恰好是「一条自包含用户消息 + 一条结论助手消息」的配对，子对话的工具调用与结果均不在其中，两条均已写入会话存档。中途取消、以及子对话跑满自身迭代上限两种情形下，助手消息位各得到一条如实说明未产出结果及原因的文本，配对结构仍成立。
- **AC20**（F20）：`history_messages` 为 0 时，子对话历史恰为一条用户消息且其内容与主历史那条同源；声明带入若干条历史时，在主历史尾部恰好是「含工具调用的助手消息 + 其工具结果」的情形下触发，子对话拿到的历史不含被拆散的半对消息，且末尾仍追加了那条用户消息。
- **AC21**（F21）：独立模式执行期间，界面能看到子对话的工具调用进度；子对话的系统提示中含本 Skill 的 SOP 正文、不含主对话已激活的其它 Skill 正文；子对话触发需要确认的工具时确认面板照常弹出；子对话的消息未写入会话存档文件；子对话中产生的超大工具结果被 C8 第一层存盘替换为占位；整条执行结束后 C9 笔记钩子照常触发一次。
- **AC22**（F22）：独立模式 Skill 声明 `model` 时子对话确实使用该模型；共享模式 Skill 声明该字段时在**启动扫描阶段**即给出警告，且激活后仍用全局模型。
- **AC23**（F23）：独立模式子对话的工具集中不含加载工具；强行构造一次调用时返回结构化错误且子对话继续。
- **AC33**（N6）：独立模式子对话跑满自身迭代上限后回流「未产出结果」消息，主循环随后仍可正常继续若干轮（迭代预算未被消耗）。
- **AC34**（F31）：Agent 循环运行期间提交 `/skills` 的任一形态，均被拒绝且界面出现**可见提示**（而非静默无反应）；循环结束后同一命令正常执行。

**命令与生命周期**

- **AC24**（F24）：每个短命令名可用的 Skill 都有对应短命令并出现在 Tab 补全候选中；执行短命令能完成一次完整的激活加执行；带参数时参数被正确传入；界面显示原始输入，而模型历史中该条消息含 Skill 名、说明与参数三项。
- **AC25**（F25）：放一个与内置命令重名的 Skill，启动有警告、该短命令未注册、内置命令行为不变；该 Skill 仍出现在 `/skills` 列表与第一阶段清单中，且能经 `/skills run <name>` 成功执行（独立模式与共享模式各验一次）。
- **AC26**（F26）：五种 `/skills` 形态各自输出符合规定内容；`/skills prompt` 的输出与实际注入内容一致；`/skills reload` 遇到冲突失败时，热更新前的短命令注册保持不变（原子性）。
- **AC27**（F27）：运行中新增一个 Skill 文件并热更新 → 新 Skill 立即可用且短命令可补全；删除一个已激活的 Skill 文件并热更新 → 它自动卸载并有提示；修改一个已激活 Skill 的正文并热更新 → 后续请求注入的是新正文，且沿用最后一次的参数完成占位符替换。
- **AC35**（F32）：无激活时状态栏不含 Skill 段；用户经短命令激活后出现标记；模型经加载工具激活后同样出现标记（验证跨线程刷新）；卸载后消失。
- **AC28**（F28）：三个样板 Skill 开箱可见、可执行；review 走独立模式路径且主历史只留那对配对消息。

**整体与安全**

- **AC29**（N3）：未激活任何 Skill 时，动态段与 C10 逐字节一致；稳定段与 C10 的差异**仅有**新增的 Skill 清单段；工具集与 C10 的差异**仅有**新增的加载工具。
- **AC36**（N4）：执行一次 Skill 后 `/resume` 恢复该会话，已激活列表为空、`/skills prompt` 中激活正文为空。
- **AC37**（N5/N9）：模型可 `read_file` 读到用户级 Skill 目录内的文件；对同一路径的写入被拒；绝对路径的 glob 被拒；原有工作区读写语义不变。Skill 正文中要求执行危险命令时仍被黑名单拦截。
- **AC38**（N8）：在一个含项目级 Skill 的项目中启动，界面出现「发现项目级 Skill」的可见提示并列出名字与来源目录；**第二次启动仍然提示**（零状态方案）。
- **AC30**（N1/N2）：Skill 层可在无终端、无网络的测试进程中用替身完成加载、校验、激活、白名单计算、卸载与热更新的验证；激活、卸载、热更新中任一环节抛异常时只影响该 Skill、对话可继续；`python -m compileall` 与全量单元测试通过。
