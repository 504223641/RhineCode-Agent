# TUI 驱动器 P1a（交互闭环）Checklist

> 每一项通过**运行代码或观察行为**来验证，聚焦系统行为而非代码结构。
> 覆盖 `spec.md` 的 AC1–AC43 与 N1–N9，外加 `plan.md` 的架构不变量与集成验证点。
>
> **三种标注**：无标注 = 自动化；**【人读】** = 只能人工通读判定；
> **【手测】** = 需在真实终端里跑。
>
> **两条全局前提**（不写清会让好几条判据在执行时自相矛盾）：
> - **凡需要「退出后读记录」的条目与场景，一律用 `--keep-workspace` 起宿主**，
>   读完手工删除该目录。理由：记录文件落在 `<临时工作区>/.rhinecode/traces/` 下，
>   正常退出会连同工作区一起删掉——「记录可解析」与「工作区被清理」不可能同时成立。
> - **代码版本标识在宿主启动时算一次并缓存**。改完产品源码后，**正在跑的宿主
>   不会看到变化**——必须重启宿主再取，这是设计而非缺陷。

## 〇、环境前置（必须先确认，否则后面大片条目会以误导性的方式失败）

- [ ] **本机可执行 `git`**
  验证：`git --version` 有输出。
  说明：预置版本控制历史依赖它，且**刻意在缺失时明确抛错而非静默跳过**——
  静默跳过会让依赖提交历史的场景假绿。git 是本地程序、不是网络依赖，不违反 N3。
- [ ] **真实模式的两个开关**（只影响真实模式条目）
  验证：`RHINE_E2E_LIVE=1` 且 `config.yaml` 的 `api_key` 不是占位符。
  未设置时真实模式条目应报告为 **skipped 而非 failed**（这本身就是 AC41）。
- [ ] **记下 P1a 的起点提交 SHA**
  验证：`git rev-parse HEAD` 在开工前记录下来，写进验收报告。
  后面「产品侧只动了三处」要以它为 diff 基线——与 `main` 比对会把 C11 与 P0 的
  全部改动一并算进来（实测 41 个产品文件），基线不钉死那条就没法验。
- [ ] **基线测试数已知**
  验证：改动前 `python -m unittest discover -s tests 2>&1 | tail -3` 为
  `Ran 714 tests ... OK`。后续 AC40 与它比对。

## 一、闭环（AC1–AC11 + N5，本轮的核心交付）

- [ ] **一个宿主进程内走完完整会话**（AC1）
  验证：启动 → `send` → `wait`（得 `pending`）→ `status` 读到面板**展示原文与可选项
  列表** → `answer` → `wait`（得 `idle`）→ **再 `send`** → `quit`，
  全程不重启宿主；断言**会话存档**中含两轮用户输入。
  注意判据来源：主历史条数取自**会话存档**而非记录——十五类事件没有一类承载它，
  记录里的请求消息列表受条数与长度双重截断。
- [ ] **真实模型下走完同一序列**（AC2）【需显式开启】
  验证：`--mode live` 起宿主，走完 AC1 的序列（含一次面板决策），
  断言记录里出现真实模型的请求与响应事件、且至少一条工具执行成功。
  只断模式与存在性，**不断言模型措辞**。
- [ ] **真实模式无凭据时明确报错而非静默降级**（F23）
  验证：把 `api_key` 置为占位符起 `--mode live` 宿主，断言进程**明确报错退出**
  （非零退出码 + 可读文案），而不是拿假 key 跑起来到第一次请求才失败。
- [ ] **等待能在两种终态上返回并告知是哪一种**（AC3）
  验证：分别构造「会跑到空闲」与「会弹面板」两种脚本各等一次，断言 `terminal` 值不同；
  再构造一次超时，断言诊断字段齐备（三个判据分量 + `last_action` + `waited` + `state`）。
- [ ] **会话忙碌时查询单次返回耗时小于一秒**（AC4）
  验证：在一次长循环运行期间连续发若干次 `status` 与 `observe`，逐次断言耗时上限，
  且状态反映为忙碌。
  说明：实测跨线程读状态是 0.2–0.3 ms 量级，一秒是极宽松的上限；
  它真正防的是「有人把文件 IO 或阻塞等待塞进了查询路径」。
- [ ] **单次会话的模型调用轮次上限可配且触顶可识别**（N5）
  验证：`--max-turns N` 起宿主 → 连发 `send` 直至触顶 → 断言收到
  `code == "turn_budget"` 的可识别失败响应；且 `status` 的 `turns` / `turn_budget`
  两字段可读、随轮次增长。
  说明口径（写进报告，避免被当成硬顶）：预算**跨 `send` 累计**、计数含主对话与
  子对话/摘要/记忆四种作用域、**挡不住单次 `send` 内的循环**——单次上界由产品既有的
  25 轮兜底，独立模式子对话另有独立预算，故实际上界高于 `budget + 25`。
- [ ] **装配期致命错误经通道回报而非静默挂起**（AC5）
  验证：预置一个白名单笔误的 Skill 起宿主，断言客户端 `status` 收到
  `code == "fatal"` 且 `message` 与既有启动测试的文案**逐字一致**，**而不是超时**。
  这条决定了控制通道必须先于装配开始监听。
- [ ] **有待决面板时退出仍能在上限内完成**（AC6）
  验证：**两个层次都要**——① 内核级（第五段）：不起宿主进程，触发确认面板后直接
  执行退出流程，断言在上限内返回；② 进程级（第六段）：驱动到面板后直接 `quit`，
  断言进程在上限内退出（退出码 0）。两者都断言记录中存在一条来源为
  `driver_forced` 的交互事件。
  **这是实测挂死路径的护栏，不可省**：不做强制结算时工作线程阻塞在等待应答上，
  Python 3.11 的运行时收尾会无限汇合它、进程永不退出。
- [ ] **强制结算这一步确实必需**（AC6 的反证）
  验证：跳过强制结算、直接等忙碌态转假，断言在短上限内**等不到**。
  没有这条反证，读代码的人会以为强制结算是保险性质的多余代码而删掉它。
- [ ] **空闲超时后自行退出，跨进程可观测项齐备**（AC7）
  验证：**用 `--keep-workspace`** + 极短 `--idle-timeout` 起宿主、不发任何指令，
  断言——进程自行退出、会话锁文件消失、记录文件可完整解析且**末条为会话结束事件**；
  读完后由用例自行删除该工作区（否则 AC42 的残留检查会红）。
  「工作区被自动清理」另用一次**不带** `--keep-workspace` 的运行单独验。
- [ ] **清理动作复位进程内状态**（AC8）
  验证：在**测试进程内**直接装配 → 调清理动作 → 断言只读路径白名单已复位、
  外部连接已回收。
  说明：与 AC7 拆成两条是因为白名单与连接都是**进程内内存状态**——
  宿主进程都退出了，外部无从检查。
- [ ] **通道只监听回环，发布信息让客户端一步连上**（AC9）
  验证：断言监听地址为回环；发布文件含端口、工作区路径与宿主进程标识；
  客户端据此**一步连上**（不需要先知道工作区在哪）。
- [ ] **发布信息陈旧时立即报错而非超时**（AC10）
  验证：伪造一份指向未监听端口的发布文件，断言客户端**立即**报出可识别的陈旧错误
  （耗时小于 1 秒），且提示里含清理办法。
- [ ] **`wait` 期间宿主退出时给出可读提示而非堆栈**
  验证：客户端 `wait` 挂起期间强制终止宿主，断言客户端得到
  「宿主在处理本指令期间退出了」这类可读提示，**而不是 JSON 解析异常的堆栈**。
  说明：长 `wait` 撞上空闲超时正是这个形态，是最常遇到的真实失败路径。
- [ ] **代码版本标识随源码变化**（AC11）
  验证：取一次标识 → 修改任一产品源文件 → **重启宿主** → 再取 → 断言两者不同。
  ⚠️ 不重启不会变（启动时算一次并缓存）。
  防的是「改完代码继续用同一个宿主，跑的还是旧代码且毫无迹象」。

## 二、驱动内核（AC12–AC22）

- [ ] **驱动的输入走真人提交入口**（AC12）
  验证：驱动一次普通消息与一次斜杠命令，断言记录里各自产出输入事件与命令分发事件
  ——证明走的是输入解析与命令分发，而不是绕到内部方法上直接调用。
- [ ] **面板挂着时被判为「待决」而非「忙碌」**（AC13）
  验证：构造必然弹确认面板的场景，断言状态判据返回待决，且整场未超时。
  **忙碌标志此时仍为真**（实测），只看它会死等到超时——这条是判据顺序的护栏。
- [ ] **四类面板各能被应答一次，且应答前置态成立**（AC14）
  验证：工具确认、需求澄清、计划审批、会话选择各构造一次并应答，逐类断言——
  ① 应答**前**面板的可见态与聚焦态均已成立；② 各产出**恰好一条**交互事件；
  ③ 前三类断言被阻塞的循环得以继续；④ 会话选择断言**历史被载入**
  （它不隶属任何循环，不能用「循环继续」判定）。
  抢跑窗口实测占比 8869/8870，第 ① 项不验等于没验。
  ⚠️ **会话面板需先预置存档**：新建的临时工作区里没有任何会话，
  `/resume` 只会返回一句文本提示、根本不弹面板。须先往
  `<工作区>/.rhinecode/sessions/` 预置一份存档。
- [ ] **应答来源可区分**（AC15）
  验证：同一次运行内经**控制通道**与**面板按键路径**各应答一次，
  断言两条交互事件的来源字段分别为「外部驱动者」与「面板按键路径」。
- [ ] **确认面板四档全可选，永久放行确实写盘**（AC16）
  验证：四档各选一次并断言结果；对「永久放行」**额外断言工作区内的本地权限配置
  新增了条目**。
  说明：四档都是要被验收的产品能力，外部驱动者应当能逐一选到；
  工作区随场景一并丢弃，写盘无外泄。
- [ ] **危险命令在第①层直接被拒，应答者压根不被问到**（AC17）
  验证：先让外部驱动者对一次普通命令确认面板选**「本会话放行」或「永久放行」**
  （把第③⑤层对该工具打开），随后脚本化一条**黑名单命中**的危险命令，断言——
  ① 权限决策事件的命中层为**黑名单**；② **本次没有弹出任何确认面板**；
  ③ **没有**对应的工具执行成功事件。
  （也可改用**放行权限模式**起宿主再跑同一条命令，第①层同样必须拦住。）
  ⚠️ **不能写成「选择放行」**——第①层命中即直接拒绝、不进人在回路，
  根本没有面板可答，那样写按字面执行做不到。
  **这条与 AC16 一起构成 spec 目标 5「不扩大权限面」的全部内容**：
  驱动器替人应答等于换了第⑤层的执行者，第①层必须证明仍拦得住。
- [ ] **工作区校验与「是否为空」解耦**（AC18）
  验证：以项目根为工作区断言被拒绝且未产生任何装配副作用；
  再以一个**含预置内容**的临时工作区断言启动成功。
  两条必须一起验——只验前者会让实现选成「必须是空目录」，于是所有需要 git 历史或
  Skill 目录的场景一条都启动不了。
- [ ] **写真实用户目录的工具不在宿主工具集内**（AC19）
  验证：断言宿主的工具清单与记录的会话启动快照**均不含**它，且两者一致。
  说明：真实模式下调什么工具由模型决定，唯一闸门是可能误判的应答者——
  从工具集里摘掉是唯一硬保证。
- [ ] **能主动取消运行中的循环**（AC20）
  验证：脚本化多轮响应，在第一轮后发取消指令，断言循环以「用户取消」结束、
  会话回到空闲且**仍可接受下一次输入**。
- [ ] **超时失败的输出可诊断**（AC21）
  验证：构造一个**耗时超过等待上限**的假模型，断言诊断信息中含当前状态、
  三个判据分量的取值与最后执行的动作。
  ⚠️ **不可用「永不结束」的假模型**——非守护线程会在解释器退出时被汇合，
  真「永不结束」会让测试进程挂死。
- [ ] **跨线程读状态不会死锁**（AC22）
  验证：另起线程反复读状态、主线程同时驱动交互，用**完成计数而非布尔标志**判定，
  带超时汇合。**同线程版本会静默通过，不可简化。**
- [ ] **主线程被长任务堵住时取消仍能返回**（N6 的行为判据）
  验证：让主线程被一个长回调占住，此时发 `cancel`，断言它仍在上限内返回。
  说明：这是「加锁四段式」的可运行判据——若有人在持锁期间做跨线程调度，
  锁会被无限占住，**恰恰在最需要取消的时候取消不了**，而静态审查很难看出来。

## 三、环境隔离与预置（AC23–AC27）

- [ ] **预置内容在会话中真实生效**（AC23）
  验证：预置一个项目级 Skill **与一段版本控制历史**，断言——该 Skill 出现在
  `/skills` 的输出里；**且只读版本控制命令能读到提交历史**（输出非空）。
  两项都要——只验前者会漏掉「有历史的仓库」这个多数场景的前提。
- [ ] **每个会话跑在新建临时工作区，异步后台工作收敛后才清理**（AC24）
  验证：断言运行期间的工作目录位于系统临时目录之下、会话结束后不存在；
  真实形态下额外断言退出前确实等待过后台记忆线程收敛（第七段随 live 用例验）。
- [ ] **连续运行不因目录占用失败**（AC24 专项护栏，**不进全量**）
  验证：连续起停宿主若干次，无一次失败。
  说明：Windows 下当前工作目录位于待删目录内时删除必然失败，
  清理顺序（关句柄 → 切回原目录 → 删除）任何一步错位都会在这里现形。
- [ ] **默认启用用户级目录隔离**（AC25）
  验证：断言宿主使用的用户级目录位于系统临时目录之下、不是开发者真实用户目录；
  **且系统提示中不含真实用户级的项目指令与记忆索引**。
  后半条不验的话，「同一场景在两台机器上结果不同」这个隐患就没被覆盖。
- [ ] **同进程内连跑两次装配互不污染**（AC26）
  验证：用不同用户目录连跑两次「装配 → 清理」，断言第二次的只读路径白名单不含
  第一次注册的路径、工作目录已切回、会话锁已释放。
- [ ] **确定性形态不建立任何外部连接**（AC27）
  验证：断言 MCP 连接状态为空；**且假模型是唯一被调用的模型实现**
  （假工厂的调用计数与记录里的模型请求数相等）；会发起网络请求的只读工具未被调用。
  控制通道的回环连接不计入。

## 四、可替换的模型（AC28–AC33）

- [ ] **注入假模型后应用其余部分为真**（AC28）
  验证：断言权限引擎、Skill 管理器、命令注册表、记录器均为真实实例，
  且工具注册中心包含真实工具。
  这条防的是「为了好测把半个系统换成假的」——那样测出来的绿是假绿。
- [ ] **模型注入参数可选，不传时行为与现状一致**（AC29）
  验证：保留一组不传该参数的装配调用并断言正常装配。
  ⚠️ 全量测试的判据分两个时点：**第二段结束时应恰好 714**；
  **终局按 AC40 口径**（714 + 新增，既有 714 条一条不少）。不要在终局要求「仍 714」。
- [ ] **独立模式自定义模型的子对话也走假模型**（AC30）
  验证：预置一个声明了自定义模型的独立模式 Skill 并驱动它执行，断言——
  ① 全程无外部连接（假工厂的调用计数可证）；

## 八、端到端场景【手测】

> 以下场景需在真实终端里跑，逐条记录**实际观察结果**。
> 场景 1–3 是本轮的价值验证（闭环到底能不能用），场景 4–5 是边界，场景 6 是回归确认。
>
> **两条通用前提**：
> - 需要退出后读记录的场景（1、2、3、5）一律加 `--keep-workspace`，**读完手工删除**；
> - `--mode scripted` 必须配 `--script MOD:ATTR`，用交付时提供的可复用脚本模块属性，
>   完整命令行以实际交付为准。

- [ ] **场景 1（闭环基本可用）**
  起一个 scripted 宿主 → 用客户端 `send` 一条会触发确认面板的请求 → `wait` →
  观察它返回 `pending` → `status` 读面板原文与四个选项 → 自行判断后 `answer` →
  `wait` 到 `idle` → `observe` 读这一轮发生了什么 → 再 `send` 第二条 → `quit`。
  **通过判据**：全程不需要看终端界面、不需要人点任何东西；
  `observe` 的输出足以看清「模型这轮收到了哪些工具、调了什么、权限走了哪层、
  界面显示了什么」。
- [ ] **场景 2（真实模型驱动）**【需凭据】
  `--mode live --keep-workspace` 起宿主 → 提一个真实请求（如「看看这个项目的测试
  怎么组织的」）→ 逐轮 `wait` / `status` / `observe` 观察 →
  遇到确认面板时**自行判断该不该放行** → 跑完 → `quit`。
  **通过判据**：能在不看界面的情况下判断模型行为是否合理；
  面板决策确实由驱动方做出且记录里标为外部驱动者。
  ⚠️ **场景结束后必须删除该工作区与记录文件**——它含真实模型往返与工具输出原文，
  若模型读过配置文件则**可能含明文密钥**。勿留存、勿外传、勿贴进任何地方。
- [ ] **场景 3（改代码 → 重跑的闭环）**
  跑完场景 1 → 记下 `status` 里的代码版本标识 → **修改一处产品源码** →
  **重启宿主** → 再取标识，确认**已变化** → 重跑同一条 `send` →
  对比两次的 `observe` 输出。
  **通过判据**：重启后标识确实不同。
  ⚠️ 不重启的话当前宿主的标识**不会变**（启动时算一次并缓存），这是设计不是缺陷。
- [ ] **场景 4（宿主异常、陈旧发布信息与多宿主）**
  ① 起一个宿主 → **强制杀掉它**（不走 `quit`）→ 再发一条指令，
  断言立即得到「宿主已不在」的可读提示与清理办法，**不是超时等待**；
  按提示清理后能正常起新宿主。**顺带确认强杀会残留临时工作区，需一并手工删。**
  ② 客户端 `wait` 挂起期间强杀宿主，断言得到「宿主在处理本指令期间退出了」的
  可读提示而非异常堆栈。
  ③ 同时起两个宿主 → 不带 `--pid` 发指令，断言提示「有 N 个宿主，请用 --pid 指定」；
  带 `--pid` 能分别驱动；`hosts` 子命令能列出两者。
- [ ] **场景 5（面板挂着时退出）**
  用 `--keep-workspace` 驱动到弹出确认面板 → **不应答，直接 `quit`**。
  **通过判据**：宿主**干净退出（不是挂死）**；到发布信息记录的工作区路径下
  读记录，能看到那条被强制结算的交互（来源为强制结算）。读完手工删除该目录。
  「工作区被自动清理」另用一次不带 `--keep-workspace` 的运行确认。

  > ⚠️ **判据更新（2026-08-05，全阶段复测）**：原文写「宿主在**数秒内**干净退出」，
  > 实测 **live 模式下约 31 秒**（`docs/e2e-sweep/testing-p1a-driver.md` 观察 O11）。
  > **这不是挂死，是刻意等待**：`control.py` 的 `shutdown_on_main` 在 live 模式下会
  > `join(timeout=30.0)` 等自动记忆线程收敛——那个线程是 daemon，不等就会被进程退出截断，
  > 记忆写一半。所以判据改成只看「干净退出」，不设秒数上限；
  > **真正的挂死表现是超过 30 秒上限后仍不退出**（原始 bug 的形态是永不返回、
  > 靠外部 40 秒超时杀掉）。scripted 模式不等记忆线程，仍是零点几秒。
- [ ] **场景 6（对真实使用零影响）**
  正常 `rhine` 启动一次（不经驱动设施），跑一次带工具调用的对话，逐项观察：
  ① 流式输出逐块出字；② 工具行逐个出现并正常转色；③ 确认面板可弹出、四个选项可选；
  ④ 状态栏正常。
  **通过判据**：与本轮改动前肉眼无差别。产品侧只动了三处、且都有缺省值，
  这条是它的最终确认。
