# C11 Skill 系统 Checklist

> ⚠️ **本清单的一部分已被 `docs/c11/align/` 的对齐改造作废。**
>
> 那次改造把 Skill 系统对齐到 Agent Skills 开放标准，三处语义变更让本清单里
> 相当一部分条目不再成立：
>
> | 已作废 | 现状 |
> | --- | --- |
> | 第四节整节「工具白名单」 | 收窄能力已移除；`allowed-tools` 改为**预授权**，判据见 `docs/c11/align/checklist.md` 第四节 |
> | 名字规则与保留词（F4 相关条目） | 命令名来自文件系统路径，字符集与长度不再校验 |
> | 层内同名去重（F29 相关条目） | 目录下命令名天然唯一，该失败原因已不存在 |
> | `mode` / `history_messages` 相关条目 | 换成 `context: fork`；带入尾部历史的能力已移除 |
> | 端到端场景 4（白名单收窄可观测） | 随收窄能力一并作废 |
>
> **未被上表覆盖的条目继续有效**，尤其两阶段加载、激活态、独立模式回流、
> 命令与热更新、安全边界几节。

> 状态：待批准（2026-07-26）
> 依据：已批准的 `docs/c11/spec.md`（AC1–AC38）、`plan.md`、`task.md`
>
> 每一项通过**运行代码或观察行为**验证，聚焦系统做什么，不检查代码写法——重构文件、改名函数但行为不变时，本清单应依然适用。
> 标记 **【自动】** 的可由单元测试覆盖；标记 **【手测】** 的需在 tmux 或真实终端里跑一遍真实对话。

## 一、Skill 定义与加载

- [ ] **写全六个 frontmatter 键的 Skill 能被正确加载**，各字段值与文件声明一致（验证：单测断言解析结果；AC1）【自动】
- [ ] **只写 `name` 与 `description` 时其余取缺省**：不收窄工具、共享模式、不带历史、用全局模型（验证：单测断言四个缺省值；AC1）【自动】
- [ ] **未知 frontmatter 键被忽略且不影响加载**（验证：加一个 `foo: bar` 仍加载成功；AC1）【自动】
- [ ] **`allowed_tools` 写成字符串而非列表 → 该 Skill 加载失败**，其余不受影响（验证：单测；AC1）【自动】
- [ ] **单文件型与目录型都能被发现**；目录型正确定位入口文件并记录其资源目录（验证：造两种形态各一份，都出现在 `/skills` 列表；AC2）【自动】
- [ ] **Skill 名字以 frontmatter 为准，与文件名不一致时以前者为准**（验证：文件名 `foo.md` 但 `name: bar` → 列表显示 `bar`；AC2）【自动】
- [ ] **同名 Skill 三层并存时项目级生效，且正文与白名单整份来自项目级**（验证：造两层字段互补的样本，断言不发生字段合并；AC3）【自动】
- [ ] **`/skills` 列表标注的来源层级正确**（验证：三层各放一个，列表显示三种来源；AC3）【自动】
- [ ] **低优先层被覆盖时不产生加载错误**（验证：`/skills` 的失败列表中无被覆盖项；AC3）【自动】
- [ ] **名字非法的 Skill 被拒绝加载**：含大写、含空格、含路径分隔符、超 32 字符、取值为保留子命令词（`reload`/`off`/`prompt`/`run`）五种，其余 Skill 不受影响（验证：单测逐种断言；AC4）【自动】
- [ ] **四种坏样本同时存在时程序正常启动**：frontmatter 语法损坏、缺必填字段、名字非法、目录型缺入口文件；其余 Skill 全部可用，`/skills` 能看到四条各自的失败原因（验证：造目录树后启动并执行 `/skills`；AC5）【自动 + 手测】
- [ ] **同层两份同名 Skill → 字典序在前的生效**，另一份在 `/skills` 中显示「与同层 X 重名」，且短命令只注册一条（验证：单测 + `/skills`；AC31）【自动】

## 二、两阶段加载

- [ ] **第一阶段清单含全部可用 Skill 的名字、说明与模式，且不含任何 SOP 正文**（验证：`/skills prompt` 观察清单段；AC6）【自动 + 手测】
- [ ] **清单超上限时被截断并标注省略条数**（验证：构造超过 200 行 / 25KB 的 Skill 集合后看 `/skills prompt`；AC6）【自动】
- [ ] **模型加载共享模式 Skill → 工具结果是一句简短确认，而非完整正文**（验证：让模型调用加载工具，观察工具行摘要与回灌内容；AC7）【自动 + 手测】
- [ ] **模型请求加载独立模式 Skill → 返回结构化错误并给出实际可用的入口**：短命令已注册时给短命令，未注册时给 `/skills run <name>`，**不得指向不存在的命令**（验证：两种情形各跑一次；AC7）【自动】
- [ ] **加载不存在的 Skill → 结构化错误并列出可用名字，循环继续不中断**（验证：让模型调一个不存在的名字；AC7）【自动 + 手测】
- [ ] **激活一个白名单极窄（如只含读文件）的 Skill 后，加载工具仍对模型可见**（验证：`/skills prompt` 的可见工具集含加载工具；AC8）【自动】

## 三、激活态

- [ ] **模型在第 N 轮激活 Skill → 第 N+1 轮请求即含其完整正文，此后每轮都在**（验证：假 Provider 编排两轮，断言第 1 轮的系统提醒不含 SOP、第 2 轮含；AC9）【自动】
- [ ] **用户经短命令激活的 Skill → 该次请求的第 1 轮即含其正文**（与模型路径的「下一轮」规则不同，F9 两条时机规则各有护栏；验证：断言首轮系统提醒已含 SOP；AC9）【自动】
- [ ] **单个正文超上限时被截断，且截断同时对模型与用户可见**：模型侧正文末尾有标注，用户侧有激活警告且 `/skills` 标记（验证：造一份超 300 行的 SOP；AC9）【自动 + 手测】
- [ ] **两种降级在用户侧可区分**：「正文被截断（超单体上限）」与「未注入（超总量上限）」措辞不同（验证：分别构造两种情形看 `/skills`；AC9）【自动】
- [ ] **先后激活两个 Skill → 两份正文都在且边界清晰可辨**（验证：`/skills prompt` 观察激活正文段；AC10）【自动 + 手测】
- [ ] **同一 Skill 连续激活两次 → 只有一份正文，位置为首次激活时的位置，参数取第二次的值**（验证：单测断言激活列表长度与顺序；AC32）【自动】
- [ ] **`/clear` 后已激活列表为空**（验证：激活后 `/clear`，再 `/skills` 看激活状态；AC11）【自动 + 手测】
- [ ] **`/skills off <name>` 只摘掉指定项，其余仍在；`/skills off` 无参清空全部**（验证：激活三个后分别执行；AC11）【自动 + 手测】
- [ ] **含 `$ARGUMENTS` 的 Skill 带参数调用 → 占位符被替换为原样参数**，含空格与引号时原样保留（验证：`/commit "修 A 和 B"` 后看 `/skills prompt`；AC12）【自动】
- [ ] **不含 `$ARGUMENTS` 的 Skill 带参数调用 → 参数出现在正文末尾的补充段，不被静默丢弃**（验证：同上；AC12）【自动】
- [ ] **激活目录型 Skill 后，注入内容含其资源目录绝对路径与随附文件相对路径清单**（验证：`/skills prompt`；AC13）【自动 + 手测】
- [ ] **模型能按该清单直接读取用户级 Skill 目录内的参考文档**（验证：让模型读一份放在用户级 Skill 目录里的 md，观察读取成功；AC13）【手测】

## 四、工具白名单

- [ ] **激活声明白名单的 Skill → 可见工具恰为白名单内容加加载工具**（验证：`/skills prompt` 的可见工具集段；AC14）【自动 + 手测】
- [ ] **再激活另一个白名单不同的 Skill → 可见工具为两者并集**（验证：同上；AC14）【自动】
- [ ] **再激活一个未声明白名单的 Skill → 可见工具恢复全量**（验证：同上；这同时验证 N10 所述的「白名单会塌缩、不是安全边界」；AC14/AC17）【自动】
- [ ] **卸载全部 Skill 后可见工具恢复全量**（验证：`/skills off` 后看 `/skills prompt`；AC14）【自动】
- [ ] **运行时注销某个白名单内的 MCP 工具后，下一轮工具集自动跳过它且不报错**（验证：单测模拟注册中心变化；AC14）【自动】
- [ ] **Plan Mode 与白名单 Skill 同时开启 → 可见工具为「白名单 ∩ 只读工具」加上加载工具与两个交互专用工具**（验证：开 `/plan` 后激活带白名单的 Skill，看 `/skills prompt`；AC15）【自动】
- [ ] **白名单写一个不存在的内置工具名 → 启动以非成功状态终止**，错误信息含 Skill 文件路径、具体工具名与版本错配提示（验证：造样本后 `python -m rhinecode`，看退出码与 stderr；AC16）【自动 + 手测】
- [ ] **该终止发生在任何 MCP 子进程创建之前**（验证：在配了 stdio MCP Server 的环境下触发该失败，**观察无孤儿子进程残留**；自动化时以「MCP 连接步骤未被执行」作为等价佐证；AC16）【自动 + 手测】
- [ ] **白名单写 `ask_user` / 加载工具名 → 正常启动，仅给「声明无效果」提示**（验证：造样本后启动；AC16）【自动】
- [ ] **白名单写 `mcp_add_server`（单下划线的内置工具）→ 正常启动，不被误判为笔误**（验证：造样本后启动；这是「校验窗口放错位置」的护栏；AC16）【自动】
- [ ] **白名单写一个未连接的 `mcp__` 工具 → 正常启动、有警告、该 Skill 可用且白名单中不含该项**（验证：造样本后启动并看 `/skills`；AC16）【自动 + 手测】
- [ ] **白名单只写一个未连接的 MCP 工具 → 该 Skill 激活后不收窄工具集，并给出警告**（验证：`/skills prompt` 显示未收窄；AC17）【自动】

## 五、共享模式

- [ ] **执行共享模式 Skill 后，其推理文本与全部工具调用记录都出现在主对话历史中**（验证：跑 `/commit`，观察聊天区完整过程；AC18）【自动 + 手测】
- [ ] **短命令的界面显示与模型历史分离**：界面与 `/resume` 回放显示用户原始输入（如 `/commit 修复登录超时`），模型历史中该条消息含 Skill 名、说明与参数三项（验证：跑一次后 `/resume` 回放观察；AC24）【自动 + 手测】

## 六、独立模式

- [ ] **执行独立模式 Skill 后，主历史新增的恰好是「一条自包含用户消息 + 一条结论助手消息」的配对**，子对话的工具调用与结果均不在主历史中，两条都已写入会话存档（验证：跑 `/review` 后 `/resume` 回放观察主历史；AC19）【自动 + 手测】
- [ ] **中途取消 → 助手消息位得到「已取消，本次 Skill 未产出结果」，配对结构仍成立，且界面出现可见提示**（验证：跑 `/review` 中途按 Esc；AC19）【自动 + 手测】
- [ ] **子对话跑满自身迭代上限 → 助手位得到对应原因文案，主循环随后仍可正常继续若干轮**（验证：单测构造死循环 Skill；AC19/AC33）【自动】
- [ ] **计划被拒 → 助手位得到「计划未获批准，本次 Skill 未执行」**，而不是把子对话的前言正文误当结论回流（验证：开 `/plan` 后跑独立 Skill 并拒绝计划；AC19）【自动 + 手测】
- [ ] **子对话触达上下文上限或流出错 → 助手位得到「模型请求出错（含上下文超限），本次 Skill 未产出结果」**，配对结构仍成立；界面上用户可见反馈**有两处**：红色错误行 + 系统提示行（验证：单测构造 stream error；这是 spec F21 要求「不参与第二层摘要就必须说明超窗兜底」的验收落点；AC19）【自动】
- [ ] **`history_messages` 为 0 时，子对话拿到的历史恰为一条用户消息且内容与主历史那条同源**（验证：单测；AC20）【自动】
- [ ] **声明带入若干条历史、且主历史尾部恰是「含工具调用的助手消息 + 其工具结果」时，子对话拿到的历史不含被拆散的半对**，末尾仍追加了那条用户消息（验证：单测构造该边界；AC20）【自动】
- [ ] **无任何用户消息的历史 + 声明带入 N 条 → 不带入任何历史**（而不是带入全部；验证：单测；AC20）【自动】
- [ ] **独立模式执行期间界面能看到子对话的工具调用进度**（验证：跑 `/review` 观察工具行逐个出现；AC21）【手测】
- [ ] **子对话的系统提示含本 Skill 正文、不含主对话其它已激活 Skill 的正文**（验证：单测断言子动态段内容；AC21）【自动】
- [ ] **子对话触发需要确认的工具时确认面板照常弹出**（验证：跑一个会写文件的独立 Skill；AC21）【手测】
- [ ] **子对话的消息未写入会话存档文件**（验证：跑完后查看 `.rhinecode/sessions/` 当前存档，只有那两条配对消息；AC21）【自动 + 手测】
- [ ] **子对话中产生的超大工具结果被上下文管理的第一层存盘替换为占位**，且第二层摘要未被调用（验证：单测；这是「子对话参与第一层、不参与第二层」这一决策的唯一收益点；AC21）【自动】
- [ ] **整条执行结束后自动笔记钩子照常触发一次**（针对主历史，不是子对话；验证：单测断言钩子被调用；AC21）【自动】
- [ ] **独立模式 Skill 声明 `model` 时子对话确实使用该模型**（验证：单测断言用了不同的 Provider 实例；AC22）【自动】
- [ ] **共享模式 Skill 声明 `model` 时在启动扫描阶段即给出警告，且激活后仍用全局模型**（验证：造样本后启动看提示；AC22）【自动 + 手测】
- [ ] **独立模式子对话的工具集中不含加载工具**；强行构造一次调用时返回结构化错误且子对话继续（验证：单测；AC23）【自动】
- [ ] **先请求取消、再执行独立 Skill → 子对话不会开局即被取消**（验证：单测；这是取消信号未重建会踩的坑；AC19 相关）【自动】

## 七、命令、热更新与生命周期

- [ ] **每个短命令名可用的 Skill 都有对应短命令并出现在 Tab 补全候选中**（验证：输入 `/` 后按 Tab 观察菜单；AC24）【自动 + 手测】

- [ ] **三条不同 Skill 的短命令各自执行正确的那一个**（验证：依次执行三条，观察各自跑对；这是闭包绑定错误的护栏——错了会表现为「菜单显示 A、执行却跑 B」；AC24）【自动】
- [ ] **与内置命令重名的 Skill → 启动有警告、该短命令未注册、内置命令行为不变**（验证：造一个 `name: context` 的 Skill，启动后 `/context` 仍是上下文报告；AC25）【自动 + 手测】

- [ ] **`/skills` 五种形态各自输出符合规定内容**（无参列表 / `reload` / `off [name]` / `run <name> [参数]` / `prompt`；AC26）【自动 + 手测】
