# C13 人眼验收步骤

三条判据机器验不了，需要你在真实终端里跑。预计 **15 分钟**，会花一点 API 费用
（子 Agent 每次调研约 1–4 万 token）。

## 准备（一次）

```bash
cd G:\RhineCode-Agent
python docs/c13/acceptance/setup_manual.py
```

它在 `~/rhine-c13-manual/` 下造一个**独立的小项目**（21 个 Python 文件，
其中 4 个含 `RETRY_LIMIT`），**完全不碰 RhineCode 本仓库**。里面预置了两个项目级角色：

| 角色 | 用途 |
| --- | --- |
| `auditor` | 只读审查 |
| `counter` | **逐个文件读**的清点员，故意做得慢——场景 A 与 B 都需要它别太快结束 |

然后：

```bash
cd C:\Users\Administrator\rhine-c13-manual
rhine --trace
```

`--trace` 会把过程记进 `.rhinecode/traces/`，测完把那个文件给我，我可以交叉核对
你肉眼看到的和程序实际做的是否一致。

## ⚠️ 先看这条：`Ctrl+B` 与 tmux 冲突

**`Ctrl+B` 是 tmux 的默认前缀键。** 如果你在 tmux 里跑，这个键会被 tmux 吃掉、
**根本到不了程序**——那不是功能坏了。

三个选择：

1. **在 tmux 之外测**（Windows Terminal / PowerShell 窗口直接跑），最省事；
2. 在 tmux 里**连按两次** `Ctrl+B`（tmux 的约定：前缀键按两次会向程序发送一个字面的前缀键）；
3. 告诉我换一个键——**这是我选键时的疏漏**，这个项目验证 TUI 的惯例恰恰是用 tmux。
   候选：`Ctrl+G`（未被 Textual 的 `Input` 占用）或 `Alt+B`。

我查过了：`ctrl+b` 在 Textual 的 `Input` 里**没有**被绑定，所以在非 tmux 环境下它能正常冒泡到程序。

## 场景 A —— `Ctrl+B` 手动切后台（AC17c）

### 步骤

1. 启动后**先别输入**，看第一屏。
2. 输入并回车：

   ```
   用 counter 角色清点一下 RETRY_LIMIT 在这个项目里的分布，我要知道它出现在哪几个文件里。
   ```

3. 等工具行出现「运行中」（大约 3–8 秒后）。
4. **在它跑完之前按 `Ctrl+B`。**（`counter` 要逐个读 21 个文件，通常要跑 1 分钟以上，
   窗口很充裕。）
5. 立刻输入另一句话，比如 `顺便告诉我这个项目一共有多少个 py 文件`，看主对话还能不能正常应答。
6. 等一会儿，看子 Agent 完成的通知行。
7. 再输入 `counter 清点的结果是什么？`，看模型能不能引用它的结论。

### 通过的样子

- [ ] **第一屏**出现「发现 2 个项目级子 Agent 角色：auditor、counter……评审 .rhinecode/agents/ 应与评审代码同等对待」
      —— 这条同时是 AC4 的**醒目程度**判据：你觉得它够不够显眼？
      （设计上它走的是普通灰色通道，比 C12 的 Hook 橙色警告低一档）
- [ ] 按下 `Ctrl+B` 后**立刻**出现一行：`子 Agent [xxxxxx] 已转入后台，跑完后结论会自动送达。`
- [ ] 那一行工具行随即收尾，**主对话立刻可以继续输入**（不用等子 Agent）
- [ ] 右下角状态栏出现 `子Agent:1`
- [ ] 第 5 步那句话能正常得到回答
- [ ] 子 Agent 跑完时自动出现一行 `子 Agent counter[xxxxxx] 已完成（N 轮 · Ns）——结论将在下一轮对话中自动交给 AI。`
- [ ] 状态栏的 `子Agent:1` 随之消失
- [ ] 第 7 步模型能说出清点结果（说明结论真的交付了）

### 不通过的样子 / 怎么区分

| 现象 | 多半是什么 |
| --- | --- |
| 按键完全没反应 | 你在 tmux 里（见上面那条），或终端吞了这个键 |
| 提示「当前没有正在前台等待的子 Agent」 | 你按晚了——它已经自己跑完，或已超 60 秒自动转后台。重来一次，早点按 |
| 按了之后界面卡住不动 | **这是真问题**，请记下来 |

> 顺带：如果你**不按** `Ctrl+B`，等满 60 秒它会**自动**转后台并出一行「前台等待超时，
> 已转入后台继续运行」。想的话可以顺手看一眼（那是 AC17b，机器已验过）。

## 场景 B —— 并发上限（AC18）

### 步骤

输入这一句（一次说清要 4 个，且都要后台）：

```
同时开 4 个后台子 Agent，都用 counter 角色，分别清点这四样东西：
1) RETRY_LIMIT 出现在哪些文件
2) TIMEOUT_SECONDS 出现在哪些文件
3) POOL_SIZE 出现在哪些文件
4) 一共有多少个 def 定义
四个都用 background=true。
```

### 通过的样子

- [ ] 前 3 个委派成功，工具行显示「后台 [xxxxxx]」
- [ ] **第 4 个明确失败**，回灌文本里出现类似
      `同时运行的子 Agent 已达上限 3 个，当前在跑：counter[aaa]、counter[bbb]、counter[ccc]`
      —— **重点看它有没有列出那三个的标识**（模型据此才知道等谁，而不是盲目重试）
- [ ] 状态栏显示 `子Agent:3`
- [ ] 模型没有卡死，会告诉你「先跑 3 个，等其中一个完成再开第 4 个」之类
- [ ] 输入 `/agents`，能看到四条任务记录（3 个在跑 / 已完成 + 1 个没建起来的不出现）

### 可能的偏差（不算失败）

模型可能**不肯一次发 4 个**，而是分两轮发。那样就撞不上上限。
遇到这种情况，等前 3 个都还在跑的时候，你再单独发一句
`再开一个 counter 后台子 Agent 数一下 import 语句有多少行`，同样能触发。

## 场景 C —— 连续运行 10 分钟（AC25e）

### 步骤

接着上面的会话继续用，**不要重启**，做完这一串（约 10 分钟）：

1. 等场景 B 的 3 个后台任务全部完成。
2. 输入 `/agents`，看报告。
3. 再开 2 个后台委派（随便找点东西清点）。
4. 在它们跑的时候，正常和主对话聊两轮（问点不需要委派的问题，比如 `README 写了什么`）。
5. 输入 `/agents cancel all`，取消掉还在跑的。
6. 再开 1 个前台委派，等它自然跑完。
7. 输入 `/clear`，看提示。
8. 再开 1 个委派，确认清空之后一切照常。

### 通过的样子

- [ ] 全程界面**不卡顿**：打字有即时回显，滚动流畅
- [ ] 聊天区**没有残留的「运行中」工具行**——每一行最终都变成了完成 / 失败 / 已转后台
- [ ] 状态栏的 `子Agent:N` **始终与实际相符**，任务全部结束后该段**消失**（不是显示 `子Agent:0`）
- [ ] 每个任务的完成通知**只出现一次**，没有重复刷屏
- [ ] `/agents` 报告读起来清楚：角色段能看懂每个角色能用什么工具、权限档位的「声明值 → 实际生效值」；
      任务段能看出每条跑了多久、多少轮、结论首行
- [ ] `/agents cancel all` 后提示「已请求取消 N 个子 Agent 任务」，且状态栏计数随之归零
- [ ] `/clear` 时若还有任务在跑，提示是「对话历史已清空（同时取消了 N 个正在运行的子 Agent）」；
      没有任务在跑时是「对话历史已清空」（**逐字如此，不带括号**）
- [ ] 清空后再委派一切正常

### 重点盯这几个

它们是本章最可能出问题、而机器又不好验的地方：

1. **界面冻结** —— 后台线程与主线程共用了不少组件（Hook 引擎、权限引擎、
   行为记录器、任务表）。设计上后台线程绝不碰界面（改成了定时轮询），
   但真出问题的话现象就是 TUI 整个不动了。
2. **残留的「运行中」行** —— 说明某条工具行没被收尾。
3. **状态栏计数不归零** —— 说明任务状态没走到终态，或轮询漏了一次。
