# C13 子 Agent 系统 Checklist

> 每一项通过**运行代码或观察行为**来验证，聚焦系统行为而非实现结构。
> 括号里是验证方式。
>
> **执行者标注**：
> - 🤖 = Claude 自己跑完（单元测试 / 脚本模式驱动设施，无需真实模型）
> - 👤 = 需要真实模型或人眼判断（花用户的钱、或判据本身是「读起来对不对」）

## 一、角色定义与加载

- [ ] 🤖 **AC1a** 一个只写了 `description` 的角色文件能被加载并成功委派
      （验证：`tests.test_subagent_parser` + `tests.test_subagent_service` 全绿）
- [ ] 🤖 **AC1b** `disallowed-tools` 与 `disallowed_tools` 两种写法产生**完全相同**的解析结果
      （验证：同一份定义只改写法，断言两个 `AgentSpec` 相等）
- [ ] 🤖 **AC1c** 写了本章不支持的字段（`memory` / `isolation` / `skills` 等）时，角色**仍可用**，
      且 `/agents` 报告里出现**含该字段名**的提示
      （验证：遍历 `UNSUPPORTED_FIELDS` 逐个断言警告文本含该键名）
- [ ] 🤖 **AC2** 同名角色在项目级与用户级各有一份时，生效的是项目级；`/agents` 显示的来源层
      与实际生效的配置一致（验证：造两层同名定义、`tools` 故意写不同，断言生效的是项目级那份）
- [ ] 🤖 **AC3a** 目录里放一个坏 YAML 文件，其余角色照常可用、**程序照常启动**，
      错误在 `/agents` 里可见（验证：`tests.test_subagent_discovery` + 启动一次宿主不崩）
- [ ] 🤖 **AC3b** 同层重名时两份都在报告里可见，且报告说明了哪份生效
      （验证：断言报告文本同时含两个路径与「生效」字样）
- [ ] 🤖 **AC4** `/agents` 报告里每个角色都标出来源层，项目级 / 用户级 / 内置三种都能区分
      （验证：三层各放一个角色，断言报告里三个标签都出现）
- [ ] 🤖 **AC5** 缺省配置（不改任何权限规则）下委派给 `explorer` 能跑完并回流结论
      （验证：脚本模式驱动设施跑一次委派，`observe` 到任务状态为已完成且结论非空）

## 二、委派入口与可见性

- [ ] 🤖 **AC6a** 模型可见的工具数量在「加载 0 个角色」与「加载 5 个角色」两种情况下**相同**
      （验证：两种目录布局各起一次，比对工具名集合完全相等）
- [ ] 👤 **AC6b** 主 Agent 在**无人点名**的情况下会主动选择委派
      （验证：真实模型下发一句「找出项目里所有调用了权限引擎的地方」，
      观察它是否调用 `run_agent` 而不是自己 grep 二十次）
- [ ] 🤖 **AC7a** 定义式子 Agent 的系统提示**不含**主对话的八模块
      （验证：断言传给 Provider 的 `stable` 逐字等于角色正文）
- [ ] 🤖 **AC7b** 工具集含网络访问工具时「外部不可信内容」段出现；不含时**不出现**
      （验证：同一角色两种 `tools` 声明各跑一次，断言 dynamic 段的差异恰好是那一段）
- [ ] 🤖 **AC8a** 分支式子 Agent 能引用父对话里提过的内容而**无需在任务描述里重述**
      （验证：父历史里放一条「项目代号叫 Rhine」，任务描述只说「说出项目代号」，断言结论含该词）
- [ ] 🤖 **AC8b** 委派之后主对话新增的消息**不进入**子 Agent 视野
      （验证：委派后立刻往主 history 追加一条，断言子 Agent 收到的历史长度不变）
- [ ] 🤖 **AC8c** 分支式**总是**走后台，即使显式传 `background=false`

## 三、运行时隔离

- [ ] 🤖 **AC9a** 子 Agent 的历史、工具集、迭代计数与主对话相互不可见
      （验证：子 Agent 跑完后主 `history` 长度只增加了「结论交付」那一条）
- [ ] 🤖 **AC9b** 子 Agent 用满自己的轮次预算后，主对话的预算**不受影响**
      （验证：角色 `max_turns: 2` 跑到上限，随后主对话仍能跑满自己的轮次）
- [ ] 🤖 **AC10** 子 Agent 正常完成时回流最后一段结论；被取消或触达上限时回流**说明文本**
      而非中途的前言（验证：造「最后一条 assistant 是计划前言 + stop_reason 非 COMPLETED」的场景）

## 四、工具过滤

- [ ] 🤖 **AC11a** 子 Agent 的工具集里查不到委派工具与 Skill 加载工具
      （验证：遍历 `GLOBAL_DENIED_TOOLS` 逐个断言不在 `allowed` 里）
- [ ] 🤖 **AC11b** 角色白名单之外的工具，即使模型调用也被**拒绝**（不只是没发给它）
      （验证：构造一次白名单外的工具调用，断言 outcome 为「本轮不可用」而非 executed）
- [ ] 🤖 **AC12** 角色 `tools` 里全写错名字时，委派**立即失败**并说明哪些名字没解析成工具，
      且**没有起过线程、没有发过任何 API 请求**
      （验证：假 Provider 计数为 0、任务表为空）

## 五、权限

- [ ] 🤖 **AC13a** 缺省档下委派一个要写文件的任务，写入被自动拒绝，
      且子 Agent 收到的是**引导性理由**而非 `DENIED_BY_USER_FEEDBACK`
      （验证：断言回灌文本是 `DENIED_NON_INTERACTIVE_FEEDBACK`）
- [ ] 🤖 **AC13b** 同一任务在用户配了对应 allow 规则后能成功写入
      （验证：加一条 `allow: Write(...)` 后重跑，断言文件真的落盘）
- [ ] 🤖 **AC13c** 非交互拒绝**不会**禁掉子 Agent 下一轮的工具
      （验证：被拒后的下一轮请求 `tools` 非空；反证：`interactive=True` 同场景下为 `None`）
- [ ] 🤖 **AC14a** 角色声明 `permissive`、主对话处于默认档时，实际生效为**默认档**，
      被声明放行的操作照样落进灰色地带被拒
- [ ] 🤖 **AC14b** 子 Agent 跑完后**主引擎的档位没变**
      （验证：跑前跑后断言 `engine.mode` 相同——这是「后台线程静默改主对话权限」的反证）
- [ ] 🤖 **AC14c** `/agents` 同时显示权限档位的声明值与实际生效值
- [ ] 🤖 **AC15** 由 Skill `allowed-tools` 授予的回合级预授权**不会**被子 Agent 继承
      （验证：主引擎 `grant_turn_rules` 后启动子 Agent，断言其引擎 `turn_rules` 为空）
- [ ] 🤖 **AC15b** 用户在主对话选过「本会话放行」的规则**对子 Agent 生效**
      （验证：往 `session_rules` 追加后启动子 Agent，断言该操作被放行——这是刻意的，
      与 AC15 的区别是「明确授予 vs 绑在某次执行上」）

## 六、后台任务

- [ ] 🤖 **AC16** `/agents` 能看到本次运行发起过的全部任务及其状态、轮次与用量
- [ ] 🤖 **AC17a** 委派工具**立即返回**，即使子 Agent 要跑很久
      （验证：慢子 Agent + 断言 `delegate` 耗时 < 0.2 秒）
- [ ] 🤖 **AC17b** 同一轮里的多个委派**并行**
      （验证：三个各 0.4 秒的子 Agent 总耗时 < 0.9 秒——串行会是 1.2 秒以上）
- [ ] 🤖 **AC17c** 缺省委派时循环在收工前等它、注入结论后再跑一轮；
      `background=true` 时循环**不停留**（反证：没有它，一个「无条件等所有任务」
      的实现也能过前一条）
- [ ] 🤖 **AC17d** 等待期间置取消信号能**立刻**结束本轮
- [ ] 🤖 **AC18** 已有 3 个任务在跑时，第 4 次委派**立即失败**并说明当前在跑的是哪几个
- [ ] 🤖 **AC19a** 后台任务完成时聊天区立刻出现通知行（验证：驱动设施 `observe` 到该行）
- [ ] 🤖 **AC19b** 结论在**同一次运行内**就能进入某一轮的请求体，**不需要用户插话**
      （验证：子 Agent 在主对话跑到第 2 轮时完成，断言后续某轮的请求体里含它。
      这是「交付点必须在迭代级」的唯一有效判据——挂在「每条用户消息一次」的
      实现会在这里失败）
- [ ] 🤖 **AC19c** **再下一轮仍能引用**——证明它进了历史而不只是一次性提醒

      这一条是本章最容易做错的地方，用系统提醒实现会在这里失败）
- [ ] 🤖 **AC20a** `background=true` 的任务在主对话按 `Esc` 后**照常跑完**
- [ ] 🤖 **AC20b** `/clear` 时未完成任务被取消且告知数量
- [ ] 🤖 **AC20c** `/agents cancel <标识>` 能取消单个任务，`/agents cancel all` 取消全部

## 十二、端到端场景

- [ ] 🤖 **场景 1（主线）** 委派 `explorer` 调研 → 前台完成 → 结论回流
      「委派 explorer 找出项目里所有实现了 Tool 抽象的文件」
      → 聊天区出现一行任务状态 → 完成后显示结论 → `/agents` 里该任务为已完成
- [ ] 🤖 **场景 2（后台闭环）** 显式后台委派 → 主对话继续 → 通知 → 引用
      委派时指定后台 → 工具立刻返回标识 → 主对话发另一条消息并得到回复
      → 子 Agent 完成后聊天区出通知行 → 再发一条消息，模型能引用结论
- [ ] 🤖 **场景 3（权限边界）** 委派一个要写文件的任务给只读角色
      → 写入被自动拒绝 → 子 Agent 在结论里**说明这一步需要用户授权**（而不是反复重试）
      → 主引擎档位未变
- [ ] 🤖 **场景 4（分支式）** 主对话里聊出一段上下文 → 分支式委派「接着刚才的分析继续」
      → 子 Agent 无需重述背景即可作答 → 强制走后台
- [ ] 🤖 **场景 5（失败路径）** 委派给不存在的角色 → 失败信息里列出可用角色
      → 模型据此改用正确的角色名重试成功
- [ ] 🤖 **场景 6（并发上限）** 连开 3 个后台任务后再委派 → 明确失败并说明在跑的是哪几个
- [ ] 👤 **场景 7（真实模型的委派判断）** 不点名的调研类请求下，模型主动委派而非自己硬做
      （这条是 C11「Skill 欠触发」同类的系统性偏差，只能用真实模型判）
- [ ] 👤 **场景 8（真实模型的结论质量）** `explorer` 的结论是否**自包含、可直接用**
      （判据是读起来对不对，机器验不了）

## 备注：哪些必须留给用户

按项目既有约定，只有**必须人眼**与**花用户钱**的才交给用户跑。本章共 4 条 👤：

| 条目 | 为什么机器验不了 |
| --- | --- |
| AC4 | 启动提示的**醒目程度**是人眼判据，机器只能验文本存在 |
| AC6b / 场景 7 | 模型会不会主动委派，只有真实模型能答 |
| AC25e | 长时间运行的手感 |
| 场景 8 | 结论质量 |

其余 **50 余条全部由 Claude 用单元测试与脚本模式驱动设施跑完**，不占用用户时间、不花 API 费用。
