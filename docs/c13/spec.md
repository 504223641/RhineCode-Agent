# C13 子 Agent 系统 Spec

## 背景

主对话现在是**唯一**的执行上下文。一次「找出项目里所有用到 XX 的地方」会读二十个文件，
这些内容全部沉淀在主历史里，此后每一轮请求都要重新发一遍——直到 C8 的压缩把它们摘掉，
而摘要本身也要花一次 LLM 调用。

C11 的 `context: fork` Skill 已经证明「开一条子对话、只回流结论」这条路走得通，
但它有三个限制：

1. **必须由一个写好的 Skill 承载**——不能临时委派一个任务；
2. **同步阻塞主对话**——跑完之前用户什么都做不了；
3. **角色不可配置**——工具集、模型、轮次预算全是硬编码。

C13 把这条路径从「Skill 的一个执行模式」提升为**独立的委派能力**。

## 目标

1. 主 Agent 能把一个子任务连同一段任务描述委派出去，子任务在**独立的对话上下文**里跑完，
   只有结论回到主历史。
2. 委派对象可以是**预定义角色**（有名字、有系统提示、有受限工具集、有独立的模型与轮次预算），
   也可以是**当前对话的一个分支**（继承父历史，无需重新交代背景）。
3. 委派**永不阻塞**，多个子任务天然并行；跑完后结论主动回到主 Agent 手里，
   **在同一次运行内**就能用上，不需要主 Agent 记得去取、也不需要用户插话。
4. 子 Agent 的能力**只会比主对话更小**，永远不会更大——这条要能被逐层论证，而不是靠约定。
5. 角色定义是**纯文本文件、多来源加载、同名覆盖**，可随代码仓库分发，也可跨项目复用。

---

## 功能需求

### 一、角色定义与加载

**F1 角色定义格式**——一个角色是一个 Markdown 文件：YAML frontmatter 描述配置，
正文是该角色的系统提示。字段如下，**只有 `description` 必填**：

| 字段 | 必填 | 语义 |
| --- | --- | --- |
| `name` | 否 | 角色标识。**缺省时取文件名**（去扩展名） |
| `description` | 是 | 什么时候该委派给它。这是主 Agent 选择角色的**唯一依据** |
| `tools` | 否 | 工具白名单。省略即继承「主对话当前可见的工具集」 |
| `disallowed_tools` | 否 | 工具黑名单，在白名单结果上再减 |
| `model` | 否 | 模型。`inherit` 或具体模型标识；缺省等同 `inherit` |
| `max_turns` | 否 | 本角色的迭代上限。缺省 15，且**被硬上限夹住**（不得超过主对话的 25） |
| `permission_mode` | 否 | 声明的权限档位。缺省 `inherit`，实际生效见 F16 |

字段名的**连字符与下划线两种写法都要认**（`disallowed-tools` 与 `disallowed_tools` 等价），
理由与 C11 相同：从别处复制来的定义文件不该因为一个字符写法而加载失败。

**未登记的字段只警告、不阻断**：Claude Code 的角色定义有 `skills` / `memory` /
`isolation` / `color` 等本章不支持的字段（见「不做的事」），遇到它们要在 `/agents` 里
明确告知「本项目不支持该字段，已忽略」，而不是静默丢弃或加载失败。

**F2 三层加载与同名覆盖**——按优先级从高到低扫描三个来源，同名角色高优先层覆盖低优先层：

| 层级 | 位置 | 说明 |
| --- | --- | --- |
| 项目级 | `<项目根>/.rhinecode/agents/` | 随代码仓库分发，团队共享 |
| 用户级 | `~/.rhinecode/agents/` | 跨项目复用 |
| 内置 | 随包分发 | 本章只有 `explorer`（F5） |

**身份以 `name` 为准，缺省回落到文件名**——这与 C11「命令名来自文件系统路径」的口径
**刻意不同**。理由：Claude Code 的角色文件把身份放在 `name` 上、允许文件名不匹配，
若我们强行改用路径，从官方生态复制来的定义会因为「文件名与 name 不一致」而变成另一个角色，
用户按 `description` 里写的名字去委派会找不到。代价是同层内可能重名，处理见 F3。

**F3 单个角色失败不阻断**——坏 YAML、缺 `description`、读不出来、目录不存在，
都只影响它自己，其余角色照常可用；目录不存在直接当空层，不算错误。
同一层内出现重名时**保留字典序靠前的那个**、另一份记一条警告，两者都在 `/agents` 里可见——
不静默择一，因为用户看到的现象会是「我明明写了这个角色却是另一套配置」。

**F4 项目级角色的可见性**——项目级角色随代码仓库分发，`git clone` 一个仓库
再启动就可能多出几个主 Agent 可委派的角色。它们的来源层必须在 `/agents` 报告里
逐个可见（`项目级` / `用户级` / `内置`）。

> **修订记录（开发期）**：本条原为「每次启动都在聊天区提示『发现 N 个项目级角色』」，
> 与 C11 的项目级 Skill、C12 的项目级 Hook 同构。**已按用户要求移除**——
> 启动提示占聊天区首屏，而这条信息的时效性没有 C12 的 Hook 那么强
> （Hook 动作直接执行、不经模型；角色正文只是发给模型的文本，它指挥的每个
> 工具调用照样过五层权限管线）。代价是这条信息只剩 `/agents` 一个入口，
> 用户不主动查就看不到。

**F5 三个内置角色**——对标 Claude Code 的 `Explore` / `Plan` / `general-purpose`：

| 角色 | 工具 | 档位 | 轮次 | 回答的问题 |
| --- | --- | --- | --- | --- |
| `explorer` | 三个只读工具 | 严格 | 15 | 现在是什么样（定位、清点、汇总事实） |
| `planner` | 三个只读工具 | 严格 | 15 | **接下来该怎么做**（改动清单、顺序、连带影响、风险） |
| `general-purpose` | **继承全部** | 继承 | 25 | 既要查又要动手的多步任务 |

`explorer` 与 `planner` **工具集完全相同**，差别全在描述与正文里——这与 Claude Code
的 `Explore` / `Plan` 同构（官方那两个也都是「read-only tools」）。因此 `planner`
的正文必须**显式点破它与调研员的区别**，否则它会退化成第二个 `explorer`、
产出一份事实清单而不是方案。

两个只读角色是缺省配置下**开箱即用**的（理由见 F15）；`general-purpose` 的写入类
操作在缺省档下会被自动拒绝，因此它的 `description` 里**必须写明这一点**——
那是主 Agent 选角色的唯一依据，不写会导致「把改代码的活派过去、收回一句需要授权」
这种白跑的往返。

内置角色**自身必须零警告**：它是用户看到的唯一范例，自己触发警告等于示范了
不该学的写法。

### 二、委派入口

**F6 统一的委派工具**——只向模型暴露**一个**工具，用一个类型参数分流两条路径。
工具列表因此始终稳定：不论加载了多少角色、有没有后台任务在跑，模型看到的工具数量不变。

参数：

| 参数 | 必填 | 语义 |
| --- | --- | --- |
| 类型 | 是 | `role`（定义式）或 `branch`（分支式） |
| 角色名 | 类型为 `role` 时必填 | 要委派给哪个角色 |
| 任务描述 | 是 | 交给子 Agent 的任务陈述，**必须自包含** |
| 后台标记 | 否 | 「这次我不要这个结果」。缺省 false；类型为 `branch` 时强制为 true（F8、F19） |

**F7 定义式路径**——从**空白对话**起步：子历史只有一条消息，即任务描述。
系统提示 = **角色正文 + 环境信息**，不含主对话的八模块结构化提示。

此外，所有子 Agent（含用户自定义角色）都会收到**两条产品级约定**：
① 用与任务描述相同的语言作答——角色正文里没有项目的语言约定，
`RHINE.md` 到不了子 Agent（实测过：中文项目里的子 Agent 开口说英文）；
② 结论会整段进入主对话上下文、因此要精炼——正文只说了「会被带回去」，
没说它有代价，模型于是没有精简的动机（实测过一份 9776 字符的方案）。
它们放在运行器而不是角色正文里，好让用户自定义的角色也盖得到。

**一处例外**：当该子 Agent 的最终工具集（F13 过滤之后）包含网络访问工具时，
必须追加「外部不可信内容」段。缺了它，子 Agent 能抓到投毒页面却没有那道约束——
这正是 web_fetch 扩展里踩过的坑（两个注入点漏一个就静默失效，界面上完全看不出来）。

**F8 分支式路径**——继承父对话历史的**快照**（发起那一刻的完整历史），
系统提示与工具集也继承主对话。它**强制为「这次我不要这个结果」**（F19 的 `background=true`），理由：
它继承的历史可能很长、跑得久，语义上就是一条「另开一路去查，回头再说」的支线；
让主对话的当前一轮停下来等它，与它的用途相悖。

继承的是快照而非引用——子 Agent 跑起来之后，主对话新增的消息**不会**进入它的视野，
反之亦然。

**F9 角色对主 Agent 可见**——已加载角色的「名字 + description」必须进入主对话的上下文，
否则模型不知道有谁可用。措辞要求**指令式而非公告式**（照 C11 的教训：
「命中就委派 / 用它替代你自己直接做 / 用户不必点名 / 拿不准就委派」），
委派工具自身的描述与角色清单**两处必须同口径**——它们是模型决定「要不要委派」时
读到的唯一两处文本，一处强一处弱等于白改。

### 三、运行时隔离

**F10 隔离与共享的分界**——每个子 Agent 有自己独立的：对话历史、系统提示、工具集、
权限追踪状态、迭代计数、token 用量统计、trace 作用域。
**共享**：模型客户端、工具注册中心、权限引擎（规则本身）、Hook 引擎、文件系统、工作目录。

**F11 跑到底模式**——子 Agent 非交互执行：模型本轮不再请求工具即视为完成，
结论取子历史中**最后一条非空的 AI 正文（整条，不是它的最后一段）**。
角色正文必须照这个口径写——实测过：正文写「最后一段是唯一会被带回去的」时，
模型在结论前面写了三段过程叙述，全都被带了回去。若因迭代上限、取消、流错误等原因非正常结束，
结论替换为对应的说明文本，**不能**把中途那段前言当成结论回流（C11 已踩过：
计划被拒时最后一条 AI 正文可能是「我打算这样做：……」，回流后用户会以为任务完成了）。

**F12 迭代预算独立**——子 Agent 的迭代上限由角色声明（缺省 15），与主对话的 25 各算各的。
一个跑偏的子 Agent 不该把主对话的预算一并耗光。

### 四、工具过滤

**F13 分层工具过滤**——最终工具集按顺序算出：

1. **全局禁止层**（任何子 Agent 都看不到，且调用了也拒绝）：委派工具自身（防无限嵌套）、
   Skill 加载工具（防间接嵌套——一个 `context: fork` 的 Skill 会再开一层子对话）、
   Plan Mode 的提问与计划提交工具（子 Agent 非交互，问不了人也没人审批）。
2. **角色限制层**：`tools` 白名单取交集，再减去 `disallowed_tools` 黑名单。
3. **后台附加层**：本章为空集。

> ⚠ **关于第 3 层的说明**：初步想法里列的三层防线中，
> 「后台白名单」在 Claude Code 里的存在理由是「后台 agent 无法交互，
> 因此要摘掉需要交互的工具」。而本章已定为**全程非交互**（F15），
> 「要不要等结果」也不影响子 Agent 能用什么工具，这一层因此没有独立内容。
> 本 spec 的选择是：**保留这一层的结构位置但当前为空集**，不为它造一批
> 「前台能用、后台不能用」的人为差异——那会让同一个角色在两种场景下行为不同，
> 而用户从配置上完全看不出来。

**F14 空工具集**——过滤后工具集为空时，该次委派**立即失败**并回灌明确理由
（哪些名字没解析成工具 / 被哪一层过滤掉了），不启动子 Agent。
一个零工具的子 Agent 只会白烧一次 API 调用然后说「我做不了」。

### 五、权限

**F15 ASK 一律自动拒绝**——子 Agent 的工具调用照样过五层权限管线，
但判定为 ASK（需人工确认）时**不弹面板**，直接判为拒绝并把结构化理由回灌给子 Agent。
不论前台后台，行为一致。

回灌文案要引导子 Agent**改用只读方式达成，或在结论里写明「这一步需要用户授权」**，
而**不是**重试或换工具绕过——这一点与 C6 的「用户面板里选拒绝」文案同源：
工具结果这个通道天生长得像技术失败，必须由文案把语义掰回来。

代价必须在文档里写明：**缺省配置下子 Agent 实际只能做只读的事**。
要让它能写文件或跑命令，用户必须在 `permissions.yaml` 里写下对应的 allow 规则，
或把主对话切到放行档之后再委派。

**F16 权限模式只能收紧**——实际生效档位 = min(主对话当前档位, 角色声明档位)。
角色可以把自己限成更严的档，但**声明放行档不产生任何提权效果**。
`/agents` 里要同时显示「声明值」与「实际生效值」，让用户看得出差异从何而来。

这与 C12「Hook 只能收紧不能放宽」是同一条原则，安全论证直接沿用：
`.rhinecode/agents/` 随代码仓库分发，一个 clone 来的角色文件**无法自行提权**。

**F17 权限追踪的继承边界**——子 Agent 继承配置里的规则与本会话已登记的放行规则
（那是用户明确授予的），但**不继承回合级预授权令牌**（Skill `allowed-tools` 授予的那种，
它绑在某一次执行上）。子 Agent 自己也不产生新的放行登记——它不弹面板，没有登记的入口。

### 六、后台任务

**F18 任务管理器**——追踪每个子 Agent 任务的：标识、类型与角色名、任务描述、
状态（运行中 / 已完成 / 失败 / 已取消）、起止时间、已用轮次、token 用量、
结论文本、结束原因。主对话与用户都通过它观察任务。

**F19 委派永不阻塞，等待交给循环**——`run_agent` 立即返回任务标识；
子 Agent 在自己的线程里跑，因此**同一轮里的多个委派天然并行**。

`background` 参数表达的是「**这次我要不要这个结果**」：

| 取值 | 含义 | 循环行为 |
| --- | --- | --- |
| 缺省（false） | 我要这个结果 | 模型准备自然结束时，若它还在跑，**循环停下来等它**，把结论注入后再跑一轮 |
| true | 这次我不要 | 循环不为它停留；结论在它跑完之后的下一条用户消息时送达 |

分支式委派强制为「不要」（spec F8）。

**等待不设体验意义上的超时**：跑子 Agent 就是在执行任务，与主 Agent 自己跑一遍
测试套件性质相同。唯一的逃生口是 `Esc`（取消整轮），因此等待必须能被取消信号
**立刻**打断。另有一个防线程挂死的兜底上限与「为子 Agent 停留的次数上限」，
两者都是安全网、不是给用户调的旋钮。

> **修订记录（开发期）**：本条原为「三种进入后台的方式：显式指定 / 前台等满
> 60 秒自动转 / 用户按 `Ctrl+B` 手动切」。真实使用中暴露出两个缺陷，
> 根因是同一个设计错误——**发起与等待被捆在了一起**：
>
> 1. 委派工具是 `system_serial`，前台等待独占串行桶 → **多个委派串行**
>    （三个各 0.6 秒的子 Agent 要跑 1.86 秒，实测）；
> 2. 与之配套的异步交付点挂在「每条用户消息一次」的位置 → 主 Agent 在同一次
>    运行里跑六轮也拿不到结论，**任务被变相中断**。
>
> 改成「发起与等待分离」后，前台阻塞等待不复存在，三种方式塌缩成一个
> `background` 参数。`Ctrl+B` 一并删除——它的语义空间本来就被
> `background`（模型声明）、`Esc`（用户取消整轮）、`/agents cancel`
> （用户取消单个）三者占满了，而「用户中途推翻模型的声明、逼它拿不完整的
> 信息回答」既罕用产出又差。

**F19a Plan Mode 规划阶段的委派**——委派工具在规划阶段**仍然开放**
（那恰恰是最需要把调研赶出主上下文的场景：规划要读很多东西，而那些内容
要一路背到执行阶段），但**只能委派给最终工具集全只读的角色**。

判据取**最终**工具集而非角色声明——角色写了 `write_file` 但被黑名单减掉时应当放行。
注册中心里查不到的工具名按「有副作用」处理：宁可多挡一次，也不要因为一个查不到的
名字把「批准前不动手」的承诺放过去。

不满足时**明确失败**并列出「当前可用的只读角色」，不静默把写工具摘掉——
静默降级会让一个写类角色在残废状态下跑完一整轮，比直接说「换个角色」更糟。

获批进入执行阶段后**不再有这条限制**，与普通模式一致。

> **修订记录（开发期）**：本条是对齐 Claude Code 时新增的。对齐过程中发现
> 一个**既有漏洞**：规划阶段守卫原本写的是
> `planning and not read_only and not system_serial`——那条 `system_serial`
> 豁免是为 `load_skill` 写的，而它 `read_only=True`、本来就被前一个条件挡在外面，
> 于是豁免长期空转。C13 的 `run_agent` 恰好把它激活了（`system_serial=True`
> **且** `read_only=False`）：实测规划阶段模型硬造一个 `run_agent` 调用，
> 它既没被守卫挡下、又因为 `system_serial` 不进权限管线，**直接执行了**，
> 而它委派出去的子 Agent 可以写文件。豁免条件已改成新增的 `Tool.plan_safe`
> ——工具必须**明确声明**自己规划期安全才被放行。

**F20 并发上限**——同时运行的子 Agent **不超过 3 个**。
超限时该次委派立即失败并回灌理由（当前有几个在跑、分别是谁），不排队。
排队会让模型拿到一个「成功了但不知道什么时候开始」的结果，比明确失败更难处理。

**F21 结果回流**——子 Agent 完成的那一刻：

1. 界面立刻出一条通知行（用户当时在做什么都不影响）；
2. 结论进入「待交付队列」；
3. **Agent Loop 每轮迭代组装请求之前**，把队列里的全部结论作为消息追加进主历史。

第 3 步选择「追加进主历史」而非「动态注入的系统提醒」，理由：系统提醒不进历史，
下一轮就消失了，模型在第三轮就会忘记子 Agent 说过什么——而子 Agent 的结论
恰恰是**有长期价值**的信息。

交付点在**迭代级**而非「每条用户消息一次」：后者会让主 Agent 在同一次运行里
跑很多轮也拿不到结论，用户必须插一句话才能让任务继续，等于把连贯的任务截断。
位置的合法性：消息协议只禁止在 `assistant(tool_calls)` 与它对应的 `tool` 结果
**之间**插消息，而两轮迭代之间上一轮的结果早已写完。

> **修订记录（开发期）**：本条第 3 步原为「下一次主对话发起请求之前」，
> 实测那等于「每条用户消息一次」——主对话跑了六轮，结论一轮都没进去。

**F22 生命周期与会话切换**——

- 主对话取消（`Esc`）**不影响**后台任务：它们是独立的执行单元；
- 提供显式的取消入口，可按标识取消单个任务，也可一次取消全部（F24）；
- `/clear` 与 `/resume` 在存在未完成任务时，**先取消全部任务再执行**，并告知用户取消了几个；
- 退出程序时取消全部并告知——**不做**跨会话持久化（见「不做的事」）。

### 七、界面与可观测

**F23 一行任务状态**——子 Agent 的运行过程在聊天区只占一行：
角色名 / 状态 / 已用轮次 / 耗时。子 Agent 内部的工具行与正文**不渲染**（仍完整进 trace）。
委派工具立即返回，因此那一行很快就收尾成「已启动，标识 X」；
子 Agent 跑完时**另出一条通知行**（F21 第 1 步）。

**F24 `/agents` 命令**——三种形态：

- 无参：列出全部角色（名字、来源层、description、最终工具集、模型、轮次上限、
  权限档位的声明值与实际生效值）、加载错误与警告、未支持字段提示，
  以及本次运行的任务列表（状态、耗时、轮次、用量、结论摘要）；
- `/agents cancel <标识>`：取消指定任务；
- `/agents cancel all`：取消全部未完成任务。

**本章不做 `reload`**——改了角色定义要重启，与 C12 同口径。

**F25 Hook 接线**——子 Agent 的每次工具调用照样触发工具级 Hook（含 `pre_tool_use` 的拦截），
否则主 Agent 可以通过「委派出去」绕过用户写的拦截规则。
生命周期复用既有的回合级事件，由负载里的作用域字段区分是哪个子 Agent，
**不新增事件类型**。

**F26 行为记录**——委派的发起与结束进 trace，负载含类型、角色名、任务描述、
结束原因、轮次、用量。子 Agent 内部的模型请求、工具执行、权限判定
全部落在**独立的作用域**下，读记录时一眼能与主对话分开。

## 非功能需求

**N1 零回归**——不发起任何委派时，主对话行为逐字不变。角色目录不存在、
一个角色都没加载，都不影响既有功能。

**N2 fail-safe 加载**——角色是可选增强，任何加载问题都不得阻断启动。

**N3 线程安全**——后台子 Agent 在独立线程运行，会**并发**触达 Hook 引擎、权限引擎、
行为记录器、任务管理器。这些组件的加锁不变量必须复核并保持：
**临界区只做纯内存读写**，动作执行、埋点、跨线程调度一律在锁外
（这条在 C11 与 C12 都是致命不变量，违反会与 Textual 的阻塞式跨线程调用组成死锁）。

**N4 不阻塞界面**——后台任务不占用 TUI 的流式 Worker；主对话在后台任务运行期间
可以正常收发消息、执行工具、弹确认面板。

**N5 上下文管理**——子 Agent 只跑 C8 第一层（工具结果存盘），不跑第二层 LLM 摘要；
不用它的用量更新主历史的估算锚点。

**N6 不写会话存档**——子 Agent 内部的消息不进 JSONL 存档。回流到主历史的结论
按主对话的正常规则存档。

**N7 可观测**——委派全过程可从 trace 复现：谁委派的、给了什么任务、
子 Agent 做了什么、为什么结束、花了多少。

**N8 注释规范**——遵循项目的中文注释要求；每一处「漏改不报错」的成对维护点
必须同步登记进 `CLAUDE.md`。

## 不做的事

| 不做 | 理由 |
| --- | --- |
| Worktree / 文件系统隔离 | 子 Agent 与主对话共用工作目录。隔离要引入 git worktree 生命周期管理，是独立一章的量 |
| 多 Agent 团队编排 | 子 Agent 之间不通信、不互相委派、无共享状态；工具集里永远没有委派工具 |
| 后台任务跨会话持久化 | 任务状态只活在本次进程内 |
| 子 Agent 的人在回路 | ASK 一律自动拒绝，永远不弹面板 |
| 角色的持久记忆 | 跨会话学习属 C9 范畴，混进来会出现两套笔记落盘路径 |
| 角色预加载 Skill | 子 Agent 工具集里排除加载工具，预加载会绕开这道防线 |
| 插件级角色 | 本项目没有插件系统，加载层级是项目 > 用户 > 内置三层 |
| 角色定义热更新 | 与 C12 同口径，改了要重启 |
| 子 Agent 内嵌 Plan Mode | 它非交互，没人能审批计划 |
| 委派任务的优先级与调度策略 | 超过并发上限即失败，不排队不调度 |
