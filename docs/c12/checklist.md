# C12 Hook 系统 Checklist

> 状态：**已批准**（2026-08-05，第 1 轮）
>
> 每一项通过**运行代码或观察行为**来验证，聚焦系统行为而非代码结构。
> 重构代码但行为不变时，本清单应当依然适用。
>
> **验证方式标记**：
> - 🤖 **无头可验** —— 用单测或端到端驱动设施（`tests/e2e/`）自动跑完，不需要人。
> - 👁 **需人眼** —— 界面呈现、排版、可读性，只能真人看。
> - 💰 **需真实模型** —— 要花钱调真模型，留作手测。

## 一、规则模型与加载（F1 / F8 / F9）

- [ ] 🤖 只写 `event` 与 `action`、省略 `if` 的规则能被加载，且该事件每次发生都触发
      （验证：写一条无 `if` 的规则，触发两次事件，观察动作执行两次）— **AC1**
- [ ] 🤖 缺 `event` 或缺 `action` 的规则被丢弃，其余规则照常加载，启动不中断
      （验证：三条规则里夹一条缺字段的，观察加载出两条 + 一条警告）— **AC1**
- [ ] 🤖 八项校验各能被独立触发，每条都产出含**规则标识与具体哪一项**的中文警告
      （验证：八个最小配置各跑一次，逐条比对警告文本）— **AC19**
- [ ] 🤖 YAML 解析失败 / 顶层非映射 / `hooks` 非列表三种情形下**整层降级为空**，
      不出现「部分规则生效」（验证：构造三份坏文件，观察该层规则数为 0）— **AC19**
- [ ] 🤖 用户级与项目级规则同时存在时全部生效，执行顺序为「用户级 → 项目级 → 层内声明序」
      （验证：两层各放两条带序号的规则，观察执行日志顺序）— **AC20**
- [ ] 🤖 一层文件损坏时另一层照常加载（验证：损坏用户级，观察项目级规则仍生效）— **AC19**
- [ ] 🤖 首次运行生成的 `hooks.yaml` 模板全部为注释，解析后规则数为 0
      （验证：在临时 HOME 跑首次运行，加载生成的模板，观察 `enabled` 为 False）

## 二、事件覆盖（F2）

      （验证：跑一次完整流程，从 trace 的 `hook_dispatch` 里数出十二个事件名）— **AC2**
- [ ] 🤖 六种「没执行」的分支——未知工具、参数解析失败、`out_of_scope`、`plan_blocked`、
      权限 DENY、用户在面板拒绝——**都不产生** `post_tool_use` / `post_tool_use_failure`
      （验证：六个场景各跑一次，观察工具级后置事件数为 0）— **AC3**
- [ ] 🤖 `ask_user` / `present_plan` 不触发任何工具级事件
      （验证：跑一次 Plan Mode 澄清流程，观察工具级事件里没有这两个名字）— **AC4**
- [ ] 🤖 只读并发工具与系统级串行工具**都触发** `pre_tool_use`
      （验证：一次调用里混入两类工具，观察两者都出现在 `hook_dispatch` 中）— **AC4**
- [ ] 🤖 `turn_start` / `turn_end` 在正常完成、用户取消、流出错三种终止下都成对产出
      （验证：三种终止各跑一次，观察每次都有配对的起止事件）— **AC2**
- [ ] 🤖 子对话产出的回合级事件带 `isolated:` 前缀的 `scope`，主对话为 `main`
      （验证：跑一次 `context: fork` 的 Skill，比对两条 `turn_start` 的 `scope`）— **AC2**
- [ ] 🤖 `/help` 触发 `user_message` 但不触发 `turn_start`
      （验证：敲一次 `/help`，观察两个事件的产出情况）— **AC2**
- [ ] 🤖 `pre_compact` / `post_compact` 只在第二层 LLM 摘要时产出，第一层存盘不产出
      （验证：构造一次只触发第一层的场景，观察压缩事件数为 0）— **AC2**

- [ ] 🤖 字段不存在或值为 `None` 时该匹配项判为不成立，**反向匹配也不成立**

## 四、四种动作（F4）

- [ ] 🤖 `command` 动作能从标准输入收到**完整事件负载 JSON**
      （验证：用一个把 stdin 回显到 stdout 的命令，比对回显内容与预期字段）— **AC7**
- [ ] 🤖 配置里写的命令串**逐字**执行，不含任何被替换的片段
      （验证：命令串里写字面 `${file_path}`，观察它原样出现在执行结果里而非被替换）— **AC7**
- [ ] 🤖 写着危险命令的 Hook 被①黑名单拦下，**子进程未启动**
      （验证：一条递归强删的 Hook 命令，观察 `ok=False` 且目标文件仍在）— **AC8**
- [ ] 🤖 `prompt` 动作注入的文本出现在**下一次**请求的 `<system-reminder>` 中，
      且**只出现一次**，再下一次请求不再包含（验证：连看三次请求的 reminder 内容）— **AC9**
- [ ] 🤖 `http` 动作指向 `127.0.0.1` / `localhost` / `file://` / 内嵌凭据四类地址时
      被拒绝并记录，**请求未发出**（验证：四条各跑一次，假客户端的调用计数为 0）— **AC10**
- [ ] 🤖 `http` 动作指向公网地址时正常发出，响应**不影响任何流程**
      （验证：假客户端返回 500，观察 Agent Loop 与工具执行不受影响）— **AC10**
- [ ] 🤖 `agent` 动作在加载期通过校验、运行期只产出「尚未支持」提示
      （验证：一条 `agent` 规则，观察加载成功且执行结果含该提示）— **AC11**
- [ ] 🤖 `agent` 动作挂在 `pre_tool_use` 上时按「不表态」处理，**工具照常执行**
      （验证：一条 `pre_tool_use` + `agent` 的规则，观察工具正常跑完）— **AC11**

## 五、执行控制（F5）

- [ ] 🤖 `once: true` 的规则在一次进程运行内只触发一次
      （验证：触发同一事件三次，观察动作执行一次）— **AC12**
- [ ] 🤖 重启后 `once` 重置，可再次触发（验证：新建 manager 后再触发，动作执行）— **AC12**
- [ ] 🤖 `pre_tool_use` + `async: true` 的规则在加载期被丢弃并给出警告

- [ ] 🤖 `async` 动作不阻塞主流程（验证：一条 sleep 较久的异步动作，

- [ ] 🤖 超时的 `command` 动作被终止并记为失败（验证：一条超过 `timeout` 的命令）— **AC17**

## 六、拦截语义（F6）

- [ ] 🤖 Hook 判 deny → 工具不执行、结构化原因回灌模型、**Agent Loop 不终止**
      （验证：观察后续轮次照常进行）— **AC14**
- [ ] 🤖 Hook 判 deny 时 `engine.decide` **一次都没被调用**
      （验证：假引擎计数为 0——防「先跑引擎再看 hook」这种顺序写反但结果碰巧对的实现）— **AC14**
- [ ] 🤖 Hook 判 ask 且权限管线判 ALLOW → **弹确认面板**
      （验证：`ask` 回调被调用一次，决策层标为 `hook`）— **AC14**
- [ ] 🤖 Hook 不表态时行为与无 Hook **逐字一致**
      （验证：同一场景跑两次，一次有不表态的 Hook 一次没有，比对事件流）— **AC14**
- [ ] 🤖 多条 Hook 命中时：一条 deny + 若干 ask/不表态 → 最终 deny；
      无 deny + 一条 ask → 最终 ask（验证：两组配置各跑一次）— **AC16**
- [ ] 🤖 拦截原因中含做出该结论的**规则名**（验证：比对回灌文本含规则标识）— **AC16**
- [ ] 👁 拦截回灌文案让模型明白「这是预先声明的规则，不要改参数或换工具绕过」
      （验证：人读一遍文案，对照 F6.3 的三项要求）

## 七、失败语义（F7）

- [ ] 🤖 `pre_tool_use` Hook 的四种失败——超时、崩溃、退出码非 0 非 2、stdout 非法 JSON
      ——**都按拦截处理**（验证：四种各跑一次，观察工具均未执行）— **AC17**
- [ ] 🤖 拦截原因文案可与「工具执行异常」区分
      （验证：比对两种文案，确认前者含「Hook 自身执行失败」字样）— **AC17**
- [ ] 🤖 非拦截类事件的 Hook 失败只产生提示与 trace 记录，
      Agent Loop 与工具执行**不受任何影响**（验证：`post_tool_use` 上挂一条必失败的动作，
      观察工具结果与后续轮次逐字不变）— **AC18**
- [ ] 🤖 `async` 动作的失败同样被记录，不被静默吞掉
      （验证：异步动作抛异常，观察 trace 中有对应 `hook_execute` 记录）— **AC18**

## 八、安全性专项

这一节是本章的核心风险面，每一条都要单独验。

- [ ] 🤖 **不存在任何 Hook 配置能让一次原本会被①黑名单拒绝的调用得以执行**
      （验证：Hook 判 ask + 一条 `rm -rf` 调用 → 仍为 DENY，确认面板不弹）— **AC15**
- [ ] 🤖 **不存在任何 Hook 配置能让一次原本会被②沙箱拒绝的调用得以执行**
      （验证：Hook 判 ask + 一条越界路径写入 → 仍为 DENY）— **AC15**
- [ ] 🤖 Hook stdout 输出 `{"decision":"allow"}` 时按「不表态」处理，**不产生放行语义**
      （验证：一条会被判 ASK 的调用配上该 Hook，确认面板照常弹出）— **AC15**
- [ ] 🤖 Hook stdout 输出未知 `decision` 取值时同样按「不表态」处理，不崩溃
      （验证：输出 `{"decision":"whatever"}`）— **AC15**
- [ ] 🤖 模型无法通过任何工具调用读取、修改或禁用 hooks 配置的加载结果
      （验证：`hooks.yaml` 不在任何工具的写入白名单里；改动它需要重启才生效）
- [ ] 👁 项目级 `hooks.yaml` 存在时，启动提示**逐条**列出事件与动作原文，
      `command` 显示完整命令串、`http` 显示完整 URL，不折叠不省略不只给计数 — **AC21**
- [ ] 🤖 项目级提示**每次启动都出现**，不做「只提示一次」的持久化
      （验证：连续两次装配都产出提示）— **AC21**
- [ ] 🤖 `http` 动作的域名硬校验与 `web_fetch` **复用同一份实现**
      （验证：往 `permission/network.py` 加一个禁止地址，`http` 动作与 `web_fetch` 同时被拦）

## 十三、端到端场景

用 `tests/e2e/` 的驱动设施跑，宿主自建临时工作区与临时用户目录。

- [ ] 🤖 **场景 1（拦截生效）**：配一条「禁止 `git push` 到 main」的 `pre_tool_use` Hook
      → 让模型尝试该命令 → 命令未执行、模型收到拦截原因、对话继续进行
- [ ] 🤖 **场景 2（升级为问）**：配一条把某只读工具升级为 ask 的 Hook
      → 触发该工具 → 确认面板弹出、面板上显示的判定层为 Hook → 选放行后正常执行
- [ ] 🤖 **场景 3（自动化正路）**：配一条「改完 `.py` 就跑格式化命令」的 `post_tool_use` Hook
      → 让模型改一个 Python 文件 → 观察格式化命令在工具执行后被跑起来
- [ ] 🤖 **场景 4（上下文注入）**：配一条 `turn_start` + `prompt` 的 Hook
      → 提交一条消息 → 观察注入文本出现在该回合首次请求的 reminder 里，且下一回合不重复
- [ ] 🤖 **场景 5（fail-closed）**：配一条命令不存在的 `pre_tool_use` Hook
      → 触发任意工具 → 工具被拦下、原因写明 Hook 自身失败、界面上可见
- [ ] 🤖 **场景 6（fail-open）**：同样一条坏 Hook 改挂到 `post_tool_use`
      → 触发同一工具 → 工具正常执行完成、只多一条提示
- [ ] 🤖 **场景 7（项目级提示）**：在临时工作区放一份项目级 `hooks.yaml`
      → 启动 → 首屏逐条列出事件与完整命令串
- [ ] 🤖 **场景 8（零配置）**：不放任何 `hooks.yaml` → 跑完一整轮交互
      → 行为与 C11 逐字一致、trace 里零条 hook 事件
- [ ] 💰 **场景 9（真实模型下的拦截反应）**：真实模型 + 场景 1 的配置
      → 观察模型收到拦截后**是否停止绕路**（不改参数、不换工具、转而向用户说明）
- [ ] 💰 **场景 10（真实模型下的注入生效）**：真实模型 + 一条注入「当前在 main 分支，
      改动前先确认」的 Hook → 观察模型的行为确实受该提示影响

**场景 9 / 10 留作手测**——它们判的是模型的反应质量，不是代码行为，无法用断言判定。
其余八个场景全部用驱动设施无头跑完。
