# C12 Hook 系统 Spec

> 状态：**已批准**（2026-08-05，第 1 轮）
>
> 性质：**章节，占章节号 C12**。它引入一个新的能力层级（`hooks/`），
> `CLAUDE.md` 的能力表要多一行、架构分层表要多一层。判据见
> [`docs/extensions/README.md`](../extensions/README.md)。

## 背景

到 C11 为止，RhineCode 里所有「在某个时刻自动做某件事」的行为**全部硬编码在代码里**：
C5 在每轮请求前注入环境信息、C8 在余量不足时压缩上下文、C9 在 Agent 自然停止后沉淀笔记。
这些节点都是开发者选的，用户改不了，也加不了自己的。

于是有一类工作只能靠人反复盯：

| 真实场景 | 现在只能怎么办 |
| --- | --- |
| AI 改完 `.py` 就跑一遍格式化 | 每次在提示词里叮嘱模型，或者事后自己跑 |
| 禁止某类命令的某种参数组合（比 `permissions.yaml` 更细，要看参数内容） | 写不出来——规则层只认「工具 + 模式」，认不了跨字段的组合条件 |
| 每个回合开始时告诉模型当前 git 分支与最近提交 | 自己在消息里粘一遍 |
| Agent 干完活了叫我一声（我切走去干别的了） | 时不时切回来看一眼 |

这四件事的共同点是：**触发条件明确、动作固定、每次都一样**——正是应该由机器做而不是由人盯的那部分。

### 与已有能力的边界

本章**不是**权限系统的替代品，也不是 Skill 的替代品。三者的分工：

| | 谁决定「做什么」 | 什么时候介入 | 能不能被模型影响 |
| --- | --- | --- | --- |
| 权限系统（C6） | 用户写的 allow/deny 规则 | 每次工具执行前 | 不能（这是它的全部价值） |
| Skill（C11） | 用户写的 SOP 正文 | 模型自己判断要不要加载 | 能——它本质是「发给模型的文本」 |
| **Hook（C12）** | **用户写的事件规则** | **生命周期的固定节点，无条件触发** | **不能——模型看不见 hooks.yaml，也无法阻止它触发** |

Hook 与权限系统最像，区别在**粒度与动作**：权限规则只能对「工具 + 一个模式」表态，
只有放行/拒绝/问三种结果；Hook 能对事件负载的**任意字段组合**表态，且动作不限于表态
（可以跑命令、注入提示、发请求）。

## 目标

- 提供声明式的「事件 + 条件 + 动作」规则，从 YAML 加载，**不改代码**即可在生命周期节点挂自动化动作。
- 覆盖会话 / 回合 / 消息 / 工具四层生命周期，外加三个系统级事件。
- 工具执行前的事件能拦截，且**拦截只能收紧、不能放宽**——Hook 的引入不得让任何原本会被拒绝的调用变成放行。
- Hook 自身的失败不污染 Agent 主流程，也不伪装成「工具坏了」。
- 全部 Hook 执行进 trace，让「我的 hook 为什么没跑」可以事后查清。

## 本章对既有代码的已知改造点

集中登记，避免 plan 阶段才发现：

1. **决策管线新增一个前置层**（F6）。它排在①危险命令黑名单**之前**，是整条管线唯一一处
   「五层之外还有东西」的位置。安全论证依赖它**只能收紧**这条性质。
2. **Agent Loop 的工具执行路径新增分发点**（F2 的三个工具级事件）。
3. **协调层新增回合级与消息级的分发点**，且必须覆盖主对话与子对话两条路径。
4. **上下文管理器新增两个分发点**（第二层 LLM 摘要前后）。
5. **系统提示的动态通道新增一个内容来源**——注入型动作的产物要能进 `<system-reminder>`（F4）。
6. **trace 新增两类事件**（F12），连带 `trace/reader.py` 的摘要函数表要加两行。
7. **新增一条斜杠命令 `/hooks`**（F11）。
8. **`.gitignore` 与安全边界文档**要登记 hooks 产物的敏感性（F12 末节）。

**Provider 范围**：本章及后续所有开发只针对 DeepSeek Provider（工具模式）。
Hook 系统中与工具无关的部分（会话级、回合级、消息级事件）对所有 Provider 生效。

## 功能需求

### F1 三要素规则模型

一条 Hook 规则由三个部分描述：

- **event**（必填）——触发时刻，取值必须是 F2 清单里的十二个之一。
- **if**（可省）——条件表达式；**省略表示无条件触发**。
- **action**（必填）——动作，取值必须是 F4 的四种之一。

另有三个可选的执行控制字段（F5）与一个可选的 `name`（人类可读标识，用于 `/hooks` 报告、
trace 记录与拦截原因文案；省略时由系统按「来源层 + 序号」生成一个稳定标识）。

一条规则的完整形态：

```yaml
- name: 格式化改动的 Python 文件
  event: post_tool_use
  if:
    all:
      - tool: edit_file
      - file_path: "**/*.py"
  action:
    type: command
    command: "black $(...)"
    timeout: 30
```

### F2 事件清单（十二个）

分五组。每个事件携带一份**事件负载**（一组命名字段），条件表达式与动作都从中取值。
所有事件的负载都包含三个公共字段：`event`（事件名）、`session_id`（当前会话 ID）、
`cwd`（项目根绝对路径）。

**会话级（2）**

| 事件 | 触发时刻 | 专有负载字段 |
| --- | --- | --- |
| `session_start` | 应用装配完成、首条消息之前；以及 `/resume` 载入、`/clear` 开新档之后 | `source`：`startup` / `resume` / `clear` |
| `session_end` | 用户退出程序；以及 `/clear`、`/resume` 切走当前会话之前 | `reason`：`exit` / `clear` / `resume` |

**回合级（2）**——一个「回合」= 一次完整的 Agent Loop 运行（`Agent.run` 的一次调用）。

| 事件 | 触发时刻 | 专有负载字段 |
| --- | --- | --- |
| `turn_start` | 一次 Agent Loop 开始前 | `scope`（`main` 或 `isolated:<skill名>`）、`trigger`（`user` / `command` / `skill`） |
| `turn_end` | 一次 Agent Loop 结束时 | `scope`、`stop_reason`（六种停止原因之一）、`last_text`（本回合最后一段 AI 正文） |

**回合级事件对主对话与子对话都触发**，由 `scope` 字段区分，条件可据此过滤。
这是刻意的：一个「回合结束跑测试」的 Hook 不该因为 Skill 开了子对话就重复跑，
用户需要有办法只挂在 `main` 上。

**消息级（2）**

| 事件 | 触发时刻 | 专有负载字段 |
| --- | --- | --- |
| `user_message` | 用户在输入框提交一条消息之后、任何处理之前（**含斜杠命令**） | `text`（原始输入原文）、`is_command`（是否被识别为斜杠命令） |
| `assistant_message` | 一段 AI 正文产出完毕时；一个回合内可能触发多次 | `scope`、`text`（该段正文全文） |

`user_message` 与 `turn_start` 的区别不是重复而是**来源不同**：`/help` 触发 `user_message`
但不触发 `turn_start`（命令不进 AI）；模型自行发起的子对话触发 `turn_start` 但没有 `user_message`。

**工具级（3）**

| 事件 | 触发时刻 | 专有负载字段 |
| --- | --- | --- |
| `pre_tool_use` | 一次工具调用即将进入权限判定之前。**唯一可拦截的事件**（F6） | `tool`、`tool_call_id`、`tool_input`（模型生成的参数对象，逐字展开为条件可用字段）、`is_read_only`、`scope` |
| `post_tool_use` | 工具**真的执行了**且结果 `ok=True` | 同上，另加 `tool_output`、`duration_ms` |
| `post_tool_use_failure` | 工具**真的执行了**且结果 `ok=False` | 同上，另加 `tool_output`、`duration_ms`、`error` |

**三条边界必须逐字遵守，否则语义会悄悄漂移：**

1. `pre_tool_use` 对**每一次即将进入执行判定的工具调用**触发，包括只读并发工具与系统级串行工具
   （后者虽然跳过权限引擎，但它确实要执行）。**不含** `ask_user` / `present_plan`——
   那两个是与用户交互，不是工具执行。
2. 「压根没执行」的分支**一个后置事件都不触发**：未知工具、参数解析失败、
   被工具收窄挡下（`out_of_scope`）、Plan Mode 规划阶段挡下（`plan_blocked`）、
   权限管线判 DENY、用户在确认面板选拒绝。理由：`post_tool_use_failure` 的语义是
   「跑了但失败了」，把「没跑」混进来会让「统计工具失败率」这类用途直接失真。

   > **勘误（2026-08-05，实现期发现）**：本条原文写的是「一个都不触发**任何工具级事件**」，
   > 那与 F6 的管线位置**自相矛盾**。`pre_tool_use` 按决策 1A 排在五层权限管线**之前**，
   > 在跑权限判定之前根本无从知道这次调用会不会被 DENY——「权限 DENY」与
   > 「用户在面板拒绝」两种情形下不触发前置事件，结构上做不到。
   >
   > 实际实现按「本条只管**后置**事件」执行（这也正是本条给出的理由所指向的语义）。
   > `pre_tool_use` 的触发范围由 F2 边界第 1 条界定：**每一次进入执行判定的调用**。
   > 前四种情形（未知工具 / 参数非法 / `out_of_scope` / `plan_blocked`）都在进入判定
   > 之前就被挡下，因此前置事件同样不触发；后两种会触发前置、不触发后置。
   > 护栏见 `tests/test_hook_intercept.py::NoExecutionBranchesTest`（六条逐一钉住）。
3. 被 Hook 自己拦下的调用（F6）同样不触发 `post_tool_use_failure`——它属于第 2 条。

**系统级（3）**

| 事件 | 触发时刻 | 专有负载字段 |
| --- | --- | --- |
| `pre_compact` | C8 第二层 LLM 摘要压缩开始之前 | `trigger`（`auto` / `manual`）、`message_count`（待压缩的历史条数） |
| `post_compact` | 第二层摘要完成之后 | `trigger`、`message_count`、`ok`（摘要是否成功） |
| `notification` | 系统需要用户注意时 | `kind`：`awaiting_confirm` / `awaiting_clarify` / `awaiting_plan` / `agent_finished`；`message`（面向用户的一行说明） |

`pre_compact` / `post_compact` **只对第二层（LLM 摘要）触发**，不对第一层（工具结果存盘）触发——
第一层每轮都可能发生若干次，挂 Hook 上去只会产生噪音。

### F3 条件表达式

条件由**字段匹配项**与**一个逻辑组合词**构成：

```yaml
if:
  all:                          # 或 any，二选一
    - tool: run_command         # 字段名: 匹配模式
    - command: "git push *"
```

**F3.1 逻辑组合**——`all`（全部满足）与 `any`（任一满足）**二选一，不混用、不嵌套**。
同一个 `if` 下同时出现两个、或一个都没有，都是加载期错误（F8）。

**F3.2 字段名**——取自该事件的负载字段（F2 的表）。`pre_tool_use` 等三个工具级事件另有一条特例：
`tool_input` 里的每个键**逐字展开为顶层字段名**，因此可以直接写 `command:`、`file_path:`、`url:`，
不必写 `tool_input.command`。展开时若与公共字段重名，**公共字段优先**，并在加载期给出警告。

引用了该事件不存在的字段名 → 加载期错误（F8），整条规则丢弃。

**F3.3 四种匹配形态**——对应你熟悉的权限规则语法：

| 形态 | 写法 | 语义 |
| --- | --- | --- |
| 精确 | `tool: run_command` | 字符串完全相等 |
| glob | `command: "git push *"` | 通配匹配；命令类字段复用 C6 的命令匹配（前缀 + 词边界），路径类字段复用 C6 的路径匹配（gitignore 风格），其余字段用通用通配 |
| 正则 | `command: "/^git (push\|reset)/"` | 用一对 `/` 包裹时按正则处理，非锚定匹配（要整串匹配自己写 `^...$`） |
| 反向 | `tool: "!run_command"` | 值以 `!` 开头表示取反；可与上面三种叠加，如 `"!/^git/"` |

字段值不是字符串时（如 `is_read_only` 是布尔、`duration_ms` 是数字），
先转成字符串再匹配（`true` / `false` / `120`）。字段不存在或为 null 时，
该匹配项**判为不成立**（反向匹配同样不成立——「字段不存在」不等于「不匹配」）。

**F3.4 省略 `if`** —— 无条件触发，等价于「所有条件都满足」。

### F4 四种动作

**F4.1 `command`——执行 shell 命令**

```yaml
action:
  type: command
  command: "..."       # 必填
  timeout: 30          # 可选，秒，默认 60
```

- 事件负载以**JSON 从标准输入**喂给命令。**配置里不做任何字符串插值**——
  命令行由用户逐字写死，模型生成的任何内容都不会被拼进命令串。理由见 N3。
- 命令经系统 shell 执行，工作目录为项目根。
- **Hook 命令过①危险命令黑名单，不过其余四层**。①层的既有性质是「不可被任何配置或权限模式放开」，
  而 `hooks.yaml` 就是配置，所以它必须照样受制于①。②③④⑤不过，理由见 N4。
- 退出码语义：

  | 退出码 | 含义 |
  | --- | --- |
  | 0 | 通过。stdout 若是合法的决策 JSON 则按 F6 解析（仅 `pre_tool_use` 有意义），否则忽略 |
  | 2 | 拦截（仅 `pre_tool_use` 有意义；其余事件按「失败」处理并记 trace），stderr 作为拦截原因 |
  | 其它非 0 | 失败，按 F7 处理 |

**F4.2 `prompt`——注入提示词**

```yaml
action:
  type: prompt
  text: "当前分支是 main，改动前先与用户确认。"    # 必填
```

- 文本注入进 `<system-reminder>` 动态通道，模型在**下一次 API 请求**时看到。
- **一次性**：注入的文本被带上一次请求后即清除。持续注入会让提醒无限增长，
  且用户无法预期它什么时候消失。
- 多条 `prompt` 动作在同一次请求前命中时，按触发顺序拼接。

**F4.3 `http`——发 HTTP 请求**

```yaml
action:
  type: http
  url: "https://example.com/webhook"    # 必填
  method: POST                          # 可选，默认 POST
  headers: { "X-Token": "..." }         # 可选
  body: "..."                           # 可选；省略时发送完整事件负载 JSON
  timeout: 10                           # 可选，秒，默认 10
```

- 请求前过②′网络边界层的**结构性硬校验**（只允许 http/https、禁止内嵌凭据、
  禁止回环与非公网地址、禁止 `localhost` 等保留名字）。**不要求域名白名单**——
  `hooks.yaml` 是用户手写的配置而非模型输出，要求白名单会让「配了 hook 却发不出去」成为常态。
- **HTTP 动作不参与任何拦截决策**：响应状态码与响应体只进 trace，不影响流程。
  让一个外部服务能决定本地工具跑不跑，可用性与安全性都不成立。
- 非 2xx 响应、连接失败、超时，一律按 F7 的「失败」处理。

**F4.4 `agent`——启动子 Agent（本章占位）**

```yaml
action:
  type: agent
  prompt: "..."      # 必填
```

- 加载期**认得这个类型并完成字段校验**（写错字段照样报错）。
- 运行期**不执行**：产出一条「子 Agent 动作尚未支持，等待 SubAgent 章节接入」的界面提示并记 trace。
- 若挂在 `pre_tool_use` 上，按「不表态」处理（**不是**失败，因此不触发 F7 的 fail-closed）。
  理由：占位不是故障，用户明知它还没接通；按失败处理会让一条占位规则把所有工具调用拦死。

### F5 执行控制

三个可选字段，写在动作同级：

| 字段 | 默认 | 语义 |
| --- | --- | --- |
| `once` | `false` | 为真时该规则在**本次进程运行内**只触发一次，此后跳过。**不持久化**——重启即重置 |
| `async` | `false` | 为真时动作在后台执行，不等待结果 |
| `timeout` | 见 F4 | 动作执行的超时秒数 |

**`pre_tool_use` 事件禁止 `async: true`**——异步意味着「不等结果」，而拦截的全部意义就是等结果。
写了即为加载期错误（F8），整条规则丢弃。

`async` 动作的失败一律按 F7 的非拦截类处理（记 trace + 提示一行），
不会因为它跑在后台就被静默吞掉。

### F6 拦截语义

**只有 `pre_tool_use` 能拦截。** 它的位置在决策管线的**最前面**：

```
Hook 前置层（本章新增）   ← 只能 deny / ask / 不表态
 ① 危险命令黑名单
 ② 路径沙箱
 ②′ 网络边界
 ③ 可配置规则
 ④ 权限模式兜底
 ⑤ 人在回路
```

**F6.1 三种结论，没有第四种**

| 结论 | 表达方式 | 效果 |
| --- | --- | --- |
| 拦截 | 退出码 2，或 stdout 输出 `{"decision": "deny", "reason": "..."}` | 不执行，把结构化原因作为工具结果回灌模型，**不终止 Agent Loop** |
| 升级为问用户 | stdout 输出 `{"decision": "ask", "reason": "..."}` | 强制弹人在回路确认面板，即使五层会判 ALLOW |
| 不表态 | 退出码 0 且 stdout 不是决策 JSON | 原样进入五层，行为与没有这条 Hook 完全一致 |

**没有 `allow`。** Hook 无法让任何调用跳过五层中的任何一层。这条性质是本章安全论证的全部依据：
Hook 加进来之后，「能通过的调用集合」只会变小，不会变大——因此 C6 建立的一切不变量原样成立，
一个字都不用重新论证。

**F6.2 多条 Hook 命中同一次调用** —— 全部执行完，再合并结论：
**任一 deny 即 deny；无 deny 但有 ask 即 ask；否则不表态**。与权限规则的「deny 优先」同哲学。
拦截原因里带上做出该结论的规则 `name`。

**F6.3 拦截结果的回灌文案**必须让模型知道这不是工具故障、也不是可以换个姿势重试的技术失败，
而是一条**用户预先声明的规则**。文案要写明：被哪条规则拦下、原因是什么、
以及「如果你认为这一步确实必要，请向用户说明理由，不要改参数或换工具绕过」。

### F7 失败语义

**F7.1 拦截类（`pre_tool_use`）—— fail-closed。**
Hook 启动失败、超时、以非 0 非 2 的退出码结束、或 stdout 是无法解析的 JSON 时，
**按拦截处理**，原因写明「Hook 自身执行失败」并附上失败详情。

理由：一个 `pre_tool_use` Hook 的存在本身就声明了「这个位置需要检查」。
fail-open 会让一条上周就写坏的安全 Hook **静默失效**，而你完全不知道；
fail-closed 会让 Agent 立刻干不了活——这是**可见**的，五秒内就会去修。

这与「Hook 失败绝不中断 Agent 主流程」不冲突：拦下一次工具调用**不是**中断循环，
模型会收到结构化原因继续调整，与 C6 的权限拒绝行为完全一致。

**F7.2 其余全部事件 —— fail-open。**
只记 trace + 在界面上给一行可见提示，不影响任何流程。

**F7.3 Hook 的失败绝不能伪装成工具故障。** 拦截文案与工具执行异常的文案必须可区分，
且 Hook 层自身的异常（分发逻辑出错、负载构造出错）一律被吞掉并记 trace——
观测与自动化设施绝不能反过来阻断被观测的系统。

### F8 加载与集中校验

规则从 YAML 声明式加载，**加载期一次性完成全部校验**，产出一份警告列表。

校验项：

1. `event` 是 F2 十二个之一。
2. `action.type` 是 F4 四种之一，且该类型的必填字段齐全、类型正确。
3. `if` 下 `all` / `any` **恰好出现一个**；不允许嵌套。
4. 每个字段名属于该事件的可用字段集（含 F3.2 的 `tool_input` 展开）。
5. 正则模式能被成功编译。
6. `pre_tool_use` 未声明 `async: true`。
7. `timeout` 是正数。
8. 非 `pre_tool_use` 事件上挂了会产出决策的动作时给出**提示级**警告（不丢弃）——
   它无害，但说明用户可能误解了拦截只在一个事件上生效。

**任一硬校验项（1–7）不通过 → 丢弃该条规则，其余规则照常加载，不阻断启动。**

**这个取舍要说清楚**：丢弃一条 `pre_tool_use` 拦截规则等于「少拦一次」，方向偏松，
与 C6 里「deny 规则写坏就降级为整工具拒绝」那种偏严处理不同。之所以只能这样，
是因为 Hook 规则没有可降级的偏严形态——一条条件写坏的拦截规则，
唯一「偏严」的处理是让它恒成立（即拦掉一切），那会让一个笔误瘫痪整个 Agent。
补偿手段是**让它可见**：加载警告在启动时展示，并在 `/hooks` 报告里单列一段。

### F9 配置层级与项目级提示

两层，**没有本地级**（本地级在 C6 里是「永久放行」的自动写入目标，Hook 没有这种自动写入场景）：

- 用户级 `~/.rhinecode/hooks.yaml`
- 项目级 `<项目根>/.rhinecode/hooks.yaml`

**合并规则**：两层的规则**全部生效**，不按层级覆盖（与 C6 的规则合并同哲学）。
执行顺序固定为「用户级在前、项目级在后，同层按文件内声明顺序」，**不提供优先级字段**。

**F9.1 项目级的启动提示是本章的核心安全措施。**

项目级 `hooks.yaml` 随代码仓库分发，`git pull` 之后可能凭空多出几条。
与项目级 Skill 不同的是，Hook 的动作**直接执行**，不经模型、不经人在回路确认。
因此启动提示必须比 Skill 那句「发现 N 个项目级 Skill」强一档：

- **逐条列出**每条项目级规则的「事件 → 动作原文」，`command` 动作展示完整命令串，
  `http` 动作展示完整 URL。不折叠、不省略、不只给计数。
- 与项目级 Skill 同理，**刻意不做「只提示一次」的持久化**——有状态的话，
  新增的规则会在状态未失效时被静默吞掉。

### F10 网络边界

`http` 动作复用②′网络边界层的结构性硬校验，见 F4.3。硬校验的**实现必须复用同一份**，
不得在 Hook 层另写一套。

### F11 `/hooks` 命令

一条新的斜杠命令，纯只读、不改状态：

- 列出全部已加载规则：来源层、`name`、事件、条件、动作摘要、`once` 是否已消耗。
- 单列一段**加载警告**（F8 丢弃的规则与原因）。
- 单列一段**最近一次执行结果**（本次运行内每条规则的触发次数、最近一次的结论与耗时），
  用于回答「我的 hook 到底跑没跑」。

### F12 行为记录（trace）

新增两类事件：

- `hook_dispatch`——某个生命周期事件被分发：事件名、命中规则数、负载摘要。
  **零命中也要记**——「事件触发了但一条规则都没命中」正是排查「我的 hook 为什么没跑」的第一现场。
- `hook_execute`——单条规则的执行：规则标识、来源层、动作类型、是否 async、
  耗时、退出码 / 响应状态码、拦截结论、stdout / stderr（按既有阈值截断）。

**敏感性**：Hook 的事件负载里含完整的工具参数与工具输出，与 trace 产物同级敏感——
若模型读过配置文件，那份内容会原样出现在 `pre_tool_use` 的负载里，
进而出现在 hook 的 stdin、以及 `hook_execute` 的记录中。`http` 动作更会把它**发到外部**。
安全边界文档必须登记这一条。

### F13 缺省零行为

两层 `hooks.yaml` 都不存在时：不读任何文件、不构造任何事件负载、不发起任何分发，
运行时行为与 C11 **逐字一致**。

## 非功能需求

- **N1 缺省零回归**：见 F13。Hook 系统的引入不改变任何既有行为的默认表现。
- **N2 不阻塞界面**：同步动作在 Agent 的 Worker 线程内执行；`async` 动作在独立线程执行。
  任何 Hook 都不得在主线程上执行。
- **N3 不建立命令注入面**：配置中不做字符串插值；模型生成的内容只能经 stdin 的 JSON 抵达 Hook，
  不能进入命令串。
- **N4 权限管线的性质不变**：Hook 只能收紧不能放宽（F6.1），因此 C6 的五层顺序不变量、
  预授权安全性论证、Skill `allowed-tools` 的「只放宽从不收紧」承诺，全部原样成立。
  Hook 命令本身不过②③④⑤层——它是用户配置而非模型行为，过管线等于每次自动化都弹确认，
  自动化即失去意义；风险由「只能 YAML 声明」+「项目级逐条展示」（F9.1）对冲。
- **N5 纯逻辑可测**：规则解析、条件求值、结论合并必须是零 I/O 的纯函数，可脱离文件系统与网络单测。
- **N6 跨平台**：`command` 动作在 Windows 与 POSIX 上都能执行。
- **N7 零命中低开销**：某个事件没有任何规则监听时，不得构造事件负载（负载构造按需惰性进行）。
- **N8 观测不干扰**：Hook 层自身的异常一律被吞掉并记 trace，绝不向上抛出。

## 不做的事

以下明确不在本章范围，**不要在实现时顺手加上**：

1. **子 Agent 动作的真实运行**——只做加载期校验与运行期占位提示（F4.4），等 SubAgent 章节对接。
2. **`once` 的持久化**——只在进程内有效，重启重置。
3. **Hook 执行顺序的显式优先级**——顺序按 F9 固定，不提供 `priority` 字段。
4. **Hook 的放行能力**——Hook 永远不能 allow（F6.1）。
5. **迭代级事件**——不开放 Agent Loop 内单轮迭代的 Hook 点。迭代是引擎内部结构，
   暴露成配置契约会让循环结构的任何调整都成为破坏性变更。
6. **配置中的字符串插值**——见 N3。
7. **HTTP 动作参与拦截决策**——见 F4.3。
8. **`/hooks reload` 热更新**——本章 `/hooks` 只读；改了规则要重启。
9. **本地级 `hooks.yaml`**——见 F9。
10. **Skill / MCP 形态的 Hook 动作**——Claude Code 支持 `prompt` / `mcp_tool` / `agent` 等由模型
    执行的 hook 类型，本章的四种动作里只有确定性的三种加一个占位。
11. **在 Skill frontmatter 里声明 Hook**——Hook 只能来自两层 YAML。
12. **Hook 修改工具参数或工具结果**——Claude Code 的 `updatedInput` / `updatedToolOutput`
    本章不做。Hook 只能拦，不能改。

## 验收标准

- **AC1**（F1）：一条只写 `event` 与 `action`、省略 `if` 的规则能被加载，并在该事件每次发生时触发。
  缺 `event` 或缺 `action` 的规则被丢弃且给出警告。
- **AC2**（F2）：十二个事件各能在其定义的时刻触发至少一次，可通过 trace 的 `hook_dispatch` 观察到。
- **AC3**（F2 边界）：未知工具、参数错误、`out_of_scope`、`plan_blocked`、权限 DENY、
  用户拒绝六种「没执行」的分支，**都不产生** `post_tool_use` / `post_tool_use_failure`。
- **AC4**（F2 边界）：`ask_user` / `present_plan` 不触发任何工具级事件；
  只读并发工具与系统级串行工具**会**触发 `pre_tool_use`。
- **AC5**（F3）：精确、glob、正则、反向四种匹配各能按预期命中与不命中；
  `all` 与 `any` 的组合语义正确；字段不存在时该匹配项判为不成立（含反向）。
- **AC6**（F3.2）：工具级事件里可直接用 `command:` / `file_path:` 等 `tool_input` 展开后的字段名。
- **AC7**（F4.1）：`command` 动作能收到 stdin 上的完整事件负载 JSON；
  配置里写的命令串**逐字**执行，不含任何被替换的片段。
- **AC8**（F4.1）：写着危险命令（如递归强删）的 Hook 命令被①黑名单拦下，不执行。
- **AC9**（F4.2）：`prompt` 动作注入的文本出现在**下一次**请求的 `<system-reminder>` 中，
  且**只出现一次**，再下一次请求不再包含它。
- **AC10**（F4.3）：`http` 动作指向 `127.0.0.1`、`localhost`、`file://` 或内嵌凭据的地址时被拒绝并记录；
  指向公网地址时正常发出，且响应不影响任何流程。
- **AC11**（F4.4）：`agent` 动作在加载期通过校验，运行期只产出「尚未支持」提示；
  挂在 `pre_tool_use` 上时按「不表态」处理，工具照常执行。
- **AC12**（F5）：`once: true` 的规则在一次进程运行内只触发一次；重启后重新可触发。
- **AC13**（F5）：`pre_tool_use` + `async: true` 的规则在加载期被丢弃并给出警告。
- **AC14**（F6.1）：`pre_tool_use` Hook 判 deny 时工具不执行、结构化原因回灌模型、
  Agent Loop **不终止**；判 ask 时即使权限管线会判 ALLOW 也弹确认面板；不表态时行为与无 Hook 逐字一致。
- **AC15**（F6.1 安全性）：不存在任何 Hook 配置能让一次原本会被①黑名单或②沙箱拒绝的调用得以执行。
- **AC16**（F6.2）：多条 Hook 命中时，一条 deny + 若干 ask/不表态 → 最终 deny；
  无 deny + 一条 ask → 最终 ask。拦截原因中含做出该结论的规则名。
- **AC17**（F7.1）：`pre_tool_use` Hook 超时、崩溃、退出码非 0 非 2、stdout 非法 JSON 四种情形，
  **都按拦截处理**，原因文案可与「工具执行异常」区分。
- **AC18**（F7.2）：非拦截类事件的 Hook 失败只产生一条界面提示与一条 trace 记录，
  Agent Loop 与工具执行不受任何影响。
- **AC19**（F8）：八类校验各能被触发；硬校验失败的规则被丢弃、其余规则照常加载、启动不中断；
  警告在启动提示与 `/hooks` 报告中都可见。
- **AC20**（F9）：用户级与项目级规则同时存在时全部生效，执行顺序为「用户级 → 项目级 → 声明序」。
- **AC21**（F9.1）：存在项目级 `hooks.yaml` 时，启动提示**逐条**列出事件与动作原文
  （命令串完整、URL 完整），且每次启动都提示。
- **AC22**（F11）：`/hooks` 输出已加载规则、加载警告、本次运行的执行统计三段；纯只读。
- **AC23**（F12）：`hook_dispatch` 在零命中时也产出；`hook_execute` 含规则标识、动作类型、
  耗时与结论，可据此回答「这条 hook 跑没跑、结论是什么」。
- **AC24**（F13 / N1）：两层 `hooks.yaml` 都不存在时，不产生任何 `hook_dispatch` 事件，
  且全套既有测试逐条通过。
- **AC25**（N2）：Hook 执行期间界面保持响应；`async` 动作不阻塞 Agent Loop 推进。
- **AC26**（N5）：条件求值与结论合并可在不触碰文件系统与网络的前提下被单元测试完整覆盖。
- **AC27**（N8）：向 Hook 层注入一个必然抛异常的分发场景时，异常被吞掉、
  Agent Loop 正常完成、trace 中留有痕迹。
