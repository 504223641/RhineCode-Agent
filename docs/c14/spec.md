# C14 子 Agent 工作区隔离 Spec

## 背景

C13 让主 Agent 能把子任务委派给独立上下文的子 Agent，但**独立的只有上下文，不是文件**。
主 Agent 和所有子 Agent 共用同一个工作目录、同一个 Git 工作现场：一个 HEAD、一个暂存区、
一份工作区文件。

后果不是理论上的：子 Agent 只要执行 `git checkout`、`git stash`，或者恰好写了主 Agent 正在
编辑的文件，主 Agent 手上的工作就被掀翻，而**双方都不会收到任何错误**。C13 因此在缺省档下
把子 Agent 实际限制成只读的（判 ASK 自动拒绝），「派子 Agent 去改代码」这条路目前是关着的。

Git 自带的多工作目录机制（worktree）能从物理上解决它：同一个仓库挂多个工作目录，版本库
共享一份，每个目录各有独立的 HEAD、分支、暂存区和工作区文件。

**四条实测结论**（本仓库，2026-08-08），它们是本 spec 多条需求的直接依据：

1. **共享版本库是真的，且开销为零。** 隔离工作区里的 `.git` 不是目录，而是一个 51 字节的
   文本文件，内容为 `gitdir: <主仓库>/.git/worktrees/<名字>`。对比完整 clone 要复制 12M 的
   `.git`。开十个隔离工作区，版本库开销仍是零，全部开销在源码 checkout 上。
2. **凡被忽略规则排除的文件，隔离工作区里一概没有。** 实测本仓库的隔离工作区中缺少
   `.rhinecode/` 与 `config.yaml`。这是 F10（环境初始化）存在的全部理由。
3. **Python 的模块解析在隔离工作区里天然正确。** 在隔离工作区中 `import` 本项目包，解析到的
   是该工作区自己那份源码，而非主项目根那份（解释器会把当前工作目录置于搜索路径最前）。
   本项目因此无需软链依赖目录；但该结论对依赖目录不在源码树内的项目（如 Node 生态）
   不成立，故 F10 仍须提供软链能力。
4. **Git 钩子天然共享。** 主项目根与隔离工作区中查询钩子目录，返回**同一个路径**
   （`<主仓库>/.git/hooks`）。钩子属于版本库的共享部分，隔离工作区原生继承，
   无需任何配置——这是 F11 的依据。

另有一条实测发现的失败形态，是 F22 的依据：当有进程的工作目录位于某个隔离工作区内时，
删除该工作区会**先注销版本库中的登记、再在删除磁盘目录时失败**，留下一个「版本库不认、
磁盘上还在」的残留目录，且后续删除命令会报告「这不是一个工作目录」。

C13 的 spec 明确把「Worktree 文件隔离」列为不做（角色定义中的 `isolation` 字段至今只产生
一条「本项目不支持」的警告）。本章兑现它。

## 目标

- **G1** 让声明了隔离需求的子 Agent 在独立的 Git 工作目录中运行，其一切文件读写与命令执行
  都发生在该目录内，与主 Agent 及其它子 Agent 互不干扰。
- **G2** 让隔离**要么真正生效、要么明确失败**，不存在「以为隔离了其实没有」的中间态。
- **G3** 让子 Agent 的成果以 Git 分支的形式交付，主 Agent 拿到的分支名与路径由系统给出而非
  模型自述。
- **G4** 把工作目录从进程级隐式状态（当前工作目录）改造成显式传递的参数，使路径边界判定按
  调用者所处的工作目录进行，且主对话的工作目录保持为不变量。
- **G5** 让隔离工作区的磁盘占用可收敛，且收敛过程绝不丢失无法从版本库取回的数据。

## 功能需求

### 一、工作目录的显式传递（隔离的地基）

- **F1** 工具执行时，调用方以显式参数告知本次调用的工作目录；工具不依赖进程的当前工作目录。
  未指定时取主项目根。
- **F2** 路径边界判定（权限管线第②层路径沙箱）以**本次调用的工作目录**为根进行，而非进程的
  当前工作目录。相对路径以该根解析，绝对路径必须解析后仍落在该根之内。
- **F3** 命令执行类工具在**本次调用的工作目录**中启动子进程。
- **F4** 主对话的工作目录恒为主项目根，全程不改变；进程的当前工作目录全程不改变。
- **F5** 只读白名单（用户级记忆目录、Skill 目录）的语义不随工作目录变化——它对任何工作目录
  下的读类判定一律生效，且仍不覆盖写类判定。

### 二、隔离工作区的创建

- **F6** 隔离工作区位于 `<主项目根>/.rhinecode/worktrees/<名字>`，随项目的忽略规则不纳入
  版本控制。
- **F7** 名字可由委派方给出，未给出时由系统生成。名字须通过安全校验：以 `/` 分段（允许嵌套），
  每段仅允许字母、数字、`.`、`_`、`-`，总长不超过 64 字符，且任何一段不得为 `.` 或 `..`。
  校验不通过则创建失败。
- **F8** 每个隔离工作区对应一个新分支，基于**当前 HEAD**。主项目工作区中未提交的改动**不带入**
  隔离工作区。分支名与已有分支冲突时，系统自动改名并以最终名字为准。
- **F9** 目标目录已存在且已被版本库登记为本仓库的工作目录时，走**快速恢复**：只做文件系统层面
  的存在性与归属确认，不调用创建命令。
- **F10** 创建后按**声明式清单**做环境初始化，清单区分两类条目：**复制**（各自独立一份，适用于
  配置文件）与**软链**（共享同一份，适用于大型依赖目录）。清单缺省为空。清单条目的来源路径
  必须位于主项目根之内且通过路径安全校验，不满足的条目跳过并记录警告；单条初始化失败不影响
  其余条目，也不导致创建失败。
- **F11** 隔离工作区继承主仓库的 Git 钩子（这是 Git 的原生行为，不做额外配置，也不做禁用）。

### 三、失败与降级

- **F12** 创建隔离工作区失败时（当前目录非 Git 仓库、Git 不可用、名字非法、创建命令失败等），
  委派**直接失败**并回灌结构化原因，**不降级为无隔离运行**。失败不终止主 Agent 的循环。

### 四、隔离需求的声明与触发

- **F13** 角色定义的 frontmatter 支持声明隔离需求，作为该角色每次委派的缺省值。该字段从
  「本项目不支持」的字段表中移除。
- **F14** 委派时可在**本次调用**上指定隔离需求，覆盖方向为**单向加严**：角色已声明隔离时，
  本次调用不能取消它；角色未声明时，本次调用可以要求隔离。
- **F15** 隔离子 Agent 的系统提示中说明：它运行在一个隔离的 Git 工作目录中、该目录的路径、
  所在分支名，以及成果应当提交到该分支。

### 五、结束与交付

- **F16** 子 Agent 结束时，系统检查其隔离工作区的变更状态：无任何变更（无未提交改动且无新增
  提交）时删除目录与分支；有变更时保留。
- **F17** 隔离子 Agent 的结论中，由**系统**追加一段固定格式的交付信息，内容包括：分支名、基点
  提交、隔离工作区路径、新增提交数、变更文件清单、是否存在未提交改动。该信息取自系统对版本库
  的实际查询，不取自模型自述。
- **F18** 主 Agent 的文件搜索类工具（模式匹配与内容检索）缺省不进入隔离工作区所在目录。

### 六、清理

- **F19** 启动时扫描隔离工作区所在目录一次，对**过期**条目执行清理。过期以目录内文件的最后
  修改时间计，阈值可配置，缺省 7 天。不提供手动触发入口。
- **F20** 任何删除操作须依次通过三层过滤，全部通过才执行：
  ① **位置**——待删路径解析后仍位于隔离工作区根目录之内且不等于该根目录本身，路径为空、
  含上级引用或解析失败一律拒绝；
  ② **归属**——该路径被版本库登记为本仓库的工作目录；
  ③ **变更**——存在未提交的工作区改动时拒绝删除。
- **F21** 通过三层过滤的条目按其是否含新增提交区分处理：含新增提交的**只删目录、保留分支**；
  不含新增提交的删目录并删分支。清理结果（含被保留的分支名）在启动时向用户报告。
- **F22** 删除过程需处理「工作目录已注销但磁盘目录仍在」的残留状态：先修剪版本库中的失效登记，
  再对残留目录执行独立的删除兜底。

### 七、观测

- **F23** 角色报告中展示每个角色的隔离声明；任务列表中展示隔离任务的工作区路径与分支名。
- **F24** 隔离工作区的创建、初始化、保留/删除决定与清理结果产生行为记录事件。

### 八、自动化钩子

- **F25** 由隔离子 Agent 触发的工具级钩子，其命令在**该子 Agent 的工作目录**中执行；由主对话
  触发的仍在主项目根中执行。钩子对隔离子 Agent 的生效范围与 C13 一致（全量生效）。

## 非功能需求

- **N1 隔离只会收紧，不会放宽。** 隔离子 Agent 的能力集合是非隔离子 Agent 的子集：它的路径
  沙箱根从主项目根缩小为隔离工作区，其余四层权限判定逐字不变。C13 已论证「子 Agent 的能力
  只会比主对话小」，本章不得使该论证失效——任何让隔离子 Agent 触及主项目根的路径都必须被
  第②层拒绝。
- **N2 路径判定 fail-safe。** 工作目录参数缺失、非法、解析失败时，路径判定一律按「越界」处理
  （拒绝），绝不回退到「按主项目根判定」——回退会让一次隔离故障静默变成一次越权。
- **N3 不改变未启用隔离时的任何行为。** 未声明也未在调用上要求隔离时，子 Agent 与主对话的
  行为与 C13 逐字一致，包括路径判定结果、权限结论、结论渲染、行为记录事件。
- **N4 并发安全。** 多个隔离子 Agent 可同时存在。它们共享同一个版本库，因此对版本库的写操作
  （创建工作目录、创建分支、删除）须能容忍并发；单个子 Agent 的创建或清理失败不影响其它。
  既有的任务表加锁不变量（临界区只做纯内存读写）不得因本章被违反——文件系统与版本库操作
  一律在锁外。
- **N5 数据安全优先于空间回收。** 任何自动删除都不得丢失无法从版本库取回的内容。未提交的
  工作区改动只存在于该目录中，故其存在即构成删除的**无条件否决**，不受过期时长影响。
- **N6 隔离状态必须可观测。** 一个子 Agent 是否运行在隔离工作区中、在哪个目录、哪个分支，
  必须能从界面或报告中看到。本章不接受任何「隔离与否在界面上看不出来」的形态——这正是
  F12 拒绝降级的同一条理由。
- **N7 非 Git 环境不受影响。** 当前目录不是 Git 仓库时，除「委派给声明了隔离的角色」会失败
  之外，既有全部能力（含非隔离的子 Agent 委派）照常可用，启动照常完成。
- **N8 隔离工作区内的产物与主项目同级敏感。** 它是一份完整的源码 checkout，且环境初始化可能
  把本地配置复制进去。该目录必须随项目的忽略规则排除在版本控制之外，其内容不得被当作
  「临时文件」对待。

## 不做的事

以下明确不在本章范围内。前四条是用户在需求澄清阶段明确划出的，其余是澄清过程中逐条判定的。

1. **主对话自身进出隔离工作区。** 本章只做子 Agent 隔离，主对话的工作目录是不变量（F4）。
   做它意味着工作目录成为运行期可变状态，C8 上下文存盘、C9 会话存档与记忆、各层配置文件的
   路径假设全部要重新定义，属于另一个章节的范围。
2. **隔离工作区之间的合并策略。** 系统只负责产出可合并的分支（F17），怎么合并由上层用
   Git 决定。
3. **跨工作区的代码同步。** 主项目根的改动不会自动流入已存在的隔离工作区，反之亦然。
4. **多 Agent 并行编排。** 子 Agent 之间不通信、不互相委派、无优先级调度（沿用 C13 的边界）。
5. **后台定时清理。** 清理只在启动时发生一次（F19）。做定时器意味着引入本项目第一个周期性
   后台线程，且清理与运行中的子 Agent 存在竞态，收益不足以抵消成本。
6. **手动清理入口。** 不提供触发清理的命令。
7. **把主项目根的未提交改动带入隔离工作区。** 基点是当前 HEAD（F8）。带入会让「子 Agent
   改了什么」失去可指认的边界。
8. **由系统代替子 Agent 提交。** 提交是子 Agent 自己的动作。系统只在结束时如实报告有没有提交
   （F17），并对未提交改动施以删除否决（F20③）。
9. **环境初始化的启发式自动识别。** 初始化只按显式清单执行（F10）。自动识别会把含密钥的本地
   配置复制进多个临时目录。
10. **Git 钩子的禁用与定制。** 隔离工作区原生继承主仓库钩子（F11）。
11. **按「已合并」判定删除分支。** 分支只在「无新增提交」时才被删除（F21）。基于
    `--merged` 的判定在 squash / rebase 后不可靠，误判方向是删掉尚未合入的成果。
12. **非 Git 版本控制系统的隔离，以及非 Git 环境下的替代隔离机制。** 不引入外部钩子作为兜底。
13. **隔离工作区的跨会话复用与持久化编目。** 系统不记录「上次那个工作区是给哪个任务用的」；
    磁盘上的目录与版本库的登记就是唯一事实来源。

## 验收标准

### 工作目录的显式传递

- **AC1**（F1/F4）在一次含隔离子 Agent 的完整会话前后，进程的当前工作目录不变；主对话的
  文件读写始终发生在主项目根。
- **AC2**（F2）隔离子 Agent 读写其工作区内的相对路径成功；读写主项目根内、但在其工作区之外
  的路径（含以绝对路径给出的形式）被第②层拒绝，拒绝原因为路径越界。
- **AC3**（F2/N2）工作目录参数缺失或非法时，路径判定结果为拒绝，而不是按主项目根放行。
- **AC4**（F3）隔离子 Agent 执行命令查询当前目录，返回的是其隔离工作区路径。
- **AC5**（F5）隔离子 Agent 读取用户级记忆目录中的文件成功；向该目录写入被拒绝。
- **AC6**（N3）在未启用隔离的情形下，子 Agent 与主对话的路径判定结果、权限结论与结论渲染与
  改造前一致。

### 创建

- **AC7**（F6）委派给声明了隔离的角色后，`<主项目根>/.rhinecode/worktrees/<名字>` 出现，
  且该路径被版本控制的忽略规则排除。
- **AC8**（F7）名字含上级引用、含非法字符、超长、或某一段为 `.`/`..` 时，创建失败且未在文件
  系统上产生任何目录；含 `/` 的合法嵌套名字创建成功。
- **AC9**（F7）委派未给出名字时，系统生成一个通过校验的名字并创建成功。
- **AC10**（F8）隔离工作区的分支基于当前 HEAD；主项目根中一处未提交的改动在隔离工作区中
  不可见。
- **AC11**（F8）目标分支名已存在时，创建仍成功，且交付信息中报告的是实际使用的分支名。
- **AC12**（F9）对一个已存在且已登记的目录再次发起创建，不产生新的版本库操作，且返回成功。
- **AC13**（F10）配置一条复制条目与一条软链条目后创建，隔离工作区中分别出现一份独立副本与
  一个指向主项目根的链接；副本被修改后主项目根中的源文件不变。
- **AC14**（F10）清单中一条指向主项目根之外的条目被跳过并产生警告，创建本身仍成功，其余
  条目照常生效。
- **AC15**（F11）在主仓库配置一个会写标记文件的提交钩子后，隔离工作区中的提交同样触发它。

### 失败

- **AC16**（F12/N7）在一个非 Git 仓库的目录中启动，委派给声明了隔离的角色时失败，失败原因
  明确指出当前目录不是 Git 仓库；同一会话中委派给未声明隔离的角色照常成功；启动过程无报错。
- **AC17**（F12）创建失败后主 Agent 的循环继续运行，能够就该失败继续对话或改派其它角色。

### 声明与触发

- **AC18**（F13）角色定义中声明隔离字段后，该角色不再产生「本项目不支持该字段」的警告，
  且角色报告中显示其隔离声明。
- **AC19**（F14）角色已声明隔离时，委派方在本次调用上要求不隔离**无效**，仍然创建隔离工作区；
  角色未声明隔离时，委派方在本次调用上要求隔离**有效**，创建隔离工作区。
- **AC20**（F15）隔离子 Agent 被问及自身工作目录时，其回答与实际隔离工作区路径一致。

### 结束与交付

- **AC21**（F16）隔离子 Agent 未产生任何变更时，其工作区目录与分支在结束后均不存在。
- **AC22**（F16）隔离子 Agent 产生了变更时，其工作区目录在结束后仍存在。
- **AC23**（F17）主历史中该子 Agent 的结论末尾含系统追加的交付信息段，其中的分支名、提交数与
  变更文件清单与直接查询版本库所得一致；即使模型在自己的正文中写了不同的分支名，交付信息段
  中的仍为实际值。
- **AC24**（F18）主 Agent 对一个同时存在于主项目根与某隔离工作区中的字符串做内容检索，结果
  只来自主项目根。

### 清理

- **AC25**（F19）存在一个超过阈值且无变更的残留工作区时，启动后它被删除，并在启动报告中列出；
  未超过阈值的同类工作区不被删除。
- **AC26**（F20①）待删路径为空、含上级引用或指向隔离工作区根目录之外时，删除被拒绝，文件
  系统无变化。
- **AC27**（F20②）隔离工作区目录下一个手工创建的普通目录不被清理。
- **AC28**（F20③/N5）一个超过阈值但含未提交改动的工作区不被删除，并在启动报告中列出原因。
- **AC29**（F21）一个超过阈值、无未提交改动但含新增提交的工作区被删除目录，其分支仍存在且
  可从版本库取回其提交内容；启动报告中列出该分支名。
- **AC30**（F22）对一个「版本库已不登记但磁盘目录仍在」的残留执行清理，目录被删除且不报错。

### 观测

- **AC31**（F23/N6）任务列表中，隔离任务显示其工作区路径与分支名，非隔离任务不显示这些字段。
- **AC32**（F24）一次隔离委派的行为记录中，可依次找到创建、初始化、结束时的保留或删除决定；
  一次启动清理的记录中可找到清理结果。

### 自动化钩子

- **AC33**（F25）在工具级钩子中执行一条打印当前目录的命令，由隔离子 Agent 触发时打印其隔离
  工作区路径，由主对话触发时打印主项目根。
- **AC34**（F25）一条会拦截某类工具调用的钩子规则，对隔离子 Agent 的同类调用同样生效。

### 并发

- **AC35**（N4）三个隔离子 Agent 被同时委派：三个工作区与三个分支全部创建成功、互不干扰，
  各自的交付信息段指向各自的分支；其中一个的创建失败不影响其余两个的运行与交付。

### 端到端

- **AC36** 主 Agent 在自己修改某个文件的同时，委派一个隔离子 Agent 修改另一个文件：两者的
  改动互不可见、互不覆盖；子 Agent 结束后主 Agent 手上的未提交改动完好；主 Agent 依据交付
  信息段中的分支名执行合并，得到两处改动的并集。
