# C14 子 Agent 工作区隔离

**一句话**：给声明了隔离的子 Agent 开一个独立的 Git 工作目录，让它和主 Agent
同时改文件而不互相覆盖——成果经一个分支交回来。

## Worktree 是什么（零基础版）

C13 之前，主 Agent 和所有子 Agent 共用一个工作目录、一个 Git 工作现场：
一个 HEAD、一个暂存区、一份工作区文件。子 Agent 只要 `git checkout`、`git stash`，
或者恰好写了主 Agent 正在编辑的文件，主 Agent 手上的工作就被掀翻，
**而双方都不会收到任何错误**。

`git worktree add` 能从物理上解决它：同一个仓库挂多个工作目录，
**版本库共享一份、工作现场各自独立**。

## 五条实测结论

它们是本章多条设计决定的直接依据，写在这里免得后来的人把「刻意不做」当成漏做。

| # | 实测 | 它决定了什么 |
| --- | --- | --- |
| 1 | 隔离工作区里的 `.git` 不是目录，是一个 **51 字节的文本文件**（`gitdir: <主仓库>/.git/worktrees/<名字>`） | 「共享版本库」开销为零；也是**快速恢复不调 git** 的物理依据——归属就写在那个文件里 |
| 2 | 凡被忽略规则排除的文件，工作区里**一概没有**（本仓库缺 `.rhinecode/` 与 `config.yaml`） | F10 环境初始化存在的全部理由 |
| 3 | Python 的模块解析在工作区里**天然正确**（解释器把 cwd 放在搜索路径最前） | 本项目无需软链依赖目录；但对 Node 这类项目不成立，故仍须提供软链能力 |
| 4 | 主项目根与工作区查询钩子目录返回**同一个路径** | F11 对 git hooks **什么都不做**——git 已经共享了 |
| 5 | 进程 cwd 在工作区内时删除它，git 会**先注销登记、再删目录失败**，留下「版本库不认、磁盘还在」的残骸 | F22 的删除流程必须有 `prune` + 独立的目录删除兜底 |

## 九个由用户拍板的设计决策

读代码前先看这几条，它们决定了本章的形态。

1. **只做子 Agent 隔离**，主对话的工作目录是不变量。做主对话进出会让工作目录
   成为运行期可变状态，C8 上下文、C9 记忆与存档的路径假设全部要重定义。
2. **分支交付**：子 Agent 把成果提交到自己的分支，主 Agent 据此 `git merge`。
   无变更自动删、有变更保留。
3. **环境初始化走声明式清单**（copy / link 二分），缺省为空，**不做启发式**。
4. **基点取当前 HEAD**，主项目根的未提交改动**不带入**。
5. **角色级声明 + 调用级覆盖，单向加严**：角色声明了隔离，模型关不掉。
6. **创建失败明确失败，不降级**。
7. **清理只在启动时扫一次**，不做后台定时器，也不提供手动命令。
8. **交付信息由系统追加**，不靠模型自述分支名。
9. **三层过滤按数据安全性分开判**：有未提交改动 → 无条件不删；无未提交改动但有
   提交 → 删目录、**留分支**；两者都无 → 目录与分支一并删。

## 四处与 Claude Code 刻意不一致

本章大量参照了 Claude Code 的 `EnterWorktree` / `ExitWorktree` / `isolation` 字段，
但有四处**刻意不同**，理由都写在 spec 里：

| | Claude Code | 本章 | 为什么 |
| --- | --- | --- | --- |
| 主会话 | `EnterWorktree` 会切换会话的工作目录 | **不做**，主对话工作目录是不变量 | 见决策 1 |
| 基点 | 缺省 `fresh`（从 `origin/<默认分支>`） | **当前 HEAD** | 它的场景是「人要开一个干净的新功能」，我们的是「主 Agent 就着当前状态派活」——起点必须跟着当前状态走，否则子 Agent 找不到主 Agent 刚写的东西 |
| 环境初始化 | 外包给 `WorktreeCreate` hook | **声明式清单** | 把通用需求变成「用户必须自己写 shell」；且 `hooks.yaml` 是本项目最大的攻击面 |
| 切换目录方式 | 会话级 chdir | **explicit cwd 参数**贯穿到权限引擎 | 用户明确要求；也让「按调用者判定边界」成为可能 |

## 本章最要紧的一条：隔离是物理的

隔离子 Agent 出不去，**不是因为它守规矩**，而是因为它每一次路径请求都在
权限管线**第②层**被以它自己的工作区为界量过。地基是这条改造：

```
c14 之前：path_guard 把「项目根」写死成 Path.cwd()，全进程一个边界
c14 之后：四个判定函数 root 必传（无默认值），Agent Loop 是唯一的 cwd 分发中心
```

`workspace_root` 因此被**重命名**为 `main_project_root`——15 个既有调用点里
12 处要主项目根、3 处要调用者的工作目录，不改名就没法强制逐个复核，
而这两者混淆一次就是隔离失效。

## 开发与验收期抓出的十五处问题

单靠设计看不出来、只有真跑起来才暴露的。**共同点是它们都不报错**——
编译过、测试绿、界面正常，只是某个行为悄悄不对：

1. **`Path("")` 等于 `Path(".")`**——`judge_removal` 里那句空路径检查从来没生效过。
   位置层兜住了它，但拒绝理由会写成「不在隔离工作区目录内」，把排查引向错误方向。
   这正是 CLAUDE.md 记的那次「空变量 rmtree 删掉整个仓库」的形态。
2. **启动清理原本永远删不掉分支**——基点未知时提交数恒为 0，我最初用「找到分支就
   当成有提交」兜底，结果是分支无限累积。改用 `git merge-base` 真正算出分叉点；
   算不出时返回 **-1 而非 0**（0 的语义是「确定没有、可以删」，混淆会删掉成果）。
3. **协调层的逐文件权限过滤器漏改后「什么都搜不到」**——构造权限请求缺 `cwd`
   → `TypeError` → 被调用点的 `except Exception: return False`（fail-safe）吞掉
   → 全部文件判拒绝，而工具照常返回 ok=True、结果为空。为此把过滤器签名改成
   `(rel_path, base)`，让漏改当场断掉而不是静默失效。
4. **`resolve_readable` 的白名单分支不校验 root**——漏传 cwd 时白名单读取仍成功。
   不构成提权（白名单本就在任何 root 下可读），但会造成「同一次漏传，工作区读取
   失败、白名单读取成功」这种一半一半的现象。
5. **循环对 hook 分发的异常是吞掉的**（设计如此，hook 不得打断循环），于是一个
   签名不匹配的 HookManager 会**静默地一条事件都不分发**。
6. **`git worktree add` 对空的已存在目录是成功的**——最初的测试前提写错了，
   有意义的场景是非空目录（git 会拒绝）。

**以下两处是验收期才抓到的，它们说明「跑完测试」不等于「验收完成」：**

7. **`worktree.copy: ["."]` 会清空刚建好的工作区。** `"."` 是完全合法的路径写法，
   越界检查照样通过，而它解析出来就是根自己 → `rmtree(工作区根)` + 把整个主项目
   （含其它隔离工作区）递归拷进去。**不是攻击构造**——用户想「把项目里的东西
   都带过去」时很自然就会这么写。是**审计产品代码里所有删除操作**时发现的。
8. **`/agents` 任务行没显示隔离工作区信息。** 那次改动用了不带断言的字符串替换，
   没匹配上就静默跳过了。是**对着实际渲染输出看**才发现的——单元测试不会替你
   看一眼那行到底长什么样。

**再往后七处是真实模型验收抓的**（2026-08-08，逐条见 `acceptance/live-model.md`）：

9. 主 Agent 会在任务描述里写「不要执行 git commit」，**成果就此搁浅**在工作区里，
   `git merge` 拿不到任何东西——而它照样报「已完成」。
10. Hook 事件负载里的 `cwd` 没跟着触发它的 Agent 走（子进程的 cwd 对了，字段没对）。
11. `worktree.link` 建出来的软链**被第②层沙箱一律拒绝**，子 Agent 一个字节读不到。
12. 主 Agent 的搜索被 `.rhinecode/` 里自己的会话存档与上下文存盘淹没，**并且自放大**。
13. 子 Agent 的环境信息段报的是主项目根，与 `<isolated-workspace>` 段自相矛盾。
14. `/agents` 对已回收的工作区仍报分支名与路径（用户照着 `git checkout` 会扑空）。
15. 「隔离子 Agent 看不到你未提交的改动」没写进模型**决策期**读到的文本里。

⚠ **其中 10 与 11 上一轮还判了 ✅。** 原因分别是：那次的 Hook 场景只量了两个来源
中的一个；那次的 `link` 场景是**直接在磁盘上验的**（`Path.open` 读得到），
而产品里没有任何一条路径是那样访问文件的——一切都要过权限管线。

## ⚠ 两处术语提醒

- **`isolation: worktree`（c14）与 `type: branch`（c13）、`context: fork`（c11）
  是三件不同的事**：前者是**文件**隔离（上下文照旧），后两者是**上下文**的处置方式
  （文件照旧）。一个隔离的定义式子 Agent 同时具备「空白上下文」与「独立工作目录」。
- **`main_project_root()` 与「本次调用的工作目录」不是一回事**。前者只用于定位
  与调用者无关的位置（配置文件、存档目录），后者用于路径边界判定。
  c14 之前它们共用一个名字，那正是要改名的原因。
