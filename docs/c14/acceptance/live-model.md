## 二、真跑抓出的七个问题

共同点仍然是那一条：**它们都不报错**——编译过、1972 项测试全绿、界面正常。

### ① 主 Agent 会指使隔离子 Agent「不要提交」，成果就此搁浅（已修）

**现场**：用户说「我这边 `core.py` 的改动先不提交」，主 Agent 把这句话推广到了委派上，
在任务描述里写下 `3. 不要执行 git commit（不提交代码），让改动留在工作目录中即可。`
连续两次委派都这么写。后果：

```
worktree_settle  dirty=true  commits=0   → git merge 拿不到任何东西
```

主 Agent 的两种反应都很糟：第一次报给用户「已完成，未提交，符合要求」（用户以为拿到了
成果）；第二次**自己钻进工作区目录逐个读 diff、再在主目录重打一遍**——隔离本该省下的
上下文全部吃回来，一次委派的价值当场归零。

交付信息段当时**只陈述事实**（「未提交改动：有」），指望模型自己看出问题，两次都没看出来。

**修**：`dirty 且 commits==0` 时由系统追加三句（成果没交回来 / 不要自己去目录里抄文件 /
下次别写「不要提交」），并同步改 `run_agent.description`——主 Agent 在两个不同时刻读到
同一条约束，一处强一处弱等于白改。

**复验**（同样的挑衅：用户明说「这件事做完不要提交」）：主 Agent 改口写成
「把改动在自己场景内提交到一个分支（这是交付成果的唯一通道）；不要 push、不要 merge
到主对话所在的主干」→ `commits=1 dirty=false`，成果交回来了。

### ② Hook 负载里的 `cwd` 没跟着触发它的 Agent 走（已修）

用一条把 `os.getcwd()` 与负载 `cwd` 都写进探针文件的 `pre_tool_use` Hook 量出来：

| 触发者 | `process_cwd` | `payload_cwd` |
| --- | --- | --- |
| 主对话 | 主项目根 ✅ | 主项目根 ✅ |
| 隔离子 Agent | **隔离工作区** ✅ | **主项目根** ❌ |

F25 只兑现了一半。这不是美观问题：C12 明令「配置里不做任何字符串插值，上下文只经标准
输入的 JSON 抵达」，**负载里的 `cwd` 因此是 Hook 脚本获取工作目录的唯一正规渠道**。
一个照着文档写的「工具写完就跑 lint」的 Hook 会拿主项目根去 lint。`cwd` 还是能写进
`if:` 的条件字段，分裂让 `cwd: "*/worktrees/*"` 永不命中，而 `/hooks` 只显示「触发 0 次」。

上一轮验收判它 ✅，是因为只看了子进程的实际目录——那一半确实是对的。

**复验**：两者一致。

### ③ `worktree.link` 建出来的软链被沙箱一律拒绝（已修为「降级 + 留痕」）

配了 `worktree.link: ["vendor"]` 之后，隔离子 Agent 连着试：

```
read_file('vendor/bigdep/VERSION')  → [权限拒绝·sandbox] 路径越界，超出工作目录
glob_files('vendor/**/VERSION')     → 同上
glob_files('vendor/bigdep/*')       → 同上
```

最后耗尽 12 轮预算失败收场。根因是 **F10 与 F2 互斥**：`link` 的源在主项目根、落点在
隔离工作区，建出来的软链天然指向工作区之外，而第②层明令拒绝这类符号链接。

**而系统认为它成功了**：`worktree_provision` 记的是 `applied=2`。配了却没生效、
界面上看不出来——本项目最忌讳的形态。

上一轮验收判它 ✅，是因为**直接在磁盘上验的**（`Path.open` 读得到），没有经工具与权限管线。

**修**：建之前先自检落点是否在工作区内，不在就直接复制并记一条说清原因的警告
（沿用本模块既有的「建不了软链就复制 + 留痕」处置）。真正让 `link` 可用要动第②层的
边界判定，属安全边界变更，已登记进 CLAUDE.md 单独立项。

### ④ 主 Agent 的搜索被 RhineCode 自己的运行期产物淹没（已修）

一次普通的 `grep_content('USAGE')` 实测返回「68 处匹配 · 5 个文件」，真正的源码命中
**只有一个**，其余来自 `.rhinecode/sessions/*.jsonl`、`.rhinecode/context/*.txt`、
`.rhinecode/memory/*.md`。三重危害，前两条那次实跑里都真的发生了：

1. **结果被自己的历史淹没**——用户说过的每句话都逐字躺在会话存档里。
2. **自放大**——结果过大 → c8 存进 `.rhinecode/context/` → 下次搜索命中这个存盘 →
   更大 → 再存盘。实测滚到 **1.8 MB**，模型分段去读它、读出来的却是上一次搜索结果的
   副本，白烧五次工具调用。
3. **它是 deny 规则的间接绕过**——`deny: Read(config.yaml)` 挡得住直接读，
   但那份内容一旦被读过就逐字躺在会话存档里，一次 grep 就能捞回来。

这不是 C14 引入的（`grep_content` 一直如此），是 C14 的场景 7 把它照出来的。

**修**：`runtime_artifact_dirs_of` 按路径相等排除 sessions/context/traces；
`memory/` 与 `agents/` 刻意保留可搜，并有用例钉住这个「刻意」。

### ⑤ 子 Agent 的环境信息段报的是主项目根（已修）

隔离子 Agent 的系统提示里同时存在两个互相矛盾的「工作目录」：环境信息段固定报主项目根，
`<isolated-workspace>` 段报工作区。模型的实际反应是把两者调和成一个相对路径——
连着去读 `.rhinecode/worktrees/<名字>/calc/percent.py`，全部落空后才改用普通相对路径。

**它不报错**：权限管线、工具执行、Hook 子进程都已按工作区判定，唯独告诉模型的那句话
没跟上。代价是每次隔离委派白烧两轮。

**修**：`environment_text` 改成收一个入参（本次子 Agent 的工作目录），**不给默认值**
——与 `PermissionRequest.cwd` 同一条理由。git 分支也随之跟着工作区走。

**复验**：环境信息段现在报工作区路径、`Git 分支：agent/dev-a00d7527`，
同一类任务 6 轮跑完（修前 8~12 轮），且一次都没再试过 `worktrees/<名字>/` 那种路径。

### ⑥ `/agents` 对已回收的工作区仍报分支名与路径（已修）

两个只读任务跑完即回收（F16），而任务行仍原样展示「隔离工作区：分支 `agent/surveyor-xxx`
· 路径 …」。用户照着它 `git checkout` 会拿到「分支不存在」。

交付信息段那边刻意「不给已删分支的名字」，是同一条理由；那边做对了、这边漏了。

**修**：`TaskRecord.worktree_removed`，报告据它改口成「已回收」。

### ⑦ 「隔离子 Agent 看不到你未提交的改动」没写在决策期读到的文本里（已修）

真实工作场景实测：主 Agent 手上改着 `pending()`，用户要求把「给 `pending()` 加 limit
参数」隔离派出去。主 Agent 自己推出了这条约束——

> 隔离委派在独立工作目录基于 `c6443e4` 跑的，那样它看不到我手上这份改动，
> 会基于旧的 `(id, dict)` 元组形态去加 limit，合并回来就和我的字典列表冲突了。

推得完全正确，但为此在一轮回复里把同一个两难**重述了七遍**，最后停下来请用户拍板。
隔离宣传的场景是「你手上有未提交改动时用它」，基点规则是「取当前 HEAD、未提交改动不
带入」，两句话组合到同一个文件上时必然冲突，而工具描述原先只讲前半句。

**修**：`description` 与 `isolation` 参数说明两处都写明。两处都写是因为模型不一定两处
都读，只写一处等于赌它读的是那一处。

## 三、真实工作场景（checklist 之外）

预置 `seed_realistic`：有包结构、有能跑的测试套件、有真实 `.gitignore` 的待办清单项目。

| 场景 | 结果 |
| --- | --- |
| **两个隔离子 Agent 并发 + 依次合并** | ✅ 两个工作区各自 checkout、各自提交，主 Agent 连着两次 `git merge --no-ff` 全过，8 个测试通过 |
| **合并冲突**（主 Agent 未提交改动 vs 子 Agent 基于旧 HEAD 改同一函数） | ✅ 主 Agent 走 `stash push → merge → stash pop → 解冲突 → add → stash drop`，最终 `pending(limit=None)` 同时含两边改动，无残留冲突标记，8 测试通过 |
| **基点跟随当前 HEAD**（决策 4） | ✅ 第三次委派的 `base_commit` 是前两次合并后的新 HEAD，不是原始提交 |
| **隔离工作区里跑测试套件** | ✅ `python -m unittest discover -s tests` 在工作区里正常运行（Python 把 cwd 放在搜索路径最前，README 的实测结论 3 成立） |

⚠ **合并冲突这条 spec / checklist 一条都没覆盖**，而它是隔离交付的**必经之路**：
子 Agent 的基点是委派时的 HEAD，主 Agent 在它跑的这段时间里完全可能提交新东西——
真实使用里这是常态，不是边角情况。产品行为经受住了，但这条应当补进 checklist。

## 四、未修，如实列出

### A. `Esc` 不会取消正在跑的隔离子 Agent（**语义保留，2026-08-10 补上提示并复验**）

> **后续处置（2026-08-10，PR #27）**：语义**保持不动**（用户拍板方案 A）——
> `Esc` 仍然只停主对话，C13「委派永不阻塞」的契约原样成立。改的是**把话说清**：
> 按下时若还有子 Agent 在跑，界面明确告知还剩几个、怎么停。
>
> **真实模型复验（`deepseek-v4-flash`，`seed_subagents`，走 `keys escape` 真人按键路径）**：
>
> ```
> （按 Esc 前 status：background.subagents = 2，state = busy）
> seq 31  ui_message [system] 已请求取消当前回合。⚠ 仍有 2 个子 Agent 在后台运行
>                             ——Esc 只停主对话，不会停它们。要一并停止请用 /agents cancel all。
> seq 46  agent_event finished → stop_reason=user_cancelled      ← 主对话确实停了
> seq 50+ subagent:explore_retry / audit_hardcode 继续跑          ← 子 Agent 确实没停
>         Esc 之后它们又产生 44 条事件（15 条 tool_execute、2 条 subagent_end，各 4 轮跑完）
> ```
>
> 四条判据全中：**条数照实**（2 = 按下那一刻的真值）、**主对话真停**、
> **子 Agent 真没停**（这正是当初那 7 轮的同一现象，只是现在用户被告知了）、
> 以及**反证**——另一轮在**空闲态**误按 `Esc`，界面一个字都没多出来。
>
> ⚠ **界面截图在这里是弱证据**：`screen` 只抓可见区域，那条提示一秒内就被子 Agent
> 的后续输出顶出了屏幕，按截图判会得出「没出现」的错误结论。判据取自 trace。
>
> 下面是当初的原始记录，保留不动。

实测：委派一个大活，25 秒后按 `Esc`（走真人取消入口）。主循环停了，**子 Agent 继续跑完
7 轮、写文件、提交、留下工作区与分支**。`request_cancel` 只置主循环的取消信号，
子 Agent 的 `cancel_event` 只有 `/agents cancel`、`/clear`、`/resume` 会置。

隔离让这件事**不至于造成损害**（写的都在工作区里），但用户的心智模型是「Esc = 停」。
更需要注意的是**非隔离**子 Agent：那时它继续往主项目根里写。

改不改属于设计决策（牵动 C13「委派永不阻塞」的契约），**本轮不动**，登记备议。

### B. 隔离工作区的累积

一个会话里四次委派 = 四份完整源码 checkout。有提交的工作区在结束时**保留**（F16），
启动清理要等 `cleanup_days`（缺省 7 天），而本章**刻意不提供手动清理入口**（决策 7）。
配合问题 ①（未提交 → 永不回收）在修复前会无限累积。修复后一般会落到「有提交」这一档，
启动清理能删目录、留分支，但仍需等到过期。

真实项目里每份 checkout 是整个源码树。这条已在 spec 的「明确不做」里，此处只记实测观感。

### C. ③层可配置规则对复合命令不拆段的 **allow 侧症状**

已知项 #12 记的是 deny 侧（`git status && git push` 绕过 `deny: Bash(git push *)`）。
实测发现 allow 侧同样存在：预置了 `allow: Bash(git *)`，而子 Agent 发出的
`cat .gitignore 2>/dev/null; echo "---"; git ls-files` **整串不命中**，在非交互环境下
被自动拒绝、白烧一轮。方向是偏严的（安全），但可用性上有真实摩擦。

同一处代码、同一条修法，仍归入已知项 #12。

## 五、方法论：为什么这轮能抓到上一轮抓不到的

三条都值得记下来：

1. **上一轮的场景 8 是「直接在磁盘上验」的**（`Path.open` 读得到软链下的文件），
   而产品里没有任何一条路径是那样访问文件的——一切都要过权限管线。
   **验一个能力，必须从模型实际会走的那条路上验。**
2. **上一轮的场景 9 只量了一半**（子进程的 cwd 对了，就没再看负载字段）。
   一个字段两处来源时，两处都要量。
3. **单元测试验的是「代码做了它该做的」，真实模型验的是「模型会不会那么用」。**
   问题 ①⑤⑦ 全部属于后者：代码一行没错，是模型读到的文本让它走了岔路。
   这与 C11 发现「Skill 欠触发」是同一类问题的第三次。
