## 端到端场景

### 场景 1 · 并行不覆盖（本章的核心承诺）

**做法**：主 Agent 改 `A.py` 且不提交 → 委派隔离子 Agent 改 `B.py` 并提交 →
主 Agent 按交付信息里的分支名合并。

| 机器判到了什么 | 据此做的判断 |
| --- | --- |
| 子 Agent 工作区里 `A.py` = `MAIN_WIP = 1`（旧版本） | 未提交改动**确实不带入**（F8） |
| 子 Agent 结束后主目录 `A.py` = `MAIN_WIP = 999`（含注释原样） | 主 Agent 手上的活**完好无损** |
| `B.py` 不在主项目根 | 子 Agent 的写**没有落到主目录** |
| `dirty=False commits=1` → 保留 | 结束决策正确（F16） |
| 合并后 `A.py` 仍是 999、`B.py` = `SUB_RESULT = 42` | **拿到了两处改动的并集**（AC36） |

✅ **通过。**

### 场景 5 · 启动清理的三种结局

预置三个过期工作区后重跑清理，启动提示原文：

```
隔离工作区清理：
- 已回收 clean（无任何变更，目录与分支一并删除）
- 已回收 committed（成果保留在分支 agent/committed，可 git checkout 取回）
- 保留 wip：存在未提交的改动，保留以免丢失
```

| 机器判到了什么 | 据此做的判断 |
| --- | --- |
| `clean`：目录否、分支否 | 纯残骸被完全回收 |

| `wip`：目录在、`half.py` 在 | 未提交改动是**无条件否决**（F20③/AC28/N5） |

✅ **通过。**

### 场景 6 · 交付信息不被模型污染

**做法**：先占掉 `agent/task` 分支逼系统改名，让模型在正文里写错的分支名。

| 机器判到了什么 | 据此做的判断 |
| --- | --- |
| 实际分支 = `agent/task-2` | 撞名改名生效（F8/AC11） |
| 模型正文说「提交到 agent/task 分支了」 | 模型的原话保留，不篡改 |
| 交付信息段 = `分支：agent/task-2（基于 9c6df51）` | **系统给的是实际值**（F17/AC23） |
| 按交付信息 merge → `r.py` 出现 | 主 Agent 拿到的名字**可直接用** |

⚠ **这条特别值得记**：模型写的 `agent/task` **确实存在**（那是预先占位的空分支），

靠模型自述分支名的方案会在这里悄无声息地失败。

## 安全边界（可运行的反证）

放行档 + 一条 `allow: Write(*)` 规则下，从隔离工作区发起：

| 请求 | 结论 | 命中层 |
| --- | --- | --- |
| `rm -rf /` | **DENY** | `blacklist` |
| 写 `../../A.py` | **DENY** | `sandbox` |
| 写主项目根的绝对路径 | **DENY** | `sandbox` |
| 写指向主项目根的符号链接 | **DENY** | `sandbox` |
| `cwd` 缺失 | **DENY** | `sandbox` |
| 同一请求但 `cwd` = 主项目根 | ALLOW | — |

最后一行是关键对照：它证明前面几条不是「什么都拒」，而是 **cwd 在起作用**。

✅ **隔离只收紧不放宽，且放行档与 allow 规则都翻不过①②层。**

## 验收期抓出的两处漏洞（已修）

1. **`worktree.copy: ["."]` 会清空刚建好的工作区。** `"."` 是完全合法的路径写法，
   越界检查照样通过，而它解析出来就是根自己 → `rmtree(工作区根)` +
   把整个主项目递归拷进去。**不是攻击构造**——用户想「把项目里的东西都带过去」
   时很自然就会这么写。已加两条判断（来源不得等于主项目根、落点不得等于工作区根）
   与三条护栏。
2. **`/agents` 任务行没显示隔离工作区信息。** 那次改动用了不带断言的字符串替换，
   没匹配上就静默跳过了——编译过、测试绿、只是那一行从来没出现过。
   **对着实际输出看才发现**，这也是为什么验收不能只跑测试。
