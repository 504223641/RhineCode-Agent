# C15 子 Agent 协作

**一句话**：让 C13 那些互不相识的一次性子 Agent 变成能协作的队员——
共享一块任务看板、按名字互相说话、干完留在场上等着被叫醒接着干。

## 零基础版：「协作」到底加了什么

C13 之前的子 Agent 是**一次性临时工**：派一件活出去，干完汇报一句结论就消失。
它们彼此不认识、所有信息经主 Agent 中转、干完历史就丢。

C15 把它们变成**同事**。用一个具体场景说清差别——用户说「给项目加登录功能」：

| | C13 | C15 |
| --- | --- | --- |
| 拆活 | 主 Agent 自己在脑子里拆 | 把 4 条任务写进**共享看板**，标注谁挡着谁 |
| 干活 | 派 explorer 去查、拿回结论，主 Agent 自己写代码 | 派 2 个**具名队员**，各自去看板上认领没被挡住的任务 |
| 协作 | 甲和乙互相不知道对方存在 | 甲做完 T1 标完成 → T2 自动解锁 → 乙自己认领开工，**不用问主 Agent** |
| 出问题 | 乙只能报告给主 Agent，主 Agent 再转告甲 | 乙**直接给甲发一条消息** |
| 再用一次 | 重新委派一个，背景重新交代一遍 | 干完的队员在**待命**，发条消息就带着原上下文接着干 |

## 本章的参照系与唯一判据

对齐 **Claude Code 现行的团队能力**：共享任务列表（`TaskCreate` / `TaskList` /
`TaskGet` / `TaskUpdate`，带 `owner` 与 `blockedBy` / `blocks`）、点对点消息
（`SendMessage`）、具名队友的唤醒续跑（「a send resumes it from its transcript」）。

**判据只有一条：Claude Code 没有的东西，本章不做。** 这是需求澄清阶段由用户
拍板的总原则，被它排除的能力逐条列在 spec 的「不做的事」里——那一节里的多数条目
**是用户最初提出、后来主动砍掉的**，写下来是为了让后来的人知道那是刻意不做。

被砍掉的包括：独立终端窗格 / tmux 后端、长期持久化的「小组」对象、
邮箱文件与锁文件、coordinator 模式、队员审批协议、Lead 自动 git 合并、广播消息。

## 三处刻意偏离 Claude Code

| | Claude Code | 本章 | 为什么 |
| --- | --- | --- | --- |
| 重名 | 后来者接管（latest wins） | **明确失败** | latest wins 会让一条发给 `worker-a` 的消息**静默送到另一个 Agent 手里**，两边都不报错。本项目没有它那套能让用户当场看清「谁是谁」的界面 |
| Hook 自动批准 | `permissionDecision: "allow"` | **不做** | C12 的硬不变量是「Hook 只能收紧不能放宽」，那是 C12 全部安全论证的依据 |
| 关闭自动唤起 | 无此开关（re-invoke 不可关） | **同样不做** | 对齐。代价见「安全边界」——用户无法靠关功能规避，只能不切放行档 |

## 六个由用户拍板的方向

1. **主 Agent 与队员共用同一套协作工具**（Claude Code 的做法）。原需求写的是
   「主入口看不到这些工具」，但那会让主 Agent 变成瞎子——它派了三个人出去却看不到看板。
2. **消息自动唤起主对话**：空闲时收到消息就自己跑一轮，用户零输入。
3. **无人轮判 ASK 一律自动拒绝**，对齐 Claude Code 的 `dontAsk` 档
   （官方原文：「denies anything not in your `permissions.allow` rules」）。
4. **会话级生命周期**：不落盘、不接 C9 的 `/resume`。
5. **重名明确失败**（见上表）。
6. **不提供关闭自动唤起的开关**。

## 四处「漏了不报错」的坑

它们是本章最容易埋雷的地方，每一条都有专门的护栏钉着。

1. **`TaskStatus` 绝不能加一个 `is_terminal` 为假的 `IDLE`。**
   主 Agent 的闸门用 `not status.is_terminal` 判断「还要不要等」，加了之后它每次
   收工都会去等一个已待命的队员，而那个队员正等着主 Agent 发消息——**双方互等，
   永远结束不了**。修法是两套状态各管一个维度：`TaskStatus` 答「结论产出了没有」，
   `MemberState` 答「人还在不在场」。
2. **`TeamGate.has_awaited` 恒为假。** 返回真会让队员为「可能有人给我发消息」
   赖着不收工。等消息发生在**待命状态**（阻塞在 `wake_event` 上），不在 Agent Loop 里。
3. **触发自动唤起前必须先判主对话空闲。** 流式 Worker 是 `exclusive=True` 的，
   不判就起新 Worker 会把正在跑的那个**挤掉**——用户正在等的回答凭空消失，
   界面上只表现为「AI 说到一半不说了」。
4. **委派的命名必须放在所有校验之后。** 往前挪会**泄漏名字**：注册成功之后
   并发超限或工作区创建失败，那个名字就被一个从未存在过的队员永久占着了。

## 开发期发现的三处 spec 没覆盖的问题

**共同点：都不是「代码写错了」，而是设计时没想到的形态。**

1. **注入消息的正文可以伪造来源。** 消息正文由**另一个 Agent** 写、进入
   **第三方**的历史。不做处理的话，一段正文就能伪造出一条来自 `main` 的消息
   （写个假的闭合标签再开一个 `from="main"`）。这不需要谁蓄意为之——一个读过
   恶意网页、被 prompt 注入污染的队员就足以产出。**能伪造的来源标注等于没有
   来源标注**，F12 也就落空了。现已一律无害化。
2. **隔离委派与待命互斥。** 「工作区什么时候结算」没有第二个说得通的答案，
   详见 `CLAUDE.md` 已知项 #16。
3. **主对话的未读在界面上看不到。** 自动唤起被连锁上限挡住时，消息会一直堆着
   而用户不知道。这是**对着实际渲染输出看了一遍**才发现的——C14 同一条教训。

## ⚠ 术语提醒

本项目现在有**四个**形似而语义不同的概念，别混：

| 概念 | 章节 | 是什么 |
| --- | --- | --- |
| `context: fork` | C11 | Skill 在**空白上下文**里跑 |
| `type: branch` | C13 | 子 Agent **继承父历史** |
| `isolation: worktree` | C14 | 子 Agent 有**独立工作目录**（文件隔离，上下文照旧） |
| **待命 / 唤醒** | **C15** | 队员**保留自己的上下文**留在场上，被消息叫醒后接着用它 |

前三个说的是「上下文或文件怎么处置」，第四个说的是「这个人还在不在、叫不叫得醒」。
