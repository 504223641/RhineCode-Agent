## 二、可用性侧：一个真实问题（**未解决**）

### ⚠ 模型不会主动组队

两轮**自然场景**（不提示协作），主 Agent 都是全程自己做：

| 轮次 | 任务 | 结果 | 它的原话 |
| --- | --- | --- | --- |
| 1 | 三个模块各把硬编码超时改成读 config | 0 次委派，自己改完 | 「三个模块结构类似，**修改很简单**。我逐一进行编辑。」 |
| 2 | 三个模块各补一份单元测试并跑通 | 0 次委派，11 轮自己做完 | —— |

**第 1 轮的判断可能是对的**：三个文件各改一行，委派开销（起线程、发请求、
回流结论）大于并行收益。**这也说明我最初的测试场景设计有问题**——
「听起来适合并行」不等于「真的值得并行」。

**第 2 轮是实打实的欠触发**：三份测试各自要读模块、写文件、跑验证，
本身就是几轮的活，且完全独立，正是组队的典型形态。

### 根因（已修一半）

首轮查 trace 发现：**协作能力一个字都没进系统提示**。缺口对比：

| 能力 | 系统提示里有没有 |
| --- | --- |
| C11 Skill | 有（140 槽位，清单 + pushy 表头） |
| C13 委派 | 有（135 槽位，角色清单 + 「拿不准就委派」） |
| C15 协作 | **没有** |

已补 134「组队协作」槽位（`team/render.py::render_team_brief`）。
**但补完之后第 2 轮仍然没组队**——所以它是**必要不充分**的。

### 一条有价值的对比证据

同一次运行里，主 Agent **加载了 `test` Skill**（写测试的任务命中了 Skill 清单）。
也就是说：**系统提示里的「清单」它会读、会遵循；我写的「说明」它没照做。**

差别很可能在于**有没有可匹配的具体项**：
看到 `test` skill 它会想「我这个任务是写测试，命中」；
看到「任务之间相不相干」它得自己做一次抽象判断——而模型在这种判断上
系统性地偏向「还好，我自己来更快」。

### 定性

这与 C11 记录的「模型欠触发 Skill」**同源**，而 `CLAUDE.md` 已经把那条
定性为**行业级的已知系统性偏差**（Anthropic 官方指导：描述要写得「有点 pushy」）。
本章的措辞已经相当 pushy，仍不足够。

**已登记为已知偏差，不假装解决。** 可能的后续方向（都需要单独设计）：

1. 把「组队」变成一个**可匹配的具体项**，而不是抽象建议；
2. 在用户目标明显可拆时，由**代码**（而非模型）给出一次提示；
3. 换更强的模型复测——本次用的是 `deepseek-v4-flash`（快速小模型），
   指令遵循能力弱于同系列的大模型，这一项**未被排除**。

### 但这不影响功能可用

**用户明说「组一个队」时，它一次就做对了，而且做得很漂亮**——
拆任务、起有语义的名字、并行派人、零冲突认领、成果正确、还会回报。
也就是说：**机制是好用的，缺的是模型主动选择去用它。**

## 三、第二轮：补齐验收缺口（2026-08-09 后续）

首轮报告里列的六条缺口，逐条处理。

### ✅ 队员之间的直接消息（AC43 的另一半）

设计一个**乙必须先从甲拿到东西**的任务，并明说「不要经过你中转」：

```
impl-worker → spec-writer   索要配置键命名规范
spec-writer → impl-worker   规范已定：docs/naming.md，TIMEOUTS 裸键名不合规
impl-worker → main          任务2完成
```

**队员之间真的直接双向往返了**，主 Agent 没有中转。

### ⚠→✅ 但它暴露了一个新问题：等回复时空转

`impl-worker` 发完请求后**反复调 `task_list` 当轮询**在等——空转六次，
**15 轮 106K token**，几乎耗尽预算（对照组 `spec-writer` 只用 7 轮 43K）。
对方再慢一点它就会耗尽轮次而失败。

根因：队员的系统提示只说了「做完手上的事就收尾」，**没说「等别人回话时也该
收尾」**。而收尾恰恰是本章设计好的等待方式——待命零成本，回话时自动唤醒、
上下文一个字不丢。模型不知道这条，就只能用它熟悉的方式：轮询。

补一段之后**同题复测**：

| | 改前 | 改后 |
| --- | --- | --- |
| impl-worker | 15 轮 · 106K token（空转 6 次） | 7 轮 22K → **idle** → 唤醒 → 11 轮 30K |
| 总量 | 106K | **52K（减半）** |
| 预算 | 几乎耗尽 | 唤醒后重置，宽裕 |

### ⚠→✅ 只读角色一个协作工具都拿不到（**最严重的一个**）

主 Agent 自己诊断出来的原话：

> 我最初给 impl-worker 派的是 **explorer** 角色，但 explorer 只有只读工具，
> **没有 `send_message`、没有写入能力**。

`explorer` / `planner` 都声明了只读白名单，交集之后协作工具一个不剩，
而 spec F22 写的是「对**全部**子 Agent 可见」。后果是「只读调研员 + 执行者」
这种最自然的分工根本跑不通。已修（豁免白名单，排在黑名单之前）。

⚠ 连带引入并已修一个回归：豁免让只读角色也拿到 `send_message`
（`read_only=False`），于是 Plan Mode 的「全只读角色」判定把
`explorer` / `planner` 也判成不可委派——**规划阶段一个角色都派不出去**。

### ⚠→✅ trace 作用域混成一片

`spec-writer` 与 `impl-worker` 都是 `general-purpose`，事件全落在
`subagent:general-purpose` 一个作用域里，排查「这一步是谁做的」只能靠猜。
改用队员名后已分开为 `subagent:impl-worker` / `subagent:spec-writer`。

### ✅ 无人值守轮撞到确认（`DENIED_UNATTENDED_FEEDBACK` 首次真实触发）

用只读权限的预置 + `background=true` 委派，让主对话先 idle、队员后发消息。
同一个 `edit_file` 拿到了**完美对照**：

```
117  edit_file · denied_by_user           （正常轮，人工拒绝）
203  edit_file · denied_non_interactive   （无人轮，自动拒绝）
```

而 F19 要求的「换条路走而不是放弃」也**如实兑现**——主 Agent 被拒之后：

1. 「这不代表有人反对，只是需要用户回到场确认」——正确理解了拒绝的性质；
2. `send_message` 给等着的队友回话，让它别干耗；
3. 「**需要您批准**修改 docs/architecture.md 第 5-6 行…」——把待批准的事
   明确留给用户；
4. 甚至和队员又往返一轮讨论了措辞。

**没有放弃整件事**——那正是这条文案与 `DENIED_BY_USER_FEEDBACK` 的分野。

### ✅ 空闲 CPU（AC39）

有待命队员、主对话空闲时实测 30 秒：**CPU 时间增量 0.0 ms（0.000%）**。
待命队员阻塞在事件等待上，无新增开销。

### 仍未验（判断为边际价值低于成本）

- **连锁上限真正达到 5/5**：本轮只到 2/5。计数与比较逻辑很简单，
  `test_team_auto_wake` 有三条单测覆盖（含「达到后停止」与「用户消息复位」）。
- **N3 降级的真实触发**：需要 6 个以上待命队员。同为纯代码判定，单测已覆盖。
- **Plan Mode 协作（F24）的真实模型验证**：同为代码判定，单测已覆盖。

## 追加（2026-08-10）：第 7 个 —— `/clear` 之后上一段对话的结论仍会回流（已修）

在验另一件事（`Esc` 提示）的真实模型跑里**顺带撞到**的，与那次改动无关。

**现场**：`/clear` 之后紧接着提一个新问题，模型的回答是

> 「explorer 已经回来了，auditor 还在跑字典档、优先级低……」

它坚称上一段对话的子 Agent 还在跑，接着给自己发消息（失败）、查了一份空的
共享清单，然后就此收工——**一次委派都没发起**。任务全被它当成「已经在做了」。

**物证是一个对不上的数字**：trace 里 `/clear` 之后的第一轮请求是
**「消息 3 条」**，而清空之后本该只有 1 条（用户那句）。多出来的两条，
正是上一段对话遗留的 `<subagent-result>` 块。

**机制**——三处各自都对，合起来漏了：

1. `TaskManager.cancel_all()` 只对 **RUNNING** 的任务置取消信号
   （这是对的，终态任务没什么可取消的）；
2. `take_deliverables()` 的判据是「终态且未交付」，**不区分这条任务属于哪一段对话**；
3. `clear()` 清空了 `history`，却把任务记录原样留在表里。

于是清空之后第一次 `_run()` 调 `_deliver_subagent_results()`，就把上一段的结论
追加进了本该空白的历史。`conversation.clear()` 里那段注释声称防的正是这件事，
但它只防住了「**还在跑的**」，没防住「**已经跑完、还没交付的**」。

⚠ **C15 让这条路径更容易被走到，而不是更难**：`_clear_team()` 会唤醒待命队员
让它们的线程退出，那恰好把它们从「待命」变成「终态且未交付」——正是会被
取走的那一档。所以这个继承自 C13 的缺陷，在 C15 之后变成了**常态**而非边角。

**修**：`TaskManager` 加会话代（epoch），创建时盖章、交付只认当前代；
`cancel_all_for_session_switch` 里取消与开新代**在同一个方法里做完**
（`/clear` 与 `/resume` 共用它）。

⚠ **为什么不是「切换时把当前任务标成已交付」**：取消是**异步**的，被取消的
子 Agent 完全可能在切换返回之后才走到终态，那时它仍是「终态且未交付」。
判据必须与时机无关——代号盖在**创建**那一刻，因此天然满足。护栏里有一条
专门钉这个时序（`test_a_task_that_finishes_after_the_switch_still_cannot_leak`）。

**单测为什么没抓到**：没有任何一条用例把「先跑子 Agent → `/clear` → 再提问」
连起来。各段都被验过，接缝没有——**与本轮另外几个缺陷同型**（第 2、5 条也都
落在两个模块的接缝上）。

**真实模型复验**（同一条链路，`deepseek-v4-flash` + `seed_subagents`，判据取自 trace）：

| # | 判据 | 结果 |
| --- | --- | --- |
| 1 | 清空**前**确实跑过子 Agent 且结论回流过 | ✅ `subagent_end explorer-1 completed`；seq 57 的主对话请求里含 `<subagent-result>` |
| 2 | 清空**后**第一轮请求不含任何历史残留 | ✅ 只有用户那句 + 每轮注入的环境提醒 |
| 3 | 那一轮请求体不含 `<subagent-result>` | ✅ |
| 4 | 模型不再声称上一段的子 Agent 还在跑 | ✅ 第一句是「我需要先找到这个文件」——正常的新对话反应 |

⚠ 判据 1 不可省：它证明**交付链路本身仍然正常**。少了它，一个「把交付整个关掉」
的错误修法也能让 2/3/4 全绿——那会静默废掉子 Agent 的整条回流链路，
而界面上完全看不出来。单测那边的对应反证是
`test_a_fresh_conclusion_after_clear_still_reaches_the_model`。

### ⚠→✅ 同一轮里发现的一个**新问题**（非本轮改动引入，已修）

`explorer` 的结论里有一句自述：「send_message 被拒绝了」。查判定：

```
seq=83  scope=subagent:retry-limit-exp  decision=deny  layer=mode
        严格模式：无规则放行，默认拒绝
```

**内置的 `explorer` / `planner` 与预置的 `auditor` 都声明 `permission_mode: strict`**，
而 `system_serial` 只把 **ASK 降级为 ALLOW**、压不过 DENY——于是这三个只读角色
**一个协作工具都用不了**。

这与本文档上面记的第 2 个问题（「只读角色一个协作工具都拿不到」）**是同一个
用户可见症状的第二次**，只是这次卡在**另一层**：那次修的是工具集（F22 让协作
工具豁免角色白名单，工具**发得出去**了），这次挡在权限管线第④层（**调用被拒**）。
模型拿到了工具、调了、被拒、白烧一轮，还要在结论里向用户解释一遍。

**成因**：`perm-system-serial-bypass`（PR #24）把 `system_serial` 工具从「绕过引擎」
改成「照常过引擎、判 ASK 时按 ALLOW 处理」。那次改动的净效果本应只有
「DENY 现在拦得住了」，但**严格档下第④层给的正是 DENY**，于是顺带把只读角色的
协作能力一起关掉了。改动本身是对的（`deny: send_message` 必须真的生效），
问题在于「严格档」与「协作工具豁免」两条规则相遇时没人定过优先级。

**修法（用户拍板方案 A）**：`system_serial` 工具**对第④层整层免疫**——
④判 ASK 或 DENY 一律按放行处理，①黑名单 / ②沙箱 / ③规则 / Hook 一字不动。

三条理由：

1. **它让实现与一句已经写下的承诺对齐。** `CLAUDE.md` 里 PR #24 那条写着
   「净效果只有一条：**DENY 现在拦得住了**」——实测净效果不止一条，
   它还顺带让严格档关掉了这七个工具。
2. **④层对这七个工具不是「灰色地带更谨慎」，是「功能整个关掉」。**
   它们走 `other` 分支、只认不带括号的整工具规则，③层绝大多数情况下不表态
   ——④是**唯一会说话的那一层**。
3. **`strict` 在那两个内置角色上全是代价、零收益。** 引擎有一条只读短路
   （`is_read_only` 在③未命中时直接放行、**不进④层**，见 `engine.py:281`），
   而 `explorer` 声明的工具全是只读——它手上唯一会走到④层的东西，
   恰恰就是 F22 特意豁免给它的协作工具。

**判据的分辨力在哪**：新增 `test_deny_rule_still_bites_under_strict_mode`——
严格档**加**③层 deny 规则同时成立时必须仍被拦住。没有它，「④层免疫」与
「一律放行」看不出区别，而后者正是 PR #24 修掉的那个缺陷。
反证实跑过：把降级改成「不看层」，3 条用例当场红。

trace 字段随之从 `ask_downgraded` 改名 `mode_downgraded`（阅读器标
⚠④层已降级）——被降级的不再只有 ASK，**严格档下降级的是 DENY，那更需要
看得见**：读的人得能分清「引擎放行了」与「引擎拒了但这类工具对该层免疫」。

**真实模型复验**（同一条链路，让 `explorer`——严格档的内置只读角色——
必须先 `send_message` 再交结论）：

```
seq=17  subagent_start  agent=explorer  permission_mode=strict
seq=42  permission_decision  ⚠④层已降级 send_message → allow（④模式）
        系统级工具（system_serial）：严格模式：无规则放行，默认拒绝；
        该结论来自权限档兜底，对这类工具不生效，按放行处理
seq=43  team_message  sender=explorer          ← 消息真的送达了
        tool_execute send_message → outcome=executed
```

修复前同一个位置是 `decision=deny layer=mode`，模型白烧一轮还要在结论里
向用户解释一遍。

⚠ 同一份记录还**坐实了上面第 3 条理由**：同一个 strict 子 Agent 里，
`grep_content` / `read_file` 走的是 `allow（③规则）· 只读工具默认放行`
——**根本没进④层**。所以 `strict` 对 `explorer` 确实只管了协作工具那一件事。
