## 二、可用性侧：一个真实问题（**未解决**）

### ⚠ 模型不会主动组队

两轮**自然场景**（不提示协作），主 Agent 都是全程自己做：

| 轮次 | 任务 | 结果 | 它的原话 |
| --- | --- | --- | --- |
| 1 | 三个模块各把硬编码超时改成读 config | 0 次委派，自己改完 | 「三个模块结构类似，**修改很简单**。我逐一进行编辑。」 |
| 2 | 三个模块各补一份单元测试并跑通 | 0 次委派，11 轮自己做完 | —— |

**第 1 轮的判断可能是对的**：三个文件各改一行，委派开销（起线程、发请求、
回流结论）大于并行收益。**这也说明我最初的测试场景设计有问题**——
「听起来适合并行」不等于「真的值得并行」。

**第 2 轮是实打实的欠触发**：三份测试各自要读模块、写文件、跑验证，
本身就是几轮的活，且完全独立，正是组队的典型形态。

### 根因（已修一半）

首轮查 trace 发现：**协作能力一个字都没进系统提示**。缺口对比：

| 能力 | 系统提示里有没有 |
| --- | --- |
| C11 Skill | 有（140 槽位，清单 + pushy 表头） |
| C13 委派 | 有（135 槽位，角色清单 + 「拿不准就委派」） |
| C15 协作 | **没有** |

已补 134「组队协作」槽位（`team/render.py::render_team_brief`）。
**但补完之后第 2 轮仍然没组队**——所以它是**必要不充分**的。

### 一条有价值的对比证据

同一次运行里，主 Agent **加载了 `test` Skill**（写测试的任务命中了 Skill 清单）。
也就是说：**系统提示里的「清单」它会读、会遵循；我写的「说明」它没照做。**

差别很可能在于**有没有可匹配的具体项**：
看到 `test` skill 它会想「我这个任务是写测试，命中」；
看到「任务之间相不相干」它得自己做一次抽象判断——而模型在这种判断上
系统性地偏向「还好，我自己来更快」。

### 定性

这与 C11 记录的「模型欠触发 Skill」**同源**，而 `CLAUDE.md` 已经把那条
定性为**行业级的已知系统性偏差**（Anthropic 官方指导：描述要写得「有点 pushy」）。
本章的措辞已经相当 pushy，仍不足够。

**已登记为已知偏差，不假装解决。** 可能的后续方向（都需要单独设计）：

1. 把「组队」变成一个**可匹配的具体项**，而不是抽象建议；
2. 在用户目标明显可拆时，由**代码**（而非模型）给出一次提示；
3. 换更强的模型复测——本次用的是 `deepseek-v4-flash`（快速小模型），
   指令遵循能力弱于同系列的大模型，这一项**未被排除**。

### 但这不影响功能可用

**用户明说「组一个队」时，它一次就做对了，而且做得很漂亮**——
拆任务、起有语义的名字、并行派人、零冲突认领、成果正确、还会回报。
也就是说：**机制是好用的，缺的是模型主动选择去用它。**

## 三、本轮验收暴露的另外两件事

1. **`Bash(python *)` 这类 allow 规则挡不住复合命令。**
   第 1 轮里模型发起 `cd src && python -c "..."`，规则没命中、弹了确认面板。
   这是 `CLAUDE.md` 已知项 #1（③规则层对复合命令不拆段）的又一次真实观测样本，
   **不是本章引入的**。

2. **`--keep-workspace` 的残留会被护栏抓到。**
   `test_e2e_host::test_zzz_no_global_leftovers` 在我留着 live 工作区时变红——
   这条护栏是有效的，验收后必须走 `sandbox.force_rmtree` 清理。
