# C15 子 Agent 协作 Spec

## 背景

C13 给了主 Agent 委派能力，C14 给了子 Agent 文件隔离。但子 Agent 至今是
**一次性的、互相隔绝的临时工**：

- 它们**彼此不知道对方存在**，没有任何通信手段；
- 任何信息交换**必须经主 Agent 中转**——主 Agent 既是唯一的信息枢纽，也是瓶颈；
- 它们**干完就消失**：对话历史是后台线程里的局部变量，随线程一起丢掉，
  任务表只留一段结论。同一个队员要再干一件事，只能从零重新委派、
  重新交代一遍背景；
- 它们**看不到彼此在干什么**。主 Agent 派出去三个人之后，全局进度只能靠
  各自回流的结论去拼。

这正是 `CLAUDE.md`「已知后续工程项」第 14 条登记的缺口：
**多 Agent 团队编排（子 Agent 之间不通信、不互相委派）**。
本章兑现其中「不通信」那一半；「不互相委派」**刻意保留**，见 F22。

### 本章范围的唯一判据

本章的参照系是 **Claude Code 现行的团队能力**：共享任务列表
（`TaskCreate` / `TaskList` / `TaskGet` / `TaskUpdate`，带 `owner` 与
`blockedBy` / `blocks`）、点对点消息（`SendMessage`，带 `to` / `message` /
`summary`）、以及具名队友的唤醒续跑。

**判据只有一条：Claude Code 没有的东西，本章不做。** 这是需求澄清阶段由
用户拍板的总原则，被它排除的能力逐条列在「不做的事」里——那一节里的多数条目
**是用户最初提出、后来主动砍掉的**，写下来是为了让后来的人知道那是刻意不做，
不是漏做。

### 与 Claude Code 的对照

| | Claude Code | 本章 | 说明 |
| --- | --- | --- | --- |

## 目标

- 让子 Agent 之间**能直接说话**，不必所有信息都经主 Agent 中转
- 让主 Agent 与所有子 Agent **共享一块任务看板**，各自认领、自我调度，
  而不是由主 Agent 逐条派发
- 让干完活的队员**留在场上待命**，一条消息就能唤醒继续干，不必重新委派、
  不必重新交代背景
- 让主 Agent 在**用户不在场时**也能推进协作，且不因此弹出无人应答的确认面板
- 上述能力**不扩大任何 Agent 的权限面**——C13「子 Agent 的能力只会比主对话小，
  永远不会更大」这条不变量原样成立

## 功能需求

### 一、队员身份

- **F1 具名队员。** 委派时可以给子 Agent 起一个名字；不给则由系统按角色名生成一个
  **在本次会话内唯一**的名字。名字是消息投递与任务认领的唯一标识，
  也是用户在界面上指代某个队员的方式。
- **F2 重名明确失败。** 名字已被占用（无论对方在跑还是待命）时，委派**失败并说明冲突**，
  **不启动线程、不建任务记录**。
  ⚠ **这是一处对 Claude Code 的刻意偏离。** 它的规则是「后来者接管这个名字，
  旧的只能用原始 id 找到」。本项目不采纳：那会让一条发给 `worker-a` 的消息
  **静默送到另一个 Agent 手里**，而两边都不报错——与本项目通篇
  「不静默降级、失败要看得见」的口径直接冲突，且本项目没有 Claude Code 那套
  能让用户当场看清「谁是谁」的界面。
- **F3 花名册可见。** 任何时候都能查到当前有哪些队员、各自的状态
  （运行中 / 待命 / 失败 / 已取消）、担任什么角色、在哪个工作目录、
  已用轮次与用量。

### 二、共享任务清单

- **F4 一份共享清单。** 本次会话内全局唯一，**主 Agent 与全部队员读写同一份**。
  清单不属于任何一个 Agent。
- **F5 任务的构成。** 每条任务含：稳定标识、标题、说明、状态
  （待办 / 进行中 / 已完成）、认领人、依赖关系（被哪些任务挡着、挡着哪些任务）。
  标识在会话内稳定且可被任何一方引用。
- **F6 四种操作。** 新建、列出、查看单条详情、更新。更新可改状态、认领人、
  标题与说明、追加依赖，也可删除任务。
- **F7 依赖是强制的，不只是提示。** 一条任务的前置任务未全部完成时处于
  **「被挡住」**状态，**不能被认领**；尝试认领时明确拒绝并说明被哪几条挡着。
  列出时逐条标明阻塞来源。（对齐 Claude Code）
- **F8 并发安全。** 多个队员同时读写清单不会互相破坏，也不会出现两人同时
  认领同一条任务——认领是一次**原子的**「无人认领 → 归我」转换，
  失败方拿到明确的「已被某某认领」而不是静默覆盖。

### 三、点对点消息

- **F9 按名字发消息。** 主 Agent 或任何队员都可以按名字给另一方发一条消息，
  含**正文**与**一句话摘要**（摘要供界面单行展示）。收件人写 `main` 表示
  发给主对话。
- **F10 收件人不存在时明确失败**，并在失败文本里列出当前花名册，
  使发送方能自我纠正。
- **F11 推送投递，收件人不需要查收。** 不提供「查收件箱」这类工具。
  正在运行的收件人在**下一轮迭代开始前**看到新消息；已待命的收件人被
  **唤醒**（F13）；主对话空闲时触发**自动唤起**（F17）。
  （对齐 Claude Code：「delivered automatically; you don't check an inbox」）
- **F12 消息来源必须可辨识。** 注入到收件人历史里的消息必须让模型能明确区分
  「这是队友 `worker-a` 说的」与「这是用户说的」。
  ⚠ 这不是体面问题：混淆会让队员把队友的话当成用户指令，
  从而绕过「用户才是最终授权方」这个前提。同理，队友消息也必须与
  C13 既有的「子 Agent 结论回流」标记块在形态上可区分。

### 四、唤醒续跑

- **F13 待命状态。** 队员**自然停止**（模型主动收工，不是失败、不是被取消、
  不是耗尽轮次）后进入**待命**状态，**完整对话历史保留**。收到消息时从原历史
  继续跑，不重新起步、不重新交代背景。待命是**非终态**。
- **F14 不可唤醒的情形。** 失败、被取消、或耗尽轮次上限而中止的队员进入终态，
  **不可唤醒**；向它发消息明确失败并说明是哪一种情形，
  提示发送方改为委派一个新队员。
- **F15 待命不占并发名额。** 并发上限只统计**运行中**的队员。
  待命队员数量另有上限，见 N3。
- **F16 轮次预算按次重置。** 每次被唤醒重新获得一份完整的迭代预算，
  对话历史则继续累积。
  理由：若累加，第三次唤醒时预算已经用光，队员一句话都说不了就被掐断——
  那等于「叫不醒」，F13 形同虚设。历史无限增长的风险由 C8 上下文压缩承担
  （子 Agent 已接入），内存增长由 N3 承担。

### 五、主对话的自动唤起

- **F17 空闲时自动跑一轮。** 主对话处于空闲（等用户输入）时收到消息，
  **自动跑一轮**处理它，不需要用户按回车。主对话正在运行时不适用——
  那条路径复用 C13 已有的迭代级注入。
- **F18 无人轮不弹确认面板。** 自动唤起的那一轮里，权限管线判定为「问用户」
  的操作**一律自动拒绝**，拒绝原因回灌给模型。
  ⚠ 这**不是**新增一条放行通路：它只把「问用户」变成「拒绝」，
  方向是**收紧**，与 C13 子 Agent 的处理逐字相同，安全论证直接沿用。
  （对齐 Claude Code 的 `dontAsk` 档）
- **F19 无人轮的拒绝理由必须与「用户按了拒绝」区分开。**
  后者（C6 的 `DENIED_BY_USER_FEEDBACK`）要求模型**停止推进、不要重试、
  转而询问用户**；前者的正确反应是**换一条现在做得到的路**（回消息、
  读文件、改清单）并**留言说明需要用户批准什么**。照搬后者的文案会让主 Agent
  误以为被否决，直接放弃整件事。
- **F20 连锁上限。** 「消息 → 自动唤起 → 回消息 → 对方又发 → 又被唤起」
  这条链**连续发生若干次后停止自动唤起**，界面明确提示已达上限、
  改为等用户回来。计数在用户提交任何一条消息时清零。
  ⚠ 没有这条，两个 Agent 能互相唤醒到天亮，把用户的额度烧光而界面上
  只是一直在动。
- **F21 无人轮在界面上必须可辨识。** 用户回来时要能一眼看出
  「这一段是我不在的时候程序自己跑的」，以及其间**有没有操作因为无人值守
  被拒绝**。

### 六、边界与可见性

- **F22 协作工具对主 Agent 与全部子 Agent 可见**（任务清单四件 + 发消息）。
- **F23 委派工具与 Skill 加载工具对子 Agent 依然不可见。**
  C13 那道防无限嵌套的闸门原样保留：**队员之间能说话、能共享看板，
  但不能自己再招人。**
- **F24 Plan Mode 的规划阶段**：任务清单工具**可用**（拆任务本就是规划的一部分，
  且它们不产生任何文件或命令副作用）；发消息**只能发给最终工具集全只读的
  待命队员，或发给 `main`**——给一个能写文件的待命队员发消息会把它唤醒去动手，
  直接绕过「批准前不动手」的承诺。判据与拒绝文案复用 C13 F19a 现成的那套。
- **F25 会话边界。** `/clear`、`/resume` 载入另一个会话、以及退出时，
  全部队员被取消、花名册 / 清单 / 未读消息一并清空，自动唤起计数复位。
- **F26 展示与记录。** `/agents` 增加队员名字与待命状态，并对已回收的
  隔离工作区如实改口（沿用 C14 的既有行为）；新增一个只读命令查看共享任务清单
  （标识 / 标题 / 状态 / 认领人 / 阻塞来源）。消息收发、任务变更、
  自动唤起各有对应的行为记录事件类型。

## 非功能需求

- **N1 不扩大权限面。** 本章新增的工具都不读写文件、不执行命令，
  副作用限于「在本进程内存里改一份清单」与「把一段文本送到另一个 Agent 的历史里」。
  队员**因本章获得的能力，一件都不能是它原本做不到的**：
  它能让别人干活，但别人干的每一件事仍逐个过完整的五层权限管线 + Hook 前置层。
- **N2 加锁不变量。** 清单与消息队列的加锁**临界区只做纯内存读写**，
  一切回调、埋点、跨线程调度（含唤醒等待线程）一律在锁外。
  这与 C11 `SkillManager`、C12 `HookManager`、C13 `TaskManager` 是同一条——
  违反会与 Textual 阻塞式 `call_from_thread` 组成**确定性死锁，整个 TUI 冻结**。
- **N3 内存有上限。** 待命队员保留完整历史，**不会自动释放**。
  因此待命队员数量必须有上限；超出时按「最久未活动」降级为终态
  （只留结论、不再可唤醒）并在界面上说明。
  ⚠ 降级必须**看得见**，不能静默——否则用户会遇到「同一个名字昨天叫得醒、
  今天叫不醒」而毫无线索。
- **N4 失败明确，绝不静默降级。** 重名、收件人不存在、向终态队员发消息、
  认领被挡住的任务、并发超限——每一种都返回可读原因，且**不产生副作用**。
- **N5 无队员、无消息时行为逐字不变。** 不使用本章能力的会话，
  C13/C14 的既有行为与既有测试**一条都不能变**。
- **N6 不新增轮询。** 队员侧的消息投递与唤醒**必须事件驱动**（零 CPU 占用）；
  主对话侧**复用既有的定时轮询，不新增任何定时器**。
  ⚠ 措辞在 plan 阶段修订过：原文写的是「不得用定时轮询实现」，
  但本项目自 C13 起已存在两处轮询且各有防死锁的硬理由
  （TUI 更新界面只能走阻塞式跨线程调用；任务表刻意不持有回调），
  绝对意义上的「零轮询」在本章开工前就不成立。
  可验证的口径因此是：**空闲会话的 CPU 占用与不使用本章能力时相同**。
- **N7 观测不阻断被观测者。** 行为记录失败一律静默吞掉，
  与既有记录器的口径一致。
- **N8 依赖方向。** 新增模块不得被 `conversation` / `tui` / `commands` 反向依赖，
  也不得让 `agent` 包依赖 `subagents`（那会撞循环导入，C13 已实测过）。
- **N9 中文注释与文档。** 所有新增代码遵循 `CLAUDE.md` 的注释规范；
  每一处「刻意这样做」的决定必须把理由写在代码旁，而不是只写在本文档里。

## 不做的事

以下条目**多数是用户最初提出、在需求澄清阶段主动砍掉的**，判据统一是
「Claude Code 没有」。写在这里是为了让后来的人知道那是刻意不做。

### 因「Claude Code 没有」而砍掉的

- **独立终端窗格 / 独立进程运行后端**（tmux、终端分屏），以及
  **运行后端抽象与按环境自动选择**。Claude Code 的队友一律同进程，
  隔离靠 worktree（文件层）而不是靠进程。另有环境事实：本项目主要开发机
  （Windows）**没有 tmux**，Windows Terminal 也**没有「向已存在的窗格发送输入」**
  的能力，做出来无法端到端验收。
- **长期持久化的「小组」对象**（`~/.rhinecode/teams/<小组名>/`、成员花名册、
  跨会话存在）。Claude Code 的团队是会话级的。
- **邮箱文件、锁文件、拿不到锁重试、锁过期判定。** 这些是**跨进程**通信才需要的，
  同进程投递用内存队列即可，一个文件锁都不需要。
- **coordinator 模式**（配置开关 + 环境变量双锁、剥夺主 Agent 的写文件工具）。
- **队员审批协议**（要审批的队员先把计划发给 Lead、Lead 用特定结构的消息
  批准或驳回）。约束队员能做什么，本项目已有 C13 的工具白名单与
  `permission_mode`。
- **Lead 自动 `git merge` 各队员目录、自动解冲突、解不了回滚上报。**
  C14 现有做法（子 Agent 提交到自己的分支、主 Agent 自己用 shell 跑 `git merge`）
  已经是 Claude Code 的形态，本章不新增合并工具。
- **广播消息。** Claude Code 的 `to` 只收单个名字。
- **关闭自动唤起的总开关。** Claude Code 的「后台任务完成后 re-invoke 主循环」
  同样不可关闭，本章据此对齐。
  ⚠ 代价写在「安全边界」第 4 条：用户无法通过配置规避
  「程序在我不在场时自己动」这件事，只能靠不切放行档、
  或收紧 allow 规则来限制它**能做什么**。这是用户明确拍板的取舍，
  **不是漏做**——将来若要补，落点是 F17 的触发处。
- **Hook 自动批准工具调用**（Claude Code 的 `permissionDecision: "allow"`）。
  ⚠ 这条与上面几条不同——它不是「Claude Code 没有」，而是**本项目刻意不做**：
  C12 的硬不变量是「Hook 只能收紧不能放宽，`HookDecision` 里根本没有 ALLOW」，
  那是 C12 全部安全论证的依据，不为本章松口。

### 本章范围之外

- **跨机器 / 分布式团队。**
- **成员间实时流式通信。** 消息是整条送达的，不做逐字流式。
- **队员之间互相委派**（无限嵌套招人）——F23 明确保留这道闸门。
- **任务清单与花名册的持久化、跨会话恢复。** 会话级，`/clear` 与退出即清空。
- **更复杂的任务依赖约束**：优先级、时限、子任务树、循环依赖检测之外的图算法。
- **消息的已读回执、撤回、编辑、附件与结构化负载。** 只有纯文本正文 + 摘要。
- **消息级 / 任务级的新 Hook 事件。** 新工具照常受既有的三个工具级 Hook 事件
  管辖（它们是工具），但不为本章新增挂载点。
- **队员的人在回路。** 队员全程非交互，判 ASK 自动拒绝，与 C13 一致。
- **多个共享清单 / 清单分组。** 全局唯一一份。

## 安全边界

本章新增的攻击面与已有防线的关系，逐条列出。

1. **协作工具不进权限管线**（与 C13 的委派工具、C11 的 Skill 加载工具同先例）。
   论证：它们既不读写文件也不执行命令，没有可映射的 Bash / Read / Edit / Write
   语义；副作用全部发生在进程内存中。

   ⚠ **验收期修订**：本条原文写的是「仍可被 `permissions.yaml` 的 `deny` 规则
   整个禁掉」，**实测证明那是错的**——`system_serial=True` 的工具在
   `agent/loop.py` 的决策预扫里直接拿到 ALLOW、根本不调 `engine.decide`。
   这是个**继承自 C13** 的既有错误（`run_agent` / `load_skill` 同样如此）。
   **唯一有效的收窄手段是 Hook 的 `pre_tool_use` 拦截**（实测拦得住）。
   已登记为 `CLAUDE.md` 已知后续工程项第 18 条。
2. **「能让别人干活」不等于提权。** 队员通过发消息唤醒另一个队员去做事时，
   那个队员做的每一件事仍逐个过完整的五层管线 + Hook 前置层，
   且它的工具集与权限档在委派时就已按 C13 的规则收窄过。
   **本章不引入任何一条能绕过管线的通路。**
3. **⚠ 本章确实放宽了「上下文外泄」的一条边界，这是已知代价。**
   C13 的设计是子 Agent 只回流**一段结论**，中间过程留在它自己的上下文里。
   现在队员可以随时发消息，因此它读到的敏感内容**可以被主动送进主对话或
   另一个队员的历史**，而不必等到结论。这与 C13 已登记的第 ⑤ 条同源
   （「子 Agent 的结论会进入主历史」），但通路更宽、时机更自由。
   缓解只有一条：F12 要求消息来源可辨识，用户在界面上看得到谁跟谁说了什么。
4. **⚠ 自动唤起意味着程序会在用户不在场时消费额度、并可能改文件。**
   「改文件」只发生在该操作被 `permissions.yaml` 的 `allow` 规则放行、
   或用户此前切到了放行档时——F18 保证「需要问用户」的一律拒绝。
   ⚠ **本章刻意不提供关闭自动唤起的开关**（用户拍板，理由见「不做的事」）。
   因此约束只剩两道，且**都不能被配置放宽**：F18 的「无人轮判 ASK 一律拒绝」
   与 F20 的连锁上限。
   ⚠ **放行档 + 自动唤起是本章风险最高的组合**：那时主 Agent 在无人值守下
   拥有完整写权限，而用户**无法通过关掉本功能来规避**——只能通过不切放行档、
   或收紧 `permissions.yaml` 的 allow 规则来限制它能做什么。
   这一点必须写进用户可见的文档。
5. **消息内容是不可信输入吗？** 不是外部不可信内容——它来自本机另一个
   由同一个用户发起的 Agent。但它**可能包含该 Agent 从外部读到的内容**
   （网页、文件），因此 F12 的来源标注同时承担「别把队友的话当用户指令」
   这一职责。
6. **`/clear` 必须真的清干净。** 花名册、清单、未读消息、待命队员的完整历史
   都含对话原文与被读过的文件内容。F25 要求一并清空，
   与 C9「会话存档含完整对话原文」同级敏感。
7. **Plan Mode 的承诺不被本章绕过。** F24 用与 C13 F19a 相同的判据封住
   「发消息唤醒一个能写文件的队员」这条旁路。

## 已知边界

以下问题本章解决不了，登记备查：

- **待命队员的历史无限增长。** F16 让轮次预算按次重置，历史则一直累积。
  单个队员被反复唤醒数十次后会撞上上下文窗口，届时由 C8 的两层压缩接手
  （子 Agent 已接入）。本章不为此单独设上限。
- **主对话在自动唤起期间收到用户输入的竞态。** 用户恰好在自动轮跑起来的
  同一刻按下回车，两者的先后由既有的运行态互斥决定，本章不新增排队机制。
- **消息投递不保证时序公平。** 多个发送方同时发给同一个收件人时，
  只保证「都送到」，不保证与发送时刻严格一致的顺序。
- **协作能力仅在 `protocol: deepseek` 且启用默认工具注册中心时可用**，
  与 C13/C14 一致。

## 验收标准

### 队员身份

- **AC1**（F1）委派时指定名字，`/agents` 里该队员以该名字显示；不指定名字时
  系统生成一个可读且唯一的名字。
- **AC2**（F1）连续委派同一个角色两次且都不指定名字，两个队员拿到**不同**的名字。
- **AC3**（F2）用一个已存在（运行中或待命）的名字再次委派，委派**失败**，
  失败文本指出冲突；观察到**没有新线程启动、任务表里没有多出记录**。
- **AC4**（F3）`/agents` 输出中每个队员都能看到：名字、状态、角色、
  工作目录（隔离时）、已用轮次。

### 共享任务清单

- **AC5**（F4）主 Agent 新建的任务，队员用列出操作能看到；队员新建的任务，
  主 Agent 也能看到——两侧看到的是同一份。
- **AC6**（F5）查看单条任务详情，能拿到标识、标题、说明、状态、认领人、
  两个方向的依赖。
- **AC7**（F6）四种操作各自可用：新建后能列出；更新状态后再查看反映新状态；
  删除后不再出现在列表中。
- **AC8**（F7）为任务 B 声明「被 A 挡着」，在 A 完成前尝试认领 B：
  **认领被拒绝**，拒绝文本指出被 A 挡着；把 A 标为完成后再认领 B：**成功**。
- **AC9**（F7）列出清单时，被挡住的任务明确标出阻塞来源。
- **AC10**（F8）两个队员并发认领同一条任务：**恰好一个成功**，
  另一个拿到「已被某某认领」；清单里该任务的认领人是成功的那个。
- **AC11**（F8）多个队员并发读写清单，结束后清单内容完整、无丢失或错乱
  （用并发压力测试观察）。

### 点对点消息

- **AC12**（F9）队员 A 给队员 B 发消息，B 的历史里出现该消息，正文一致。
- **AC13**（F9）队员给 `main` 发消息，主对话收到。
- **AC14**（F10）发给一个不存在的名字：**明确失败**，失败文本列出当前花名册。
- **AC15**（F11）收件人正在运行时，消息在它**下一轮迭代开始前**出现在它的历史里；
  全程**没有**任何「查收件箱」类工具被调用（工具清单里也不存在这样的工具）。
- **AC16**（F12）观察注入到收件人历史里的消息文本：能明确读出发件人是谁，
  且与「用户消息」在形态上可区分；与 C13 的子 Agent 结论标记块也可区分。

### 唤醒续跑

- **AC17**（F13）队员自然停止后，`/agents` 显示其状态为**待命**；
  向它发一条消息，它**继续运行**，且在新一轮里能引用先前对话中的内容
  （证明历史没丢）。
- **AC18**（F14）向一个失败 / 被取消的队员发消息：**明确失败**，
  文本说明是哪一种情形并建议改派新队员。
- **AC19**（F15）在有 N 个待命队员的情况下委派新队员：**不受待命数量影响**，
  只要运行中的数量未达上限即可成功。
- **AC20**（F16）一个 `max_turns` 为 3 的队员，跑满 3 轮后待命；
  唤醒后它**又能跑满 3 轮**（而不是立刻被掐断）。

### 主对话的自动唤起

- **AC21**（F17）主对话空闲时，一个后台队员发消息给 `main`：
  **用户不做任何输入**，主对话自动跑起来并处理该消息。
- **AC22**（F18）在无人轮里触发一个会判「问用户」的操作
  （如写一个未被 allow 规则覆盖的文件）：**确认面板一次都不弹出**，
  该操作被拒绝，拒绝原因回灌给模型。
- **AC23**（F18）同一个操作在**正常轮**（用户提交消息后）里执行：
  确认面板**照常弹出**——证明无人轮的处理是局部的，没有改变主对话的常规行为。
- **AC24**（F19）对比无人轮的拒绝文本与「用户按了拒绝」的文本：
  **两者措辞不同**，前者不含「停止推进 / 不要重试」的指令。
- **AC25**（F20）构造互相回消息的两个 Agent：自动唤起达到上限后**停止**，
  界面出现明确提示；用户随后提交任意一条消息，计数复位、自动唤起恢复可用。
- **AC26**（F21）用户回到界面时，能看出哪一段是自动唤起跑的，
  以及其间有没有操作因无人值守被拒绝。
- **AC27**（安全边界 4）自动唤起**没有**任何配置项能关闭它——
  遍历配置字段确认不存在这样的开关，且 F18 与 F20 两道约束
  **同样不能被配置放宽**。

### 边界与可见性

- **AC28**（F22）主 Agent 与子 Agent 的可见工具清单里**都有**协作工具。
- **AC29**（F23）子 Agent 的可见工具清单里**没有**委派工具与 Skill 加载工具
  ——C13 的既有护栏原样通过。
- **AC30**（F24）Plan Mode 规划阶段：任务清单操作**成功**；
  给一个工具集含写工具的待命队员发消息**被拒绝**并说明理由；
  给 `main` 或全只读队员发消息**成功**。获批进入执行阶段后不再受限。
- **AC31**（F25）`/clear` 之后：花名册为空、清单为空、原队员不可唤醒、
  自动唤起计数复位；`/resume` 载入另一个会话时同样。
- **AC32**（F26）`/agents` 显示名字与待命状态；新命令能列出共享清单的
  标识 / 标题 / 状态 / 认领人 / 阻塞来源。
- **AC33**（F26）开启行为记录跑一遍协作流程，阅读器里能看到消息收发、
  任务变更、自动唤起三类事件，且**没有**「（未登记类型）」。

### 非功能

- **AC34**（N1）审查新增工具：无一读写文件或执行命令；用 `deny` 规则
  禁掉其中一个后，该工具调用被拒绝。
- **AC35**（N2）结构护栏：清单与消息队列的加锁临界区内不存在任何回调调用或
  跨线程调度（用与 C13 `TaskManager` 同形的结构测试钉住）。
- **AC36**（N3）待命队员数超过上限时，最久未活动的那个被降级为终态，
  **界面上有明确说明**，之后向它发消息按 AC18 的方式失败。
- **AC37**（N4）逐一触发五种失败（重名、收件人不存在、向终态队员发消息、
  认领被挡住的任务、并发超限）：每一种都返回可读原因，
  且事后检查**没有留下任何副作用**。
- **AC38**（N5）全量回归：C13/C14 的既有测试**全部通过**，无一条需要修改断言。
- **AC39**（N6）一个空闲、有待命队员的会话持续若干分钟：CPU 占用与
  **不使用本章能力的同等空闲会话相同**（即没有**新增**的周期性开销）；
  且待命队员的线程阻塞在事件等待上、**不做任何轮询**。
- **AC40**（N8）导入检查：新增模块不被 `conversation` / `tui` / `commands`
  反向依赖，且 `agent` 包不依赖 `subagents`。
- **AC41**（N7）把行为记录的目标置为不可写后跑一遍完整协作流程：
  流程**照常跑完**，不抛错、不中断，只是记录为空。
- **AC42**（N9）人工审查新增代码：每一处「刻意这样做」的决定
  （F2 的重名失败、F16 的轮次重置、F18 的无人轮拒绝、N3 的降级方向、
  以及「自动唤起不可关闭」）在代码旁都能读到理由，而不必翻回本文档。

### 端到端

- **AC43 完整协作闭环**：给出一个需要拆成 4 条带依赖任务的目标 →
  主 Agent 建清单、派 2 个具名队员 → 队员各自认领、完成、
  在看板上解锁后续任务 → 队员之间至少发生一次直接消息往来（不经主 Agent）→
  全部完成后主 Agent 汇总。**全程观察：清单状态与实际进度一致，
  消息各自送达，没有一条信息被静默丢弃。**
- **AC44 无人值守闭环**：派一个后台队员 → 用户不再输入 →
  队员中途发消息给 `main` → 主对话自动唤起、回消息 → 队员继续并完成 →
  用户回来后能从界面上完整看出这段过程发生了什么。
- **AC45 唤醒续跑闭环**：派一个队员做完第一件事 → 待命 →
  发消息指派第二件事 → 它**不重新交代背景**就接着干 →
  在第二件事的产出里能看到它引用了第一件事的上下文。
