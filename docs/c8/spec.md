# C8 上下文管理（两层压缩）Spec

## 背景

RhineCode 的每次模型请求都是无状态的：Agent Loop（`loop.py`）每一轮都要把**整段对话历史**（`ConversationManager.history`）重新发给模型。模型有上下文窗口（context window）的硬上限——DeepSeek 系列约 64K～128K token。一旦历史累积的 token 超过窗口，请求直接失败，Agent 就此瘫痪。

历史里的 token 大头是**工具结果**（`role="tool"` 消息）：一次 `read_file` 可能几百行、一次 `grep` 几十个匹配、一次 `run_command` 一大段输出。这些内容体积大、机器生成、且很快过时。相比之下用户消息通常很短，却是任务意图的锚点。业界共识是「从工具结果下手压缩、尽量保住用户原文」。

当前 RhineCode 完全没有上下文管理：历史只增不减，长任务必然溢出。本章（C8）为其装上**两层压缩策略**：

- **第一层·轻量预防**：不调模型、成本低。把过大的工具结果存盘，历史里只留预览和文件路径，从源头抑制单条消息膨胀。
- **第二层·重量兜底**：整体历史逼近窗口上限时，调 LLM 生成结构化摘要，把较早的消息压掉、近期原文留下，并补一条边界提示防止模型照摘要脑补。

两层策略参考了当前主流 Agent（Claude Code 的三层级联、Aider/OpenHands/Gemini CLI 的阈值触发摘要），并结合本项目现有的 usage 采集能力做近似 token 估算，避免引入精确 tokenizer 依赖。

## 目标

- 让 RhineCode 在有限 token 预算里长时间干活，对话累积再多也不会因上下文溢出而瘫痪。
- 优先压缩工具结果这一 token 大头；用户的原始消息尽量原文保留，不被摘要改写。
- 第一层预防低成本、不调模型，从源头抑制单条消息膨胀。
- 第二层兜底在逼近窗口上限时用 LLM 生成结构化摘要，保住近期原文与任务连续性。
- 用户可手动触发压缩；压缩失败能自我保护（熔断），绝不陷入死循环或崩溃。
- 用户能在界面看到当前上下文用量与压缩的发生。

## 功能需求

### 配置与估算

- **F1**：提供可配置的**上下文窗口上限**，作为「是否逼近溢出」的判断基准。从主配置读取，缺省时回退到内置默认值；配置缺失或非法均不崩溃，按默认值运行。
- **F2**：以**近似估算**得出「当前上下文 token 数」，不引入精确 tokenizer。估算方法：以上一次 API 请求返回的精确输入用量（`usage.prompt_tokens`）为**锚点**，只对锚点之后新增的消息按字符数近似换算，累加到锚点上。尚无锚点（本次会话首个请求）时，对全部消息按字符数估算。

### 触发时机与顺序

- **F3**：每次 API 请求前，按固定顺序执行两步——① 先跑第一层轻量预防（管单条消息 / 工具结果大小）；② 再评估累积历史是否逼近窗口上限，需要时跑第二层重量兜底。第一层先行，因为它可能把大结果存盘、直接降低第二层的触发压力。

### 第一层·轻量预防（工具结果存盘）

- **F4**：**单结果存盘**——当单个工具结果的估算体积超过「单结果阈值」时，把完整结果写入磁盘文件（位于 `<项目根>/.rhinecode/context/` 下），对话历史中该结果替换为「预览片段 + 文件路径」占位。预览保留结果头部若干内容，供模型判断相关性并决定是否重新读取。
- **F5**：**聚合存盘**——当同一轮 / 新增的多个工具结果各自都未超单结果阈值、但合计超过「聚合阈值」时，按体积从大到小依次存盘，直到合计降到阈值以下为止（挑大的先存，最小改动换最大收益）。
- **F6**：存盘只作用于**工具结果类内容**（`role="tool"` 消息）。用户原始消息（`role="user"`）永不被存盘或改写。
- **F7**：存盘**幂等**——已被替换为占位（预览 + 路径）的消息，后续轮次不会被再次存盘或二次处理。

  > ⚠ **勘误（2026-09-17）：占位里的「路径」已删除，改为「来源」。**
  > 幂等这条本身不变，变的是占位内容。原文案写着「完整内容见文件：`<存盘路径>`
  > （需要完整内容时，请用 `read_file` 读取该文件路径）」，而那条指引会形成一个
  > **不收敛**的循环：`read_file` 的行号前缀让读回来的内容比存盘原文更大
  > （实测 22.2K → 25.2K），于是必然再次超阈值、再次存盘、再生成新路径。
  > 真实 trace 里 14 次读存盘文件 100% 触发二次存盘，一条 25 轮的任务
  > 36% 的迭代白烧。现在占位写的是**来源**（`来源：read_file(path=docs/a.md)`）
  > 并提示缩小范围重调，路径一个字不给；`read_file` 另行拒绝 `.rhinecode/context/`
  > 作为纵深防御。详见 `docs/internals/known-issues.md` 的 #21。

### 第二层·重量兜底（LLM 摘要）

- **F8**：当上下文 token 估算逼近窗口上限时触发 LLM 摘要。留**安全余量**吸收估算误差：自动触发的余量较宽（默认 13K），用户手动触发时余量收窄（默认 3K，因为是用户主动要压、可接受更贴近上限）。
- **F9**：**保留策略**——从历史尾部按 token 往回数，保留最近约 1 万 token 或至少 5 条消息的**原文**（两者取更能保住上下文的一方）；其余较早消息交给 LLM 摘要压缩。保留边界须落在完整的消息边界上，不切碎单条消息，且不破坏 `assistant(tool_calls)` 与其对应 `tool` 结果的配对完整性。
- **F10**：摘要按**固定的几个结构化部分**组织（例如：任务目标 / 已完成的关键步骤与结论 / 涉及的关键文件与改动 / 当前状态与待办 / 重要约束与决策）。固定结构让模型压缩时不遗漏关键维度，也便于后续模型快速定位。
- **F11**：摘要 Prompt **明确禁止模型调用任何工具**，并要求模型**先输出「分析草稿」再输出「正式摘要」**；草稿仅供模型组织思路，正式摘要落地后即丢弃、不进入对话历史。
- **F12**：摘要落地后把历史**重构**为：摘要内容 + 保留的近期原文；并在两者之间补一条**边界消息**，提示模型「要文件细节请重新读取，不要照摘要脑补代码」。
- **F13**：被摘要覆盖范围内的用户诉求应被摘要**如实保留、不改写**；保留区内的用户消息保持原文。

### 手动触发与熔断

- **F14**：提供 `/compact` 斜杠命令，用户主动触发第二层重量压缩（安全余量收窄到 3K）。命令需成对维护（`conversation.py` 逻辑 + `CommandPanel.COMMANDS` 补全列表）。
- **F15**：摘要**连续失败达到 3 次时熔断**——暂停自动摘要尝试，避免在失败上死循环；把熔断作为可读提示反馈，后续普通对话不受阻断、不崩溃。（熔断在成功压缩或新会话后重置。）

### 可观测

- **F16**：提供 `/context` 斜杠命令，只读展示当前上下文用量——估算 token 数、距窗口上限的余量、已存盘的工具结果数等，让用户判断何时该手动压缩。命令需成对维护。
- **F17**：压缩发生时（第一层存盘 / 第二层摘要）在界面给出可见反馈（如系统提示行），让用户知道刚刚发生了什么、压掉了多少。

## 非功能需求

- **N1**：**低侵入**——压缩逻辑封装为独立组件，在「请求前」这一单一接入点被调用；Agent Loop 的决策与执行主流程不被打散、不为压缩铺满分支特例。
- **N2**：**健壮性**——存盘 I/O 失败、摘要 LLM 调用失败都被捕获：存盘失败则本次不存盘（保留原文），摘要失败则本次不摘要并计入熔断计数，绝不崩溃或阻断对话。
- **N3**：**近似即可**——不引入精确 tokenizer 依赖；估算误差由安全余量吸收。
- **N4**：**用户原文不失真**——摘要不改写用户诉求；第一层存盘不触碰用户消息。
- **N5**：**教学可读**——新增代码遵循项目中文注释规范，关键流程（估算锚点与增量、两层触发顺序、摘要保留边界与重构、熔断）注释清楚设计意图与边界条件。
- **N6**：**与权限系统正交**——存盘写文件是内部可信机制，不作为模型可调用的工具、不经工具权限管线弹确认，但写入路径限制在 `<项目根>/.rhinecode/context/` 内；摘要的 LLM 调用不携带工具、不触发任何工具执行。

## 不做的事

- 不做精确 tokenizer / 与计费分词严格对齐——本章只做近似估算。
- 不做摘要策略的机器学习或自动调参优化——保留策略与阈值用固定规则 + 可配置常量。
- 不做已存盘工具结果的向量检索 / 语义召回——模型要细节时按文件路径重新读取，不做 embedding。
- 不做跨会话持久化的上下文记忆——本章限于单次运行期内的历史管理，`/clear` 或重启即重置。
- 不做分支 / 子 Agent handoff 式的上下文管理。
- 不改变「工具能力仅在 `deepseek` 协议 + 启用默认工具注册中心时生效」这一现状——上下文压缩随之仅在该模式下生效。
- 不为图片 / 二进制工具结果做特殊压缩处理（当前工具结果均为文本）。

## 验收标准

- **AC1（可配置窗口）**：配置指定窗口上限时按其取值判断触发；配置缺失或非法时回退默认值且正常运行。对应 F1。
- **AC2（近似估算锚点）**：有上一次 API 用量时，估算值 =「锚点用量 + 锚点后新增消息的字符估算」；无锚点时对全部消息字符估算。给定构造历史，估算值落在合理范围内。对应 F2。
- **AC3（两层顺序）**：单次请求前先跑第一层预防、再评估第二层兜底；第一层把大结果存盘后，第二层看到的估算值已相应下降。对应 F3。
- **AC4（单结果存盘）**：构造一个超过单结果阈值的工具结果，压缩后该消息在历史里变为「预览 + 文件路径」占位，且磁盘上存在对应完整内容的文件。对应 F4。
- **AC5（聚合存盘）**：构造多个各自不超阈值但合计超聚合阈值的工具结果，压缩后按体积从大到小依次存盘，直到合计降到阈值以下；较小的结果保持原文。对应 F5。
- **AC6（用户原文保留）**：历史含用户消息与工具结果，第一层压缩后所有 `role="user"` 消息逐字不变。对应 F6。
- **AC7（存盘幂等）**：对已存盘替换过的历史再次运行第一层，占位消息不被二次处理、磁盘不产生重复文件。对应 F7。
- **AC8（摘要触发阈值）**：估算值超过「窗口 − 自动余量」时自动触发摘要；`/compact` 用「窗口 − 手动余量」这一更贴近上限的阈值触发。对应 F8/F14。
- **AC9（保留近期原文）**：摘要后，历史尾部约 1 万 token 或至少 5 条消息保持原文，且保留边界不切碎消息、不拆散 `assistant(tool_calls)` 与其 `tool` 结果。对应 F9。
- **AC10（结构化摘要 + 边界消息）**：摘要产物按固定几个部分组织；重构后的历史里，摘要与近期原文之间存在一条「要细节请重读文件」的边界消息。对应 F10/F12。
- **AC11（摘要 Prompt 约束）**：摘要请求不携带任何工具 schema；Prompt 要求先草稿后正文，且草稿不进入落地后的历史。对应 F11。
- **AC12（熔断）**：连续 3 次摘要失败后暂停自动摘要并给出可读提示，后续普通对话仍可进行、不崩溃、不死循环。对应 F15。
- **AC13（/context 展示）**：运行时输入 `/context`，展示估算 token、距上限余量、已存盘工具结果数；`/context` 出现在输入 `/` 的补全面板中。对应 F16。
- **AC14（/compact 命令）**：运行时输入 `/compact` 触发一次重量压缩；`/compact` 出现在补全面板中；压缩发生时界面有可见反馈。对应 F14/F17。
- **AC15（低侵入 + 健壮）**：压缩逻辑在请求前单点接入，Loop 主流程不新增压缩分支特例；构造存盘 I/O 失败与摘要调用失败，二者均被捕获、对话继续。对应 N1/N2。
