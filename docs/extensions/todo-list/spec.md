# 主对话的待办清单 Spec

> **这是扩展，不占章节号。** 判据是 `docs/extensions/README.md` 那一条：
> `CLAUDE.md` 的能力表要不要多一行——不要。它在既有的工具层上加一个工具、
> 在既有的 TUI 层上加一块显示区，不引入新的能力层级。

## 背景

### 症状

一个十几步的任务跑起来，用户**看不出它做到哪了**。

屏幕上唯一的进度信号是一行行工具调用，而那是「做了什么」不是「还剩什么」——
用户只能从 `Read(auth.py)`、`Edit(auth.py)` 这些行去反推 AI 心里那张计划表，
而那张表从来没有被写出来过。

tui-activity-fold 把连续的只读检索调用归并成一行之后，这件事**更看不出来了**：
归并压掉的正是那些可供反推的痕迹。两者是互补关系——**归并回答「做了什么」，
待办清单回答「还剩什么」**。

### 已经有的一半地基，以及它为什么不是这个东西

C15 有一份共享任务清单（`team/board.py`，命令入口 `/tasks`）。它**不能直接用**：

| | C15 共享清单 | 本扩展的待办 |
| --- | --- | --- |
| 写入方 | 主 Agent + 全部队员，**并发** | 主 Agent 一个，**串行** |
| 存在理由 | 「**谁**来做这条」——多方抢活的协商媒介 | 「**做到哪了**」——单一执行者的进度 |
| `owner` 字段 | 核心 | **恒空** |
| `blocked_by` / `blocks` | 核心（阻塞不可认领） | **恒空** |
| `claim` 原子认领 | 核心（AC10 有 20 线程并发护栏） | **用不到** |
| 环检测 | 核心 | **用不到** |

一份数据结构里一半字段永远不用、一半方法永远不调，通常说明它不是同一个东西。

更要紧的是**混表的后果**：两者进同一张表之后，用户查清单时会同时看到
「[3] 待办 · 重构解析器」（主对话的）与「[4] 待办 · 修 CI（被 2 挡着）」（队员的），
而**没有任何线索分辨哪条是谁的**。

### 参照系

Claude Code 的 `TodoWrite` 工具 + 一块常驻显示区。本扩展对齐它的**接口形态**
（整表覆写、三态、不做依赖），但**显示形态按本项目的布局约束重新设计**
——Claude Code 没有本项目底部四层区块的历史包袱。

## 目标

- 用户在多步任务进行中，**随时**能看到还剩哪几件事、现在在做哪一件。
- **不新增底部布局层**。底部已有活动区 / 状态行 / 输入框 / 状态栏四层，
  再加一层会让历史区显著变矮。
- 不与 C15 的共享清单发生任何混淆——两份清单在数据、显示、命令三处都不相交。
- 不使用这个能力时，**界面与现在逐字一致**。

## 功能需求

### 一、清单与工具

- **F1 一份清单，会话内唯一。** 它属于主对话，不属于任何子 Agent，
  也与 C15 的共享清单完全独立（两份清单互不可见、互不同步）。

- **F2 一条待办只有两样东西：标题与状态。**
  **刻意没有**认领人、依赖、说明、优先级、时限。
  展示时按清单里的先后顺序编号，**该编号是位置而非稳定标识**——
  整表覆写下不存在「引用某一条」的场景，因此不需要稳定标识
  （这是 F3 换来的直接简化）。

- **F3 唯一的写入操作是「用一份完整清单替换当前清单」。**
  模型每次传完整列表，不传增量指令。

  ⚠ **C15 那份是增量的，原因不是它更省 token，是并发。** 共享清单有 N 个
  并发写入方，覆写语义在那里是错的：甲提交整表时会静默抹掉乙刚加的那条
  （典型 lost update），而两边都不报错。主对话的待办只有一个写入方、
  串行跑在 Agent Loop 里，这个约束不存在，于是可以选更省心的那个——
  模型不必维护标识、不必维护状态机、不会出现「改了一条漏了另一条」的中间态。

- **F4 三个状态：待办 / 进行中 / 已完成。**
  **不设「已取消」「已阻塞」**——那是多方协作才需要的，单一执行者用不上；
  一条不做了，下次覆写时不带它即可。

  ⚠ **不限制「进行中」的条数。** 状态要**如实反映实际执行情况**：
  真的在跑就标进行中，并行执行多件事时可以多条同时进行中。
  Claude Code 强制「同时最多一条进行中」，本扩展**刻意不抄**——
  本项目的模型确实会并行发起多个工具调用，强制单条会让清单在那种场合
  被迫说假话。

- **F5 非法的覆写明确拒绝，并给出可读原因。** 至少覆盖：条目为空标题、
  状态值不认识、条数超过硬上限。拒绝时**一个字节都不改**当前清单，
  且原因要让模型能自我纠正（说清是第几条、哪里不对、该怎么改）。

- **F6 硬上限。** 一份清单最多容纳固定条数（数量级：几十条）。
  超出即拒绝而不是截断——截断会让模型以为写进去了，而清单上少了几条，
  它下一轮据此做的判断全是错的。

- **F7 这个工具不弹确认面板，但仍过一次完整的权限判定。**
  它不读写文件、不执行命令、不联网，副作用限于改本进程内存里的一份清单，
  与 C15 的协作工具同类。因此沿用同一个先例：**对第④层（权限档兜底）免疫**，
  ①②③层与 Hook 一字不动——用户写下的整工具拒绝规则**拦得住它**。

- **F8 规划阶段仍可用。** Plan Mode 的规划阶段本身可能有多步调研，
  而这个工具无任何外部副作用（纯内存）。

- **F9 子 Agent 拿不到这个工具。** 子 Agent 的进度已由活动区呈现，
  再给它一份待办会让屏幕上出现**两处对不上的进度数字**，
  而用户无从判断该信哪个。

### 二、显示

- **F10 位置：钉在历史区内部的最底下。** 历史内容在它上面正常滚动，
  它**不跟着滚**——用户往上翻查旧对话时，待办仍在原处。

  ⚠ **它在历史区之内，不是历史区下方的新一层。** 后者会真的多出一层布局，
  与「不新增底部布局层」直接冲突。

- **F11 出现条件：清单非空且未全部完成。** 清单为空、或全部条目已完成时，
  整块**不显示且不占布局空间**，界面与现在逐字一致。

- **F12 它占位，不浮起。** 条目数变化时历史区的可视高度随之变化，
  上面的内容会移动一格。这是**明确接受的代价**：换来的是历史内容
  一个字都不会被盖住。

  ⚠ 浮层方案（不占位、盖在内容上）已评估并否决：待办是**常驻**元素，
  浮起等于永久遮住历史区最底部若干行，而那几行恰恰是 AI 刚说完的话。
  这与 tui-activity-fold 把四个**打断性**面板改成浮层不是同一个场景。

- **F13 限高：最多显示 5 条**，其余收成末尾一行摘要（形如「……还有 N 条，
  已完成 M 条」）。显示优先级：**进行中 > 待办 > 已完成**——
  用户要看的是「还剩什么」，已完成的让位。

- **F14 状态用一个统一的圆点前缀 + 颜色 + 文字标签表示。**
  颜色口径与子 Agent 活动区同源：进行中橘、已完成绿、待办灰。

  ⚠ **不引入新符号。** 项目的界面符号白名单是收敛过的，圆点专表
  「发生了一件事」、状态靠颜色区分，这里沿用同一条。
  文字标签不可省——**脱离颜色也要认得出**是哪一档。

- **F15 全部完成时，先往对话里留一行事件级记录，再收起整块。**
  记录形如「待办 4/4 全部完成」。

  ⚠ 不留记录的话，用户只要那一刻没盯着屏幕，就永远不知道它列过哪几条待办——
  而收起是必然的（F11）。这与子 Agent 跑完在历史区留一行终态是同一个做法。

- **F16 不进状态行，不新增斜杠命令。** 待办的全部呈现集中在 F10 那一块。

  ⚠ 状态行加一段「N/M 项」在评审时被否决为冗余——待办块本身就常驻可见，
  同一个数字在同屏出现两次只会分散注意力。斜杠命令同理：
  清单没有「藏起来需要翻出来看」的状态。

### 三、与既有能力的接线

- **F17 会话切换必须清空清单并收起显示区**，覆盖 `/clear` 与 `/resume`
  两条路径，且**走同一个复位收口点**——各写一遍必然出现「清空能复位、
  恢复不能」这种一半对的状态。

- **F18 行为记录（trace）覆盖每一次覆写**：记下操作前后的条数与各状态计数，
  以及被拒绝的覆写及其原因。新增的事件类型要能在只读阅读器的时间线里
  显示成一行有意义的摘要。

- **F19 系统提示里要有一段告诉模型什么时候该用它。**

  ⚠ **这一条不能省，理由有先例**：C15 的协作能力当初一个字都没进系统提示，
  真实模型验收下的结果是 0 次使用——工具描述只在「模型已经想到要用它」
  之后才起作用，它决定不了「要不要用」。

  ⚠ **口径取「积极使用」一侧，但下限必须可数。** 与委派（`run_agent`）
  **刻意相反**：委派要起一整条子对话、冷启动，是贵的路径，故默认不做；
  维护待办只是改一份内存清单，成本近于零，失败模式也只是「多了一块清单」。
  这与 Skill 加载那一侧同侧。下限写成**可数的**（少于三步的活不必列），
  不写成抽象判断——模型对有具体可匹配项的指令遵循得好，对抽象判断
  系统性偷懒（这条经验来自委派触发口径的两次反转）。

## 非功能需求

- **N1 不新增底部布局层。** 底部四层（活动区 / 状态行 / 输入框 / 状态栏）
  的结构与高度一字不动。

- **N2 清单的数据与逻辑是叶子包，不依赖 `team` / `subagents` / `tui` / `conversation`。**

  ⚠ **连状态枚举也不复用 C15 那份。** 复用它要让两个叶子包互相知道对方，
  省下的是十几行，换来的是一条会长期误导人的跨包依赖。这与项目里
  「三份权限层名表刻意不合一」「子 Agent 的两套状态刻意分开」是同一条经验。

- **N3 加锁不变量：临界区只做纯内存读写**，一切回调与跨线程调度在锁外。
  本项目已因「加锁临界区内做跨线程调度」死锁五次。
  最稳妥的形态是**这份数据结构不持有任何回调**，从结构上杜绝违反。

- **N4 一切进入界面的文本必须经项目自己的转义函数。**
  待办标题来自模型给的参数，落单的方括号会在布局阶段抛错，
  **没有任何 try/except 兜得住，整个应用退出**。

- **N5 零回归。** 不使用这个能力时（清单始终为空），界面、布局、
  滚动行为与改造前逐字一致。

- **N6 显示区的数据获取不引入从工作线程到界面的推送。**
  与活动区同一条理由：跨线程推送与持锁相遇就是确定性死锁。

## 不做的事

- **跨会话持久化。** 清单随会话生灭，与 C15 那份同理。
- **用户手动增删待办。** 不提供命令层的写路径。
  两条并行的写路径里，命令层那条绕开了「谁改的」这个记录；
  而在整表覆写语义下它还多一层麻烦——模型下一次覆写会把用户的改动整个抹掉，
  **两条写路径与覆写语义天然冲突**。
- **子任务树、优先级、时限、依赖、认领人。** 全部是 C15 那份的领域。
- **待办与 C15 共享清单的双向同步。**
- **对齐 Claude Code 的 `activeForm` 字段**（「Run tests」→「Running tests」）。
  那是英语的时态需求，中文的「跑测试」在两种场合同形。
- **「同时最多一条进行中」的强制约束**（见 F4）。
- **状态行的进度段与只读斜杠命令**（见 F16）。
- **子 Agent 各自的待办**（见 F9）。
- **进入分类器审查。** 它不跑命令、不联网、不发消息，不落那三类中的任何一类。

## 验收标准

### 清单与工具

- **AC1**（F1/F3）模型提交一份三条的清单后，界面与内部状态都反映这三条；
  再提交一份两条的清单，结果**恰好是那两条**——第一次那三条不残留。
- **AC2**（F2）一条待办只承载标题与状态；清单里不存在认领人与依赖概念。
- **AC3**（F4）同一次提交里把两条都标成「进行中」，**提交成功**，
  两条都显示为进行中。
- **AC4**（F5）提交含空标题的条目被拒绝，原因指明是第几条；
  被拒之后再读清单，内容与提交前**逐字相同**。
- **AC5**（F6）提交超过硬上限条数的清单被拒绝而不是被截断。
- **AC6**（F7）这个工具的调用**不弹确认面板**；
  在配置里写下针对它的整工具拒绝规则后，调用**被拒绝**。
- **AC7**（F8）Plan Mode 的规划阶段调用它能成功执行。
- **AC8**（F9）子 Agent 的可用工具集里**不含**这个工具；
  即使角色定义把它写进白名单也拿不到。

### 显示

- **AC9**（F10/F11）清单非空且未全部完成时，待办块出现在历史区内部最底下；
  历史内容滚动时它**留在原处**。
- **AC10**（F11/N5）清单为空时，待办块不显示且不占布局空间——
  历史区的可用高度与不使用该能力时相同。
- **AC11**（F12）条目从 4 条增加到 5 条后，历史区的可视高度减少一行，
  且历史内容**没有任何一行被遮挡**。
- **AC12**（F13）提交 15 条待办后，块内最多显示 5 条，末尾一行给出
  剩余条数与已完成条数；显示出来的 5 条里**进行中的排在待办之前**，
  已完成的**不占用**这 5 个名额（除非没有别的可显示）。
- **AC13**（F14）三种状态各自有可区分的颜色**和**文字标签；
  只看文字（忽略颜色）也能判断出是哪一档。
- **AC14**（F14）待办块使用的符号在项目的界面符号白名单之内，
  **没有引入新符号**。
- **AC15**（F15）最后一条待办被标为完成后，历史区新增一行「全部完成」记录，
  且待办块随之收起。
- **AC16**（F16）状态行的内容与改造前逐字一致；
  斜杠命令清单里**没有**新增命令。
- **AC17**（N4）标题里含方括号的待办能正常显示，**应用不退出**。

### 接线

- **AC18**（F17）有未完成待办时执行 `/clear`：清单清空、待办块收起。
- **AC19**（F17）有未完成待办时 `/resume` 载入另一段会话：同上。
- **AC20**（F18）一次成功的覆写与一次被拒绝的覆写都产生行为记录，
  且在只读阅读器的时间线里各显示成一行有意义的摘要
  （不是「（未登记类型）」）。
- **AC21**（F19）系统提示中含一段说明模型何时该维护待办的文本，
  且其中的下限是**可数的**（例如「少于三步不必列」）而非抽象判断。

### 端到端

- **AC22** 给模型一个需要四五步才能完成的真实任务：
  它在开工前列出待办、每完成一步更新一次、全部完成后清单收起，
  期间历史区的对话内容**一行都没有被遮挡**。
- **AC23** 全程不使用这个能力的一次普通对话里，
  界面、布局与滚动行为与改造前**逐字一致**。
