# 主对话的待办清单 Checklist

> 每一项通过**运行代码或观察行为**来验证。括号里是验证方式与对应的
> spec 验收标准编号。
>
> ⚠ **本项目的历史教训：TUI 改动的单元测试事前抓到的问题接近于零。**
> tui-activity-fold 那一轮真机复核跑出 24 条，单测事前 0 条。
> 因此本清单的**第五节（真机复核）不是可选项**——前四节全绿只说明
> 「代码是对的」，第五节才回答「屏幕上对不对」。

---

## 一、清单本身（纯逻辑，不需要界面）

- [ ] **整表覆写真的是覆写**：先提交 3 条再提交 2 条，读回来**恰好是那 2 条**
      （验证：`python -m unittest tests.test_todo_store` 的覆写用例 / AC1）
- [ ] **一条待办只有标题与状态**：数据结构上不存在认领人、依赖、说明
      （验证：`TodoItem` 的字段数为 2 / AC2）
- [ ] **两条同时「进行中」提交成功**，读回来两条都是进行中
      （验证：同上测试文件的对应用例 / AC3）
- [ ] **非法提交被拒且原因指明是第几条**
      （验证：四类校验各跑一次，断言 `reason` 含序号 / AC4）
- [ ] **被拒时清单一个字节都没变**：先写一份合法的，再提交非法的，
      前后快照**逐字相同**（验证：同上 / AC4）
- [ ] **超上限是拒绝不是截断**：提交 31 条被拒，且读回来**仍是上一份**、
      不是被截成 30 条（验证：同上 / AC5）
- [ ] **版本号只在成功时递增**：失败一次后版本号不变（验证：含反证的用例）
- [ ] **并发覆写不产生混合结果**：20 个线程各写一份不同的清单，
      结束后快照**恰好等于其中某一份**（验证：并发用例）
- [ ] **加锁不变量的结构护栏**：遍历 `TodoStore` 实例属性，
      除记录器外**不存在 callable 成员**（验证：结构护栏用例 / spec N3）

## 二、显示逻辑（纯函数，不需要界面）

- [ ] **空清单不显示**：`build_view` 对空清单返回「不该显示」
      （验证：`python -m unittest tests.test_todo_render` / AC10 的逻辑半边）
- [ ] **全部完成不显示**：同上（/ AC15 的逻辑半边）
- [ ] **表头数字正确**：4 条里完成 2 条时表头是 `待办 (2/4)`（验证：同上）
- [ ] **限高生效**：15 条时只产出 5 行，末尾摘要含**剩余条数**与
      **其中已完成的条数**（验证：同上 / AC12）
- [ ] **进行中排在待办之前**（验证：同上 / AC12）
- [ ] **已完成不占名额**：「5 条已完成 + 2 条待办」时，
      显示出的 5 条里那 2 条待办**都在**（验证：同上 / AC12）
- [ ] **同优先级保持原序**：交换两条待办的输入顺序，输出顺序跟着换
      （验证：稳定性用例）
- [ ] **快照不受显示排序影响**：`store.snapshot()` 永远返回模型给的原序
      （验证：对比 `snapshot` 与 `build_view` 的顺序）

## 三、工具与接线

- [ ] **工具属性正确**：`read_only=False` / `system_serial=True` /
      `plan_safe=True` / **无** `classifier_scope`
      （验证：`python -m unittest tests.test_todo_tool`）
- [ ] **`execute` 接受 `plan_stage` 关键字参数**
      （验证：`inspect.signature` 断言。这是 `plan_safe=True` 的硬约定，
      漏了会在规划阶段抛 `TypeError` / spec F8）
- [ ] **参数里的状态取值与内部枚举逐字相等**
      （验证：集合相等断言。不等会让模型写出一个工具认不出的状态）
- [ ] **不弹确认面板**：权限引擎对该工具的结论不是 ASK
      （验证：`python -m unittest tests.test_todo_integration` / AC6 前半）
- [ ] **`deny: todo_write` 真的拦得住**：配一条**不带括号**的整工具拒绝规则后，
      结论是 DENY（验证：同上 / AC6 后半）
- [ ] **规划阶段不可用**（⚠ 2026-08-18 反转，见 spec F8 勘误块）：Plan Mode 规划阶段调用它**被守卫拦下、清单一个字节都不变**，回灌理由**不说它有副作用**；计划获批后同一个调用照常成功
      （验证：同上 / AC7）
- [ ] **子 Agent 拿不到**：即使角色定义写 `tools: [todo_write]`，
      最终工具集里也没有它（验证：同上 / AC8）
- [ ] **系统提示里那段只出现一次**：传入 brief 后 `stable` 段中该文本
      **恰好出现一次**（验证：计数断言。出现两次说明 `_FILLED` 漏改 / AC21）
- [ ] **提示里的下限是可数的**：brief 文本含「少于三步」这类**可数**表述，
      且**不含**「拿不准就列」这类无下限措辞
      （验证：含反证的断言 / AC21、spec F19）
- [ ] **两处口径一致**：工具描述与系统提示那段都含同样四层意思
      （每次传完整清单 / 状态如实反映 / 多步才列 / 随时更新），
      且去掉任一处的任一层会让护栏变红
      （验证：`SameVoiceTest` 含反证 / plan 的成对维护点第 1 条）
- [ ] **记录事件在阅读器里有摘要**：跑一次带 `--trace` 的覆写，
      用阅读器读时间线，那一行**不是「（未登记类型）」**
      （验证：`python -m rhinecode.trace.reader <文件>` / AC20）
- [ ] **成功与被拒都留痕**：一次成功、一次被拒，记录里**各有一条**
      （验证：同上 / AC20）

## 四、编译与全量测试

- [ ] **编译无错**（验证：`python -m compileall rhinecode tests`）
- [ ] **全量测试全绿，skipped 仍是 4 项**
      （验证：`python -m unittest discover -s tests`）
- [ ] **`todo` 包是叶子包**：单独 import 它只拉起 `todo` 自身与 `trace`
      （验证：`python -X importtime -c "import rhinecode.todo" 2>&1 |
      grep -o "rhinecode\.[a-z_.]*" | sort -u`，输出**只有** `rhinecode.todo*`
      与 `rhinecode.trace*` 两族；出现 `team` / `tools` / `permission` 即违反 spec N2）
- [ ] **符号白名单没被突破**（验证：`python -m unittest tests.test_tui_symbols`）
- [ ] **既有会话切换路径没被碰坏**
      （验证：`python -m unittest tests.test_clear_stale_deliverables tests.test_tui_keybindings`）

## 五、真机复核（⚠ 不可跳过）

> 前四节全绿只说明代码是对的。**这一节回答屏幕上对不对**，
> 而本项目的历史是：这两件事经常不是一回事。
>
> 用 e2e 宿主起真实界面，或直接 `rhine` 跑一个真实会话。

### 布局

- [ ] **不用这个功能时，界面与改造前逐字一致**：跑一次普通对话，
      对照改造前的截图——历史区高度、框线、滚动行为**一处不差**
      （验证：肉眼 + `screen` 导出对比 / AC23、spec N5）
- [ ] **待办块出现在历史区最底下**，框线是连续的一整圈、
      **没有出现两个框**（验证：肉眼 / AC9）
- [ ] **它钉得住**：往上翻历史，待办块**留在原处**（验证：肉眼 / AC9）
- [ ] **它不遮挡**：待办块出现前后，历史内容**一行都没有被盖住**
      （验证：出现前后各 `screen` 导出一次，比对最后几行文字是否都还在 / AC11）
- [ ] **加一条会挤上去一行**：从 4 条变 5 条后，可滚动区高度**减少 1**
      （验证：`screen` 前后对比 / AC11）
- [ ] **确认面板弹出时不打架**：待办块显示期间触发一次确认面板，
      面板正常弹出、框线正常（验证：肉眼。⚠ 面板会盖住待办块，
      这是已知且可接受的——面板是打断性的、转瞬即逝）

### 内容

- [ ] **三个状态各自可区分**：屏幕上三档的颜色不同，**且**中文标签不同；
      把终端调成单色后**仍能分辨**（验证：肉眼 / AC13）
- [ ] **没有引入新符号**：待办块上出现的符号只有白名单里的那个圆点
      （验证：肉眼 + `screen` 导出搜索 / AC14）
- [ ] **超过 5 条时收起来**：让模型列 8 条，屏幕上只有 5 行加一行摘要
      （验证：肉眼 / AC12）
- [ ] **标题含方括号不炸**：手工构造一条标题含 `[` 的待办，
      **应用不退出**、内容正常显示
      （验证：脚本化剧本触发一次 / AC17、spec N4）
- [ ] **待办块的文字能拖选、能复制**（验证：真实终端里拖选一行再复制，
      粘贴出来是那行文字。⚠ 只测「全选复制」不够——上一轮的教训是
      那样测会全绿而用户「连选都选不了」）

### 生命周期

- [ ] **全部完成后留一行记录，然后收起**：屏幕上先出现
      「待办 N/N 全部完成」，随后待办块消失（验证：肉眼 / AC15）
- [ ] **那一行只出现一次**（验证：`screen --selector "#history-messages"`
      导出后计数 / AC15）
- [ ] **`/clear` 之后待办块收起**（验证：肉眼 / AC18）
- [ ] **`/clear` 之后重新列待办能正常显示**
      （验证：肉眼。⚠ 这条专防「版本号没复位导致第一次刷新被跳过」，
      症状是「换了会话之后第一次列待办不显示」，看起来像功能坏了）
- [ ] **`/resume` 载入另一段会话后待办块收起**（验证：肉眼 / AC19）
- [ ] **状态行一个字没变**：对照改造前，状态行内容逐字相同、
      **没有多出进度段**（验证：`screen` 导出对比 / AC16、spec F16）
- [ ] **斜杠命令没多**：`/help` 的命令列表与改造前**逐字相同**
      （验证：`/help` 输出对比 / AC16）

## 六、端到端场景

- [ ] **场景 1（主场景 / AC22）**：给模型一个需要四五步的真实任务
      （例：「把某个模块的错误处理统一改一遍并跑测试」）。
      预期依次观察到——开工前列出待办 → 每完成一步清单原地更新
      → 全部完成后留一行记录并收起 → **全程历史区的对话内容一行都没被遮挡**。
      （验证：真实模型跑一遍，全程录屏或分段 `screen` 导出）

- [ ] **场景 2（零回归 / AC23）**：一次完全不涉及待办的普通对话
      （问一个问题、读一个文件）。预期：待办块**从未出现**，
      界面、布局、滚动行为与改造前**逐字一致**。
      （验证：改造前后各跑一次同样的输入，`screen` 导出逐行比对）

- [ ] **场景 3（拒绝路径）**：让模型提交一份超上限（31 条）的清单。
      预期：工具返回失败、模型收到可读原因并自我纠正（重新提交一份短的），
      **屏幕上的待办块保持上一份内容不变**。
      （验证：脚本化剧本 + `screen` 导出）

- [ ] **场景 4（边界 / spec F9）**：让主 Agent 委派一个子 Agent 干活。
      预期：子 Agent **调不到**这个工具（它的工具集里没有），
      屏幕上不出现第二份待办，活动区照常显示子 Agent 进度。
      （验证：真实模型或脚本化剧本 + `/agents` 报告）

- [ ] **场景 5（Plan Mode / AC7）**：在 `plan` 模式的规划阶段让模型列待办。
      预期：调用成功、待办块正常显示，且**规划阶段守卫没有拦它**。
      （验证：`/mode` 切到 plan 后跑一轮）
