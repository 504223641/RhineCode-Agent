## 怎么测的

宿主起 `--mode live`，用 `--seed` 预置一份与 `G:\Rhine-test` 内容一致的
小项目（三个模块各两处裸 `except` + 一个拼错的函数名 + 一份测试）。

四条场景**双向**设计——既测「该列没列」，也测「不该列却列了」。
上一次做委派触发口径时踩过「治好欠触发、变成过触发」的来回。

⚠ 提示词里**一个字都不提「待办」「清单」「列步骤」**。一提就等于把答案
告诉它，测出来的不是它自己的判断。

| 场景 | 提示词 | 期望 |
| --- | --- | --- |
| B1 | 三个文件的裸 except 都改掉 + 跑测试（**5 步**） | ✅ 该列 |
| B2 | 改一个拼错的函数名（**1 步**） | ❌ 不该列 |
| B3 | 看一眼某函数有什么问题（**1 步**） | ❌ 不该列 |
| B4 | 纯问答，没有要执行的动作 | ❌ 不该列 |

## 结果

| 模型 | B1 | B2 | B3 | B4 | 通过 |
| --- | --- | --- | --- | --- | --- |
| `deepseek-v4-flash` | ❌ **没列** | ✅ 没列 | ✅ 没列 | ✅ 没列 | 3/4 |
| `deepseek-v4-pro` | ❌ **没列** | ✅ 没列 | ✅ 没列 | ✅ 没列 | 3/4 |

**不该列的三条全过**（两个模型、三轮，一次都没有误触发）。
**该列的那条全败**，三轮都是 0 次。

B1 的规模不小——flash 跑了 13 轮做了 23 次工具调用（12 次 `edit_file`），
pro 跑了 11 轮做了 16 次。这不是「任务太小所以不必列」。

## 三个杠杆，逐个加，逐个验证送达

| 轮次 | 加了什么 | 送达验证 | B1 结果 |
| --- | --- | --- | --- |
| 第 1 轮 | 系统提示 133 槽（能力描述式） | trace 里 `## 待办清单` 完整出现 | flash 0 次 / pro 0 次 |
| 第 2 轮 | 改写成**指令式**：「这不是可选项」+ 四条可匹配条件（改 2 个以上文件 / 三步或更多 / 多件事 / 多处重复应用）；工具描述同口径 | 工具 schema 里 `description` 全文送达 | flash 0 次 / pro 0 次 |
| 第 3 轮 | **每轮 `<system-reminder>` 注入**（Claude Code 真正用的那个机制） | 第 1 轮 messages 里逐字出现「你的待办清单目前是空的」 | flash 0 次 / pro 0 次 |

⚠ **每一轮都先验证「送到了没有」再看结果**，没有一次是靠猜的。
这是 C15 那次的教训：当初协作能力 0 次使用，根因是一个字都没进系统提示——
如果不查 trace，会误判成「模型不听话」而去改措辞。

## 决定性对照：不是「不能」，是「不用」

单独跑一次，**明确命令**它用这个工具：

> 请用 todo_write 工具把接下来要做的四步列出来：改 auth.py、改 orders.py、
> 改 payments.py、跑测试。列完就停下，先别动手。

结果：

```
todo_write 调用次数: 1
参数: {'todos': [{'title': '改 auth.py', 'state': 'pending'},
                 {'title': '改 orders.py', 'state': 'pending'},
                 {'title': '改 payments.py', 'state': 'pending'},
                 {'title': '跑测试', 'state': 'pending'}]}
结果 ok: True | 4 条待办，已完成 0 条
```

**一次成功、参数完全正确。** 所以：

- 不是接线问题（工具在 `tool_names` 里）；
- 不是 schema 问题（描述全文送达、参数解析正确）；
- 不是能力问题（叫它就会用，用得还挺规范）。

**是它自己不选这条路。**

## 这说明什么

这与 C11 记录的「模型欠触发 Skill」是**同一类系统性偏差**，
但程度更重：Skill 那次靠改写清单表头（改成「指令」口径）就明显改善了，
待办这次**三个杠杆全用尽仍然纹丝不动**。

⚠ **值得记下的一条**：欠触发与过触发不是同一个旋钮的两端。
委派那次是「推得太狠 → 过触发」，说明那个旋钮是灵的；
待办这次是「推到底也不动」，说明**DeepSeek v4 对这一类「先规划、
再动手」的元动作有很强的先验**——它倾向于直接开干。
两个模型（flash / pro）表现完全一致，**不是模型强弱问题**。

## 查证 Claude Code：差距是**示例**，不是措辞

上面三个杠杆全是**规则**。查了 Claude Code 的实际做法之后，
差距一眼就看出来了。

| 杠杆 | Claude Code | 本扩展（三轮之后） |
| --- | --- | --- |
| 系统提示里的 Task Management 段 | 有，写「use these tools **very frequently**」 | ✅ 槽位 133 |
| 工具结果回灌完整清单 | 有——**根本没有 TodoRead 工具**，模型只能从每次写入的返回值里学到当前状态 | ✅ `output="当前待办清单：…"` |
| 每轮 `<system-reminder>` | 有，紧跟在工具输出之后 | ✅ 位置已经相同（见下） |
| **工具描述里的 many-shot 示例** | **8 个**，四正四负，每个带 `<reasoning>`，全文约 1400–1500 词、规则只占开头两小节 | ❌ **1 个正例、0 个负例**，全文约 400 字 |

⚠ **一处最初判断错、查代码后纠正的**：曾以为本项目的提醒挂在系统提示区域、
离决策点远，而 Claude Code 挂在工具输出后面。**实际位置本来就一样**——
`agent/loop.py:1093-1100` 把 reminder 追加在 `req_messages` **末尾**，
而工具结果在上一步已经进了 `history`，所以它天然紧跟在工具输出之后。
这条不用改。

**为什么示例比规则管用**：规则要求模型自己做抽象判断（「这算不算多步」），
而模型对抽象判断**系统性偷懒**——这条经验本项目已经付过两次学费
（C13 委派触发口径的两次反转、C11 的 Skill 欠触发）。示例把判断降级成
模式匹配，给它可直接对齐的参照物。

⚠ **四个负例比四个正例更要紧。** 本轮 B2/B3/B4 三条全过，靠的是模型自己
保守的先验——**而那个先验同时也在压着 B1**。负例是「不该列」那条边界
唯一的形状来源；只给正例就是单向推力，那正是委派那边翻过一次的车。

## 第四个杠杆（已实施，待复测）

按上表补齐：工具描述改成「规则两小节 + 四正四负八个示例，每个带一段判据」，
系统提示那段加一个负例并指向工具描述。落点是 spec 新增的 **F20 / AC22**。

四个负例里有一个是**贴着下限的临界情形**（「加个 parse_date 函数，再补个
测试」——确实两件事，但只有两步，示范成不列）。这一个是刻意挑的：
「一步」与「纯问答」那种负例模型本来就不会误判，真正需要示范的是
最容易往上凑的那一档。

护栏：`tests/test_todo_tool.py::ManyShotExamplesTest`——钉住正反各 4 个、
每个都带判据、临界负例在、且描述侧不含无下限推力。
⚠ 最后那条**是本轮补齐的一半护栏**：此前只有系统提示那侧钉了「无下限推力」
反证，工具描述侧是空的——成对维护点少了一半，描述可以单方面滑走而没人发现。
（写这一轮时我自己就差点写下「拿不准就数步数」，被 brief 那侧的护栏当场拦下。）

## 复测结果（2026-08-18，同一套四场景）

| 模型 | B1 该列 | B2 | B3 | B4 | 通过 |
| --- | --- | --- | --- | --- | --- |
| `deepseek-v4-flash` | ✅ **列了，3 次** | ✅ | ✅ | ✅ | **4/4** |
| `deepseek-v4-pro` | ❌ 仍然 0 次 | ✅ | ✅ | ✅ | 3/4 |

**flash 从 0 次变成 3 次，且质量完全合规**——每次都传完整清单、状态如实、
按执行顺序、**没有攒到最后一起标完成**（那是最担心的失败模式）：

| 次 | 内容 |
| --- | --- |
| 1 | 4 条，标题具体到「2 处裸 except」（先调研过），首条 `in_progress` |
| 2 | 三个文件 `completed`、跑测试 `in_progress` |
| 3 | 全部 `completed` → 界面上待办块自动收起 |

⚠ **B2/B3/B4 零误触发，没有推成过触发。** 这是本轮最该盯的一条
（已知项 #17 那次就是治欠触发翻车成过触发）。

### 两个模型第一次分叉了

此前三轮 flash 与 pro **表现完全一致**（都 0 次），据此写下过
「不是模型强弱问题」。**示例这一轮把它们分开了**：同一份提示词，
flash 用，pro 不用。原结论要按这个新证据修正。

pro 的 B1：9–10 轮、13 次工具调用，改 3 个文件、跑 2 次命令——
**三条触发条件全中**（改 2 个以上文件 / 三步或更多 / 多处重复应用），
正文里连「先规划」都没提过，读完就直接改。这与社区记录的现象一致：
**效率更高的模型更倾向跳过待办工具**。

### 第五个杠杆：时点锚点（对 flash 有效、对 pro 无效）

不再加推力（那会把 flash 推成过触发），改为给一个**可匹配的时点**：

> 在你本次任务第一次调用 `edit_file` / `write_file` / `run_command` 之前。

「开始动手之前」是抽象判断，模型对它系统性偷懒；三个工具名是可匹配项。
同时写明「这是**时点**不是新增触发条件」，并说明只读调研发生在列清单
之前很正常（那正是列得出清单的前提）。

实测：**pro 0 次 → 0 次**（无效）；**flash 首次调用从第 5 轮提前到第 4 轮**
（正是锚点想要的位置），4/4 复现、无回归。

### 送达验证（每一轮都查了，没有一次靠猜）

pro 那轮逐轮确认：系统提示的 `## 待办清单`、工具 schema 里的
`## 不该用的例子` 与「临界情形」、每轮 `<system-reminder>` 的
「你的待办清单目前是空的」——**全部在，逐轮在**，`todo_write` 也在
`tool_names` 里。（第 6、8 轮没有，那是 C16 分类器的请求，pro 恰好跑了
2 次 `run_command`，对得上。）

**所以 pro 不是没看见，是看见了不用。**

### 邻接假设有了实证，但解释不了全部

dump 系统提示确认：待办段（133）**紧接着**就是组队段（134）那一大段
「⚠️ 这些都不构成组队信号」「你自己顺序做完更快」的克制措辞。
串味的假设因此有了实证基础——**但 flash 读的是同一份提示词却触发了**，
所以邻接顶多是原因之一，不是全部。

## 还剩什么路（都只针对 pro，flash 已经通了）

⚠ **先记一条方法论：措辞这条路对 pro 已经试到第五个杠杆了。**
再往下加推力的边际收益很低，而**每加一分推力都在拿 flash 那侧的
零误触发冒险**——两侧要一起看，不能只盯 B1。

1. **调整槽位相邻关系**（成本最低，已有实证）。把待办段挪开、
   或在它与组队段之间插一个隔断。风险是可能影响组队那侧的触发口径，
   要连 C15 的场景一起复测。
2. **把触发条件搬进固定模块。** 现在它在可选槽位（110–140），
   而 `任务模式` / `动作执行` 那几个固定模块（priority 10–70）是模型
   当成「核心规则」读的。会动 C5 的模块结构，需要单独评审。
3. **接受按模型分档。** pro 走「用户显式要求才列」，flash 走自动维护。
   ⚠ 这条的代价要说清楚：**同一个功能在两个模型上行为不同，
   而界面上完全看不出来**——本项目通篇最忌讳的正是这种静默分叉。
   真要这么定，至少得在 `/context` 或启动提示里让用户看得见。

## 当前该怎么用这个功能

- **`deepseek-v4-flash`：自动维护已经工作。** 多步任务它会在动手前列出来、
  过程中逐条更新，且不误触发。
- **`deepseek-v4-pro`：仍然是用户显式触发。** 明确要求它列就一定能用，
  界面、限高、顺序、留痕全部正常（A 组已逐条验过）。

# 第二轮：进度纪律与规划阶段（2026-08-18）

上面那一整章解决的是「**列不列**」。这一章解决的是用户随后报的两个新症状，
两者都发生在「已经列了」之后：

1. **任务还没确认好就直接生成 todo**（规划阶段就冒出清单）；
2. **中途一直不更新，最后一次性把所有任务标完成**。

改动与理由见 `spec.md` 的 F4 / F8 两个勘误块。这里只记实跑结果。

## 怎么测的

同一套测试台（`seed_todo_bench`），`--mode live`，模型 `deepseek-v4-flash`。
⚠ **提示词里仍然一个字不提「待办」「清单」「列步骤」**，与第一轮同口径。

七个场景，覆盖两个症状 + 防过触发的反向对照：

| 场景 | 模式 | 提示词大意 | 期望 |
| --- | --- | --- | --- |
| C1 | auto | 三个文件的裸 except 都改掉 + 跑测试（**4 步**） | ✅ 列，且逐步更新 |
| C2 | plan | 同 C1 | ❌ 规划阶段不列；获批后可用 |
| C2b | plan | 给三个模块各写一份单元测试 + 跑测试（**4 步**） | ❌ 规划阶段不列；✅ 获批后列并更新 |
| C3 | auto | 改一个拼错的函数名（**1 步**） | ❌ 不该列 |
| C4 | auto | 纯问答，没有要执行的动作 | ❌ 不该列 |
| C5 | auto | 补类型注解 + 跨文件改名 + 补测试 + 跑测试（**6 步**） | ✅ 列，且逐步更新 |
| C6 | auto | 三个模块的 docstring 改英文 + 跑测试（**4 步**） | ✅ 列，且逐步更新 |

## 结果：七个场景全过

判据**机器化**跑在 trace 上，不靠肉眼读界面：

| 判据 | C1 | C2b 获批后 | C5 | C6 |
| --- | --- | --- | --- | --- |
| ① 每次提交至多一条 `in_progress` | ✅ | ✅ | ✅ | ✅ |
| ② 不许 `pending` → `completed` 跳步 | ✅ | ✅ | ✅ | ✅ |
| ③ 中途更新而非批量收尾 | ✅ 5 次 | ✅ 5 次 | ✅ 7 次 | ✅ 5 次 |
| ④ 第一次动手之前先列 | ✅ | ✅ | ✅ | ✅ |
| ⑤ 相邻两次动手之间有更新 | ✅ | ✅ | ⚠ 见下 | ✅ |
| ⑥ 收尾时全部 `completed` | ✅ | ✅ | ✅ | ✅ |

规划阶段：**C2 与 C2b 各 0 次 `todo_write`**，且每一轮请求的工具清单里
**都没有 `todo_write`**（12 个工具）；获批后那一轮变成 16 个、含它。
两道防线都验到了——第一道是它压根不在 schema 里，第二道是守卫。

防过触发：**C3 与 C4 各 0 次**。新加的三条规矩没有把口径推到另一侧。

### ⚠ 那处 ⚠ 是判据写错了，不是模型的问题

C5 的 `seq=182`（`write_file`）与前一个动作 `seq=170`（`run_command`）之间
没有更新。查下来两者属于**同一条待办**（170 是验证改名生效的命令、
182 是写测试文件），中间本来就没什么可更新的。

**判据⑤「每个动作边界都要有更新」本身过严**——一条待办完全可以跨多个动作。
记在这里免得下次有人照着这条去「修」一个不存在的问题。

## 最有说服力的一段：发动机真的在转

C1 的 `seq=76` 模型改完了 `auth.py`，但**没有立刻汇报**。
下一轮（`seq=80`）注入的提醒念出了具体条目：

> 你的待办清单上标着 in_progress 的是第 1 条：**改 src/auth.py 的裸 except**。
> **它做完了吗？**

模型在 `seq=90` 就补上了——把第 1 条标 completed、第 2 条标 in_progress。

这正是设计意图的直接观测：**「同一时刻只有一条」制造出「必须开口」的时刻，
而念出具体条目的提醒把那个时刻变成一个指名道姓、很难当没看见的问句。**

## 送达验证（每一轮都查了，没有一次靠猜）

沿用第一轮的纪律。C1 的 9 轮主对话请求逐轮查提醒内容：

| 轮次 | 注入的提醒 |
| --- | --- |
| seq 8 / 24 / 56 | 空清单提醒（此时确实还没列） |
| seq 69 / 80 | 念出「第 1 条 改 src/auth.py 的裸 except」 |
| seq 97 | 念出「第 2 条 改 src/orders.py 的裸 except」 |
| seq 114 | 念出「第 3 条 改 src/payments.py 的裸 except」 |
| seq 134 | 念出「第 4 条 跑 tests 里的测试确认没坏」 |
| seq 148 | **无提醒**（全部完成，按设计不再打扰） |

序号与标题每一轮都与当时的清单一致，最后一轮正确地闭嘴。

## 界面侧的物证

C6 的五条 `todo_update` 事件（界面被告知要显示什么）：

```
completed 0 / in_progress 1   ← 刚列出来
completed 1 / in_progress 1
completed 2 / in_progress 1
completed 3 / in_progress 1
completed 4 / in_progress 0   ← 收尾，待办块随之收起
```

`in_progress` 全程恰好一条，`completed` 单调递增且每次只涨 1——
用户在屏幕上看到的就是「一步一步在走」，而不是「一直不动然后突然全绿」。

## 还没验到的

- **`deepseek-v4-pro` 没测。** 第一轮里它在「列不列」上就是 0 次
  （与 flash 分叉），因此本轮那些「列了之后怎么走」的判据在它身上
  暂时无从谈起。它那侧的结论仍是第一轮的：用户显式要求才列。
- **点火分支一次都没触发。** 七个场景里模型始终维持着恰好一条
