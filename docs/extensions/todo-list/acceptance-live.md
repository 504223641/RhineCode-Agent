# B 组 · 触发口径的真实模型验收

> 2026-08-18 · `deepseek-v4-flash` 与 `deepseek-v4-pro` **各三轮**
> · 判据取自 trace（`tool_execute` 事件），不取界面
>
> **结论先说：三个杠杆全部用尽，两个模型在「该列」那条上仍然是 0 次。
> 这是模型的判断问题，不是本扩展的缺陷——但它意味着这个功能在
> DeepSeek v4 上的实际触发率接近于零。**

## 怎么测的

宿主起 `--mode live`，用 `--seed` 预置一份与 `G:\Rhine-test` 内容一致的
小项目（三个模块各两处裸 `except` + 一个拼错的函数名 + 一份测试）。

四条场景**双向**设计——既测「该列没列」，也测「不该列却列了」。
上一次做委派触发口径时踩过「治好欠触发、变成过触发」的来回。

⚠ 提示词里**一个字都不提「待办」「清单」「列步骤」**。一提就等于把答案
告诉它，测出来的不是它自己的判断。

| 场景 | 提示词 | 期望 |
| --- | --- | --- |
| B1 | 三个文件的裸 except 都改掉 + 跑测试（**5 步**） | ✅ 该列 |
| B2 | 改一个拼错的函数名（**1 步**） | ❌ 不该列 |
| B3 | 看一眼某函数有什么问题（**1 步**） | ❌ 不该列 |
| B4 | 纯问答，没有要执行的动作 | ❌ 不该列 |

## 结果

| 模型 | B1 | B2 | B3 | B4 | 通过 |
| --- | --- | --- | --- | --- | --- |
| `deepseek-v4-flash` | ❌ **没列** | ✅ 没列 | ✅ 没列 | ✅ 没列 | 3/4 |
| `deepseek-v4-pro` | ❌ **没列** | ✅ 没列 | ✅ 没列 | ✅ 没列 | 3/4 |

**不该列的三条全过**（两个模型、三轮，一次都没有误触发）。
**该列的那条全败**，三轮都是 0 次。

B1 的规模不小——flash 跑了 13 轮做了 23 次工具调用（12 次 `edit_file`），
pro 跑了 11 轮做了 16 次。这不是「任务太小所以不必列」。

## 三个杠杆，逐个加，逐个验证送达

| 轮次 | 加了什么 | 送达验证 | B1 结果 |
| --- | --- | --- | --- |
| 第 1 轮 | 系统提示 133 槽（能力描述式） | trace 里 `## 待办清单` 完整出现 | flash 0 次 / pro 0 次 |
| 第 2 轮 | 改写成**指令式**：「这不是可选项」+ 四条可匹配条件（改 2 个以上文件 / 三步或更多 / 多件事 / 多处重复应用）；工具描述同口径 | 工具 schema 里 `description` 全文送达 | flash 0 次 / pro 0 次 |
| 第 3 轮 | **每轮 `<system-reminder>` 注入**（Claude Code 真正用的那个机制） | 第 1 轮 messages 里逐字出现「你的待办清单目前是空的」 | flash 0 次 / pro 0 次 |

⚠ **每一轮都先验证「送到了没有」再看结果**，没有一次是靠猜的。
这是 C15 那次的教训：当初协作能力 0 次使用，根因是一个字都没进系统提示——
如果不查 trace，会误判成「模型不听话」而去改措辞。

## 决定性对照：不是「不能」，是「不用」

单独跑一次，**明确命令**它用这个工具：

> 请用 todo_write 工具把接下来要做的四步列出来：改 auth.py、改 orders.py、
> 改 payments.py、跑测试。列完就停下，先别动手。

结果：

```
todo_write 调用次数: 1
参数: {'todos': [{'title': '改 auth.py', 'state': 'pending'},
                 {'title': '改 orders.py', 'state': 'pending'},
                 {'title': '改 payments.py', 'state': 'pending'},
                 {'title': '跑测试', 'state': 'pending'}]}
结果 ok: True | 4 条待办，已完成 0 条
```

**一次成功、参数完全正确。** 所以：

- 不是接线问题（工具在 `tool_names` 里）；
- 不是 schema 问题（描述全文送达、参数解析正确）；
- 不是能力问题（叫它就会用，用得还挺规范）。

**是它自己不选这条路。**

## 这说明什么

这与 C11 记录的「模型欠触发 Skill」是**同一类系统性偏差**，
但程度更重：Skill 那次靠改写清单表头（改成「指令」口径）就明显改善了，
待办这次**三个杠杆全用尽仍然纹丝不动**。

⚠ **值得记下的一条**：欠触发与过触发不是同一个旋钮的两端。
委派那次是「推得太狠 → 过触发」，说明那个旋钮是灵的；
待办这次是「推到底也不动」，说明**DeepSeek v4 对这一类「先规划、
再动手」的元动作有很强的先验**——它倾向于直接开干。
两个模型（flash / pro）表现完全一致，**不是模型强弱问题**。

## 还没试过的两条路（留给下一轮）

1. **调整槽位相邻关系。** 待办段（133）后面**紧挨着**组队段（134），
   而后者开头就是 ⚠️「**默认不要组队**」。两段贴着，克制的语气可能串味。
   把待办段挪到别处、或在两段之间插一个隔断，是最便宜的一次试验。
2. **把触发条件搬进固定模块。** 现在它在可选槽位（110–140 那一段），
   而 `任务模式` / `动作执行` 那几个固定模块（priority 10–70）是模型
   当成「核心规则」读的。搬过去成本不高，但会动 C5 的模块结构，
   需要单独评审。

## 当前该怎么用这个功能

**明确要求它列就一定能用**，界面、限高、顺序、留痕全部工作正常
（A 组已逐条验过）。所以现在的实际形态是：

> 一个**用户显式触发**的功能，而不是模型自动维护的功能。

如果这不是你要的形态，下一轮从上面那两条路里挑一条试。
