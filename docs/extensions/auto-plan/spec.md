# 只留 `auto` / `plan` 两个模式 Spec

> 扩展，不占章节号。判据（`docs/extensions/README.md`）：`CLAUDE.md` 的能力表
> **不多一行**——本扩展不引入新能力层，只把既有的两条轴重新包装成用户看得见的
> 两个预设，并顺带补一处环境变量泄漏。

## 背景

### 现状是「两个开关六种组合」

RhineCode 现在有两个互不相干的运行期开关：

| 开关 | 取值 | 语义 |
| --- | --- | --- |
| `/perm` | 严格 / 默认 / 放行 | 权限管线**第④层**的兜底档：规则未命中的灰色地带怎么算 |
| `/plan` | 开 / 关 | **阶段状态机**：规划 → `present_plan` → 审批 → 执行 |

两者正交，笛卡尔积是六种组合。用户要在脑子里同时维护两个变量，而其中四种
组合从来没人用过（「严格 + 计划模式」是什么意思？）。

### 用户要的是两个模式

对齐 Claude Code 的体验：一个放手干活的 `auto`，一个先看方案的 `plan`，
`Shift+Tab` 两态切换。**`auto` 里连 `run_command` 也自动批准。**

### 为什么现在能做

本扩展要做的事，本质是**把「写文件要弹确认」那次面板去掉**。而那次面板此前
是「模型改写自己的 `permissions.yaml` / `hooks.yaml` / `agents/` 从而持久化提权」
这个缺口的**唯一实际拦截**。

②″保护路径收紧器已于 2026-08-14 落地
（[`docs/extensions/protected-paths/`](../protected-paths/spec.md)），
它在 `decide` 的**出口**把保护路径的写入无条件升级为 ASK，
**任何 allow 规则、任何权限档、任何预授权都消解不掉它**。顺序前置条件已满足。

### 结构上抄 Codex，不抄它的实现

Codex 对用户只暴露 `Read Only` / `Auto` / `Full Access` 三个 **preset**，
底下其实是 `sandbox`（能做什么）× `approval`（什么时候问）两条正交轴。
我们的「权限档 × 规划阶段」正好同构，所以两个模式做成 **preset 而不是新枚举值**。

⚠ 只抄结构不抄保障：Codex 的 `auto` 靠 **OS 级沙箱**兜底
（macOS Seatbelt / Linux Landlock+seccomp），而**两家都不支持原生 Windows**。
本扩展的 `auto` 没有沙箱兜底，这是明知的取舍，收窄手段留给后续的分类器章节。

## 目标

- 用户界面上**只剩两个模式**：`auto` 与 `plan`，`Shift+Tab` 两态循环。
- 底层的两条正交轴**一个字不改**，preset 只是它们的一个固定组合。
- `auto` 成为**启动缺省**。
- 顺带堵住一处随之从「隐患」升级为「常态」的泄漏：被执行的命令能看到 API Key。

## 功能需求

### 预设本身

- **F1**：定义两个预设，各自是「权限档 × 规划阶段」这两条既有轴上的一个点。
  - `auto` = 放行档 + 规划阶段**关**
  - `plan` = 放行档 + 规划阶段**开**

- **F2**：`plan` 预设**不改动权限档**。它的「只读」性质完全由**规划阶段的工具
  过滤**保证，与权限档无关。
  ⚠ 这是本 spec 与 todo 原文措辞的一处**刻意分歧**，理由见「与 todo 原文的分歧」。

- **F3**：启动缺省预设为 `auto`。

- **F4**：预设层是**纯映射**，不引入第三条状态轴。系统里可查询的运行期状态仍
  只有「权限档」与「规划阶段」两个；「当前是哪个预设」由这两者**推导**而来，
  不单独存一份。

### 切换入口

- **F5**：`Shift+Tab` 在两个预设间循环，且**不改变焦点**。

- **F6**：提供一个切换命令，语义与 `Shift+Tab` 完全相同（两态循环）。
  `/plan` 保留为它的别名——老用户的肌肉记忆不断。

- **F7**：**删除切换权限档的命令及其全部别名。** 运行期不再有任何入口能把主对话
  的权限档切到放行档以外的值。

- **F8**：切换后立即刷新状态栏，并回显当前预设。

### 枚举与配置的兼容

- **F9**：**不新增权限档枚举值。** 三个既有档位（严格 / 默认 / 放行）全部保留在
  枚举里——内置的两个只读角色声明了严格档，删掉会破坏它们。

- **F10**：严格档与默认档**退出用户的运行期切换循环**，但仍可经两条路径抵达：
  `permissions.yaml` 与角色定义的 `permission_mode` 字段。
  手法对齐 Claude Code 的 `dontAsk`——那个档位存在、可被显式指定，只是永不进
  `Shift+Tab` 循环。

- **F11**：配置文件与角色定义里写的**仍是原来的字面量**（`strict` / `default` /
  `permissive`）。本扩展**不得**要求用户改写任何已有配置。

### 审批后的归属

- **F12**：计划**获批**时，预设**当场且永久**切回 `auto`：状态栏立刻变，
  下一条用户消息也在 `auto` 下运行。

- **F13**：计划**被拒**时，预设**留在 `plan`**。拒绝意味着方案不对、还得接着规划，
  自动退出会让下一轮重想时失去保护。

- **F14**：F12 的切换**不得影响当前回合已经在跑的那一轮**——循环拿到的规划阶段
  标志是入参快照，切换只对后续回合生效。

### 文案

- **F15**：所有面向用户展示「当前模式」的地方统一显示两个预设名，不再展示权限档。
  至少覆盖：状态栏、子 Agent 报告里的档位列、切换命令的描述与帮助文本。

- **F16**：子 Agent 报告里的档位列有特殊性——它要同时显示角色的**声明值**与
  **实际生效值**，而声明值可以是严格档或默认档（F10 的两条路径）。
  那一列**保留三档的完整显示能力**，只把「放行」的显示名改成 `auto`。

### 连带修复

- **F17**：执行命令时，子进程的环境变量按**黑名单**过滤，剔除疑似密钥的条目。
  命令全部自动批准之后，「每条被执行的命令都能看到 API Key」从隐患变成常态。

  > **为什么这条比看起来更要紧**：模型拿到密钥的**另一条**路已经被堵死了——
  > 真正存 API Key 的 `config.yaml` 在用户主目录、不在工作区内，读它会被②层
  > 路径沙箱直接拒绝。于是命令全放行之后，环境变量成了最省事的一条路
  > （一句打印环境的命令就够）。本条堵的正是它。
  >
  > **不设「例外的例外」名单**：调研过 `GITHUB_TOKEN` 这类「既是密钥又是工具
  > 必需品」的情形，实测本项目所依赖的 `gh` 走的是系统 keyring 而非环境变量
  > （`gh auth status` 显示 `keyring`），过滤它**代价为零**。环境变量形式的
  > `GITHUB_TOKEN` 主要是 CI 注入的用法。一份豁免名单会成为新的成对维护点，
  > 却挡不住任何东西。
  - **F17a**：必须是黑名单，**不得**做成白名单——白名单会让一大批正常命令
    （走代理的 `git`、认 `PATH` 的一切）突然坏掉，且坏得莫名其妙。
  - **F17b**：过滤对**所有**起子进程的调用方生效，不只是模型调用的那个工具。
  - **F17c**：被剔除的条目数量要能在行为记录里看到——静默剔除会让「命令为什么
    认证失败」变成一个查不出根因的问题。

- **F18**：同步三处项目文档，它们描述的缺省行为在本扩展之后不再成立：
  - 子 Agent 那条「缺省配置下子 Agent 实际只能做只读的事」；
  - 安全边界总述里描述缺省体验的段落；
  - 已知工程项里登记 OS 级沙箱的那条，补一句「两家都不支持原生 Windows」。

## 非功能需求

- **N1**：**权限管线的任何一层判定逻辑都不改。** 本扩展不新增层、不调整层序、
  不改任何一层的判据。它改的只是「主对话的权限档取什么值」与「用户怎么切」。

- **N2**：②″保护路径收紧器**必须继续生效**，且不因预设为 `auto` 而被削弱。
  它是 `auto` 档下「模型改不了自己配置」的**唯一**依据。

- **N3**：①危险命令黑名单**不可被预设放开**。这是它从 C6 起的既有性质。

- **N4**：不破坏既有配置（F11 的另一面）：升级本版本后，用户已有的
  `permissions.yaml`、`hooks.yaml` 与角色定义**逐字继续有效**。

- **N5**：预设的推导必须是**单一来源**。「当前是哪个预设」只有一个计算它的地方，
  展示、切换、行为记录都取它——各处自己按两条轴拼一遍的话，迟早出现「状态栏说
  `auto`、实际在规划阶段」这种不一致。

- **N6**：环境变量过滤**不得**依赖取值内容（不做「看起来像密钥」的启发式），
  只按**变量名**匹配。按内容猜会误伤正常配置，且不可预测。

## 不做的事

- **命令的白名单 / 已知安全命令集 / `auto_ask` 清单。** 评审时给过三种更保守的
  形态，**用户逐条看过后选了「一律放行」**，理由是体验要对齐 Claude Code。
  实现时不得因为「这样不安全」而偷偷加回任何一份白名单。
  真正的收窄手段是分类器，那是**另一条 todo**。

- **分类器审查**（`docs/todo/3-classifier.md`，将成为 C16）。本扩展做完就有一个
  能用的 `auto`；分类器是之后盖上去的一层。合起来做的话中间没有可用状态。

- **OS 级沙箱**（长期登记在已知工程项）。

- **把 `plan` 做成一个权限档枚举值。** 它是阶段状态机，与「灰色地带怎么兜底」
  不是一个维度。合并之后「批准计划之后回到哪一档」会变成一个说不清的问题。

- **「批准后进哪个模式」的三选一。** Claude Code 有这一步，是因为它退出 plan
  时要在三个模式里选；本项目只有两个预设，`plan` 退出后的去向唯一，无此维度。

- **预设的持久化**（记住上次用的是哪个）。每次启动都是 `auto`。

- **新增配置项来指定启动预设。** 缺省即 `auto`，不给开关。

- **主对话运行期回到「写文件要确认」的档位。** F7 删掉了那个入口，这是用户明确
  选的取舍：想要更严只能写 `deny` 规则或给角色声明更严的档位。

## 与 todo 原文的分歧

todo 写的是 `plan = 只读 + 规划阶段开`，本 spec 的 F2 改成「不动权限档」。

**理由有两条，第二条是硬的**：

1. 代码里根本没有「只读」这个权限档值；最接近的是严格档，而规划阶段暴露的
   本来就全是只读工具，只读工具在权限引擎里**走只读短路、压根不进第④层**——
   把档位设成严格档在规划阶段几乎没有任何实际效果。

2. **获批是回合中途发生的**（规划阶段标志是每轮的局部变量，获批后同一回合内
   立刻放开全部工具）。若 `plan` 预设动了权限档，就得在 Agent 循环里回头改
   那个**单实例共享**的权限引擎的档位——而那正是项目明令禁止的形态
   （`CLAUDE.md` 子 Agent 那条：「权限必须派生，绝不改主引擎的 `mode`」）。

净效果不变：规划阶段一个文件都改不了，这件事由**工具过滤 + 预扫拦截**两道钉着
（已知工程项 #2 已修复的那条），不依赖权限档。

## 验收标准

- **AC1**（F1/F3）：启动后不做任何操作，界面显示的模式是 `auto`。

- **AC2**（F1）：`auto` 下让模型连续修改三个工作区内的文件，**一次确认面板都不弹**。

- **AC3**（F1）：`auto` 下让模型执行一条普通命令（如跑测试套件），**不弹面板**。
  这条是本扩展与「只自动批准编辑」那类方案的分野。

- **AC4**（N2，**反证**）：`auto` 下让模型写 `.rhinecode/hooks.yaml`，**仍然弹面板**，
  且该面板**不提供「永久放行」**选项。

- **AC5**（N3，**反证**）：`auto` 下让模型执行一条命中危险命令黑名单的命令，
  **被拒绝**，且拒绝理由指向第①层。

  > ⚠ AC4 与 AC5 是两个方向的反证，缺任何一条就分不清「`auto`」与「什么都不管」。

- **AC6**（F5/F6/F8）：按 `Shift+Tab` 在两个预设间来回切换，状态栏随之变化，
  且**输入框焦点不丢**；切换命令与其别名产生完全相同的效果。

- **AC6a**（F4）：`auto` → `plan` → `auto` 走一个来回之后，两条底层轴回到与出发时
  **逐字相同**的取值。预设层没有偷偷记住第三份状态。

- **AC7**（F7）：原先切换权限档的命令及其全部别名**不再存在**——执行它会得到
  「未知命令」提示，且它不出现在帮助列表与 Tab 补全候选里。

- **AC8**（F12/F14）：切到 `plan` → 提一个要改文件的需求 → 确认规划阶段**一个文件都
  没被修改** → 批准计划 → 模型**在同一回合内继续把活干完**（F14：切换没有打断
  正在跑的那一轮），且**状态栏当场变回 `auto`**；该回合结束后再发一条消息，
  它在 `auto` 下运行（不再要求先提计划）。

- **AC9**（F13）：切到 `plan` → 拒绝模型提交的计划 → **仍在 `plan`**。

- **AC10**（F9/F10/F11/N4）：一份声明了严格档的角色定义、一份既有的
  `permissions.yaml`，在本扩展之后**逐字继续生效**：角色的实际生效档位仍是
  两者取严的结果，配置里的规则仍被求值。

- **AC11**（F15/F16）：状态栏与子 Agent 报告里不再出现旧的三个档位显示名；
  子 Agent 报告对声明了严格档的角色，仍能同时显示声明值与实际生效值。

- **AC12**（F17/F17a）：执行一条打印全部环境变量的命令，输出里**不含**当前进程里
  那些疑似密钥的变量；同时输出里**仍含** `PATH` 与常规变量（F17a 的反证：
  没把环境变量删干净）。

- **AC12a**（F17b）：经 Hook 的命令动作执行同一条打印命令，结果相同——过滤发生在
  起子进程的**共同落点**上，不是只给模型调用的那个工具打了补丁。

- **AC13**（F17c）：上一条发生时，行为记录里能看出**剔除了几个**。

- **AC14**（F18）：三处文档已同步，且不再有任何一处声称「缺省配置下子 Agent
  只能做只读的事」。
