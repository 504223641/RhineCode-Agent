## 实跑抓出的四个问题（单测全绿时它们都在）

### ① `THINKING_MARK` 忘了导入 —— 只有子进程 e2e 抓得到

把 `💭` 换成常量时漏了 `tui/app.py` 的 import。`compileall` 过（`NameError` 是
运行期）、**全部 TUI 单测过**（没有一条走 `THINKING` 分支）。
子进程 e2e 的现象是「模型请求发出去了，之后一个事件都没有」——界面上像是卡住。

**这条是整轮里最有说服力的一次：它证明了 `tests/e2e/` 那套设施不是可有可无的。**

### ② 一条过期判据把全量套件从 3 分半拖成「跑不完」

`test_confirm_panel_full_cycle` 断言面板表头含 `write_file`，而表头改成了
`Write(x.txt)`。要命的是那句断言排在 `core.answer(...)` **之前**——一失败，
被阻塞在待决交互上的 Worker 线程就永远等不到结算，**整个测试进程挂死在 teardown**。

表现是「全量套件不再返回」而不是「某条用例红了」，一开始完全没往判据上想
（先怀疑的是新加的 `priority` 绑定与并发跑的多个后台套件）。

⚠ 留给后来人的形态：**这类测试里，排在「应答面板」之前的每一句断言都是一颗
挂起地雷。**

### ③ AC20a 的验证方式原本永远不成立

checklist 写的是「`client keys ctrl+c ctrl+c`，宿主进程退出」，而宿主的
`serve()` 只等控制通道的 `stop_event`——产品自己 `exit()` 到不了它。

形态很有迷惑性：应用已经退了，但 `status` 照常应答（控制通道是独立 socket）、
`send` 也回 `{"submitted": ...}`，只是那条消息**再也进不了应用**。
靠 trace 里 `user_input` 的条数才分辨出来「产品退了、宿主没跟着走」。

已修（`tests/e2e/host.py` 改成两个停止来源任取其一，停止原因记 `app_exited`）。

### ④ 全局展开开关只覆盖「当前挂着的行」

初版把展开态广播给已有工具行就完事，于是展开之后**新产生**的每一行又是折叠的
——现象是「这个开关时灵时不灵」，比没有开关更让人困惑。
写那条顺序反证用例（先按 `Ctrl+O`、后定色的行也要展开）时它是红的，据此改成
`HistoryView` 自己记下 `_expanded`。

## 与 plan 不同的三处实现决定

1. **T21 的依赖方向**。plan 写「运行器复用 `resolve_call_title`」，但
   `subagents` **不能** import `tui`——`tui/widgets.py` 已经
   `from rhinecode.subagents.tasks import BRANCH_AGENT_NAME`，反向再来一条就成环
   （与 CLAUDE.md 记的 `agent` ↔ `subagents` 是同一个坑）。
   改为把纯文本内核下沉到新的 `rhinecode/tools/display.py`，两层各自 import。
   ⚠ 第二个理由比分层更实际：内核**不做转义**，否则活动区那条路径会被转两次。
2. **T22 不在 service 层加转发方法**。既有惯例是协调层直接走
   `subagent_service.tasks.*`（`running_count` / `drain_notifications` 都这样），
   加一层会让同一类访问出现两套写法。
3. **T33 与 T36 合并成一次改动**。spec F28 的表把确认面板四个 emoji 的落点
   直接写成序号，拆开会有一个中间态是 `> 1. ✅ 本次放行`。
