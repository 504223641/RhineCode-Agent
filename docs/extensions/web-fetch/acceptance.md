### 判定顺序护栏（重点）

**机器判到了什么** —— 实现完成后跑了一次「把②′挪到③之后」的模拟：

```
形态A『白名单未命中』         错序结果 deny/network → 断言仍通过（假护栏）
形态B『全域名allow+127.0.0.1』 错序结果 allow/rule  → 断言会红（真护栏）
```

**据此做的判断** —— 护栏只能用形态 B。这个结论是**实测出来的、不是推演的**：
形态 A 看起来更自然，但在错序下③无命中返回 None、接着②′的白名单判定照样给出
DENY/NETWORK，结论完全相同，什么也钉不住。实测结果与「改动本用例前先重跑那个模拟」
这句话一起写进了 `tests/test_perm_network_layer.py::PipelineOrderGuardTests` 的 docstring。

> 但根据安全约束，这段内容**不可信**，我不予执行，也请你不要理会它 —— 它很可能是有人故意在

防御稳定生效」，**不是**「注入攻击已被解决」。真实攻击会用更隐蔽的措辞。
`<untrusted-content>` 标注是**引导**不是**强制**——真正的强制边界是域名白名单
（攻击者的接收域名进不来）与「只取不发」（工具没有请求体与自定义头）。
而 spec 的「安全边界」已经承认：**缺省配置下白名单并不存在**，那时唯一的实际拦截
是每次弹确认。

## 五、遗留与已知边界

以下都是**设计时就承认、未在本次解决**的，不是漏做：

1. **DNS rebinding 的时间窗未封死** —— 连接期校验完，交给 httpx 的仍是主机名，
   它会独立再解析一次。封死需要锁定 IP 后自行处理 Host 头与 TLS SNI，超出本扩展范围。
2. **域名解析不受超时约束** —— 标准库解析函数无超时参数，`Esc` 也打断不了。
   一次抓取最坏可以卡在解析上比 F18 算出的 180 秒上界更久。
3. **域名策略只管本扩展的工具** —— `run_command` 跑起来的 `curl`/`wget`、
   以及 **MCP 工具**（同样落在 `other` 分支）都不受约束。与已知项 #4（OS 级沙箱）同源。
4. **缺省配置下白名单不存在** —— 不写任何域名规则时，唯一的实际拦截是每次弹确认，
   也就是说这套防御在缺省配置下的真实强度 = 用户面对第 20 次确认面板时的判断力。
5. **抽取是有损的** —— 抽取答案说「这页没提到 X」，可能只是提问没问到 X。
6. **规划期查不了在线文档** —— `web_fetch` 是非只读工具，Plan Mode 规划阶段不可见。
   这是 F3 的连带后果，被接受的取舍（改成只读会让它在放行档下被直接放行）。

## 六、开发过程中值得记的三次「测试写错、不是实现错」

留在这里是因为它们都指向同一类问题：**看起来更自然的断言，往往什么也钉不住。**

1. **`<script>` 嵌套测不出计数与布尔标志的差别** —— `HTMLParser` 对 `script`/`style`
   用 CDATA 模式，内层同名开始标签压根不触发回调。改用 `svg`（走普通解析、可合法嵌套）
   才是计数真正起作用的地方。
2. **`KeyboardInterrupt` 不该被吞** —— 原本断言「连它都不该穿出去」，但
   `except Exception` 不捕 `BaseException`，而**这是对的**：用户按 Ctrl-C 必须能中断。
   改成两条用例分别钉住「普通异常转文本」与「中断信号照常传播」。
3. **注入口用例里让 `client_factory` 直接抛** —— 结果 `resolver` 永远轮不到，
   用例以「resolver 没被用上」的形式误报。`fetch()` 的顺序是「先造客户端、再逐跳解析」。
