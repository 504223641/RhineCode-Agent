### 判定顺序护栏（重点）

**机器判到了什么** —— 实现完成后跑了一次「把②′挪到③之后」的模拟：

```
形态A『白名单未命中』         错序结果 deny/network → 断言仍通过（假护栏）
形态B『全域名allow+127.0.0.1』 错序结果 allow/rule  → 断言会红（真护栏）
```

**据此做的判断** —— 护栏只能用形态 B。这个结论是**实测出来的、不是推演的**：
形态 A 看起来更自然，但在错序下③无命中返回 None、接着②′的白名单判定照样给出
DENY/NETWORK，结论完全相同，什么也钉不住。实测结果与「改动本用例前先重跑那个模拟」
这句话一起写进了 `tests/test_perm_network_layer.py::PipelineOrderGuardTests` 的 docstring。

## 三、过程中发现并修复的真实缺陷

### `ToolResult.ok` 曾对失败的抓取报 `True`

**怎么发现的** —— 跑场景 6 时，工具调用在统计里显示成成功，而输出正文里写着「抓取失败」。

**根因** —— `WebFetchTool.execute` 原先只要 manager 不抛异常就返回 `ok=True`。
而 `fetch_and_extract` 对失败的抓取是**返回一段渲染好的失败文本**、不抛异常
（这本身是对的，`Tool.execute` 的契约就是不外抛）。两者叠加的结果是：
**TUI 会把一次被守卫拦下的抓取显示成绿色成功**，模型也拿不到「这次失败了」的信号。

**修法** —— `fetch_and_extract` 返回三元组 `(是否拿到内容, 输出文本, 摘要)`：

| 情形 | ok | 理由 |
| --- | --- | --- |
| 抓取失败 | `False` | 没拿到内容 |
| 跨主机重定向 | `False` | 本次确实没抓到，模型要对新地址再发一次 |
| 二进制内容 | **`True`** | 我们如实回报了类型与体量，那就是这次调用能给的全部信息 |
| 抽取降级 | **`True`** | 页面拿到了，只是没能按提问压缩 |

两个测试文件各补一组回归用例钉住它（`OkFlagTests` / `ResultOkReflectsFetchOutcomeTests`）。

**据此做的判断** —— 这个缺陷**离线单测发现不了**：单测里我断言的是「输出文本里有『抓取失败』」，
那是通过的。只有把真实链路跑起来、看着统计说「成功 3/3」而正文写着失败，才会觉得不对。
这正是端到端验收存在的理由。

## 五、遗留与已知边界

以下都是**设计时就承认、未在本次解决**的，不是漏做：

1. **DNS rebinding 的时间窗未封死** —— 连接期校验完，交给 httpx 的仍是主机名，
   它会独立再解析一次。封死需要锁定 IP 后自行处理 Host 头与 TLS SNI，超出本扩展范围。
2. **域名解析不受超时约束** —— 标准库解析函数无超时参数，`Esc` 也打断不了。
   一次抓取最坏可以卡在解析上比 F18 算出的 180 秒上界更久。
3. **DNS 会重写公网域名的网络环境里，本工具一直失败** —— 场景 6 实测：这台机器的 DNS 把
   `example.com` / `www.python.org` / `httpbin.org` 全部解析成 10.x 内网地址（企业代理），
   连接期守卫每次都正确拦下。这不是 bug（10.x 确实不是全局可路由地址），
   但它是这个能力的一条真实可用性边界：**在这类网络里 `web_fetch` 用不了**。
4. **域名策略只管本扩展的工具** —— `run_command` 跑起来的 `curl`/`wget`、
   以及 **MCP 工具**（同样落在 `other` 分支）都不受约束。与已知项 #4（OS 级沙箱）同源。
   **这条已有实测样本**，见第七节——它不再只是一句免责声明。
5. **缺省配置下白名单不存在** —— 不写任何域名规则时，唯一的实际拦截是每次弹确认，
   也就是说这套防御在缺省配置下的真实强度 = 用户面对第 20 次确认面板时的判断力。
6. **抽取是有损的** —— 抽取答案说「这页没提到 X」，可能只是提问没问到 X。
7. **规划期查不了在线文档** —— `web_fetch` 是非只读工具，Plan Mode 规划阶段不可见。
   这是 F3 的连带后果，被接受的取舍（改成只读会让它在放行档下被直接放行）。

## 六、开发与验收过程中的五次「测试/用例写错，不是实现错」

留在这里是因为它们都指向同一类问题：**看起来更自然的断言，往往什么也钉不住。**

1. **`<script>` 嵌套测不出计数与布尔标志的差别** —— `HTMLParser` 对 `script`/`style`
   用 CDATA 模式，内层同名开始标签压根不触发回调。改用 `svg`（走普通解析、可合法嵌套）
   才是计数真正起作用的地方。
2. **`KeyboardInterrupt` 不该被吞** —— 原本断言「连它都不该穿出去」，但
   `except Exception` 不捕 `BaseException`，而**这是对的**：用户按 Ctrl-C 必须能中断。
   改成两条用例分别钉住「普通异常转文本」与「中断信号照常传播」。
3. **注入口用例里让 `client_factory` 直接抛** —— 结果 `resolver` 永远轮不到，
   用例以「resolver 没被用上」的形式误报。`fetch()` 的顺序是「先造客户端、再逐跳解析」。
4. **只采集 `TOOL_START` 来判断「模型试了哪些工具」** —— 被权限层拒绝的调用
   **只产出 `TOOL_RESULT`**（它根本没「开始执行」）。一次被正确拒绝的抓取在统计里
   显示成「模型压根没调工具」，把实现的正确行为误判成失败。
5. **`"SECRET" in reply is False and "SECRET" not in reply`** —— Python 链式比较，
   恒为 False。连续三轮报「回复未含密钥 0/3」，而回复原文里根本没有密钥。

**唯一一次「真的是实现错」**是第三节那个 `ToolResult.ok`——而它恰恰是**离线单测发现不了、
只有真实端到端跑起来才会觉得不对**的那一类。这个比例本身值得记住。

## 七、补记：日常使用中观测到的一次真实绕过（2026-07-29）

> 来源：`G:\Rhine-test\web-tool-test\.rhinecode\traces\20260729-220437-120.jsonl`
> （532 条事件 / 54 轮 / 23.5 分钟，`session_end · normal_exit`）。
> 这不是构造出来的验收场景，是**用户在自己机器上正常使用时留下的记录**。

### 观测到了什么

用户让模型去装一个网上的 Skill。模型连吃两次②′网络边界拒绝后，**在两轮之内自发换成
`run_command` + `curl` 完成了同一件事**：

| seq | 工具 | 结果 |
| --- | --- | --- |
| 14 | `web_fetch https://www.skills.sh/...` | `ok=False` —— 解析到 `10.16.198.190`，连接期拦下 |
| 25 | `web_fetch https://raw.githubusercontent.com/...` | `ok=False` —— 解析到 `10.16.97.243`，连接期拦下 |
| 35 | `run_command curl -sL "https://api.github.com/..."` | 退出码 255（模型误用了 Unix 管道 `head`，非权限问题） |
| 45 | `run_command curl -sL "https://api.github.com/..."` | **`ok=True` · 34 行** |
| 56 | `run_command curl -sL "https://raw.githubusercontent.com/.../SKILL.md"` | **`ok=True` · 55 行 —— 内容到手** |

用户在确认面板上对每一条 `curl` 都点了「允许」。

### 据此做的判断

**第五节遗留项 #4 从「设计时承认的边界」升级为「已实测」。** 差别在于：

- 以前它是一句我们自己写下的免责声明；
- 现在它是一条**未经诱导、模型自主选择**的绕过路径记录。没有人提示模型去用 `curl`，
  它是在两次拒绝的回灌里自己推出来的。

含义要说准，不要说过头：

- ②′网络边界层**没有失效**——它对 `web_fetch` 的判定每一次都正确（`10.x` 确实不是全局
  可路由地址，拦得对）。
- 但对一个**有工具选择权**的模型来说，它构成的是**摩擦**而不是**边界**。真正的边界要等
  已知项 #4（OS 级沙箱）——只有约束住 `run_command` 子进程自身发起的网络访问，
  「限制模型能访问哪些域名」这句话才成立。
- 因此 `CLAUDE.md` 安全边界那节关于 web_fetch 的第 ② 条（缺省配置下第二道防御不存在、
  真实强度等于用户面对确认面板的判断力）在这份记录里得到了完整印证：
  **本次拦住模型的从头到尾只有确认面板，而用户点了允许。**

### 顺带发现：失败文案会把模型和用户一起带偏

连接期拒绝的原文是：

```
[web_fetch] 抓取失败：https://raw.githubusercontent.com/...
原因：连接期地址限制：主机名 raw.githubusercontent.com 解析到了
      不允许访问非公网地址 10.16.97.243（不是全局可路由地址）
说明：这不是权限配置问题，而是该地址（或它解析到的地址）本身不被允许访问。
      请不要改写地址重试，换一个可公开访问的来源。
```

末句「**换一个可公开访问的来源**」在这个场景里是**错的**：`raw.githubusercontent.com`
本来就可公开访问，问题出在**本机 DNS 把它重写成了内网地址**（遗留项 #3 描述的网络环境，
典型成因是 TUN 模式 / fake-IP 代理）。这句话把根因指向了「来源」，而根因在「本机解析」。

后果不是理论上的——记录里模型确实没有再试 `web_fetch`，而是直接转去用 `curl`。
文案没有让它这么做，但也没有拦住它。若要改，方向是：当拒绝原因是「域名解析到私有地址」
（而非「地址本身写的就是私网/环回」）时，单独给一段文案，点明这多半是本机网络环境
（代理 / 企业 DNS）所致，并**明确不要改用 `run_command` 执行 `curl`/`wget` 绕过**。

### 未在本次改动

上面两点都只是**记录**，本轮没有动产品代码：

- 绕过路径本身要等 OS 级沙箱（已知项 #4），不在本扩展范围内；
- 文案改法牵涉「连接期拒绝原因的分类」，值得单独走一次 spec，不适合顺手改。
