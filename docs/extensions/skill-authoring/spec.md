# Skill 作者期 Spec

> 本扩展在 C11 Skill 系统（以 [`docs/c11/align/spec.md`](../../c11/align/spec.md) 为现行语义）之上
> 补齐「创作」这条路径。**不新增能力层级**，故不占章节号。
>
> ⚠️ 阅读前提：Skill 的现行语义以 `docs/c11/align/` 为准。顶层 `docs/c11/spec.md`
> 是已废止的旧设计（`allowed-tools` 在那份文档里是「收窄工具集」，与现在**语义相反**）。

## 背景

Skill 系统经「对齐 Agent Skills 开放标准」的改造后**可导入**了——从任何来源拿一个
Skill 目录复制进来即可用。但它仍然**不可创作**：系统只会读 Skill 目录，
不会帮用户写，也不会检查用户写得对不对。

这个缺口由**真实使用**暴露（用 RhineCode 做一个番茄闹钟时）。在那之前 C11 的
43/43 端到端判据全部通过，却完全没有覆盖「用户想创建或适配一个 Skill」这条路径——
既有判据全部建立在「已经有一份写好的 Skill」这个前提上。

现状下用户要自己做一个 Skill，必须先自行掌握三件系统从不告知的事：定义文件放在
哪一层目录、目录型 Skill 的入口文件名是固定的、frontmatter 有哪些字段以及各自的
语义（尤其「预授权」字段是**放宽确认**而不是**限制工具**）。写错时的反馈也极弱：
要么静默失效（如域名规则漏写前缀，那条预授权无声消失），要么给出一句只陈述现象、
不给改法的警告。

已有的三类反馈各司其职，但都不回答「那我该怎么改」：

| 现有反馈 | 它说的是 |
| --- | --- |
| 加载失败 | 这份文件我看见了但没能用上，原因是…… |
| 警告 | 这次运行过程中发生了什么 |
| 字段提示 | 你的某个声明与实际行为有出入 |

缺的是第四类：**这份 Skill 能用，但有更好的写法，建议改成……**

## 目标

- 一个不了解 frontmatter 的用户，说一句「把刚才那套流程存成 Skill」，就能得到一份可运行的 Skill
- 一份从外部下载的 Skill，说一句「帮我适配一下」，就能被检查并按需调整
- 写得有改进空间的 Skill，用户在查看 Skill 状态时能看到**可操作的建议**——
  给出具体改法，而不只是陈述问题
- 用户认可某条建议后，能让系统**代为修改**，并在改动落盘前看到改前改后
- 体检逻辑是纯函数、零 IO，可独立单测

## 功能需求

### 一、体检

- **F1**：体检产出**建议**，与既有的「加载失败 / 警告 / 字段提示」并列为**第四类反馈**。
  每条建议必须同时说清三件事：**涉及哪个 Skill**、**发现了什么**、**建议怎么改**。
  凡是能给出具体替代写法的，必须把替代写法写进建议正文。

  「可操作」是这一类反馈存在的全部理由。一条只说「说明字段过长」而不说
  「建议压到多少字符以内、把触发条件挪进哪个字段」的建议，与既有的警告没有区别，
  不值得为它新增一整类反馈。

- **F2**：体检覆盖以下**八项**。前七项对**所有来源层级**（项目级 / 用户级 / 内置）
  一视同仁；第 8 项按定义只可能命中非内置层。

  | # | 检查什么 | 判定 | 为什么值得报 |
  |---|---|---|---|
  | 1 | 说明字段过长 | 超过 100 字符 | **状态报告的列表与命令菜单只显示说明字段**，过长会把每个条目撑成多行，扫一眼看不完。建议里要指出「若超出部分是在描述『什么时候该用』，请挪进触发说明字段」，但**必须同时说明这不会省下清单预算**——两个字段在第一阶段清单里拼成同一行、共享同一份预算，挪动只改善列表与菜单的可读性 |
  | 2 | 说明字段未显式声明 | 作者未在 frontmatter 中写该字段（由正文第一段自动回填） | 自动提取的第一段往往是流程开场白，不是「这个 Skill 做什么」。模型在第一阶段清单里只看得到这一句，据此判断何时该用会失准 |
  | 3 | 声明了触发说明却没声明说明字段 | 触发说明有、说明字段无 | 作者显然知道有 frontmatter 却漏了最关键的一项，多半是笔误。**与第 2 项互斥**——命中本项则不再报第 2 项，同一处问题只给一条建议 |
  | 4 | 正文不含参数占位符 | 占位符未出现 | 参数**不会丢**（会被追加到正文末尾的补充段），但作者若希望参数出现在流程中间的某一步，必须显式写占位符。实测中作者常因此误以为「参数没生效」。建议正文必须写明「不会丢、只是位置在末尾」，否则会把「位置不对」误导成「功能失效」 |
  | 5 | 预授权给得过宽 | 声明了**有副作用**类别（命令执行 / 写入 / 编辑 / 网络访问）却不带参数模式 | 一条不带模式的命令类预授权，等于该类别的**全部**操作在本次执行内免确认。作者本意通常只是免掉某几条。只读类别不带模式**不报**——它没有副作用 |
  | 6 | 预授权声明全军覆没 | 有声明，但一条都没能翻译成权限规则 | 现象是「我明明写了预授权，还是每次弹确认」。单条认不出已有警告，但**一条都没生效**说明作者对该字段的写法整体有误解，值得单独指出并给出正确写法范例 |
  | 7 | 逼近注入上限 | 渲染后的注入段达到单个 Skill 注入上限的 80%（行数或字节数任一） | 超过上限会被截断，且**只在激活时才显形**，届时模型会「做了一半」。逼近时提前告知，让作者有机会拆分或把细节挪进随附资源。⚠️ 量的必须是**实际注入的那一段**（含边界标识、说明行与随附资源清单），不是正文原文——截断作用在前者，按后者判会漏报 |
  | 8 | 覆盖了内置样板 | 生效的这份来自项目级或用户级，而**内置层存在同命令名的一份** | 跨层覆盖是**整份替换且完全静默**的：内置那份的每个字段都不再存在，系统不记错误也不发警告（这对**有意定制**是正确的设计）。但**无意撞名**时后果很重——用户随手建了个同名文件，内置样板凭空消失、对应命令行为完全变了，而现场唯一的线索只是状态列表里一个来源标签。用户几乎不可能把「命令不好使了」联想到几天前建的那个文件。**收窄到只报覆盖内置层**：用户级的 Skill 是用户自己放的，撞掉了他心里有数；内置样板是他从没主动装过、却确实存在的东西，最容易被无意撞掉。措辞必须中性并明确写出「若是有意定制请忽略本条」——这条命中的多数情况是正常用法 |

- **F2a**：**体检所需的事实必须由产出它的那一层如实保留**，体检不得重跑下层逻辑
  做启发式推断。有两处事实现在**没有被保留下来**，必须补上，否则对应的检查项
  在当前数据结构下根本无法判定：

  | 缺失的事实 | 服务哪一项 | 现状为什么判不出来 |
  |---|---|---|
  | 说明字段是否由作者**显式声明** | 第 2、3 项 | 未声明时会被正文第一段自动回填，成品里**永不为空**，也不带任何「这是回填的」标记 |
  | 某个命令名**覆盖掉了哪一层的同名定义** | 第 8 项 | 跨层覆盖时低优先层那份被直接丢弃，成品清单里**根本不存在**，覆盖这件事没有留下任何痕迹 |

  两处都不能靠体检自己推断补救。第一处若在体检里重新提取一遍正文第一段再比对，
  既是启发式（作者手写的说明恰好等于第一段时会误报），又等于把解析规则复制成
  两份、日后必然分叉；第二处更彻底——**信息已经被丢弃了**，无从推断。

  这是本次仅有的两处需要改动既有数据流的地方，故单列成一条需求，
  以免在设计阶段被当作实现细节顺手塞进去。

- **F3**：体检结果并入 Skill 状态报告，作为**独立一段**呈现，排在既有三类反馈之后。
  **不新增子命令**——多一个命令词，就多一个「用户不知道它存在便永远看不到」的入口。

- **F4**：体检**每次现算**，不缓存。热更新改了 Skill 定义后，下一次查看状态即反映
  新结果，不存在需要同步失效的第二份状态。

- **F5**：无任何建议时，报告中**不出现建议段**（不显示「无建议」之类的空段落）。

- **F6**：随程序分发的内置样板**自身必须零建议**。它们是用户能看到的唯一范例，
  自己触发建议等于示范了不该学的写法。本条对**新增的内置 Skill 同样成立**。

### 二、创作与适配

- **F7**：随程序分发一个新的内置 Skill，命令名为 `skill-creator`，承担三种用途：

  1. **创作**——用户描述一段重复流程，由它引导产出一份合格的 Skill 定义文件
  2. **适配**——用户拿来一份外部 Skill，由它检查并按需调整
  3. **修复**——用户认可体检建议后，由它按建议改写既有 Skill

  三种用途共用一个入口，不为「修复」单独开子命令。

- **F8**：该 Skill **留在主对话执行**，不开子对话。三种用途都需要与用户往复确认
  （写到哪一层、命令名叫什么、某条建议要不要采纳）。

  理由是两种执行模式的**结构差异**，不是提问能力的差异——两种模式下模型都拿不到
  主动提问的工具（那个工具只在 Plan Mode 的规划阶段暴露）。差别在于：
  主对话是多轮的，模型输出一段话、用户回复、再继续，往复天然成立；
  而子对话**一次性跑完、只把最后一条结论回流**，用户既看不到中间过程、
  也无从插话。把引导型流程放进子对话，会让「引导」在结构上不成立。

- **F9**：该 Skill 必须让用户**确认关键决策**而不是替用户决定，至少包括：
  命令名取什么、以及（修复用途下）每条建议是否采纳。

  **唯独存放层级不问**：用户未明确指定时**一律创建为项目级**，不追问。
  理由是项目级几乎总是对的——新建的 Skill 多半服务当前这个仓库的流程，
  且项目级随代码仓库分发，团队里其他人 `git pull` 就能拿到。
  为一个九成情况下答案相同的问题打断用户，是把实现者的犹豫转嫁给用户。
  用户明确说了「装到用户级 / 全局都能用」时才写到用户级。

  ⚠️ 内置层**永不写入**：它随程序分发，用户写进去的东西会在下次升级时消失。

- **F10**：所有文件落盘走**完整权限管线**——由模型调用既有的写入 / 编辑工具完成，
  用户在既有确认面板上看到完整内容或改前改后再决定。
  **不新增任何写盘旁路，也不新增任何确认交互态。**

- **F11**：该 Skill 必须携带一份**完整的字段参考**：全部 frontmatter 字段的语义、
  取值与缺省，本系统明确不支持的标准字段清单，以及一份可照抄的最小范例。
  模型据此判断，而不是靠先验记忆——先验记忆正是「同一字段两种相反语义」
  这类事故的来源。

  该参考**不占用注入预算**：它作为随附资源存在，模型按需读取，不进第一阶段清单，
  也不进激活正文。

- **F12**：**不做自动导入适配**。适配必须经过模型判断与用户确认，不提供
  「一条命令自动转换」的入口。格式差异是**语义层面**的（同一个字段名在不同实现里
  含义可能相反），代码只能猜，而**猜错是静默的**——用户会拿到一份看起来正常、
  行为却不对的 Skill，比直接报错危险得多。

- **F13**：状态报告在存在建议时，附一句指向 `skill-creator` 的入口提示，
  让用户知道这些建议可以被代为执行，而不是只能自己去改文件。

### 三、清理

- **F14**：Skill 状态报告接收的「当前注册工具名」参数是**上一轮作者期改造的残留**——
  签名上存在、函数体从不使用、其文档字符串还在描述一套已随对齐改造删除的检查
  （「白名单是否等于全集」）。本次一并移除该参数及其过期描述，并更新全部调用方。

  留着它的代价不是性能而是**误导**：下一个人读到那句文档，会以为体检依赖它，
  从而在一个错误的前提上做设计。

## 非功能需求

- **N1**：体检是**纯函数、零 IO**——输入是已解析的 Skill 定义，输出是建议列表。
  不读文件、不访问网络、不依赖工具注册中心的状态。这使它可以用字符串字面量
  直接单测，无需创建任何临时目录。

- **N2**：分层不变——Skill 层仍是**叶子包**，不反向依赖命令层、协调层或界面层。
  体检不引入除权限层之外的新依赖（判定预授权是否生效必须复用既有的规则解析，
  不得另写一份平行实现）。

- **N3**：Skill 管理器的**加锁不变量不得被破坏**：临界区只做纯内存读写，
  一切回调与跨线程调度在锁外。违反会与界面框架的阻塞式跨线程调用组成
  **确定性死锁**，整个界面冻结。体检既是纯函数，就必须在锁外算。

- **N4**：本次**不新增任何权限旁路**。新增的内置 Skill 与其它 Skill 一样受五层防御
  约束；它的预授权声明同样只能放宽第④⑤层，翻不过前三层。

- **N5**：新增的内置样板（含其随附资源）必须随分发包一起安装，
  不能出现「开发模式正常、真实安装后凭空消失且不报错」。

  ⚠️ **这条现在不成立，必须一并修**：现有的分发资源声明只覆盖内置目录下的
  **单层**文件。而 F11 要求随附一份字段参考，该 Skill 必然是目录型
  （入口文件 + 随附资源各占一层），恰好落在覆盖范围之外。
  不改的话，正好复现本条要防的那个故障。

- **N6**：体检**不改变任何加载行为**——一份触发了建议的 Skill 照常可用、
  照常可触发，建议只是信息。

## 不做的事

- **`/skills new <名字>` 脚手架**：原范围内的第三项，本次砍掉。它只解决
  「格式我不记得」，而 `skill-creator` 覆盖了这个场景且能真正帮用户想内容；
  单独维护一份模板反而多一处「与字段表脱节」的风险。
- **自动导入适配**（理由见 F12）。
- **无人确认的自动修复**：修复必须经用户在确认面板上认可，不提供「一键全部应用」。
- **体检项的可配置化**：字符预算等阈值本次写死，不提供配置项
  （与既有的「清单预算不随窗口缩放」属同类问题，一并留待后续）。
- **对正文内容质量的检查**：只检查结构性与声明性问题，不评判 SOP 写得好不好——
  那需要模型判断，不属于纯函数体检的职责，也无法单测。
- **Skill 的删除、重命名与版本管理**。
- **从网络安装 Skill**：与对齐改造的结论一致，它有独立的威胁模型，留待独立立项。

## 安全边界

- `skill-creator` 会指挥模型**写入文件**（创建 Skill）与**编辑文件**（按建议修复）。
  这两类操作全程走完整权限管线，用户在确认面板上看到内容后才落盘。
  它的预授权声明**只覆盖只读调研类操作**——写入与编辑**刻意不预授权**，
  那正是需要用户看一眼的那一步（与既有 `commit` 样板「不预授权 `git commit`」同理）。
- 它写出来的产物是**新的 Skill 定义文件**，而 Skill 正文是「发给模型的文本」，
  可以指挥模型读写文件与执行命令。因此一份由它生成的 Skill 与手写的 Skill
  具有**同等的信任要求**，既有的「发现 N 个项目级 Skill」提示继续适用。
- 体检**只观测、不改变判定**：它不影响任何 Skill 的加载结果，
  也不影响权限管线的任何一层。它读不到、也不需要读任何文件内容。

## 验收标准

- **AC1**：说明字段超出字符预算的 Skill，状态报告中出现一条建议，
  且建议中含具体改法（对应 F1、F2-1）
- **AC2**：未显式声明说明字段的 Skill 触发一条建议；若同时声明了触发说明却未声明
  说明字段，**只触发后者那一条**，不重复触发前者（对应 F2-2、F2-3）
- **AC2a**：作者**显式写下**的说明字段，即使其内容恰好与正文第一段完全相同，
  也**不触发**「未显式声明」那条建议——判定依据是解析层保留的事实，
  不是对正文的重新推断（对应 F2a）
- **AC3**：正文不含参数占位符的 Skill 触发一条建议，且建议正确说明
  「参数会被追加到正文末尾而不是被丢弃」（对应 F2-4）
- **AC4**：声明了不带参数模式的**有副作用类别**预授权时触发一条建议；
  同一类别带了参数模式时不触发；**只读类别不带模式时也不触发**（对应 F2-5）
- **AC5**：预授权有声明但一条都没能翻译成规则时触发一条建议；
  **部分认不出、部分生效时不触发本条**（对应 F2-6）
- **AC6**：**渲染后的注入段**达到注入上限 80% 时触发一条建议；未达到时不触发。
  一份正文原文未达阈值、但加上随附资源清单后达到阈值的目录型 Skill **应当触发**
  （对应 F2-7）
- **AC6a**：项目级或用户级存在一个与内置样板同命令名的 Skill 时，
  触发一条中性措辞的建议，且该建议含「若是有意定制请忽略」的说明；
  命令名不与任何内置样板重合时**不触发**；**项目级覆盖用户级**（两边都不是内置）
  时也**不触发**（对应 F2-8）
- **AC6b**：跨层覆盖后，被丢弃那一份的存在**仍可被体检感知**——即「覆盖了内置」
  这一事实在成品清单之外被单独保留（对应 F2a 的第二处）
- **AC7**：建议段排在加载失败、警告、字段提示三段之后；
  无任何建议时该段**整段不出现**（对应 F3、F5）
- **AC8**：修改一份 Skill 定义并热更新后，再次查看状态，得到与新定义一致的建议
  （对应 F4）
- **AC9**：三个既有内置样板与新增的 `skill-creator`，逐一体检**均为零建议**
  （对应 F6）
- **AC10**：`skill-creator` 能被发现、能被用户以斜杠命令触发，
  且**留在主对话执行**（对应 F7、F8）
- **AC11**：`skill-creator` 的随附字段参考可被模型读取，
  且**不进入**第一阶段清单与激活正文的注入预算（对应 F11）
- **AC12**：以「把这套流程做成 Skill」触发 `skill-creator`，最终产出的文件
  **落盘前弹出确认面板**；确认后经热更新，新 Skill 即可被发现并触发（对应 F7、F9、F10）
- **AC13**：以「按建议修复」触发 `skill-creator`，改动**落盘前弹出确认面板**
  并可看到改前改后（对应 F7、F10）
- **AC14**：Skill 状态报告的函数签名不再接收「当前注册工具名」参数，
  且全部既有调用方随之更新、测试全绿（对应 F14）
- **AC15**：构建出的分发包中**实际包含** `skill-creator` 的入口文件与随附资源
  （通过检视包内文件清单验证，不依赖「在本机装一遍看看」这种不可复现的方式）；
  且从该包安装后 `skill-creator` 仍能被发现（对应 N5）
- **AC16**：体检可用字符串字面量构造的 Skill 定义直接单测，
  **不需要创建任何文件**（对应 N1）
- **AC17**：体检在 Skill 管理器的锁**之外**求值——持锁期间不调用体检
  （对应 N3）
