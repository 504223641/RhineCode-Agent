#### 缺陷一：「预授权过宽」的建议被读成了「换个更窄的工具类别」

| 机器判到了什么 | 据此做的判断 |
| --- | --- |
| 模型把裸写的 `Write` 改成了裸写的 `Edit`，并在汇总表里自评「✅ 改已有文件才免确认」。体检结果从 4 条降到 **1 条而不是 0 条**——新冒出来的那条正是同一个 `broad_grant` | 按 checklist 判据（「改完之后对应的建议消失」）**不通过**。根因在**建议文案**：只说「加一个具体的参数模式收窄」，模型把「收窄」理解成了「换一个更窄的类别」 |
| 修正后重跑：4 条 → **0 条**，字段提示也清了。模型这次把 `Bash` 收窄成六条具体 git 子命令模式，并**直接去掉 `Write`** 而不是换成裸写 `Edit` | 措辞修正有效。补了两条用例钉住「建议正文必须含那句警告」与「裸写 `Edit` 必须同样命中」 |

#### 缺陷二：「适配」这条触发说明太窄，模型根本没加载 `skill-creator`

| 机器判到了什么 | 据此做的判断 |
| --- | --- |
| trace 里 **`load_skill` 一次都没出现**。模型直接读了外部 `SKILL.md`，然后开始瞎试 `rhine --help`、`rhine skill` 这类不存在的命令 | **不通过**。根因在第一阶段清单：模型在那里只看得到 `description` 与 `when_to_use`，而原触发说法只有「我下了个 Skill 帮我适配」一种写法，没覆盖住「从别的工具拿来的」「能不能用」这类自然说法。场景 3 之所以成功，是因为「把这套流程做成 Skill」几乎逐字命中 |
| 修正后重跑，工具序列变成 `read_file`（目标文件）→ **`load_skill`（激活 skill-creator）**→ `read_file`（255 行手册）→ 逐项报告 **7 处差异**（下划线语义相反 / `Task`+`TodoWrite` 会被静默丢弃 / `disallowed-tools` 不支持 / `background`·`agent`·`effort`·`hooks` 各自的实际行为 / 命令名来自目录名）→ **停下来问用户按哪种语义意图改** | 通过。「若模型不问就直接改，本条不通过」这条判据守住了。措辞里加了一句「凭记忆判断必然出错」——给模型一个**不加载就会出错的理由**，而不只是一串关键词 |
