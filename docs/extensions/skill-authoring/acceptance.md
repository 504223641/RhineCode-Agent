#### 缺陷一：「预授权过宽」的建议被读成了「换个更窄的工具类别」

| 机器判到了什么 | 据此做的判断 |

| 修正后重跑：4 条 → **0 条**，字段提示也清了。模型这次把 `Bash` 收窄成六条具体 git 子命令模式，并**直接去掉 `Write`** 而不是换成裸写 `Edit` | 措辞修正有效。补了两条用例钉住「建议正文必须含那句警告」与「裸写 `Edit` 必须同样命中」 |

| 三轮的请求措辞各不相同（「创建个前端页面」/「加一个设置界面」/「做个订单列表的页面」），**没有一句包含「Skill」二字** | 召回不依赖用户点名。⚠️ 措辞刻意**不迁就实现**——没有写成「用前端 Skill 帮我做个页面」，那恰恰是这条场景要证明不必要的东西 |

### ⚠️ 过程记录：三轮曾被判成「全不通过」，那是驱动器的错

第一次跑出「3 轮全不通过、load_skill 一次没命中」，**结论是假的**。
三个驱动器缺陷叠在一起：

| 缺陷 | 后果 |
| --- | --- |
| `hosts` 输出是**纯文本**不是 JSON，我按 JSON 解析 | 宿主明明起来了却报「没起来」，还留下孤儿进程 |
| **宿主自己的 pid 与 `Popen.pid` 不一致**（实测 Popen=3184 而宿主发布 pid=26776） | `quit --pid` 报「找不到名片」→ 每轮漏一个孤儿 → 累积到 6 个 → 之后**所有**客户端命令因「有 N 个宿主，请用 --pid 指定」集体拒绝执行 |
| trace 记录是**扁平**的（负载字段直接在顶层，没有 `payload` 这一层）；`wait` 的 JSON 顶层是 `{"terminal", "state"}` 而非 `{"status"}` | 工具名与终态全部解析成 `?`，判定静默变成「未命中」 |

**三条的共同形态都是「假阴性」**——驱动器自己瞎跑，却报告成「被测功能不行」。
这比跑不起来危险得多：跑不起来会去查，而一个看起来言之有据的「不通过」
会让人跑去改本来没问题的代码。

修完之后先跑一轮 smoke 确认「pid 正确 / 终态 idle / 工具读得出 / 宿主停干净」
四件事都成立，才开始正式计费的三轮。**驱动器本身要先被验一遍**，这条以后照办。

#### 一处真实发现：建议的「出口」与用户的「全部采纳」会打架

场景 5 一度**三轮稳定**地剩同一条 `no_placeholder`。查下去发现**不是模型失误，
也不是功能缺陷，是我的判据写错了**——那条建议的正文自带出口：
「不需要参数的 Skill 可以忽略本条」。模型读到它、判断发版流程不需要参数、
于是跳过。**它是照着建议自己给的出口走的。**

但顺带暴露了一个真问题：用户明确说了「**全部采纳**」时，模型**静默**跳过并不合适——
用户会以为都改了，下次 `/skills` 里那条还在，只会困惑。

两处都改了：

- **判据分两档**：非可选建议必须清零（硬判据）；可选那条单独记，
  并要求「跳过时把理由说出来」（软判据）。
- **`skill-creator` 的分支 C 补一条**：判断某条不适用而跳过时**必须讲出来**；
  用户说「全部采纳」时**那句话优先于建议里的出口**，仍想跳就回去问一句。

重跑后三轮全通过，且模型在证据里**直接引用了这条新措辞**——
「按 skill-creator 分支 C 的说明：『那句话优先于建议里的出口』。好，加上去。」

#### ⚠️ 驱动器的五次假阴性，全部记在这里

这轮 21 次跑批里，**判成「不通过」的绝大多数是驱动器自己的问题**，
不是被测功能。逐条留存，因为它们的共同形态值得记：

| 现象 | 真实原因 | 形态 |
| --- | --- | --- |
| 场景 8 三轮全「未命中」 | `hosts` 输出是纯文本却按 JSON 解析；宿主 pid ≠ `Popen.pid` 导致每轮漏孤儿、累积到 6 个后客户端集体拒绝执行；trace 记录是扁平的（无 `payload` 层）、`wait` 顶层是 `{"terminal","state"}` | 三个解析错误叠加，判定静默变「未命中」 |
| 场景 3 三轮不通过 | 脚本的固定回合数用完时模型还在按 SOP 提问——**那是设计如此** | 把脚本的耐心当成被测对象的判据 |
| 场景 3 「没问命令名」 | 我在第二条消息里**主动报了命令名**，模型自然不用问 | **把答案提前喂给被测对象，测的就不再是它了** |
| 场景 4 三轮不通过 | 模型把命令写成 `cd "<工作区>" && git status`，我用 `startswith` 判 | 判据太死 |
| 场景 7 三轮全 0 | trace 里 decision 是小写 `'ask'`/`'allow'`，我按 `'Decision.ASK'` 比 | 全部落空 → 判据静默变「什么都没发生」 |

**共同点：驱动器出错时不会报错，而是产出一个看起来言之有据的「不通过」。**
跑不起来会去查，而一个假的「不通过」会让人跑去改本来没问题的代码。

**由此定下一条纪律**：正式计费跑批之前，先跑一轮 smoke 验驱动器本身——
「pid 对不对 / 终态读不读得出 / 工具名解析得对不对 / 宿主停不停得掉」四件事。
另：**文本类判定必须带原文证据**，失败时把原文摆出来由人判读，
**不许靠调关键词调到过**——那是「重跑到过为止」的变体。
