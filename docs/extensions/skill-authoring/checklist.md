# Skill 作者期 Checklist

> 对应 [`spec.md`](spec.md) / [`plan.md`](plan.md) / [`task.md`](task.md)。
> 每一项通过**运行代码或观察行为**验证，聚焦系统行为而非实现细节。

## 谁来跑

| 标记 | 含义 |
| --- | --- |
| 🤖 | **我自己跑完**——离线单测、本地命令观察、包内容检视。不花你的钱 |
| 👤 | **要花你的钱**——真实模型端到端。开跑前我会跟你确认一次 |

### ⚠️ 关于「端到端一律用真实模型」

**体检部分刻意不用真实模型**，不是偷懒：`/skills` 是**本地命令，不进 AI**——
命令层直接调状态报告并把文本回显，整条链上没有任何一次模型调用。
拿真实模型跑它，产出的证据与离线跑**逐字相同**，只是多烧一次钱。

反过来，`skill-creator` 的四个场景**必须**用真实模型：它本身只是一份 Markdown 文本，
它的全部作用是「让模型读完之后按预期行动」。用假模型（`scripted` 模式）跑，
验的是我自己写的脚本会不会按脚本走，等于**用自己写的答案验自己出的题**——
这正是既有记忆里记着的那个取样错误。

**每个真实模型场景跑 3 轮**，理由不是凑数：模型行为有随机性，
一次通过可能是运气。3 轮里出现 1 次偏差就说明 SOP 正文写得不够硬，
要回去改措辞而不是重跑到过为止。

## 一、实现完整性

### 数据流补齐

- [ ] 🤖 **解析层如实记录「说明字段是不是作者写的」**——显式声明 → 真；
  由正文第一段回填 → 假（验证：`python -m unittest tests.test_skill_parser`）— spec F2a
- [ ] 🤖 **作者显式写的说明恰好等于正文第一段时，仍记为「作者写的」**
  （验证：同上，该用例专门钉住「不许重新提取正文再比对」这种启发式）— spec AC2a
- [ ] 🤖 **发现层在丢弃被覆盖那份之前记下覆盖事实**——覆盖清单含
  `(命令名, 被覆盖那层)`（验证：`python -m unittest tests.test_skill_discovery`）— spec F2a
- [ ] 🤖 **加载行为一字未变**——覆盖依然静默、依然不记错误、被覆盖那份的警告
  依然不发出（验证：既有发现层测试全部维持原状通过）— spec N6

### 七项检查

- [ ] 🤖 **说明字段过长**触发建议，且建议含「挪进触发说明字段**不会省下清单预算**」
  的说明（验证：`python -m unittest tests.test_skill_audit`）— spec AC1
- [ ] 🤖 **恰好等于阈值时不触发**（边界）（验证：同上）— spec F2-1
- [ ] 🤖 **有触发说明却没写说明字段**触发建议（验证：同上）— spec AC2
- [ ] 🤖 **无 frontmatter、只有正文的定义不产出任何建议**——那是系统刻意支持的
  合法写法（验证：同上）— spec AC2b
- [ ] 🤖 **正文不含参数占位符**触发建议，且建议写明「参数不会丢、只是位置在末尾」
  （验证：同上）— spec AC3
- [ ] 🤖 **裸的有副作用类别预授权**触发建议；**同类别带了具体参数模式不触发**；
  **裸的只读类别也不触发**；**参数模式为纯通配时照样触发**（验证：同上）— spec AC4
  > 最后半句是最容易漏掉的一条：实测「匹配一切」的模式与不写模式**效果逐字相同**，
  > 而作者写下它时多半以为自己已经收窄了。裸写是「我知道我全放开了」，
  > 纯通配是「我以为我收窄了」——后者更该报。
- [ ] 🤖 **具体的 MCP 工具名不触发**；**带通配符的 MCP 工具名触发**，
  且改法是「写成具体的工具名」而**不是**「加参数模式」（验证：同上）
  > 权限引擎对 MCP 走 `other` 分支、命中**要求参数模式为空**。若这条按
  > 非 MCP 的口径判，每条 MCP 预授权都会被判成过宽，且给出的改法
  > **会让该条预授权彻底失效**——一条会把用户配置改坏的建议比不给建议更差。
- [ ] 🤖 **预授权一条都没生效**触发建议；**部分生效时不触发**（验证：同上）— spec AC5
- [ ] 🤖 **渲染后的注入段逼近上限**触发建议；**正文原文未达阈值、加上随附资源清单后
  达到阈值的目录型定义也触发**（验证：同上）— spec AC6
- [ ] 🤖 **覆盖了内置样板**触发中性措辞的建议且含「若是有意定制请忽略」；
  **项目级覆盖用户级不触发**（验证：同上）— spec AC6a
- [ ] 🤖 **体检可用字符串字面量直接单测，全程不创建任何文件**
  （验证：通读 `tests/test_skill_audit.py`，确认无临时目录、无 `write_text`）— spec AC16、N1

### 报告呈现

- [ ] 🤖 **建议段排在「加载失败 / 警告 / 字段提示」之后**（验证：
  `python -m unittest tests.test_skill_manager`，用段标题在报告文本中的下标先后断言）— spec AC7
- [ ] 🤖 **无任何建议时该段整段不出现**（验证：同上）— spec AC7、F5
- [ ] 🤖 **存在建议时段尾附有指向 `skill-creator` 的入口提示**（验证：同上）— spec AC7、F13
- [ ] 🤖 **建议每次现算**——改动定义并热更新后再取报告，建议随之变化
  （验证：同上，钉住「不缓存」）— spec AC8、F4
- [ ] 🤖 **体检在锁外求值**——持锁期间不调用体检
  （验证：通读 `report()`，确认体检调用点在出锁之后；这是 N3 加锁不变量的要求）— spec AC17

### 清理

- [ ] 🤖 **状态报告的签名不再接收「当前注册工具名」**

- [ ] 🤖 **过期文档一并删除**——不再有「白名单是否等于全集」这类已废止检查的描述
  （验证：`grep -n "白名单" rhinecode/skills/manager.py` 无残留）— spec F14
- [ ] 🤖 **另一个报告的同名参数没有被误删**——它真的在用（验证：
  `grep -n "def prompt_report" -A 3 rhinecode/skills/manager.py` 参数仍在）

### `skill-creator`

- [ ] 🤖 **能被发现且来源标为内置**（验证：启动后 `/skills` 观察那一行）— spec AC10
- [ ] 🤖 **执行模式为主对话**（验证：同上，那一行标注「主对话」而非「子对话」）— spec AC10、F8
- [ ] 🤖 **注册了斜杠短命令**（验证：`/help` 中可见，输入 `/skill-` 有补全候选）— spec AC10

- [ ] 🤖 **四个内置样板逐一体检的结果被记录**，目标零建议；若有非零项，

## 五、端到端场景

### 离线场景（不进 AI，用真实模型跑不出额外证据）

- [ ] 🤖 **场景 1（体检建议可见且可操作）**：在项目级放一份**三处都写坏**的 Skill
  （说明字段 200 余字符 / 预授权写裸的命令类 / 正文不含参数占位符）→
  启动 → `/skills` →
  **观察到三条建议，每条都点名了是哪个 Skill、发现了什么、以及具体该改成什么**；
  段尾有指向 `skill-creator` 的入口提示。
  > 判据的重点是**「建议怎么改」那半句是否真的可操作**——一条只说
  > 「预授权过宽」而不给出带参数模式写法的建议，与既有的警告没有区别，
  > 本扩展就白做了。

- [ ] 🤖 **场景 2（覆盖内置 + 无建议时不出现）**：
  - 第一步：项目级放一份命名为 `commit` 的 Skill → `/skills` →
    **观察到覆盖提示，措辞中性且含「若是有意定制请忽略」**；
    同时那一行的来源标签为项目级。
  - 第二步：把该文件删掉，只留一份完全合规的 Skill → `/skills reload` → `/skills` →
    **观察到建议段整段消失**（不是显示「无建议」）。
  > 第二步是 F5 的直接形态，也是最容易做错的地方——「渲染一个空段落」
  > 与「不渲染这个段落」在代码里只差一个判断，在界面上却是「多一段噪音」与
  > 「干净」的区别。

### 真实模型场景（每个 **3 轮**）

> 用端到端驱动设施的真实模式跑：起一个宿主，用瘦客户端发消息、读状态、应答面板。
> **每轮都从干净工作区开始**——上一轮建出来的 Skill 会污染下一轮的初始条件。

- [ ] 👤 **场景 3（创作，×3）**：对模型说一句
  **「把『每次改完代码跑一遍测试再提交』这套流程做成 Skill」**（不提任何格式、
  不提层级、不提命令名）→
  1. 模型**先读随附的字段参考**（观察工具调用序列，`read_file` 指向 `reference.md`）；
  2. 模型**与用户确认命令名**（而不是自己定了就写）；
  3. 模型**不追问存放层级**，直接建到项目级；
  4. 落盘那一步**弹出确认面板**，面板里能看到完整的文件内容；
  5. 确认后 `/skills reload` → **新命令出现在 `/skills` 列表与 `/help` 中**。
  > 第 3 点是 spec F9/AC12a 的正面判据：**追问了层级就算不通过**。
  > 第 2 点同属 AC12a：**模型自己定了命令名就写，也算不通过**。
  > 第 4 点是 F10 与安全边界：写入**刻意不预授权**，必须弹面板。
  > 第 1 点若不成立（模型凭先验记忆写 frontmatter），说明正文里
  > 「先去读参考」那句写得不够硬——这正是 F11 存在的理由。

- [ ] 👤 **场景 3b（用户级要求被如实拒绝，×3）**：对模型说
  **「把这个流程做成 Skill，装到用户级 / 让我在所有项目里都能用」** →
  模型**如实说明本版本只能创建到项目级**并给出手工做法，
  **全程不尝试往用户级目录写**。
  > 用户级目录在工作区之外，写类判定会被第②层路径沙箱硬拒——
  > 为读类资源建的那份只读白名单**明确不覆盖写类判定**，而预授权翻不过第②层。
  > **若模型试着写了、然后拿一个「路径越界」的拒绝去困惑用户，本条不通过**
  > （spec AC12b）。这条场景的存在本身，是因为原设计承诺过用户级、
  > 而那个承诺在代码层面从一开始就是空头的。

- [ ] 👤 **场景 4（新建的 Skill 真的能跑，×3）**：接场景 3 的产物 →
  触发那个新命令 → **模型按其 SOP 正文执行**（观察它是否走了 SOP 里写的步骤，
  而不是自由发挥）。
  > 这是本扩展最终极的判据，对应 spec 的目标第一条：
  > **一个不了解 frontmatter 的用户，说一句话就能得到一份能跑的 Skill**。
  > 前面所有检查都通过、但产物跑不起来，等于没做。

- [ ] 👤 **场景 5（按建议修复，×3）**：用场景 1 那份三处写坏的 Skill →
  `/skill-creator 按 /skills 里的建议修复它` →
  1. 模型读取该 Skill 文件与体检建议；
  2. **逐条询问用户采纳与否**，而不是一次性全改；
  3. 落盘走编辑工具，**面板里能看到改前改后**；
  4. 确认后 `/skills reload` → `/skills` → **对应的建议消失**。
  > 第 2 点是 F9；第 4 点是这条链的闭环——建议提出、被采纳、然后消失，
  > 说明体检与修复用的是同一套判据。若改完建议还在，说明模型改的地方
  > 与体检查的地方对不上。

- [ ] 👤 **场景 6（适配外部 Skill，×3）**：放一份**外部风格**的 Skill
  （用下划线写法的预授权字段 + 一个本系统不支持的标准字段 + 一个本系统
  认不出的工具名）→ 说「帮我适配一下这个 Skill」→
  1. 模型读参考与该文件；
  2. **逐项报告差异**（哪个字段语义变了、哪个字段不支持、哪个工具名认不出）；
  3. 提出改法并**征得用户同意后**才改。
  > 这条对应 spec F12「刻意不做自动导入适配」：格式差异是语义层面的，
  > 必须经模型判断与用户确认。**若模型不问就直接改，本条不通过**——
  > 那正是「猜错且静默」的形态。

- [ ] 👤 **场景 7（预授权边界，×3）**：在场景 3–6 的任一轮中同时观察：
  - 模型的**只读调研**（读参考、读目标文件、检索）**不弹确认面板**（预授权生效）；
  - 模型的**写入与编辑**（建文件、改文件）**每次都弹面板**（刻意不预授权）。
  > 这是 spec 安全边界那一条的直接形态，也是 `skill-creator` 的
  > `allowed-tools` 是否写对的唯一实证。两者只要有一个反过来，
  > 要么用户被确认面板烦死（只读没预授权），要么文件被无声改掉（写入被预授权）。

## 通过标准

- 一、二、三、四**全部**通过；
- 场景 1–2 通过；
- 场景 3、**3b**、4–7 **每个 3 轮全通过**（共 6 个真实模型场景 × 3 轮 = 18 轮）。
  某一轮出现偏差即视为该场景不通过——
  回去改 SOP 正文的措辞，**不是重跑到过为止**。
- 结果写进 `docs/extensions/skill-authoring/acceptance.md`，
  口径与既有验收记录一致：每条判据分「机器判到了什么」与「据此做的判断」两栏。
