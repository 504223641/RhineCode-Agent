## 二、判定范围与路径形态（AC1/AC3/AC4/AC5）

| 判据 | 机器判到了什么 | 据此做的判断 |
| --- | --- | --- |
| 保护范围 | `ScopeTest` 遍历 11 条路径全部命中（含 `permissions.yaml` / `permissions.local.yaml` / `hooks.yaml` / `mcp.yaml` / `agents/` / `skills/` / `memory/` / `worktrees/` / `.git/config` / `.git/hooks/pre-commit` / 一个虚构的新配置文件） | 黑名单式方向成立——**将来新增的配置文件自动被保护**，不需要有人记得回来改表 |
| 排除范围 | `sessions/` `context/` `traces/` 三条不命中 | 纯机器副本不必过人眼 |
| 普通路径 | 4 条业务路径不命中 | 日常改代码不受影响 |
| 路径形态 | 相对 / `./` 前缀 / 绝对三种写法命中，且**解析后的路径相等** | 豁免键三种写法算出同一个，「本会话放行」不会只对其中一种生效 |
| 符号链接 | 真建软链后命中，`hit.path` 等于软链目标 | 「在工作区内建一条指向 `hooks.yaml` 的软链再写它」绕不过。这条依赖 `resolve_in_workspace`——换成自己拼 `Path` 会静默失效 |
| 大小写变体 | Windows 上 `.RHINECODE/hooks.yaml` 命中并归一为 `.rhinecode` | ⚠ **实现期发现的一处真实缺口**：`path_guard.is_inside` 用 `relative_to` 逐字符比较，在 Windows 上一个大小写变体就能静默跳过整层保护，而它写到的还是那份真正的配置。改用 `os.path.normcase` 后 POSIX 上仍把 `.RHINECODE` 当成另一个目录——那里它确实是 |
| fail-safe | `cwd=None` / `""` / `"   "` / 含 `..` 四种都按命中处理，不抛异常 | 偏严方向。这一支经引擎调用时其实不可达（②层已给 DENY），是给直接调用方的兜底 |

## 三、升级语义（AC6/AC7/AC8/AC9）

| 判据 | 机器判到了什么 | 据此做的判断 |
| --- | --- | --- |
| 顺序护栏 | 先断言 `_decide_core` 对 `allow: Write(.rhinecode/**)` 给出 `ALLOW @ RULE`，再断言 `decide` 给出 `ASK @ PROTECTED` | **两步都要**。少了第一步，哪天有人把模式写成匹配不上的形式，这条护栏会静默退化成「③层没命中」的形态而仍然全绿 |
| 反证一 | `deny: Write(.rhinecode/hooks.yaml)` → 仍 `DENY @ RULE` | 用户明确写下的禁止不被降级 |
| 反证二 | 严格档 → 仍 `DENY @ MODE` | 严格档的兜底不被降级 |
| 反证三 | 路径越界 → 仍 `DENY @ SANDBOX` | ②层的拒绝不被降级 |
| 放行档 | `ASK @ PROTECTED` | 本扩展要解决的主场景 |
| **默认档** | `ASK @ PROTECTED`（**不是 `ASK @ MODE`**） | plan 阶段那处修正的落点：层不换的话面板照常给出「永久放行」，骗人的按钮换个入口原样存在 |
| Skill 预授权 | `turn_rules` 里一条 allow → 仍 `ASK @ PROTECTED` | 「`allowed-tools` 只放宽从不收紧」与本层不冲突——它翻不过本层 |
| `edit_file` | 同样命中 | 不能只覆盖 `write_file` |
| 其余 kind | 命令 / 读取 / glob / URL / 未映射五类，`decide` 与 `_decide_core` **逐字相等** | ⚠ 每个用例的 specifier 都刻意指向保护路径——用普通路径构造的话，「漏判 kind」这种错误测不出来 |

## 四、本会话豁免（AC11/AC12/AC13/AC14）

| 判据 | 机器判到了什么 | 据此做的判断 |
| --- | --- | --- |
| 面板选项 | 保护路径 → `["yes","yes_session","no"]`；普通场景 → 四项含 `yes_permanent` | 「永久放行」写的是③层规则，本层不被③层消解，留着它就是一个点了没用的按钮。⚠ 反证同样必要 |
| 选项文案 | 「本会话放行」说明含「不写入配置」 | 用户对这个选项的既有心智是「登记一条会话规则」，机制换了必须说破 |
| 不落盘 | `persist_local_rule` **零次调用**（计数）、`session_rules` 长度不变、豁免集合 +1 | ⚠ 断言的是**调用次数**不是返回值——「悄悄写了盘但照常放行」与「没写盘」在返回值上完全一样 |
| 真机不落盘 | 端到端场景 5：`permissions.local.yaml` 里没有任何 `Write` 规则 | 单测看调用计数，真机看磁盘——「换一条路径写了盘」在计数上看不出来 |
| 不扩散 | 同目录另一个文件仍 `ASK @ PROTECTED` | 最小授权 |
| 不解除 deny | 豁免 + deny 规则同时成立 → 仍 `DENY` | 豁免**只解除本层的升级** |
| 键是解析后路径 | 为相对写法登记后，绝对路径写法也认 | |
| 派生共享 | 主引擎登记后派生实例不再升级，且两者是**同一个 set 对象** | 与 `session_rules` 同口径。⚠ 与 `load_errors` 同一个坑：构造函数会新建，不显式赋值则共享静默不成立 |
| 非保护路径 | `grant_protected_exemption` 返回 `False` 且集合不变 | |

## 八、遗留与已登记的边界

三条都已登记进 `CLAUDE.md` 已知后续工程项 #5。

⚠ **本层的分量会随 todo 第 2 条（auto 成为缺省档）显著上升**：那时子 Agent 的
生效档位也是 auto，能写文件、后台、并行、用户不在场，而②″是唯一挡住它写配置的
东西。端到端场景 6 正是这条的回归护栏。
