# 保护路径层（②″）Spec

> 扩展，不占章节号。判据：`CLAUDE.md` 的能力表不多一行——它在既有的权限管线上
> 加一道边界，不引入新的能力层级。
>
> 上游：`docs/todo/2-perm-protected-paths.md`（本 spec 落地后删除）。
> 本 spec **修正了那份 todo 的两处推理**，见「与 todo 原文的两处分歧」。

## 背景

`.rhinecode/` 下有一批文件，它们的内容决定**「以后会发生什么」**：

| 文件 | 改了之后 |
| --- | --- |
| `permissions.yaml` / `permissions.local.yaml` | 模型给自己加 `allow` 规则 |
| `hooks.yaml` | Hook 动作**直接执行、不过五层管线**（C12 安全边界第 ② 条：本章最大的攻击面） |
| `mcp.yaml` | 启动一个外部程序，并把它的工具注册进工具中心 |
| `agents/*.md` | 造一个新角色，或给既有角色加工具白名单 |
| `skills/*.md` | 一段会被自动加载、指挥后续所有行为的文本 |

**现在这五处的写入没有任何特殊待遇。** 走一遍现有管线：

- ①黑名单——只管命令类，`write_file` 不进这层
- ②沙箱——`.rhinecode/` **就在项目根内**，`is_within_workspace` 判它合法
  （`path_guard._RUNTIME_ARTIFACT_RELATIVE` 那三条只排除 `sessions` / `context` /
  `traces`，而且只对**搜索类**工具生效，写入完全不受影响）
- ③规则——用户没写 deny 就不表态
- ④模式——放行档直接 ALLOW；默认档弹一次面板，用户点了「永久放行」之后连面板都没了

所以**放行档下，或存在一条宽松 allow 规则时，模型可以直接改写自己的权限配置**。

⚠ 一条限定，别把危害说过头：这五份配置**都是装配期加载**的（`/hooks` 与 `/agents`
都刻意不做 reload），所以不是即时提权，是**持久化提权、下次启动生效**。但用户当然会
重启——而且重启之后 `/hooks` 的项目级启动提示会照常列出那条新规则，用户看到的是
「我的项目里怎么多了条 hook」，不会想到是上一段对话里模型自己写的。

### 为什么值得单独做

**它绕过的不是某一层，是整套论证的前提。**

C11 / C12 / C13 / C14 / C15 的安全边界全都建立在同一句话上：**配置由人写下，模型
只在配置划定的范围内行动**。所以那些论证才成立——「Skill 拿不到权限捷径」
「`allowed-tools` 翻不过前两层」「子 Agent 的能力只会比主对话小」。

一旦模型能改配置，这些话的主语就变了。而这条路径**在现有的任何一层里都不违规**：
每一步都是合法的 `write_file`，落在工作区内，没碰黑名单。

Claude Code 对同一个问题的做法叫 **protected paths**：`.claude`、`.git`、`.bashrc`
这类文件的写入**永不自动放行**，且这道检查**不被 allow 规则消解**——settings 里写
`Edit(.claude/**)` 也盖不过它。

### 这条为什么排在「auto/plan 两 preset」之前

三条 todo 同源（2 → 3 → 4 串行）。第 3 条会把 `auto` 定为缺省档，届时**写文件与
跑命令都不弹面板**——本层就成了「模型改不了自己的配置」的唯一依据。
**顺序颠倒的后果不是「少做一件事」而是「安全性净下降」**：3 先做等于把唯一的拦截
先拆了。

## 目标

- 让「模型改写自己的配置」这件事**必须经过人眼**，且该判定**不被任何 allow 规则消解**
- **不误伤 C14 的隔离子 Agent**——它的工作目录整个坐落在保护目录之内（从主项目根看），
  按主项目根判定会让它的每一次写入都被拦，而它非交互、判 ASK 即自动拒绝
- **不制造一个骗人的按钮**——不让「永久放行」写下一条永远不会被求值的规则
- **只收紧，不放宽**：加了这层之后，能通过的调用集合只会变小，一条都不会变多

## 与 todo 原文的两处分歧

两处都是读代码时发现的推理缺口。审批时若不认同，本 spec 按 todo 原文改。

### 分歧一：本层不是「管线中的一站」，是一个后置收紧器

todo 写的是「排在②沙箱之后、③规则之前，命中即返回 ASK」。**按字面实现会静默
放宽两种情况**：

| 场景 | 既有结论 | 按 todo 字面实现 | 差别 |
| --- | --- | --- | --- |
| 用户写下 `deny: Write(.rhinecode/hooks.yaml)` | ③层 DENY | ②″先短路 → **ASK** | 用户明确写下的禁止被降级成「问一下」 |
| `/perm` 切到**严格档**，写 `hooks.yaml` | ④层 DENY | ②″先短路 → **ASK** | 严格档的「灰色地带一律拒绝」被降级 |

两处都是**放宽**，与本层的目标正相反。

正确语义与 **C12 的 Hook ASK 完全同型**：跑完既有管线拿到结论，**只把 ALLOW
升级为 ASK，绝不把 DENY 降级为 ASK**。

「必须在③之前」这句话的**实质**因此要重述为：**本层的升级效力不被③层的 allow
规则消解**。位置论证原样成立（一条 `allow: Write(.rhinecode/**)` 盖不过它），
而 deny 与严格档不再被误伤。

### 分歧二：`worktrees/` 与 `memory/` 不在排除清单里

todo 的排除理由各有一处不成立：

- **`worktrees/`** —— todo 说「C14 的隔离子 Agent 就在这里面干活，保护它等于把隔离
  功能整个关掉」。**这句话与坑 1 自相矛盾**：判定基准是 `request.cwd`，而隔离子
  Agent 的 `cwd` **就是**那个工作区目录，它拼出的保护根是
  `<工作区>/.rhinecode/` 与 `<工作区>/.git`，跟主项目根的 `.rhinecode/` 毫无关系。
  排除它唯一的实际效果是：**主对话/非隔离子 Agent 可以随手改写别人的隔离工作区**
  ——而 C14 明说「不要自己进工作区目录抄文件，成果经分支交付」。保护它零代价。
- **`memory/`** —— todo 说「记忆落盘是内部可信写盘、压根不走工具管线，这层管不到
  它也不需要管」。**前半句对，后半句不对**：自动沉淀确实不走管线（不受本层影响），
  但模型**主动用 `write_file` 写 memory 目录**是走管线的，而记忆会经索引注入系统
  提示——那正是「给自己写持久指令」。保护它的代价接近零（模型极少主动写它），
  收益是堵住与 `skills/` 同性质的一条路。

于是排除清单收敛成三项，且共用同一条理由：**纯机器副本，改了不影响「以后会发生什么」**。

## 功能需求

### 判定

- **F1**：决策管线新增一层「保护路径」（记作 ②″）。它**只对写入类路径请求生效**；
  命令类、读取类、glob 类、URL 类、未映射类请求的判定逐字不变。

- **F2**：本层的判定基准是**本次调用的工作目录**，与②路径沙箱完全同口径。
  保护根以该工作目录拼出，**绝不使用主项目根**。
  工作目录缺失或无法解析时按「命中保护」处理（偏严），不回退到主项目根。

- **F3**：保护范围（黑名单式——默认保护，排除项需要理由）：

  **保护**：
  - `<工作目录>/.rhinecode/` 及其下全部内容
  - `<工作目录>/.git/` 及其下全部内容

  **排除**（写清理由，免得后来的人当成漏改顺手补上）：
  - `<工作目录>/.rhinecode/sessions/` —— 会话存档
  - `<工作目录>/.rhinecode/context/` —— 上下文存盘的工具结果原文
  - `<工作目录>/.rhinecode/traces/` —— 行为记录

  三项共用一条理由：**纯机器副本，改了不影响「以后会发生什么」**。
  （它们恰好也是 `path_guard._RUNTIME_ARTIFACT_RELATIVE` 那三条，但**两张表刻意
  不合一**——那张表的语义是「搜索时跳过」，本表是「写入要过人眼」，语义不同，
  合一会让将来任一侧的增删误伤另一侧。）

- **F4**：判定路径时**以解析后的真实路径**与保护根比较，口径与②层一致：
  相对路径按工作目录展开、绝对路径按真实位置判断、符号链接解析后再判。
  因此「在工作区内建一个指向 `.rhinecode/hooks.yaml` 的符号链接再写它」同样命中。
  解析失败按命中处理（偏严）。

- **F5**：本层的结论是 **ASK，不是 DENY**。「让模型帮我加一条 deny 规则」是完全
  正当的需求，DENY 会把它变成做不到；本层要的只是**人眼必须过一遍**。

- **F6**：本层是**收紧器**，不是短路站（见「分歧一」）。既有管线的结论为 ALLOW 时
  升级为 ASK；结论为 DENY 时**保持 DENY**；结论已是 ASK 时保持 ASK。
  逐条展开：
  - ③层 allow 规则命中（含 `allow: Write(.rhinecode/**)`）→ **ASK**
  - ③层 deny 规则命中 → **DENY**（不降级）
  - ①黑名单 / ②沙箱 DENY → **DENY**（不降级）
  - ④严格档 DENY → **DENY**（不降级）
  - ④默认档 ASK → ASK
  - ④放行档 ALLOW → **ASK**
  - Skill `allowed-tools` 预授权命中（本次执行级 allow）→ **ASK**

- **F7**：升级发生时，命中层标为本层（用于原因展示、确认面板与行为记录），
  拒绝/放行原因文本说明这是一次保护路径判定，并点出**为什么这个文件特殊**
  （它改变以后会发生什么），而不只是「需要确认」。

### 本会话豁免

- **F8**：确认面板在保护路径场景下**不提供「永久放行」**。
  理由：面板的「永久放行」写的是一条③层规则，而本层的升级效力不被③层消解——
  那条规则永远改变不了结论，用户会看到「点了永久放行，下次还是弹」。
  **这比不做还糟**，因为它让一个明确的用户决定看起来失效了。

- **F9**：面板提供「本次放行 / 本会话放行 / 拒绝」三项。选「本会话放行」时**不产生
  任何③层规则、不写任何配置文件**，而是登记进本层自己的**内存豁免集合**。

- **F10**：豁免**精确到那一个解析后的绝对路径**，不扩展到目录，与既有确认面板
  「本会话放行」的最小授权口径一致。

- **F11**：豁免的生命周期与既有会话级规则一致——**关程序即失效**，不落盘，
  不随 `/clear`、`/resume` 清空。

- **F12**：豁免命中时本层不再升级，判定回落为既有管线的结论。
  ⚠ 豁免**只解除本层的升级**，其余各层照常——被豁免的路径若同时命中一条
  `deny` 规则，结论仍是 DENY。

- **F13**：子 Agent 派生的引擎视图**共享同一个豁免集合**，与既有会话级规则同口径
  （用户在面板上的明确授予理应对子 Agent 生效）。这不破坏 C13 的「子 Agent 的
  能力只会比主对话小」——子 Agent 拿到的豁免不多于主对话。

### 与既有能力的关系

- **F14**：**隔离子 Agent（C14）不受本层影响**。它的工作目录是自己的隔离工作区，
  拼出的保护根落在那个工作区内部，而隔离工作区里没有 `.rhinecode/`（被忽略规则
  排除、checkout 不出来）。它对自己工作区内业务文件的写入一条都不命中。
  ⚠ 它写自己工作区里的 `.git`（在 worktree 里那是个**文件**）仍会命中——这是
  期望行为，不作特例。

- **F15**：**非隔离子 Agent 的写入命中本层时判 ASK，而它非交互、自动拒绝**。
  这是期望行为（子 Agent 不该改配置），不是缺陷，须在文档里写明，
  以免将来有人把它当误伤「修」掉。

- **F16**：本层的判定与豁免命中都必须在**行为记录**里可见。
  只记最终结论的话，读的人分不出「这次弹面板是因为保护路径」还是「因为默认档兜底」，
  也分不出「这次没弹是因为豁免」还是「因为切了放行档」。

- **F17**：新增的判定层在**三份展示表**里都要有名字（枚举本身、行为记录阅读器、
  确认面板的层名映射）。三份表刻意不合一——合一要让只依赖标准库的行为记录叶子包
  反向依赖权限包。

## 非功能需求

- **N1**：**只收紧，不放宽，且可逐条论证**。这是本层全部安全价值的依据，
  论证形态与 C12「Hook 只能收紧不能放宽」一致：本层不产生 ALLOW，
  也不把任何 DENY 变成非 DENY。

- **N2**：**纯判定**。给定「请求 + 工作目录 + 豁免集合」即可复现结论，
  不读配置、不发请求。路径解析复用既有路径边界模块，不新增 I/O 形态。

- **N3**：**判定失败一律偏严**（任何异常按命中保护处理），且异常绝不向上抛——
  权限判定入口必须保持「不会因坏输入崩溃」。

- **N4**：**其余种类的请求逐字不变**。关掉本层（或本层未命中）时，
  整条管线的行为与本扩展之前逐字一致，须有对照护栏钉住。

- **N5**：可被纯单测覆盖，不依赖真实文件系统写入、不依赖 TUI。

- **N6**：**顺序护栏必须用「宽 allow + 保护路径」构造**。用「③层没命中」的形态构造
  护栏，在实现写错（本层被 allow 规则消解）时**照样通过**，发现不了问题——
  这是②′网络边界层验收期已经付过一次学费的教训。

## 不做的事

- **`run_command` 的旁路不堵**（`echo >> .rhinecode/hooks.yaml`）。命令串里无法区分
  读写——做了会让 `cat .rhinecode/hooks.yaml`、`git status` 之类无害命令也弹面板，
  而变量拼接、heredoc、命令替换一律绕得过，是「看起来堵上了」。
  **登记为已知边界**，与已知项 #4（OS 级沙箱）同源；真正的堵法是 todo 第 4 条的
  分类器审查。

- **MCP 工具不受本层约束**。它们落未映射分支、没有路径判定，且 MCP Server 是装配期
  以主项目根为工作目录启动的外部进程。与 C14 已登记的同名边界是同一条。

- **不保护项目根的 `RHINE.md`**。它确实是注入系统提示的指令文本，与 Skill 同性质，
  但属高频合法写入（`/init` 生成、用户让更新项目说明），保护它会让日常操作频繁弹
  面板；而 `/init` 本来就走完整管线、默认档下已经弹过一次。

- **不保护用户级 `~/.rhinecode/`**。它在工作区外，②路径沙箱对写类判定一律拒绝，
  本层不必重复。

- **不管读取**。只管写入类请求。读配置文件不改变「以后会发生什么」；
  `config.yaml` 的密钥泄漏是另一个已登记问题，手段是 deny 规则。

- **不做落盘的永久豁免**。落盘的豁免本身就是一份「能改变以后会发生什么」的配置，
  绕一圈又回到原问题。

- **不做目录级豁免**（「本会话内整个 `.rhinecode/` 都放行」）。

- **不提供关掉本层的开关**（没有配置项、没有命令、没有权限档能关掉它）。
  与①危险命令黑名单同一性质。

- **不做保护清单的可配置化**。用户自定义保护清单是合理需求，但那份配置本身又要被
  保护，且它与本层的「不可被配置放开」性质需要单独论证，留待后续。

## 验收标准

- **AC1**（F1/N4）：命令类、读取类、glob 类、URL 类、未映射类请求的判定结果与本扩展
  之前逐字一致；写入类请求中未落在保护范围内的同样逐字一致。

- **AC2**（F2/F14，**坑 1 的护栏**）：**同一个绝对目标**
  `<主项目根>/.rhinecode/worktrees/w/a.py`，以主项目根为工作目录时**命中**
  （那是主对话去改别人的隔离工作区），以该工作区为工作目录时**不命中**
  （那是隔离子 Agent 在写自己的业务文件）。

  ⚠ 这条**不能写成「同一个相对路径 `.rhinecode/hooks.yaml` 在两个 cwd 下结论相反」**
  ——那句话是错的：以工作区为 cwd 时它指的是 `<工作区>/.rhinecode/hooks.yaml`，
  落在该工作区自己的保护根内，**照样命中**（F14 已写明这是期望行为）。
  按那个错写法建的护栏在「判定基准退回主项目根」时**照样通过**，坑 1 漏掉。
  实现期实测发现。

- **AC3**（F2/N3）：工作目录缺失或无法解析时，写入类请求按命中保护处理，且不抛异常。

- **AC4**（F3）：`.rhinecode/` 下的 `permissions.yaml`、`permissions.local.yaml`、
  `hooks.yaml`、`mcp.yaml`、`agents/` 下任意文件、`skills/` 下任意文件、
  `memory/` 下任意文件、`worktrees/` 下任意文件，以及 `.git/` 下任意文件，
  写入时全部命中；`sessions/`、`context/`、`traces/` 下的写入**不命中**。

- **AC5**（F4）：绝对路径写法、`./` 前缀写法、以及工作区内指向 `.rhinecode/hooks.yaml`
  的符号链接，三种写法都命中。

- **AC6**（F5/F6，**顺序护栏**）：存在一条 `allow: Write(.rhinecode/**)` 时，
  写 `hooks.yaml` 仍判 **ASK** 且命中层为本层。
  （⚠ 这条必须用「宽 allow」构造，见 N6。）

- **AC7**（F6，**反证一**）：存在一条 `deny: Write(.rhinecode/hooks.yaml)` 时，
  结论仍是 **DENY**，不被降级为 ASK。

- **AC8**（F6，**反证二**）：严格档下写 `hooks.yaml` 结论仍是 **DENY**，
  不被降级为 ASK。
