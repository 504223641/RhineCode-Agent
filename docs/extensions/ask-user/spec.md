> **这是扩展，不占章节号。** 判据是 `docs/extensions/README.md` 那一条：
> `CLAUDE.md` 的能力表要不要多一行——**不要**。
>
> 本次不引入新的能力层级：`ask_user` 是 C4 就有的工具、`ClarifyPanel` 是 C4 就有的

## 背景

### 用户要的是什么

> 我希望当模型需要向用户确认细节时**总是**通过这个面板来获取用户的选择。目的是方便
> 用户，对于选择不用手动打一大堆文字，而是通过预定义的选项来进行选择，提高用户体验。
> 面板的实现可以参考 Claude Code 的澄清提问面板。

拆成两条可验收的诉求：

1. **覆盖面**——不再只有 Plan Mode 规划阶段能弹面板。
2. **表达力**——面板要能承载 Claude Code 那套结构（多问题、多选、自己输入），
   否则模型会因为「面板表达不了我要问的」而退回用正文提问，第 1 条等于没做。

### 已经有的一半地基（开工前实测，不是照抄 todo）

| 件 | 位置 | 现在的样子 |
| --- | --- | --- |
| 工具 | `agent/plan_tools.py` `AskUserTool` | 单问题 + 若干选项（`summary` / `detail`），约定第一个最推荐 |
| 面板 | `tui/widgets.py:3547` `ClarifyPanel` | 单选。表头是问题，每项一行可选概述 + 一行 disabled 详情（导航跳过、不占序号） |
| 回调链 | `conversation.clarify_callback` → `tui/app.py:2765` `_clarify` → `_interact` | 阻塞式，与确认面板同一条机制 |
| 拦截路由 | `agent/loop.py:1333` | **无条件**分流，与阶段无关 |
| 唯一门槛 | `agent/loop.py:911-912` | `if planning: base = base + plan_schemas()`——平时模型看不到这个工具 |
| 驱动设施 | `tests/e2e/control.py` `settlement_for` | 支持 `clarify`，但**明令拒绝 `via=keys`**（`protocol.py:113`） |

### 开工前实测发现的四件事（todo 未记录）

**① C15 的无人值守轮会把面板弹给一个不在场的人。**

`conversation.py:1912-1937` 那次 `run()`：

```python
ask = None if unattended else self._build_ask()   # 确认面板：无人轮时置空
events = self._agent.run(
    ..., ask,
    self.clarify_callback,                        # 澄清面板：无人轮时照传不误
```

今天无害（`ask_user` 只在规划阶段可见，而无人轮不在 Plan Mode）。放开之后：队友消息
半夜唤起主对话跑一轮 → 模型提问 → 面板弹出 → **没人在** → Agent 线程停在
`box["event"].wait()` 上，**没有超时**。次日用户回来打字，输入框会回一句
「正在等待你的确认，请先在面板上做出选择」——而那个问题关于一件他从没提过的事。

C15 安全边界第 ④ 条写着无人轮「确认面板一次都不弹」。本条是那条约束的漏网之鱼。

**② `ask_user` 连「工具排除」都绕得过。** `loop.py:1333` 的分流发生在 `_visible()`
检查**之前**就 `continue` 了，因此 C11 fork 子对话用来防嵌套的 `excluded_tools`
对它不生效。今天无害，放开后要明确写下「fork 子对话能不能提问」。

**③ 澄清面板期间输入框是被禁用的**（`_show_clarify_panel` 里 `InputBar.disabled = True`），
确认面板不是。这一行直接决定自由输入怎么落地。

**④ 驱动设施明令拒绝 `clarify` + `via=keys`**，理由是详情行让「按几次方向键」推不准。
多选一做这条就必须破——多选要在好几行上依次操作，不走按键路径根本验不到。

### 参照系：Claude Code 的 `AskUserQuestion`

数据形状（官方 *Handle approvals and user input* 与该工具自身的说明书，两处一致）：

| 字段 | 约束 |
| --- | --- |
| 每次调用的问题数 | **1–4** |
| `question` | 问题原文 |
| `header` | 短标签，**最多 12 字符**，渲染成一枚徽章 |
| `options` | **2–4** 项，每项 `label` + `description` |
| `multiSelect` | 为真时可多选 |
| 答案回传 | `{问题原文: 选中的 label}`；多选传数组或 `", "` 拼接 |
| 子 agent 中可用 | **否**（官方 Limitations 明写） |

两条**官方明确交给客户端补**的：

> Display an additional "Other" choice after Claude's options that accepts text input.
> Use the user's custom text as the answer value (not the word "Other").

> If you recommend a specific option, make that the first option in the list and add
> "(Recommended)" at the end of the label

触发口径（本次最该抄的部分，**两侧都写，「不该用」那侧更长**）：

> Use this tool only when you are **blocked** on a decision that is genuinely the user's
> to make: one you cannot resolve from the request, the code, or sensible defaults.

> **Reserve this** for decisions where the user's answer changes what you do next —
> **not** for choices with a conventional default or facts you can verify in the codebase
> yourself. In those cases **pick the obvious option, mention it in your response,
> and proceed**.

⚠ 机制上还有一条对照：Claude Code 那边 `AskUserQuestion` 与权限确认**走同一条
`canUseTool` 回调**（官方原话「both trigger your `canUseTool` callback, which pauses
execution until you return a response」）。本项目的 `clarify_callback` 与 `ask_callback`
正是同构的两条阻塞回调——**这个结构本次一个字不改**。

### 两条直接决定本次做法的项目内前车之鉴

**已知项 #17（C13 委派口径）**：只写「该用」的理由 = 单向推力 = 必然过触发。
真实反馈是「一个非常简单的任务都要让子 Agent 去做」，且**欠触发与过触发出自同一个
模型**——问题在默认值定在哪一侧，不在模型强弱。

**todo-list 扩展的真机复测（2026-08-18，就在昨天）**：静态规则那条路**走到头了**。
能力描述 → 带可匹配条件的指令 → 每轮 `<system-reminder>`，三个杠杆逐个加满，
两个模型在一个明确五步的任务上仍是**各 0 次**调用；补上 Claude Code 那种
**四正四负八个带 reasoning 的示例**之后，`deepseek-v4-flash` 从 0 次变成 4/4 通过。
证据链在 `docs/extensions/todo-list/acceptance-live.md`。

→ **本扩展的触发口径必须从一开始就带示例，而不是只写规则。**（F20）

## 目标

- 模型在**任何阶段**卡在「有好几种都说得通的做法」上时，都能弹面板让用户点一下，
  而不是在正文里写一段问句然后停下来等用户手打一大段。
- 面板的表达力覆盖 Claude Code 那套结构：多问题、选项说明、多选、自己输入。
- **默认值定在「不问」那一侧**，用可数的下限与正反示例把它钉住，
  不重演已知项 #17 的「欠触发 → 过触发」。
- 用户不在场时**一个面板都不弹**，Plan Mode 的既有行为**逐字不变**。

## 功能需求

### 一、覆盖面

**F1 `ask_user` 的可见性判据从「阶段」换成「有没有人可问」。**
本次运行拿到了澄清回调，就把这个工具的说明书发给模型；没拿到就不发。
Plan Mode 的规划阶段、执行阶段、以及完全不开 Plan Mode 的普通对话，三者一视同仁。

⚠ **`present_plan` 的判据不变**，仍然只在规划阶段拼接。两个特殊工具从此判据不同——
这是刻意的：提交计划只在「有计划要审批」的阶段有意义，向用户提问任何时候都有意义。

**F2 子 Agent 仍然拿不到它，这是不变量不是缺口。**
子 Agent 全程非交互、用户不在场，与官方登记的限制（*not currently available in
subagents*）同一个理由。F1 的判据天然兑现这一条——子 Agent 那条运行链传的澄清回调
本来就是空的，工具因此不会出现在它的说明书里。**结构上做到，不靠另立一张禁用清单。**

**F3 无人值守轮（C15 自动唤起）不弹面板，且分两道。**

- **第一道**：那一轮不提供澄清回调，因此模型**看不到**这个工具。
  （与既有的 `ask = None if unattended else ...` 同一手法。）
- **第二道（纵深防御）**：模型仍可能凭训练先验硬造出一次调用（本项目已多次实测到
  这种形态）。此时**不弹面板**，直接回灌一句说明并让循环继续。

**F4 「问不了人」时的回灌文案按原因分三种。** 三种情形下模型该做的事不同，
一句通用的「当前不支持向用户澄清」说不清楚：

| 情形 | 判据 | 回灌要说的 |
| --- | --- | --- |
| 子 Agent | 本次运行不可交互 | 你是子 Agent，没有人能回答；按最佳判断继续，把不确定处写进结论 |
| 无人值守轮 | 本次运行是无人轮 | 这一轮由队友消息自动唤起、用户不在场；按最佳判断继续 |
| 其它 | —— | 当前拿不到澄清通道；按最佳判断继续 |

三种都**不终止循环、不置「用户拒绝」**——没有任何用户做过决定。

**F5 Skill 的 fork 子对话可以提问。** 现状即如此（它传的是真实的澄清回调），
本条只是把它**写下来**：fork 子对话是用户触发或模型发起的一条短子对话，
用户就在屏幕前，问他是合理的。

⚠ 连带写下一条已知形态：`ask_user` 的分流发生在工具收窄检查之前，因此
`excluded_tools` 对它不生效。这不是漏洞——那个机制是为「防止 Skill 里再激活 Skill」
造的，与提问无关。

**F6 `ask_user` 仍然不进工具注册中心、不过权限管线，但理由要换一条。**

旧理由是「它只在规划阶段可用」，覆盖面放开后不成立了。新理由，两条独立成立：

1. **它没有副作用可判**——五层管线判的是「读哪个文件、跑哪条命令、访问哪个域名」，
   而它一样都不做，落到管线里只会走 `other` 分支、除第④层外没有任何一层会说话。
2. **它本身就是人在回路**——弹面板等用户点，正是第⑤层在做的事。
   给一个「问用户」的动作再加一道「问用户要不要问用户」是循环论证。

⚠ 与 C15 那七个 `system_serial` 工具**刻意不同**：那些进注册中心、照常过 `engine.decide`
（只对第④层免疫），因为 `deny: send_message` 是文档承诺过的手段。`ask_user` 从 C4 起
就不在注册中心里，本次不改变这一点——改了要动装配层，超出扩展范围。

**F6a ⚠ 已知边界：`ask_user` 现在没有任何「关掉它」的手段，本扩展也不新增一个。**

开工前实测确认：特殊工具的分流发生在 **Hook 前置层之前**（`loop.py` 里那句分流在
Hook 唯一分发点的上游），因此 **`pre_tool_use` 对 `ask_user` 不触发**——用户写
`deny` 规则也没用（它不在注册中心）、写拦截 Hook 也没用。

**这一条必须原样写进 `CLAUDE.md` 的安全边界，不许含糊过去。** 本项目已知项 #18 的
教训就是这个形态：文档承诺「可被 deny 规则禁掉」而实际不能，**错误的安全承诺比没有
承诺更危险**。

现在真实可用的只有三样，都不是开关：
- **可见性判据**（F1）——没有可问的人就不发这个工具；
- **跳过熔断**（F17）——一次运行里被跳过 2 次即自动停问；
- **`notification` 事件**——面板弹出时照常分发（种类是「等待澄清」），
  用户可以据此收通知，但**只能观测、不能拦截**。

把它接进 Hook 前置层是合理的后续项，但要挪那个分发点的位置，而那处位置有
「两头都不能挪」的理由注释钉着，属于独立评审的改动，**不在本扩展范围内**。

### 二、提问的形状

**F7 一次调用带 1–4 个问题，参数名对齐官方。**
顶层是 `questions` 数组，每项含 `question`（问题原文）、`header`（短标签）、
`options`（候选项数组）、`multiSelect`（是否多选）；每个候选项含 `label`（选项名）
与 `description`（选了会怎样）。

⚠ **对齐官方名字是刻意的**：模型对 `AskUserQuestion` 那套字段名有很强的先验，
用它见过的名字能降低「参数名写错 → 解析不出 → 白问一轮」的概率。代价是内部数据类的
字段要跟着改名（`summary` → `label`、`detail` → `description`），驱动设施同步。

⚠ **接口一次定成数组是刻意的**：定成单问题的话，将来扩成多问题是**破坏性变更**
（模型侧的调用格式变了，而那套格式还进了系统提示与示例）。

**F8 每题 2–4 个选项，界面另外无条件追加一项「其它…」。**
「其它…」**不是模型给的**，是界面补的（对齐官方明写的客户端责任）。
用户选它并打字后，**打的原文就是答案值**，不是「其它」两个字。

**F9 `header` 最多 12 个字符，缺省不显示徽章。**

**F10 模型给的形状有瑕疵时，一律「能救就救、救不了就说清楚」，绝不崩溃。**

| 情形 | 处理 |
| --- | --- |
| `questions` 不是数组，或一个可用问题都没有 | 整次调用失败，回灌「至少要有一个带候选项的问题」 |
| 问题多于 4 个 | **只呈现前 4 个**，并在回灌里明写「你提了 N 个，只呈现了前 4 个，其余未提问」 |
| 某个问题缺问题原文，或一个可用候选项都没有 | **跳过该问题**（不毁掉整次提问），回灌里说明跳了哪几个 |
| 某题候选项多于 4 个 | 只取前 4，回灌里说明 |
| 某题候选项恰好 1 个 | **放行**——加上「其它…」实际仍是两个可选项 |
| `header` 超长 | 截断并加省略号 |
| `multiSelect` 不是布尔 | 当作单选 |

⚠ **「截断 + 在回灌里说破」与 todo-list 那条「`MAX_ITEMS` 是拒绝线不是截断线」
方向相反，这是刻意的。** 那边截断有害，是因为模型以为整份清单写进去了、
后续判断全建立在一个假的进度上，而它**无从察觉**；这边模型拿回的答案是一份
按问题原文列出的清单，少了哪个问题**它看得见**，回灌里还会明说。
两处不同的判据只有一条：**被截掉的事实，模型下一轮能不能自己发现。**

**F11 多选：`multiSelect` 为真时用户可勾选任意多项（含零项）。**
答案以 `", "` 拼接回传（对齐官方）。零项与「按 Esc 跳过」**是两回事**：
前者是「一项都不要」，后者是「我不选，你定」，回灌文案必须能分辨。

**F12 答案回灌成一份给模型读的清单，逐题对应。**

形态（含四种答案类型各一例）：

```
用户的回答：
- 报告用什么格式？ → 摘要
- 要包含哪几节？ → 概述, 结论建议
- 配置文件放哪一层？ → 放到 docs/ 下面（用户自己输入的）
- 用什么命名风格？ → （用户没有选择，请按你的最佳判断继续）
```

有解析瑕疵时在末尾追加一行说明（见 F10）。

### 三、面板与交互

**F13 面板的呈现结构：徽章 + 问题 + 带序号的选项 + 说明 + 进度 + 提示行。**

```
─────────────────────────────────────────────────────
[配置位置]  新建的配置文件放在哪一层？
> 1. 项目级 .rhinecode/（推荐）
     跟着代码仓库走，团队共用
  2. 用户级 ~/.rhinecode/
     只对你自己生效，不进版本库
  3. 其它…（自己打字）
  ↑↓ 选 · 数字键直选 · 回车确认 · Esc 我不选，你自己定
```

- 徽章缺省时整个 `[…]` 不出现，退回现状那样直接是问题原文。
- **进度 `（问题 2/3）` 只在这次调用不止一个问题时出现**，单问题时一个字都不多。
- 选项说明仍然是紧随其后的一行、不可选、导航跳过、**不占序号**（沿用现状）。

**F14 一次调用里的多个问题串行呈现，面板不收。**
答完第一题，面板原地换成第二题的内容，直到问完才结算。

**F15 多选的勾选状态用行首的 `[x]` / `[ ]` 表达，回车逐项勾选并自动前进，末尾的
「提交」行回车交出去。**

```
─────────────────────────────────────────────────────
[要改哪些]  这次一起改哪几个地方？（可多选）
  1. [x] 工具说明书        模型决定要不要调它时读的
  2. [ ] 系统提示词        每轮都发给模型的那段
> 3. [x] 面板底部提示行    用户看的那行
  4.     其它…（自己打字）
  5.     提交（已选 2 项）
  回车勾选并跳到下一项 · 数字键直选 · 最后在「提交」行回车 · Esc 我不选
```

- **用 ASCII 而不是 `☑ ☐ ✓`，是为了不往界面符号白名单里加新符号**（那三个都落在
  扫描区间内，加一个就要同步 `CLAUDE.md` 那张表与 `tests/test_tui_symbols.py`）。
  这个「刻意」要有护栏钉着，免得后来的人当成将就顺手换成图形符号。
- **回车勾选后光标自动落到下一项**；勾完最后一个候选项时**跳过「其它…」直达
  「提交」**——落在「其它…」上再按回车会进自由输入态，而用户此刻想做的是交卷。
  要用「其它…」得自己按方向键过去。
- 多选下**数字键 = 切换该项勾选**（不是立即提交）。它与回车走**同一条**路径，
  因此两者不可能分叉。
- 已选条数显示在**「提交」那一行上**——它是用户正要按的那一行，不必挪视线去别处确认。
- **一项都不勾也能提交**（显示「提交（一项都不选）」），那是「这几个都不要」，
  与按 Esc 跳过（「你自己定」）是两回事。

> **修订（2026-08-18，用户要求，对齐 Claude Code）**
>
> 初版是「**空格**切换勾选、回车提交」，且没有「提交」行。改掉的理由是一个面板上
> 要用户同时记住两个键，而两个键的语义只差一点点。现在**只有回车**：
> 按在候选项上是勾选并前进，按在「提交」行上是交卷。
>
> ⚠ 连带一处结构变化：勾选逻辑从 `activate_choice`（只覆盖数字键）挪到了
> `action_select`（回车与数字键唯一的汇合点）。原位置会让两条路分叉，
> **而分叉在界面上看不出来**——用回车测一遍全对，用数字键测一遍也全对，
> 只有混着用才露馅。

**F16 「其它…」被选中后进入自由输入态：面板保留为提示态，打字在主输入框里。**

```
─────────────────────────────────────────────────────
[配置位置]  新建的配置文件放在哪一层？
  ⎿ 直接在下面打字，回车提交 · Esc 退回选项
─────────────────────────────────────────────────────
◈ ▏放到 docs/ 下面，跟文档一起管
```

状态机：

```
        ┌──────────────┐
   ┌───→│  选项列表态   │
   │    └──────┬───────┘
   │  选中「其它…」│
   │           ▼
   │    ┌──────────────┐
   └────┤  自由输入态   │
   Esc  └──────┬───────┘
       回车（非空）│
              ▼
        本题作答完毕 → 下一题 / 结算整次提问
```

逐条定死：

- **面板不收起**——「现在到底在干什么」必须一直看得见。收起来的话用户会以为提问
  已经结束（而回调其实还阻塞着），那正是本项目反复吃亏的「静默中间态」。
- 输入框在此期间**解除禁用并取得焦点**。
- **回车且内容为空 → 不结算**，停在自由输入态（与主输入框「空提交零副作用」同口径）。
- **自由输入态下的 `Esc` 只退回选项列表**，不结算整次提问。
- **这段文本不是一条新消息**：不进对话历史、不触发消息类 Hook、不开新回合。
- **自由输入态下不做斜杠命令解析与补全**——用户答案里的 `/` 是答案的一部分。
- 自由输入态下连按两次 `Ctrl+C` 仍然退出程序（既有行为，进程消亡带走阻塞的线程）。
  本条只要求「不新增例外」，不新增机制。

**F17 `Esc` 的语义按阶段分两种，并加一道「别再问了」的熔断。**

| 阶段 | Esc 的意思 | 行为 |
| --- | --- | --- |
| Plan Mode 规划阶段 | 我不想规划了 | **维持现状**：整轮循环停止 |
| 其余任何时候 | 我不选，你自己定 | 回灌一句话，**循环继续** |

非规划阶段的回灌必须包含两层意思：**① 按你的最佳判断继续，并在回答里说明你采用了
哪种做法；② 不要为同一件事再问一次。** 少了第 ② 层，模型下一轮会原样再问一遍
（与「用户在确认面板里选拒绝」那条软约束同型，那次实测过一个不听劝的模型把 25 轮
迭代全烧在重试上）。

**熔断**：同一次运行里用户跳过 **2** 次之后，后续的 `ask_user` **一律自动跳过、
不再弹面板**，并在界面上说明一次。连按两次 Esc 已经把「别问我」表达得很清楚了。

**F18 面板存在期间的输入框守卫要为自由输入态开一条岔路。**
现在只要有待决交互，输入框提交就一律被挡下并提示「请先在面板上做出选择」。
自由输入态必须放行到澄清结算路径。其余待决交互（确认 / 审批 / 选项列表态）行为不变。

### 四、触发口径

**F19 五层意思，三处文本同口径。** 三处是：

1. `ask_user` 的工具说明书（模型决定**要不要调它**时读）
2. 系统提示的任务模式那段（模型**每一轮**都读）
3. Plan Mode 的完整版提醒（模型**在规划阶段**读）

五层：

| # | 意思 | 要点 |
| --- | --- | --- |
| 1 | **该用**：卡住了，而这个决定本来就该用户拍板 | 三个来源都定不下来：他说的话、代码、常规默认做法 |
| 2 | **不该用（可数下限）**：一两次只读调用能查清的事实 | **写成可数的**——「一两次」是可匹配项，「能自行确认的」是抽象判断 |
| 3 | **不该用**：有约定俗成的默认做法、或跟着周围代码走就行的 | 自己定，在回答里说一句 |
| 4 | **不该用**：用户这轮已经说过的 | 翻回去看，不要重问 |
| 5 | **怎么用**：2–4 个都说得通的选项，每项一句「选了会怎样」，最推荐的排第一 | —— |

⚠ 第 2 层写成可数的，依据是已知项 #17 留下的线索：**模型对有具体可匹配项的指令
遵循得好，对抽象判断系统性偷懒。**

⚠ 三处**刻意不合并成一份共享常量**：受众时刻不同（决定要不要用 / 正在用 / 在规划），
篇幅语气该不一样。要一致的是那五层意思，不是字面。

⚠ Plan Mode 那段现在写着「**一次一个问题**」——F7 落地后这句话当场过期，必须同改。

**F20 工具说明书里必须有四正四负八个带判据的示例。**

依据是 todo-list 扩展 2026-08-18 的真机复测：三个静态规则杠杆加满，两个模型仍是
各 0 次调用；补上示例后 flash 从 0 次变成 4/4。**规则要模型做抽象判断，示例把它
降级成模式匹配。**

- **负例比正例更要紧**——只给正例是单向推力，正是已知项 #17 翻车的形态。
- 负例里**必须留一个贴着下限的临界情形**（听起来像该问、实际不该问的那种）。
  「用户已经明说了」这类模型本来就不会误判，放进去等于白占篇幅。
- ⚠ 这八个示例是本工具最可能被「顺手删掉省 token」的部分，要有护栏钉住。

### 五、接线（这些漏了都不报错）

**F21 驱动设施必须能无头驱动新面板，否则本扩展没有验收依据。**

- 澄清面板的应答取值从「单个序号」扩成三类：**单选序号 / 逗号分隔的多个序号 /
  自由输入文本**，格式判定与结算跟着改。
- **放开「澄清面板 + 模拟按键」**。原先禁它的理由（详情行让按键次数推不准）
  由面板已有的「序号 → 下标」映射解决——按键路径改用那张现成的映射，
  不再自己数行数。**多选必须能走按键路径**，那是它的核心交互。
- 结算值仍**与产品侧走同一份计算**（现状是刻意读 App 的私有属性，这个原则不变）。

**F22 行为记录要能看出「问了几个、怎么答的」，但不新增事件类型。**
仍然是一条交互事件，扩充负载：问题条数、每题是否多选、答案的类型
（选了选项 / 多选 / 自己输入 / 跳过）。新增的字段要同步进阅读器的摘要行，
否则等于白记。

**F23 界面登记三处，其中两处是「刻意不动」。**

- 交互种类不新增——仍是澄清那一种，Hook 的通知条件取值不变。**写下来是因为
  「新增了一种交互态」看起来就该登记一个新种类**，而那会破坏用户已按文档写好的条件。
- 界面符号白名单不新增（F15 用 ASCII）。这个「刻意」要有护栏。
- `CLAUDE.md` 要改三处：安全边界补 F6 的新论证、成对维护点新增两条
  （三处文本同口径 / 驱动设施的结算式子）、`/help` 类文档提到 Plan Mode 专属的地方。

**F24 `/skills` 报告里那句「Plan Mode 的规划阶段会另外附加 ask_user / present_plan」
要改。** 它现在会告诉用户一件不再为真的事。

## 非功能需求

- **N1 模型给什么形状都不能崩。** 参数缺字段、类型不对、数组套错层，
  一律走 F10 的宽松解析，界面与循环都不抛异常。
- **N2 不新增跨线程形态。** 面板仍走既有那条阻塞回调链；「登记待决盒 + 改状态行 +
  弹面板」仍在同一个主线程回合内完成（那是为消除「pending 但没有面板」的窗口
  刻意合成的一次，不许拆开）。自由输入态不引入第二条唤醒路径。
- **N3 Plan Mode 零回归。** 规划阶段的可用工具、`present_plan` 的可见性、
  Esc 停整轮、计划审批面板，四处逐字不变。
- **N4 一切模型给的自由文本必须转义**（问题、选项名、说明、徽章），
  且用本项目自己那版转义函数。勾选框的 `[` 同样要转义——落单的 `[` 会在布局阶段
  抛错并**拆掉整个应用**。
- **N5 不新增界面符号。**
- **N6 不新增底部布局层。** 面板仍占现在这一格。
- **N7 不引入第三方依赖。**
- **N8 不使用这个能力时，界面与现在逐字一致。**

## 不做的事

- **选项预览**（官方的 `preview` / `previewFormat`，给选项配 ASCII 或 HTML 小样）。
  终端里 HTML 无意义，ASCII 小样会把面板撑得很高，而底部已经四层了。
- **一屏并排显示多个问题**。只做串行（F14）。
- **用户主动召唤面板**（「我想让你问我几个问题」）。那是第二条入口，
  与 C15「共享清单不提供命令层写路径」同理。
- **把权限确认面板也统一成这套结构**。两者只是长得像：确认面板的选项是**固定四个**
  且带安全语义（会写规则、会落盘），澄清面板的选项是模型现编的。
- **跨会话记住用户的选择**。
- **子 Agent 里可用**（F2 是不变量，不是缺口）。
- **答案回传成结构化数据**。回灌的是给模型读的文本（F12）。
- **面板超时自动跳过**。面板可以无限等，与现状及官方一致
  （「The callback can stay pending indefinitely」）。
- **把 `ask_user` 搬进工具注册中心**（F6 已论证不搬）。

## 验收标准

### 覆盖面

- **AC1**（F1）不开 Plan Mode 的普通对话里，模型能看到 `ask_user` 的说明书；
  调用它会弹出澄清面板。
- **AC2**（F1）`present_plan` 在非规划阶段**看不到**——两个特殊工具的可见性判据
  确实分开了。
- **AC3**（F2）子 Agent 的那次运行里，`ask_user` 不在它的说明书中；
  即便硬造出一次调用，也不弹面板、循环继续。
- **AC4**（F3）无人值守轮里 `ask_user` 不在说明书中；硬造出一次调用时
  **面板一次都不弹**，回灌无人轮那条文案，循环继续。
- **AC5**（F4）三种「问不了人」的情形回灌**三条不同**的文案，且都不置「用户拒绝」、
  都不终止循环。
- **AC6**（F5）Skill 的 fork 子对话里调 `ask_user` 会正常弹面板。
- **AC6a**（F6/F6a）`ask_user` 不在工具注册中心里；调用它时**不产生**任何权限判定，
  也**不触发** `pre_tool_use`；而面板弹出时**照常**分发「等待澄清」通知事件。
  ⚠ 这条要断言的是**事实本身**（有没有发生），不是「结果对不对」——
  只断言「面板弹出来了」的话，「压根没判定」与「判定放行了」看不出区别。

### 提问的形状

- **AC7**（F7）一次带 3 个问题的调用会串行弹 3 次面板，答案一次性回灌。
- **AC8**（F8）每个问题的选项列表末尾都有一项「其它…」，且它不来自模型给的数据。
- **AC9**（F10）逐条覆盖那张瑕疵表：问题超 4、某题无候选项、候选项超 4、
  候选项恰好 1 个、徽章超长、多选字段类型不对——六种输入下都不抛异常，
  且被截掉的事实出现在回灌文本里。
- **AC10**（F11）多选题勾选两项后提交，回灌的答案是两个选项名用 `", "` 拼接；
  一项都不勾选提交，回灌的说法与「按 Esc 跳过」**不同**。
- **AC11**（F12）回灌文本逐题对应，四种答案类型（单选 / 多选 / 自己输入 / 跳过）
  都能在同一份回灌里正确呈现。

### 面板与交互

- **AC12**（F13）单问题时面板上**不出现**进度指示；多问题时出现且序号正确。
  徽章缺省时不出现空的 `[]`。
- **AC13**（F15）多选面板上勾选状态可见、回车能勾选并自动前进、勾完末项跳过
  「其它…」直达「提交」行、数字键切换而不是提交、单选题没有「提交」行、
  提示行显示已选条数。
- **AC14**（F16）选中「其它…」后：面板仍然可见、输入框可用且聚焦；
  空回车不结算；Esc 退回选项列表而不是取消整次提问；提交的文本不进对话历史。
- **AC15**（F17）规划阶段按 Esc 整轮停止；非规划阶段按 Esc 循环继续，
  且回灌文本同时包含「按最佳判断继续」与「不要再问同一件事」两层意思。
- **AC16**（F17）同一次运行里跳过 2 次之后，第 3 次调用**不弹面板**、自动跳过。
- **AC17**（F18）自由输入态下回车能提交；其余待决交互下回车仍被挡下并提示。

### 触发口径

- **AC18**（F19）五层意思逐个在三处文本里都出现；护栏自身钉住「五层」这个数量，
  缩表当场红。
- **AC19**（F19）三处文本**互不相同**（不许偷懒合并成一份常量）；
  Plan Mode 那段不再含「一次一个问题」。
- **AC20**（F20）工具说明书里正反示例各 4 个、每个都带判据，
  且负例里有一个贴着下限的临界情形。

### 接线

- **AC21**（F21）无头驱动能完成三条路径：单选序号应答、多选（走按键路径逐项回车、
  末尾在「提交」行回车）、
  自由输入文本应答。
- **AC22**（F22）记录里能看出这次问了几个问题、每题是否多选、答案是哪一类；
  这些字段出现在阅读器的摘要行里。
- **AC23**（F23）界面符号白名单**未新增任何一项**，且有护栏钉住这个「刻意」；
  Hook 的通知种类取值集合**未新增任何一项**。
- **AC23a**（F23/F24）文档里凡是说「`ask_user` 是 Plan Mode 专属」的地方全部改掉：
  `CLAUDE.md` 的安全边界（含 F6a 那条已知边界）、成对维护点两条新条目、
  `/skills` 报告里那句「规划阶段会另外附加 ask_user / present_plan」。
- **AC24**（N3）Plan Mode 既有行为的回归用例全绿。
- **AC25**（N8）不触发提问的普通运行里，界面输出与改动前逐字一致。

### 端到端

- **AC26** 一次普通（非 Plan Mode）任务里：模型提两个问题（一单选一多选），
  用户在第一题选序号、第二题勾两项，模型拿到答案后继续把活干完。
- **AC27** 同上场景，用户在第一题选「其它…」打了一段文字、第二题按 Esc 跳过，
  模型据此继续并在回答里说明了它自己定了什么。
- **AC28** 真实模型下的触发率观测（该问的问了没、不该问的问了没），
  记录进本扩展的验收记录，**不作为阻塞项**——依据是 todo-list 那轮实测，
  两个模型对同一份文本的反应可能分叉。

## 与 todo 原文的分歧

| 处 | todo 原文 | 本 spec | 理由 |
| --- | --- | --- | --- |
| 「Other」自由输入 | 倾向方案 A（收面板 → 回主输入框） | **A′：面板保留为提示态 + 主输入框** | A 会造出一个「面板没了但还在等答案」的静默中间态，用户会以为提问结束了 |
| 同口径的文本处数 | 「至少两处」 | **三处**（多一处 Plan Mode 提醒） | 那段现在写着「一次一个问题」，F7 落地后当场过期 |
| 触发口径的手段 | 两侧都写 + 可数下限 | **再加四正四负八个示例**（F20） | todo-list 2026-08-18 真机复测：三个静态规则杠杆加满仍是 0 次调用 |
| 无人值守轮 | 未提及 | **F3 / F4**，且是本次唯一会真的把产品搞坏的地方 | 实测发现澄清回调在无人轮里照传不误 |
| 面板取消（Esc） | 非规划阶段回灌并继续 | 同上，**外加跳过 2 次即熔断** | 只有软文案时，不听劝的模型会原样再问一遍 |
| 多选的勾选符号 | 「新符号要先进白名单」 | **不新增符号**，用转义后的 ASCII | 白名单那张表越短越有用；ASCII 在任何终端都不会退化 |
| 参数命名 | 未提及 | **对齐官方**（`questions` / `header` / `label` / `description` / `multiSelect`） | 模型对这套名字有强先验，降低「参数名写错白问一轮」 |
| 不过权限管线的理由 | 「要重新论证一次，并写进安全边界」 | 论证只剩**两条**成立，第三条（Hook 拦得住）**实测不成立**，改为登记 **F6a 已知边界** | 特殊工具的分流在 Hook 前置层**上游**，`pre_tool_use` 对它不触发。写成「拦得住」就是已知项 #18 那种错误的安全承诺 |
