# 澄清提问面板：从「Plan Mode 专属」到「随时可用」 Checklist

> 每一项都通过**运行代码或观察行为**来验证，聚焦系统行为而不是实现细节。
> 括号里是验证方式；`AC` 编号对应 [`spec.md`](spec.md) 的验收标准。
>
> ⚠ **本项目的三条验收纪律，本轮同样适用**：
> ① **先有证据再下结论**——先跑命令看输出，再报状态；
> ② **反证与正证同等重要**——「结果对」不等于「机制对」，凡是能靠巧合通过的判据
>    都要配一条反向用例；
> ③ **断言事实而不是结果**——例如熔断要断言「回调被调了几次」，
>    只断言「结果是跳过」的话，两种完全不同的机制看起来一模一样。

### 验收过程中发现的四个问题（都已处理）

**① AC24 的验证命令指向一个不存在的模块。** 写的是 `tests.test_plan_mode`，
仓库里没有这个文件（真实名字是 `test_auto_plan_integration`）。照着跑会拿到
一条 `ModuleNotFoundError`——**那不是「Plan Mode 没坏」的证据，是「没验」**。
已就地更正并留下说明。这正是「checklist 必须真的执行一遍」的价值：
它自己也会写错，而写错的地方只有跑一遍才现形。

**② AC6a 声称的第三条手段没有任何护栏。** `CLAUDE.md` 把
`notification` 事件列为 `ask_user` 唯三可用的手段之一，而「面板弹出时确实分发
了它」此前**一条测试都没有**。⚠ 真机验收里这条**测不出来**：那个工作区没有任何
hook 规则，记录里一条 hook 事件都没有，看起来像是没分发。已补
`test_clarify_dispatches_the_notification_hook` 直接盯分发动作本身。
不补的话它就是已知项 #18 那个形态——**文档承诺了一件实际可能不成立的事**。

**③ AC17 的反面此前零护栏，而且第一版护栏验错了东西。**
初版走 `core.send` 断言「打字没被当成结算」，看起来通过了——
但把产品的例外条件**整个去掉**之后它**照样全绿**：驱动器自己在 `send` 那一层
就拒绝了非空闲态的提交，判据实际验的是驱动器而不是产品。
重写成盯真正的保护机制（`InputBar.disabled` 那对开关：进自由输入态解禁、
退回时锁上），变异后当场红。
⚠ **记下这个形态**：一条通过的测试可以什么都没验到，而它看起来与真护栏一模一样。

**④ 新修的「其它…带上已勾的项」没有对应 AC。** 已补 AC14c。

### 已知未覆盖（不阻塞，理由逐条写明）

- **自由输入态与跳过熔断没有真实模型证据**。两者都有端到端与单元护栏，
  但真机那三次会话模型没走到这两条路。
- **`deepseek-v4-pro` 的触发率未测**。todo-list 那轮实测过两个模型会分叉
  （flash 4/4 而 pro 0/4），因此本轮结论**不能外推**。
- **AC17 在「确认面板」上的反面未覆盖**。澄清面板期间输入框是锁着的，
  确认面板期间不是（spec 背景第 ③ 条量到的差异），因此那条例外真要扩大时
  受害的是确认面板。要覆盖它得在本扩展的夹具里造一次确认面板，
  属于既有守卫（C11）的护栏缺口而非本扩展引入，**登记在此不顺手补**。
