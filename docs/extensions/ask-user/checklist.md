# 澄清提问面板：从「Plan Mode 专属」到「随时可用」 Checklist

> 每一项都通过**运行代码或观察行为**来验证，聚焦系统行为而不是实现细节。
> 括号里是验证方式；`AC` 编号对应 [`spec.md`](spec.md) 的验收标准。
>
> ⚠ **本项目的三条验收纪律，本轮同样适用**：
> ① **先有证据再下结论**——先跑命令看输出，再报状态；
> ② **反证与正证同等重要**——「结果对」不等于「机制对」，凡是能靠巧合通过的判据
>    都要配一条反向用例；
> ③ **断言事实而不是结果**——例如熔断要断言「回调被调了几次」，
>    只断言「结果是跳过」的话，两种完全不同的机制看起来一模一样。

## 一、覆盖面

- [ ] **（AC1）普通对话里模型看得到这个工具，调用它会弹面板。**
      不开 Plan Mode 起一个剧本宿主，让模型调一次 `ask_user`；
      （验证：`client status` 显示 `pending` 且面板类型是 `clarify`，
      面板原文里有问题文本）
- [ ] **（AC2）`present_plan` 在非规划阶段看不到。**
      （验证：读同一次运行的记录，非规划阶段那轮请求的工具名列表里
      **有** `ask_user`、**没有** `present_plan`；规划阶段那轮两个都有）
- [ ] **（AC3）子 Agent 的运行里没有这个工具。**
      （验证：委派一次，读记录里子 Agent 那轮请求的工具名列表——不含 `ask_user`；
      **反证**：同一份剧本让子 Agent 硬造一次 `ask_user` 调用，
      面板**零次**弹出、循环照常跑完）
- [ ] **（AC4）无人值守轮一个面板都不弹。**
      让队友消息自动唤起主对话，剧本在那一轮里硬造一次 `ask_user`；
      （验证：整段过程 `client status` **从未**出现 `pending`；
      回灌文本里说明了「用户不在场」；那一轮正常收工）
- [ ] **（AC5）三种「问不了人」回灌三条不同的文案，且都不终止循环。**
      （验证：三条文本两两不相等；三次运行的收尾原因都不是「用户取消」）
- [ ] **（AC6）Skill 的 fork 子对话里能正常提问。**
      （验证：跑一个会调 `ask_user` 的 fork Skill，面板照常弹出并可应答）
- [ ] **（AC6a）这个工具确实不进权限管线，也确实拿不到 Hook 拦截。**
      （验证：一次含 `ask_user` 的运行里，记录中**没有**针对它的权限判定事件、
      **没有**针对它的 `pre_tool_use`；但**有**一条「等待澄清」的通知事件。
      ⚠ 断言的是**有没有发生**，不是「结果对不对」——只看「面板弹出来了」的话，
      「压根没判定」与「判定放行了」看不出区别）

## 二、提问的形状

- [ ] **（AC7）一次带 3 个问题会串行弹 3 次，答案一次性回灌。**
      （验证：`client wait` → `answer` 三轮，中间两次应答后面板**仍然可见**；
      最终回灌文本里三个问题各占一行）
- [ ] **（AC8）每题末尾都有「其它…」，且它不来自模型给的数据。**
      （验证：面板快照的可选项数 = 模型给的选项数 + 1；
      **反证**：模型给的数据里没有任何一项叫「其它」）
- [ ] **（AC9）七种瑕疵输入都不抛异常，被截掉的事实出现在回灌里。**
      逐条覆盖：`questions` 非数组 / 无可用问题 / 问题超 4 / 某题缺原文 /
      某题无候选项 / 候选项超 4 / 候选项恰好 1 个。
      （验证：`python -m unittest tests.test_ask_user_parse -v` 全绿，
      且「问题超 4」那条断言回灌文本里出现了「只呈现了前 4 个」这层意思）
- [ ] **（AC10）多选勾两项与一项都不勾，回灌说法不同。**
      （验证：勾两项 → 回灌里是两个选项名用 `", "` 拼接；
      一项都不勾 → 回灌里是「一项都没选」这层意思，
      且**与按 Esc 跳过的说法不相等**）
- [ ] **（AC11）四种答案类型能在同一份回灌里正确共存。**
      （验证：构造一次四问的调用，分别用单选 / 多选 / 自由输入 / 跳过应答，
      回灌文本逐题对应且四种措辞各不相同）

## 三、面板与交互

- [ ] **（AC12）单问题不显示进度，无徽章不显示空括号。**
      （验证：面板快照的表头原文里**不含**「问题 1/1」；
      不传徽章时**不含** `[]`；**反证**：两问题时含「问题 1/2」、
      传了徽章时含该徽章文本）
- [ ] **（AC13）多选能勾、能看、数字键不误提交。**
      （验证：按 `enter` 后面板快照里该行出现勾选标记、光标前进一项、「提交」行显示「已选 1 项」；
      按数字键切换的是勾选而**不是**结算——面板仍然可见、`status` 仍是 `pending`）
- [ ] **（AC13b）勾选之后移动光标，勾选还在。**
      ⚠ 这条是 plan.md D6 那个「只改屏幕不改 `_choices`」bug 的专用护栏——
      **不移动光标的手测完全看不到它**。
      （验证：勾两项 → 按 `down` → 面板快照里两个勾选标记**仍在**）
- [ ] **（AC14）自由输入态的四条行为。**
      （验证：选中「其它…」后 ① 面板**仍然可见** ② 输入框可用且聚焦
      ③ 空回车**不结算**（`status` 仍是 `pending`）
      ④ `Esc` 退回选项列表而**不是**取消整次提问（面板重新出现选项））
- [ ] **（AC14b）自由输入提交的文本不进对话历史。**
      （验证：应答前后对比历史区，**没有**多出一条用户消息；
      回灌文本里是那段原文而不是「其它」两个字）
- [ ] **（AC15）Esc 在两个阶段行为不同。**
      （验证：规划阶段按 Esc → 本回合以「用户取消」收尾；
      非规划阶段按 Esc → 循环**继续**，回灌文本里同时含
      「按你的最佳判断继续」与「不要再问同一件事」两层意思。
      **反证**：这两条必须是两个方向的断言，缺一条就分不出「改对了」
      和「两边都改成了同一种」）
- [ ] **（AC16）跳过两次之后不再弹面板。**
      （验证：断言 clarify 回调的**调用次数**——前两次各一次，第三次**零次**。
      ⚠ 只断言「第三次的结果是跳过」的话，「熔断了」与「又弹了一次而用户又跳过」
      看不出区别）
- [ ] **（AC17）输入框守卫只为自由输入态开岔路。**
      （验证：自由输入态下回车能提交；确认面板 / 计划审批 / 选项列表态下回车
      **仍然**被挡下并给出提示）

## 七、端到端场景

- [ ] **（AC26）场景一：一单选 + 一多选，模型拿到答案后把活干完。**
      普通（非 Plan Mode）任务里模型提两个问题；用户第一题选序号、
      第二题勾两项。
      （预期：两次应答之间面板不收、焦点不跳；模型的后续动作与所选一致；
      本回合正常收工）
- [ ] **（AC27）场景二：一题自己打字 + 一题跳过。**
      同上场景，用户第一题选「其它…」打一段文字、第二题按 Esc。
      （预期：循环**继续**；模型在最终回答里说明了它自己定了什么；
      对话历史里没有多出用户消息）
- [ ] **（AC27b）场景三：中途跳过时面板确实收起来了。**
      三问的调用，用户在第 2 题按 Esc。
      （预期：面板**收起**、输入框**恢复可用**——
      这条专门盯 plan.md D3 那个 `keep_panel` 的边界，
      漏了 `and result is not None` 时界面会假死）
- [ ] **（AC26b）场景四：Plan Mode 全程照旧。**
      规划阶段提问 → 应答 → 提交计划 → 批准 → 执行。
      （预期：与改动前的行为逐字一致，包括规划阶段按 Esc 会停掉整轮）

## 八、真实模型观测（**不作为阻塞项**）

> ⚠ 依据是 todo-list 2026-08-18 那轮实测：**同一份文本，两个模型的反应会分叉**
> （flash 4/4 通过而 pro 0/4）。把触发率当验收闸门会卡在一个我们控制不了的地方。
> 因此这一节只**记录观测结果**，写进本目录的验收记录，不决定这次改动能不能合。

- [x] **该问的问了没。** 设计一个「有两三种都说得通的做法、猜错要返工」的任务，
      看模型是弹面板还是在正文里问 / 自己猜。（记录：调用次数、问题质量）
- [x] **不该问的问了没。** 设计一个「答案在代码里、一两次检索就能查到」的任务，
      看模型是去查还是弹面板。（记录：调用次数——**这一侧为 0 才是对的**）
- [x] **⚠ 两侧必须一起看。** 已知项 #17 那次翻车就是只盯着「该问没问」这一侧
      加推力，结果推到了另一个极端。任何一侧的改善都要拿另一侧的数字来验。
- [x] **多问题与多选真的被用起来了没。** 模型会不会一次只问一个、
      会不会该多选时用了单选。（记录：`multiSelect` 的实际出现次数）
- [x] 观测结果写进 `docs/extensions/ask-user/acceptance-live.md`，
      含每条判据的「机器判到了什么」与「据此做的判断」两栏。

**2026-08-18 实跑结果**（`deepseek-v4-flash`，三次干净会话，全程走按键路径）：
该问侧 2/3 触发（未触发那条是**场景设计不够硬**，模型识别出取舍点后按
「有默认做法的自己定」处理，符合 F20 下限）；不该问侧 **0/2**，
而 `ask_user` **6/6 轮送达**——是克制不是失灵。多问题 2 次都用上了，
`multiSelect` 出现 1 次。详见 `acceptance-live.md`。
