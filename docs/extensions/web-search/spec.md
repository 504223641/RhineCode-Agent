# 网络搜索工具（web_search）Spec

> 状态：**已批准**（2026-08-19，第 2 轮——plan 评审裁定「带括号写法不做加载期容错」后回填 F10 已知边界、F10a、AC10a 与安全边界第 8 条）
>
> 性质：**工具扩展，不占章节号**。它在既有的 C6 权限系统 + C16 分类器上加一个工具、
> 一种请求种类、一类分类器审查范围，不引入新的能力层级。文档收在
> `docs/extensions/web-search/`，见 [`docs/extensions/README.md`](../README.md)。
>
> 前置阅读：[`docs/extensions/web-fetch/spec.md`](../web-fetch/spec.md)（本扩展大量复用它建立的
> 机制与文案约定）、[`docs/c16/spec.md`](../../c16/spec.md)（分类器的边界与熔断口径）。

## 背景

`web_fetch` 已于 2026-07-29 落地，它解决的是「**上网取**」——给一个地址，把那页拿回来。

但模型不能「**上网找**」：

```
你：帮我查一下 httpx 的超时怎么配
模型：（没有 web_search）只能凭训练时的记忆猜一个地址，猜错就抓不到；
     或者反过来问你要链接
```

两个工具在实际使用里是**配合**的：搜索给**路标**，抓取才**取货**——搜索结果那几行标题
与摘要通常不足以回答问题。

### 为什么它不是「照着 web_fetch 再抄一个」

`web_fetch` 那一轮建立的东西本扩展**直接复用、一个字不改**：②′网络边界层的硬校验、
`<untrusted-content>` 标注与系统提示里那条固定约束、`web` 包的分层约定、
「离线替身 + 真实模型多轮」的验收形态。这是它比 web_fetch 轻的地方。

**但难点跟它完全不在同一处。** `web_fetch` 往外发的只有**地址**，而且受域名白名单约束
（spec F2「只取不发」）。`web_search` 往外发的是**用户的问题本身**，发给一家第三方
搜索服务商：

```
web_search("RhineCode PermissionEngine decide 方法 AttributeError policy_ruleset")
web_search("公司内部 xxx 系统 数据库连接超时 排查")
```

**项目名、内部系统名、代码里的标识符就这样进了那家公司的日志。**
「只取不发」这句话在本扩展里**不成立**——搜索的本质就是把查询词发出去。

这条外泄面是本扩展的核心安全议题，F5–F8 与「安全边界」第 1 条专门处理它。

### 与既有能力的关系

- **已知后续工程项 #5**「权限系统后续项」——本扩展**不兑现**其中任何一项
  （网络请求限制已由 web_fetch 兑现；资源配额指的是通用配额机制，而 F13 只是本工具
  自己的一道上限）。
- **已知后续工程项 #4**「OS 级沙箱」——不在范围内。`run_command` 跑起来的 `curl`
  仍可访问任意搜索 API，本扩展管不住（与 web_fetch 同一个缺口）。
- **C16 分类器**——本扩展新增它的**第四类**审查范围。这不是可选项，见 F9 的论证。

## 本扩展对既有代码的已知改造点

集中登记，避免 plan 阶段才发现。**每一条都是「漏改不报错」的形态**，因此全部列出：

1. **权限请求的「种类」新增取值**（搜索类）。它落在既有的「其它类」匹配分支上，
   因此**规则匹配层一行都不用改**（F10 论证）；但第④层权限模式兜底要为它加一格（F12）。
2. **「本会话 / 永久放行」的规则翻译新增一个分支**，且**确认面板要为它去掉「永久放行」选项**
   （F14——不去掉就是一个点了没用的按钮，与 ②″保护路径同型的已知缺陷形态）。
3. **C16 分类器新增第四种审查范围**。这是 `CLAUDE.md` 明确登记的成对维护点，
   四处齐改：分类器的范围常量、Agent Loop 的待判动作翻译、分类器提示词的待判动作段落、
   分类器界面文案的范围名表。**漏后三处不报错**，只表现为「声明了但从不被审查」。
4. **C16 的「宽泛放行规则丢弃」新增一类**（F16）——`allow: WebSearch` 要被丢掉。
   该判定当前只认命令类规则，入口要放宽。
5. **系统提示「外部不可信内容」模块的注入条件要改**（F19）：它当前挂在 `web_fetch` 的
   总开关上，关掉 web_fetch 而只开 web_search 时那条约束会凭空消失。
6. **配置新增一段**，含一个新的敏感字段（搜索服务密钥），行为记录的配置快照要跟着加掩码。
7. **Skill 的 `allowed-tools` 词汇表新增一项**，否则 Skill 无法为它预授权。
8. **装配层新增一个注入口**（搜索客户端工厂），且 `build_app` 的**第二个真实调用方**
   （端到端驱动宿主）要同步。

**Provider 范围**：本扩展及后续所有开发只针对 DeepSeek Provider（工具模式）。

## 目标

- 让模型能用一句自然语言搜到相关网页的**标题、地址与摘要**，并接着用 `web_fetch` 取其中一条。
- **明确承认并处置「搜索词外泄」这条新的外泄面**——它是本扩展与 web_fetch 最本质的差别。
- 给这个按次计费的能力一道**会话级上限**，使一个跑飞的 Agent Loop 烧不掉一个月额度。
- 把搜索结果当作**不可信输入**，且认识到它的注入面在**标题与摘要**里（SEO 投毒），
  比网页正文更容易被模型直接采信。
- 保证该能力可被整体关闭，关闭后系统行为与本扩展之前逐字一致。

## 功能需求

### 一、工具形态与接口

- **F1**：新增一个搜索工具。输入两项：**查询词**（必填，自然语言）与**结果条数**
  （可选，缺省 5，夹取到 1–10；越界只夹取、不报错）。输出是若干条结果，
  每条含**标题 / 地址 / 摘要**三项。

- **F2**：**参数只有这两项。** 不支持自定义请求头、请求体、cookie、结果语言 / 地区 /
  时间范围等任何其它入口。传入多余参数不产生任何效果。

  ⚠ **但不得把这条写成「只取不发」**——`web_fetch` 那句话在本扩展里是错的。
  这里限制的是「除查询词之外还能往外发什么」，而**查询词本身就是发出去的数据**，
  且不受任何白名单约束。文案上必须区分这两件事（见 F5）。

- **F3**：工具声明为**有副作用**（非只读）。

  **这不是风格选择，是硬约束。** 权限引擎里有一条捷径：只读工具在第③层未命中时
  **直接放行、根本不进第④层**。而 C16 分类器的触发条件是「结论来自第④层」——
  把本工具声明为只读，等于让**分类器对它完全失效，而且没有任何声音**
  （配置上看不出、界面上看不出、测试里也看不出，因为结果确实是放行）。

  **已知后果，写在此处让审批者看见**：非只读工具在 Plan Mode 规划阶段**不可见**，
  因此模型在「规划」阶段搜不了网，只能在计划获批进入执行阶段后再搜。
  这与 `web_fetch` 的 F3 是同一个取舍，本扩展接受它。

- **F4**：该能力可被**整体关闭**（配置里的一个开关，缺省**启用**）。关闭时：工具不注册、
  不出现在工具清单里、搜索类的分类器审查不发生、`allow: WebSearch` 不被丢弃、
  搜索相关的启动提示不产生。关闭后系统行为与本扩展之前**逐字一致**。

- **F5**：**工具描述里必须写明查询词会原样发给第三方搜索服务商**，并要求模型避免把
  内部项目名、内部系统名、私有代码标识符、密钥、以及完整代码片段放进查询词。

  这条约束**刻意放在工具描述里而不是系统提示的固定模块里**：它只在使用这个工具时有意义，
  而系统提示的固定模块是全局约束、走稳定可缓存通道，为一个工具的使用建议占那条通道
  不划算。（对比 F19 的不可信标注约束——那条确实是全局的，因为被标注的内容会一直留在历史里。）

### 二、查询词的外泄面

- **F6**：**这条外泄面必须被明确承认并写进「安全边界」**，而不是靠一句提示词带过。
  三道对冲，缺一不可，且必须承认它们各自的局限：

  | 对冲手段 | 挡得住什么 | 挡不住什么 |
  |---|---|---|
  | F5 的工具描述约束 | 模型「顺手」把内部标识符写进查询 | 模型不听（提示词是引导不是边界） |
  | F9 的分类器审查 | 模型有意或无意把敏感内容外发 | 分类器会误判（官方公布拦截率 89%） |
  | F7 的完整展示 | 用户回看时能发现发出去了什么 | 用户不看 |

- **F7**：**查询词在界面上完整展示、不截断**——确认面板与工具活动行两处。

  「不截断」是安全要求，与 `web_fetch` 的 F9 同一条理由：用户正是靠面板上那段文字
  来决定放不放行的，被截断意味着攻击者只要把敏感部分放在可见范围之后，
  人在回路这一层就形同虚设。

- **F8**：**不做代码层的关键词过滤。**

  「查询词里出现项目名就拦下来」这类规则**明确不做**，理由有二：① 判定不了什么是
  「内部标识符」——`PermissionEngine` 是本项目的类名，也是一个通用英文词组，
  按名单过滤要么漏光、要么把正常查询全拦下；② **更糟的是它给人虚假的安全感**，
  用户会以为「配了过滤就安全了」，而真正的判断能力在 F9 的分类器那里。

### 三、权限管线中的位置

- **F9**：**本工具进 C16 分类器，作为第四种审查范围（搜索类）。**

  ⚠ **不能复用网络类那一支。** 网络类的待判内容取的是调用参数里的**地址**，
  而搜索的参数是**查询词**。照抄那一支会让分类器拿到一个**空的待判内容**，
  然后因为「看不出有什么问题」而放行——**完全无声**。
  （`send_message` 的参数名那次踩过同一个坑：待判内容取错字段，判定毫无意义，
  而没有任何东西报错。）

  分类器看到的是**完整查询词**，它的职责正是回答「这条查询里有没有不该发出去的东西」
  ——那是代码判不了、只有语义判断才做得到的事，也是 F8 不做代码过滤的正当理由。

- **F9a**：**搜索类不参与分类器的判定缓存。** 网络类按「主机名 + 端口」缓存，
  是因为同一个主机会被反复访问；而查询词几乎每次都不同，缓存命中率接近零，
  一旦命中反倒意味着两条不同的查询共享了同一个结论。

- **F10**：**权限规则只支持整工具形式**（`allow: WebSearch` / `deny: WebSearch`），
  **不支持任何带括号的写法**。

  论证：域名规则（`WebFetch(domain:...)`）限制的是「模型能访问哪个主机」，
  而搜索请求打的是**配置里写死的固定端点**，不是模型指定的地址——没有可限制的对象。
  至于「限制结果里能出现哪些域名」，那是过滤展示而不是访问控制：真正的访问控制
  发生在模型拿着结果去 `web_fetch` 的那一刻（见 F20）。

  实现上这条**零成本**：搜索类请求落在既有的「其它类」匹配分支上，
  该分支的既有语义正是「只有空模式的整工具规则才命中」。规则匹配层一行都不用改。

  ⚠ **已知边界（plan 评审 2026-08-19 明确决定不处理）**：既然带括号的写法一律不命中，
  那么 **`deny: WebSearch(*)` 也一律不命中**——一个想拦住搜索的用户写下这条规则后，
  **什么都没拦住，而且没有任何提示**。

  `web_fetch` 对同型问题做过加载期容错（它的 F13：写坏的 allow 丢弃、写坏的 deny
  降级为整工具拒绝，两支都出警告）。本扩展**明确不做**，代价即上述静默失效。
  唯一的缓解手段是 F10a 的文档化：**权限配置模板里必须写明搜索只支持整工具形式**，
  并给出 `deny: WebSearch` 这一种正确写法。

  ⚠ 这一条属于本项目已知项 #18 反复警告的形态（「文档承诺可以 deny，实际不能」），
  区别在于这里是**明知而接受**、且已在 spec 与配置模板两处写下，不是一句错误的承诺。

- **F10a**：**权限配置模板里必须写明搜索规则的正确写法与那条限制。**
  内容至少三层：只支持 `WebSearch` / `deny: WebSearch` 这种**不带括号**的整工具形式；
  带括号的任何写法**一律不生效且不会有警告**；想彻底关掉请改用配置里的总开关。

  这不是文档美化，它是 F10 那条已知边界的**唯一**缓解措施——写规则的人只会看那个模板。

- **F11**：**①危险命令黑名单、②路径沙箱、②′网络边界层、②″保护路径对本工具均不生效**，
  这是既有代码的结构性结果而非新增豁免：①只对命令类、②只对路径类、②′只对网络类（地址）、
  ②″只对写路径类，四者都按请求种类早退。本扩展**不为搜索类新增任何一层**。

  ⚠ **搜索 API 的 HTTP 请求刻意不过②′层的硬校验**（协议限制除外，见 F17）。
  ②′拦的是「模型自己指定的地址」；搜索端点由**用户在配置里写死**，与 MCP Server 的
  地址同性质。让它过②′的后果是**用户配一个内网搜索代理就用不了**——而那是个合理需求。

- **F12**：**权限模式对搜索类的兜底行为，与网络类同格**：

  | 权限模式 | 对其它副作用工具 | 对搜索类 |
  |---|---|---|
  | 严格 | 拒绝 | 拒绝（相同） |
  | 默认 | 交人工确认 | 交人工确认（相同） |
  | **放行** | **放行** | **交人工确认**（例外，与网络类同） |

  然后由 F9 的分类器把这个「交人工确认」覆写成放行或拒绝。净效果是：
  **日常搜索零打扰，而分类器在中间真的看了一眼。**

  ⚠ **为什么基线必须是「交人工确认」而不是「放行」**：这决定了分类器熔断
  （连不上、或连续拦截被停用）之后退回到哪里。基线是 ASK 则退回**逐次弹面板**，
  基线是 ALLOW 则退回**一律放行**——后者意味着「查询词外泄」这条防线在故障时
  完全消失，而用户只看到一条熔断提示。N1 的 fail-safe 要求偏严的那一侧。

- **F13**：**会话级搜索次数上限**，缺省 **50 次**，可配置（配 0 或负数 = 不限制）。

  达到上限后**不报错**，而是返回一条明确的说明：本次会话的搜索次数已用完、这不会恢复、
  请用已经拿到的信息继续、不要重试。**返回错误会诱导模型重试**，而重试一个永远不会成功
  的调用只会把剩下的迭代轮次全部烧光。

  计数规则：**只有真的向服务商发出了请求才计数。** 未配置密钥、配额已耗尽、被分类器拦下、
  被权限规则拒绝——这四种情形都没有发出请求，一律不计。（配额是一道**花钱**的护栏，
  没花钱就不该扣。）

  计数在**主对话与全部子 Agent 之间共享**（额度是钱，不是每条对话各一份），
  因此计数器必须线程安全。`/clear` 时复位——那正是「新一次会话」的既有语义所在。

- **F14**：**搜索类的确认面板不提供「永久放行」选项**（只有：本次 / 本会话 / 拒绝）。

  ⚠ **这条不直觉，但它是前面几条决定的必然结果，且不做就是一个已知形态的缺陷。**
  推导链：

  1. 搜索类唯一可写的规则形状是整工具的 `allow: WebSearch`（F10）；
  2. 「永久放行」把规则写进**本地级配置文件**，下次启动时它属于文件规则集；
  3. 而 F16 要求分类器启用时从**文件规则集**里丢掉 `allow: WebSearch`；
  4. 于是：用户点了「永久放行」，下次启动那条规则被丢掉，**面板照弹**。

  这与 ②″保护路径那条「骗人的按钮」是**同一个形态**：一个明确的用户决定看起来失效了，
  而界面上没有任何线索说明为什么。既有代码已有现成的处置手法（该场景下不渲染那个选项），
  照抄即可。

  「本会话放行」**不受影响、照常提供**——它登记的是会话级规则，F16 只动文件规则集。

- **F15**：`deny: WebSearch`（⚠ **必须不带括号**，见 F10）**永远生效、永不被丢弃**，
  且压得过分类器（③排在④之前）。这是「我不想让它上网搜」的两种可靠写法之一
  （另一种是 F4 的总开关），也是本扩展里唯一一条不受任何条件影响的规则。

- **F16**：**分类器启用时，从文件规则集里丢弃 `allow: WebSearch` 并逐条告知用户。**

  理由与 C16 F20 对命令类的处置一致：用户写的 allow 会**直接短路**分类器
  （连模型调用都不会发生），一条整工具放行等于对搜索这一类关掉整层审查。

  ⚠ **必须逐条说明是哪一条、为什么、以及用户有哪两个选择**（改用 `deny` 收紧，
  或在配置里关掉分类器让这条规则恢复生效）。静默丢弃会让「我明明配了为什么还弹」无从查起。

  ⚠ **这里有一个闭环要写清楚**：关掉分类器 → 不再丢弃 → `allow: WebSearch` 恢复生效
  → 搜索直接放行。这是自洽的，不是漏洞：用户关掉了那个把关人，就该由他自己写的规则说了算。

### 四、请求、结果与降级

- **F17**：**搜索端点由配置指定**，缺省用所选服务商的官方地址。端点必须是 `http` / `https`
  之一（其余协议一律拒绝，与②′的协议限制同口径）；端点不是 `https` 时**启动提示一条警告**
  但不阻断——查询词是明文外发的数据，走明文通道值得说一句，而内网代理用 `http` 是合法场景。

- **F18**：**结果形态**。每条结果三项：标题、地址、摘要。整份结果**不再经过一次抽取模型**
  ——搜索结果本来就短，多一次模型往返只是多一条失败路径、多一次计费、多一处可被注入的地方
  （对比 `web_fetch` 的 F15：那里抽取是必须的，因为一整页正文塞不进上下文）。

- **F19**：**结果一律包裹在「外部不可信内容」标记中**，并带出来源（服务商 + 原始查询词）。

  ⚠ **注入面在标题与摘要里，不在正文里。** 攻击者可以做 SEO 投毒，让一个精心构造的标题
  排到前面；而标题 / 摘要比网页正文**更容易被模型直接采信**——它看起来像「系统给我的检索结果」，
  而不是「某个网页里的一段话」。因此标注不可省，且**元信息（服务商、条数、配额用量）必须在
  标记之外**，与 `web_fetch` 的渲染约定一致：元信息由我们的代码生成、可信，结果来自外部、不可信。

  ⚠ **系统提示里那条固定约束的注入条件必须改**：它当前挂在 `web_fetch` 的总开关上，
  关掉 web_fetch 而只开 web_search 时会凭空消失——两个工具任一启用即注入。

- **F20**：**搜索结果里的地址被 `web_fetch` 时，照常走完整的域名策略与②′硬校验。**
  搜索**不给任何地址开后门**，也不做任何预先过滤或可访问性标注（那需要搜索模块去读权限规则，
  把两个本来互不相识的模块绑在一起，而且标注可能与真实判定不一致）。
  这是本扩展与 `web_fetch` 的衔接点，**必须有护栏钉住**。

- **F21**：**四类情形各有自己的文案，且必须能被模型区分**——文案要直接回答「我该怎么办」：

  | 情形 | 模型该怎么办 | 是否计入配额 |
  |---|---|---|
  | 未配置搜索密钥 | **不要重试**，告诉用户去配置文件里填 | 否 |
  | 配额已用完（F13） | **不要重试**，用已有信息继续 | 否（已用完） |
  | 服务不可用 / 超时 / 返回无法解析 | 可以换个说法**重试一次**；连续失败则告诉用户检查网络与配置 | 否 |
  | 搜到 0 条结果 | 换个说法或换个关键词重试 | **是**（请求真的发出去了） |

  前三条与第四条的区别是「有没有真的问出去」，这也决定了成功标志：

  | 情形 | 成功标志 | 理由 |
  |---|---|---|
  | 搜到结果（含 0 条） | **真** | 如实回报了这次能给的全部信息 |
  | 未配置密钥 / 配额用完 / 服务失败 | **假** | 这次确实什么都没拿到 |

  这张表照抄 `web_fetch` 验收期修掉的那个真实缺陷：成功标志若不反映「有没有拿到内容」，
  **界面会把一次失败显示成绿色成功**，而正文里写着失败——界面在撒谎，模型也拿不到信号。

- **F22**：**单次搜索有超时上限**，超时按「服务不可用」处理（F21 第三行）。
  上限要在实现时算出具体秒数写进注释。

- **F23**：结果中要能读出：原始查询词、服务商、返回条数、本次会话已用 / 上限。

### 五、集成与可观测

- **F24**：新增的判定与调用必须在既有行为记录（trace）里可见：一次被分类器拦下的搜索
  要能读出查询词、判定范围与拒绝原因；一次真实搜索要能读出查询词与结果条数。
  **本扩展不新增记录作用域**——搜索是一次 HTTP 调用而非模型调用，走既有的工具执行记录即可。

- **F25**：**搜索服务密钥进行为记录的配置快照掩码白名单**。既有快照是白名单式逐字段取值，
  新增字段默认不记录，因此「不记录」是天然安全的；但**显式记录一个掩码值更有用**
  ——排查时「有没有配 key」是第一个要问的问题。

- **F26**：**Skill 的 `allowed-tools` 词汇表需登记本工具**，使 Skill 能为它预授权，
  且不产生「无对应工具类别」警告。按 F10，只有整工具形式合法。

- **F27**：**启用但未配置密钥时，启动阶段给一条可见提示**（说清是哪个配置项、填在哪）。
  这不替代 F21 的调用期文案，两者服务不同的人：启动提示给用户，调用期文案给模型。

- **F28**：**搜索的网络调用必须提供可注入的替身入口**，且一路透传到装配层，
  使端到端场景能离线跑。装配层的**两个真实调用方**都要同步。

## 非功能需求

- **N1 — Fail-safe（安全优先）**：任何不确定或出错的情形都必须偏向更严。
  权限基线取「交人工确认」而非「放行」（F12）；分类器判定失败按拒绝处理（沿用 C16）；
  配置里的安全开关写错抛错而非静默回退（与既有同类字段同口径）。

- **N2 — 权限由代码强制，不依赖模型**：模型输出、系统提示、RHINE.md、Skill 正文、
  以及**搜索结果本身**都无法改变一次搜索的放行 / 拒绝结论。

  ⚠ **本条有一处刻意的例外，与 C16 同源**：第④层那一格的结论由分类器（一个模型）给出。
  该例外的三道对冲沿用 C16——只喂用户消息与工具调用、结论只在④层生效、失败一律拒绝。

- **N3 — 轻量**：不引入新的启动期开销；未使用该工具时不发起任何网络连接。

- **N4 — 叶子性**：搜索的实现模块**不依赖** `permission` / `agent` / `conversation` / `tui`。
  它不需要知道权限规则（F20 明确不做可访问性标注），因此这条是结构性成立的，不靠约定。

- **N5 — 可测试性**：全部单元测试**不真连网、不真调模型**。搜索客户端必须可注入替身，
  且该入口一路透传到装配层，使端到端场景也能离线跑。
  这条同时是安全要求——测试套件不应因为跑测试而向外发出请求，**尤其是发出查询词**。

- **N6 — 兼容性与非破坏**：仅在 `protocol: deepseek` 且启用默认工具注册中心时生效。
  不破坏 C6 既有各层判定、C16 分类器对既有三类的行为、`web_fetch` 的任何行为。
  **能力关闭时（F4）系统行为与本扩展之前逐字一致。**

- **N7 — 跨平台正确性**：Windows 与类 Unix 下行为一致。

- **N8 — 中文注释规范**：遵循项目 `CLAUDE.md` 的中文注释规范。

## 安全边界

1. **查询词是一条新的外泄面，且它比 `web_fetch` 的地址通道宽得多。**

   `web_fetch` 的「只取不发」把模型能主动往外发的数据压缩到「地址及其查询参数」，
   而且那个地址受域名白名单约束。`web_search` **没有等价的约束**：查询词是自由文本，
   发给一家固定的第三方，没有白名单可言（限制「能搜什么」在语义上不成立）。

   真实形态不需要攻击者参与——模型在排查一个报错时，很自然就会把项目内部的类名、
   模块名、报错原文拼进查询词。**这不是滥用，这是正常使用。**

   处置是 F6 的三道对冲，而必须承认的是：**三道全部依赖判断，没有一道是硬边界。**
   唯一的硬边界是 `deny: WebSearch`（F15）——即「不用这个能力」。

2. **它把 `web_fetch` 那条外泄链路的出口拓宽了。** web_fetch 的安全边界第 1 条描述过
   「读文件 + 访问网络」凑齐后的外泄链路（页面里藏指令 → 骗模型读配置 → 把内容拼进
   下一次抓取的查询参数）。本扩展给这条链多了一个**更方便**的出口：拼进查询词比拼进
   URL 查询参数更自然、更不容易被人一眼看出异常。F7 的完整展示与 F9 的分类器是对冲手段。

3. **搜索结果的注入面在标题与摘要里**，见 F19。与网页正文相比，它更短、更像「系统给的
   检索结果」、更容易被模型直接采信，而 SEO 投毒的成本远低于攻陷一个具体网站。

4. **搜索服务商看得到全部查询词**，且本扩展不提供任何匿名化手段。选择服务商即选择了
   把这些数据交给谁。这一点应在配置模板里对用户说明。

5. **域名策略与本工具无关。** 用户写的 `allow: WebFetch(domain:github.com)` 不影响搜索
   能搜到什么（F20），它只影响模型能抓取哪些结果。**别把「建了白名单」误读成
   「模型只能看到白名单内的东西」。**

6. **`run_command` 与 MCP 工具仍可绕过。** 一句 `curl 'https://api.search.example/?q=...'`
   不受本扩展任何约束——与 web_fetch 的已知边界同源（已知项 #4）。web_fetch 的验收记录
   第七节有一次**未经诱导、模型自主选择**的同型绕过实例。

7. **搜索密钥是又一个敏感配置字段**，与 API Key 同级：勿提交、勿外传（F25 只保证配置快照）。

8. ⚠ **「关掉搜索」只有两种写法有效，第三种看起来有效但没有。**

   | 写法 | 有效吗 |
   |---|---|
   | 配置里 `search.enabled: false`（F4） | ✅ 工具根本不注册 |
   | `deny: WebSearch`（**不带括号**，F15） | ✅ 第③层拦下，分类器也翻不过 |
   | `deny: WebSearch(*)` 或任何带括号写法 | ❌ **一律不命中，且没有任何警告**（F10 已知边界） |

   第三行是评审时明知而接受的取舍（不做加载期容错），缓解手段只有 F10a 的配置模板说明。
   **写权限规则的人只会看那个模板，所以那段说明是这条边界的唯一防线。**

## 不做的事

- **搜索结果的可访问性过滤或标注**（F20 已论证）。
- **带括号的搜索规则语法**（`WebSearch(domain:...)` / `WebSearch(query:...)`，F10 已论证）。
- **带括号写法的加载期容错**——即 `web_fetch` F13 那套「allow 丢弃 / deny 降级 + 警告」。
  **plan 评审 2026-08-19 明确决定不采纳。** 代价是 `deny: WebSearch(*)` 静默无效，
  已作为已知边界记在 F10 里，缓解手段是 F10a 的配置模板说明。
  ⚠ 日后若要补上，请连同 F10 的那段已知边界与 AC10 的反证一起改——
  **AC10 现在正面断言「不产生任何警告」**，补警告会让它红，那是刻意的提醒机制。
- **代码层的查询词关键词过滤 / 脱敏**（F8 已论证）。
- **搜索结果的二次抽取 / 摘要**（F18 已论证）。
- **多服务商同时启用或自动故障切换**——一次只用一家（配置里选哪家就是哪家）。

  ⚠ **勘误（2026-08-20）**：原文还写着「**只实现一家**」，理由是「没有第二个真实
  实现来检验的抽象，很容易设计成只适配想象」。落地当天就接了**第二家**（博查），
  原因是本机网络连不通 Brave。**那句理由本身应验了**：接缝假设了所有搜索 API 都是
  「GET + query 参数」，而博查是「POST + JSON body + Bearer 头」——补 `method` 与
  `auth_prefix` 两个字段即可，结构没被推翻。

  「一次只用一家」这条**仍然成立**：不做同时启用、不做自动故障切换。
- **搜索结果缓存**——每次调用都是一次真实请求（与 `web_fetch` 同）。
- **翻页 / 更多结果**——只取第一页。
- **图片、新闻、学术等垂直搜索**——只做通用网页搜索。
- **结果语言、地区、时间范围等检索参数**（F2）。
- **按调用方（主对话 / 各子 Agent）分别计配额**——F13 明确共享一份。
- **配额的持久化**——只在本次运行内计数，重启即清零。持久化要引入一份状态文件，
  而它本身又是一份「能改变以后会发生什么」的东西。
- **代理配置**——不做 HTTP 代理 / SOCKS 配置项（与 `web_fetch` 同；端点可配已覆盖内网代理场景）。
- **OS 级网络隔离**——同已知后续项 #4。
- **扩展到其它 Provider。**

## 验收标准

### 工具形态

- **AC1**（F1）— 给定一个查询词，工具返回若干条含标题、地址、摘要的结果；
  指定条数时返回条数不超过该值；条数越界（0 或 99）时被夹取到 1–10 而不报错。
- **AC2**（F2）— 参数集合中不存在请求头、请求体、语言 / 地区 / 时间范围任何入口；
  **传入多余参数不产生任何效果**。
- **AC3**（F3）— 该工具在 Plan Mode 规划阶段不出现在可见工具集里；
  且它**确实会进入第④层判定**（反证：把它当作只读工具时分类器一次都不会被调用）。
- **AC4**（F4）— 关闭后：工具不在清单中、系统提示逐字等于关闭前（**前提是 web_fetch 也关闭**）、
  `allow: WebSearch` 不被丢弃、不产生任何搜索相关的启动提示。
- **AC5**（F5）— 工具描述中包含「查询词会发给第三方」与「不要放入内部标识符 / 密钥」两层意思。

### 外泄面与展示

- **AC5a**（F6）— 本 spec 的「安全边界」第 1 条明确承认查询词外泄，并逐条列出三道对冲
  各自挡得住什么、挡不住什么；`CLAUDE.md` 的「安全边界」一节有对应条目。
- **AC6**（F7）— 一条超长查询词在确认面板与工具活动行上**完整可见、未被截断**。
- **AC7**（F8）— 代码中不存在任何按关键词过滤 / 改写查询词的逻辑（反证：
  一条含项目名的查询词被原样发给替身服务商）。

### 权限与分类器

- **AC8**（F9）— 一次搜索调用触发分类器审查，且分类器收到的待判内容**是完整查询词**
  （反证：查询词非空时待判内容必然非空——这条专门钉住「取错参数名导致空内容然后放行」
  那个无声缺陷，用工具真实声明的参数表逐项比对）。
- **AC9**（F9a）— 连续两次不同查询词各触发一次真实判定；**同一查询词第二次仍触发判定**（不缓存）。
- **AC10**（F10）— `deny: WebSearch` 拦得住搜索；`allow: WebSearch` 在分类器关闭时放行；
  **`allow: WebSearch(anything)` 与 `deny: WebSearch(anything)` 都不命中任何调用**，
  且**不产生任何警告**——后半句是对「已知边界」的正面钉住，防止有人日后
  「顺手补一个警告」而没有走一遍这条边界的评审。
- **AC10a**（F10a）— 首次运行生成的权限配置模板中，含搜索规则的写法说明：
  正确写法（不带括号）、带括号一律不生效且无警告、以及总开关这条退路。
- **AC11**（F11）— 四条并列：搜索请求不进危险命令黑名单、不进路径沙箱、不进网络边界层、
  不进保护路径收紧器（构造一条查询词形如 `rm -rf /` 与一条形如 `../../etc/passwd`，
  均不被这些层拦下，而是照常走到第④层）。
- **AC12**（F12）— 无任何规则命中时，同一次搜索在三档模式下分别为：
  严格→拒绝、默认→确认、**放行→仍然确认**；同一放行档下一次写文件调用仍被直接放行。
- **AC13**（F12）— 分类器判放行时，第④层的「确认」被覆写为放行，**确认面板一次都不弹**；
  分类器判拦截时被拒绝，且回灌模型的是固定文案而非分类器写的理由。
- **AC14**（F12）— 分类器熔断后，搜索**退回逐次弹确认面板**（而不是一律放行），
  且熔断提示明确区分「它认为这条有问题」与「它连不上」两种成因。
- **AC15**（F14）— 搜索类的确认面板只有三个选项，**不含「永久放行」**；
  「本会话放行」照常提供，且选择后同一会话内不再弹。
- **AC16**（F15）— `deny: WebSearch` 在分类器启用时**不被丢弃**，且分类器判放行也翻不过它。
- **AC17**（F16）— 分类器启用时 `allow: WebSearch` 被丢弃，启动时逐条说明是哪一条、
  为什么、以及两个选择；**关掉分类器后该规则恢复生效**（闭环反证）。

### 配额与降级

- **AC18**（F13）— 达到上限后，工具返回「用已有信息继续」而**不是错误**，文案明确要求不要重试；
  上限可配置；配 0 时不限制。
- **AC19**（F13）— 四种不发出请求的情形（无密钥 / 已耗尽 / 被分类器拦 / 被规则拒）**均不计数**。
- **AC20**（F13）— 主对话与子 Agent 共享同一份计数；多线程并发调用时计数不丢失。
- **AC21**（F13）— `/clear` 后计数复位。
- **AC22**（F21）— 四类情形的文案各不相同、各自指向正确的下一步动作；
  成功标志按 F21 那张表取值（**0 条结果为真**，其余三类为假）。
- **AC23**（F17/F22）— 端点非 https 时启动警告一条但不阻断；端点为非 http/https 协议时被拒绝；
  超时按「服务不可用」处理并说明原因。

### 结果与不可信

- **AC24**（F18）— 一次搜索只发生一次对外请求，**不发生任何模型请求**（抽取未被引入）。
- **AC25**（F19）— 结果被包裹在不可信标记中并带出服务商与原始查询词；
  元信息（服务商、条数、配额用量）位于标记**之外**。
- **AC26**（F19）— **关掉 `web_fetch` 但开着 `web_search` 时，系统提示中那条
  「外部不可信内容」约束仍然存在**（这条专门钉住注入条件漏改）。
- **AC27**（F19·端到端）— 搜索结果的**标题或摘要**中含伪装成系统指令的文本时，
  模型不执行该指令，而是把它作为检索结果陈述出来。
- **AC28**（F20）— 搜索结果里的一个地址被 `web_fetch` 时，仍完整走一遍域名策略：
  在已建立白名单且该域名不在其中时**被拒绝**；且搜索本身不因该域名不可访问而过滤或标注它。
- **AC29**（F23）— 结果中可读出原始查询词、服务商、返回条数、已用 / 上限。

### 集成与可观测

- **AC30**（F24）— 一次被分类器拦下的搜索在行为记录中可读出查询词、判定范围与拒绝原因；
  一次真实搜索可读出查询词与结果条数；**未新增记录作用域**。
- **AC31**（F25）— 配置快照中搜索密钥为固定掩码，且不以任何其它形式出现在记录里。
- **AC32**（F26）— 一个 `allowed-tools` 声明了本工具的 Skill 能正常预授权，
  不产生「无对应工具类别」警告。
- **AC33**（F27）— 启用但未配置密钥时，启动阶段有一条可见提示，指明配置项与位置。
- **AC34**（F28）— 端到端场景在注入替身后**不发出任何真实网络请求**；
  装配层的两个真实调用方都能透传该替身。
