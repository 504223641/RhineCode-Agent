# 结构化系统提示与缓存策略（c5）Spec

## 背景

RhineCode 当前**没有基础全局 System Prompt**——发给模型的消息里唯一的 `role="system"` 内容，是 Plan Mode 开启时临时注入的那段引导（由 `build_plan_prompt()` 产出），且每一轮原样重复。这带来三个问题：

1. **模型缺少稳定的身份与行为约束**：没有统一告知「你是谁、怎么用工具、要遵守什么规范」，对「优先用专用工具」「编辑前必先读」这类约定的遵守靠运气。
2. **没有利用缓存**：稳定指令与工具描述本可以走 Provider 的缓存通道省钱省时间，现在完全没有组织。
3. **动态指令注入粗糙**：Plan Mode 指令每轮整段重发，既费 token 又稀释模型注意力，且没有一种「不污染缓存、又不会被模型当成用户提问来回复」的补充指令机制。

## 目标

把全局指令重构成**结构化、分层、可缓存**的 System Prompt 体系，让 RhineCode 从「能干活」变成「干得好」：

- **结构化**：按职责拆成多个模块，按优先级拼装，方便以后插新模块。
- **可缓存**：区分稳定内容与动态内容，稳定内容走可缓存通道（DeepSeek 自动前缀缓存），并能通过缓存命中字段验证生效。
- **强约束**：关键规则在工具描述和全局指令里双重强化，提高遵守率。
- **动态注入**：用带特殊标签的系统级补充消息在运行中注入动态指令，不污染缓存、不会被模型当成用户输入；会话级开关指令按轮次控制注入频率。
- **可扩展**：结构 Provider 无关，将来接入新 Provider 或新模块（记忆、Skill）时不用推翻重来。

## 功能需求

> 本节聚焦「系统做什么」的行为描述，刻意不写函数名/类名/文件路径（留给 plan.md 与 task.md）。

- **F1 模块化系统提示**：系统提示由七个固定模块构成，固定优先级顺序为：身份 → 系统约束 → 任务模式 → 动作执行 → 工具使用 → 语气风格 → 文本输出。模块之间以空行分隔，按优先级从前往后拼接成一段完整文本。

- **F2 环境信息模块**：在七个固定模块之后追加一个环境信息模块，包含四项：工作目录（项目根绝对路径）、操作系统/平台、当前日期、当前模型名与 protocol。

- **F3 可选模块槽位**：在环境信息之后预留三个可选模块槽位——自定义指令、已激活的 Skill、长期记忆，各有固定优先级位置。c5 中这三个模块内容为空，不产出任何文本（也不产生多余空行）。

- **F4 可扩展拼装**：新增一个模块时，只需声明其内容与优先级位置即可被拼装进系统提示，无需改动已有模块的代码或顺序逻辑。

- **F5 稳定/动态分离**：系统提示区分稳定内容与动态内容。稳定内容（七个固定模块文本 + 工具描述）走「可缓存通道」并置于发送序列的最前；动态内容（环境信息、对话历史、运行中补充指令）走「消息通道」，排在稳定内容之后。

- **F6 Provider 无关的缓存抽象**：「可缓存通道」是一个 Provider 无关的概念。DeepSeek 通过「稳定内容固定置顶 + 依赖其自动前缀缓存」落地；该抽象需为将来的显式缓存断点机制（如 Anthropic cache_control）预留扩展空间，不与任一 Provider 的具体缓存实现耦合。

- **F7 关键规则双重强化**：对「优先使用专用工具而非通用命令」「编辑文件前必须先读取」这类关键约定，在「工具使用」全局指令模块与对应工具自身的描述中各强化一次，形成双重提示。

- **F8 带标签的补充指令注入**：运行过程中，通过一种带特殊标签的系统级补充消息注入动态指令。该消息走消息通道、不进入可缓存的稳定前缀；并且「身份/系统约束」类固定模块中须明确告知模型：带此类标签的消息是系统补充上下文，不是用户输入，模型不应把它当成用户提问来直接回复。

- **F9 会话级开关的按轮注入**：会话级开关（如 Plan Mode）的指令按轮次控制注入强度——开关激活后的首轮注入完整版指令；其后每隔 3 轮（第 4、7、10… 轮）重发一次完整版；其余轮次只注入一句精简提醒。

- **F10 缓存命中可验证**：每次模型请求结束后，把该次 usage 中的缓存命中/未命中 token 字段写入一个调试日志文件，用于验证缓存策略是否真正生效。

## 非功能需求

- **N1 Provider 无关与可扩展**：系统提示的结构、模块拼装、缓存通道抽象都不得与 DeepSeek 的具体实现耦合。将来新增 Provider 时，只需在该 Provider 内落地「稳定内容如何走缓存」，无需改动模块定义与拼装逻辑。

- **N2 行为不回归**：接入结构化系统提示后，现有的纯对话、工具调用、Plan Mode 两段式工作流、逐项确认、各停止原因等行为必须保持不变。

- **N3 缓存不改变语义**：缓存策略只影响成本与延迟，不得改变模型输出的语义。命不命中缓存，相同输入应得到一致的行为。

- **N4 注入不污染缓存**：动态内容（环境信息、补充指令、按轮注入的开关指令）的存在与变化，不得破坏稳定前缀的可缓存性——即稳定前缀在多轮之间保持逐字节一致，从而能持续命中缓存。

- **N5 中文注释规范**：所有新增/修改代码遵循 CLAUDE.md 的中文注释规范，关键模块、拼装流程、缓存边界、注入时机都要有解释「为什么」的注释，让初次接触者能据此复现行为。

- **N6 调试日志可控**：缓存命中日志写入独立调试文件，不污染 TUI 界面，也不应在未配置时产生意外的大量磁盘写入或报错（如目录不可写时应安全降级）。

## 不做的事

明确划在 c5 范围之外，留给后续章节：

- **项目指令文件加载**：不实现读取 `CLAUDE.md` 这类项目级外部指令文件并注入系统提示的能力（自定义指令模块在 c5 仅为空槽）。
- **自动记忆**：不实现长期记忆的写入/检索/注入（长期记忆模块在 c5 仅为空槽）。
- **真实 MCP 接入**：不接入任何 MCP server，不实现 Skill 的发现与激活（已激活 Skill 模块在 c5 仅为空槽）。
- **自动化评估 / 评分基准套件**：c5 不做自动化的 prompt 效果评估或回归打分；这是一个独立子系统，留给后续章节（c6）。本章只用「解析缓存命中字段 + 一组典型场景人工定性对比」来验证。
- **其他 Provider 的缓存落地**：不在 Anthropic / OpenAI 上实现工具调用或缓存断点；只保证系统提示结构与缓存抽象为它们预留扩展点。
- **缓存数据的界面化展示**：不把缓存命中数据做成常驻 TUI 显示（之前已移除 Token UI）；仅写入调试日志文件。
- **系统提示内容的运行时可配置**：七个固定模块的文本在 c5 中由代码内置，不做成运行时可编辑/可热加载的配置项。

## 验收标准

> 每条 AC 都可通过运行代码或观察行为来验证；与具体实现解耦。

- **AC1（对应 F1）**：构造一次系统提示，输出文本中七个固定模块按「身份→系统约束→任务模式→动作执行→工具使用→语气风格→文本输出」顺序出现，模块间以空行分隔。

- **AC2（F2）**：系统提示末尾（固定模块之后）出现环境信息模块，且包含工作目录、操作系统/平台、当前日期、模型名/protocol 四项，取值与运行环境一致。

- **AC3（F3）**：在三个可选模块均无内容时构造系统提示，输出中不出现这三个模块的任何文本，也不产生多余空行；给任一可选模块填入内容后，它出现在环境信息之后的正确优先级位置。

- **AC4（F4）**：新增一个测试用模块并声明其优先级，无需修改已有模块代码，该模块即按声明的优先级出现在拼装结果中。

- **AC5（F5 / N4）**：连续两轮请求中，发送序列里「稳定前缀」（固定模块文本 + 工具描述）部分逐字节一致；动态内容（环境信息、补充指令、历史）排在稳定前缀之后。

- **AC6（F6 / N1）**：可缓存通道的抽象不引用任何具体 Provider 的缓存字段或参数；DeepSeek 落地下，稳定内容位于发送序列最前。（验证：检视接口与调用方，确认无 Provider 特定耦合。）

- **AC7（F7）**：至少存在一条关键规则（如「编辑前必先读」），在「工具使用」全局指令模块文本与对应工具的描述文本中各出现一次。

- **AC8（F8）**：运行中注入的补充指令以带特殊标签的系统级消息形式出现在消息通道（不在稳定前缀内）；固定模块文本中包含「带该标签的消息为系统补充上下文、不应作为用户提问直接回复」的说明。

- **AC9（F9）**：模拟一次会话级开关激活的多轮循环——第 1 轮注入完整版指令；第 2、3 轮注入精简提醒；第 4 轮再次注入完整版；第 7 轮再次完整版；其余轮次为精简提醒。

- **AC10（F10）**：发起一次真实请求后，调试日志文件中新增一条记录，包含该次的缓存命中/未命中 token 字段；对同一稳定前缀连续两次请求，第二次的命中 token 明显高于第一次（人工对比，定性验证缓存生效）。

- **AC11（N2）**：现有单元测试（路径越界、确认回调、会话级免确认、Plan Mode 计划展示/拒绝/获批后逐项确认等）全部通过，纯对话与工具调用行为无回归。
